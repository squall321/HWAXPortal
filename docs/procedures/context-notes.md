## W-1. 착수 전에 구상을 한 군데 고쳤다 — **기록이 절차를 복원하지 못한다**

사용자 구상의 절반은 "챗으로 한 일을 기억했다가 재생" 이다. 만들 수 있는지 보려고
**지금 무엇이 기록되고 있는지**부터 전수로 봤다. 여섯 갈래가 있는데 **어느 하나도 단독으로
절차를 복원하지 못한다.**

| 갈래 | 순서 | 도구명 | 인자 | 결과 | 짝짓기 |
|---|---|---|---|---|---|
| 포털 `meta.activity[]` | 배열 순서만 | O | 220자 | 220/2000자 | **없음** |
| SSE `status` | 스트림 순서 | O | 140~220자 | 1개 지점만 | **없음**(`run_id` 버림) |
| 게이트웨이 `audit.jsonl` | **벽시계+ms** | O | **없음** | **없음** | 없음 |
| 포털 `agent_audit` | — | 컬럼만 존재 | — | — | **미배선** |
| 워크플로 `journal.jsonl` | started/result | **없음** | **없음** | 문자열 | agentId |
| `delib-jobs/*.json` `steps[]` | 최근 30개 | 버림 | 버림 | 버림 | 없음 |

(개정 3) 게이트웨이 `audit.jsonl` 은 MCP 경로에서 **호출자도** 안 적는다 — caller 는 REST
프록시만 넘긴다. W-17.

**결정적 증거.** 실제 대화 저장소에서 한 메시지에 `predict_sed` 가 `ap_cx=50.1 … 50.5` 로
다섯 번 병렬 호출됐는데, 기록은 `호출×5 → 완료×5` 순서이고 **결과 다섯의 프리뷰가 전부
같다.** 어느 결과가 어느 입력의 것인지 알 수 없다.

부족한 것은 넷이다 — ① 호출 식별자 ② 시각·소요시간 ③ 절단 안 된 인자 ④ 앱 귀속.
**①과 ④는 이미 방출 지점에 있는 값이다.** LangGraph `astream_events(version="v2")` 의
`on_tool_start`/`on_tool_end` 훅에 `event["run_id"]` 가 손에 있는데 싣지 않는다
(`app.py:2607`·`:2633`).

→ **P0 을 절차보다 앞에 뒀다.** 관측할 수 없는 절차는 기록할 수 없다. 이 순서를 뒤집으면
나머지가 전부 짐작 위에 선다. 그리고 P0 은 절차 기능이 취소돼도 **그 자체로 값어치가 있다** —
챗 활동 패널이 정확해지고 핸드오프 근거의 인자가 살아난다.

## W-2. 막힌 곳은 계산기가 아니라 추출기다 — 그리고 그 조각은 **이미 있다**

`predict_sed` 의 필수 입력 10개가 전부 기판 레이아웃·패키지 배치 치수다. STEP 에 솔더볼이
없고 k파일에도 없다. **`ball_size`·`pad_size` 는 ODB++ 전용**이고, `pkg_type` 은 어떤 형상
데이터로도 유도할 수 없다. 게다가 **465종 중 SedInput 을 만들어 주는 어댑터가 0개다.**

그런데 조사 중 예상 밖의 것을 찾았다.

```
/home/koopark/claude/ODB     dev 에 실재 — 파서 14종 · 체크리스트 룰 39개 · FastAPI
                             서비스 계층이 CLI·REST·MCP 공용으로 이미 설계됨
documents/MCP_INTEGRATION.md 447줄 규격서 — 도구 13종 제안까지 합의돼 있음
```

규격서가 직접 말한다 — *"서비스 계층은 MCP를 염두에 두고 이미 인터페이스 독립적으로
설계되어 있습니다. 서버를 얹기만 하면 됩니다."*

제안된 도구가 막힌 슬롯과 정확히 맞물린다(`odb_list_components` → 좌표,
`odb_interposer_ratio` → `board_type`, `odb_extract_parts` → `ball_size`·`pad_size`,
`odb_copper_ratio` → 워피지 3인자). (개정 3) 이 화살표는 전부 **가정**이다 — 특히 `board_type`
은 인터포저 비율로 INT 만 가려지고 HALF/FULL 은 못 가른다. W-25.

→ **ODB 부재를 "나중에 해결할 전제" 가 아니라 "설계로 흡수할 제약" 으로 뒀다.** 공급자 없는
슬롯은 실패가 아니라 **사람에게 묻는 칸**이다. 나중에 도구가 붙으면 **같은 절차가 손대지
않고** 무인으로 돈다. 이게 §4 슬롯 모델의 존재 이유다.

⚠ cae00 에는 `odb-hub` 가 붙어 있지만 **무엇을 내주는지 확인 못 했다**(dev 에서 도달 불가,
페르소나 `key_tools` 비어 있음, 매니페스트에 `mcp:{}` 없음). 로컬 엔진이냐 cae00 허브냐는
결정 대기다.

## W-3. A→Z 가 끊기는 진짜 이유는 엔진이 아니라 **과제 키**다

```
StepForge      project_id    24-hex
DynaForge      session_id    user 스코프
ThermalShock   project       그냥 문자열 메타(README 가 명시)

```

이 다섯을 묶는 것이 **없다.** 문서 자체가 열린 질문으로 남겨 놨다 —
`docs/design-risk-review/plan.md:4760` *"크로스도메인 부품 명명 규칙(ECAD refdes ↔ MCAD
파트명 ↔ Dyna `Group\Name`)이 조직에 있는가 → **없음 가정**"*.

→ **P1 을 절차보다 앞에 뒀다.** 절차가 아무리 정교해도 단계 사이에서 키가 끊기면 사람이
손으로 잇는다. 그리고 키 레지스트리는 **절차가 없어도 쓸모가 있다** — 사람이 앱을 오갈 때
찾아 주는 것만으로. (개정 2 에서 "작다·병렬" 로, 개정 3 에서 **S3 뒤**로 — W-22.)

## W-4. 토폴로지 B — agent-server 에 붙이지 않는 이유는 취향이 아니다

사용자 요구가 "챗·심의에 지장 없는 독립 구성" 이라 붙일 자리를 전수로 봤다.

**agent-server 는 탈락이다.**

- 인증이 아예 없다 — `Depends`/`Security`/`HTTPBearer` 0개. `start.sh:37-49` 가 의도라고
  적어 놓았고 방어는 `127.0.0.1` 바인드뿐이다.
- 전역 가변 상태가 12개 넘고 **그중 둘은 이미 교차오염 사고가 났다** — `tool_degraded` 가
  다른 요청의 스트림에 가짜 배너를 주입했고 `ContextVar` 로 고쳤다(`deliberation.py:983-986`).
  여기 쓰면 **이미 두 번 고친 버그를 세 번째로 낸다.**
- **아티팩트 정리에 생산자 네임스페이스가 없다** — 오래된 것부터 500개로 깎으므로
  절차 산출물을 챗이 지우고, 반대도 된다.

**포털 공유 자원도 탈락이다.**

- `agent_semaphore`(64)는 큐 없이 **429 즉시 거절**이다.
- `agent_client` 는 풀 64에 read 타임아웃이 없어, 먹히면 챗이 429 가 아니라 **조용히 멈춘다** —
  더 나쁜 고장 모양이다.
- **실증이 있다.** HWAXRisk 의 예외 클래스 이름이 그대로 *"엔진 슬롯이 없다(포털
  agent_semaphore 429)"* 이고, 패널 하나가 챗 슬롯을 **최대 40분** 쥔다.

→ **리스크 심사가 간 길(토폴로지 B)을 그대로 간다.** 그 결정의 근거가 이번 구상과 같다 —
*"과제 수십 개·수년치가 쌓이는 장기 자산이라 포털 릴리스·박스 수명에 묶이면 안 된다"*.
비용도 이미 측정돼 있다(커밋 `943252f`) — **포털 백엔드 0줄**, 기존 파일 3개 + 새 페이지 1개.

## W-5. 절차 모델을 새로 발명하지 않는다 — **부품이 거의 다 있다**

범용 워크플로 엔진은 스택 어디에도 없다(게이트웨이·포털·agent-server 에서
`workflow|pipeline|procedure|macro|playbook` grep **히트 0건**). `infra/pipeline/*.js` 1,801줄은
**심의 전용**이고 도메인 프롬프트가 파일의 22%다.

그런데 인벤토리에 필요한 조각은 흩어진 채로 이미 있다.

| 자산 | 왜 정답에 가까운가 |
|---|---|
| **KooRemapper `catalog_data.json`** | 스택에서 **유일하게 완성된 선언형 능력 카탈로그**. 47 ops × {타입·필수·기본·enum·전제조건·검증된 예제·함정} + JSON Schema 파생 + Draft2020 검증 |
| **SmartTwinMCP `audit_events`** | 절차 기록의 정답 모양 — `(occurred_at, actor, tool@version, action, target, detail=args)`. **`pipeline_step` 액션까지 이미 있다** |
| **SmartTwinMCP 템플릿** | `{name, applies_to[], args{}}` — "이름 붙인 인자 세트 + 적용 가능 도구". 레코드 형식을 발명할 필요가 없다 |
| **HEAXHub `POST /jobs/{id}/rerun`** | **판본(`app_version_id`)을 박아** 인자+입력파일까지 복원하는 유일한 구현 |
| **ReportArchive 잡 큐** | 운영급 — 우선순위·백오프·dedup·reaper·하트비트·스케줄러. 새 절차 = 핸들러 파일 하나 |
| **`saved_searches`** | 스냅샷이 아니라 **조건 저장 + 라이브 재실행 + 구독 + 워터마크** |
| **`invoke_tool`** | 이름으로 실행하는 통로. 인가·캐시·사용자 위임·감사를 **그대로 탄다** |

→ **빠진 것은 이들을 엮는 순서 모델과, 호출을 짝지을 식별자 한 필드다.** 그래서 계획이
"엔진을 만든다" 가 아니라 "모델을 정하고 부품을 엮는다" 가 됐다.

**함정 하나 — "템플릿" 이라는 말이 스택에서 서로 무관한 세 뜻으로 쓰인다.** 보고서 양식(RA) ·
잡 인자 프리셋(SmartTwin) · 클러스터 제출 템플릿. 절차 문서에서 이 말을 쓸 때 어느 뜻인지
반드시 밝힌다.

## W-6. RA 프리셋은 "절차 저장" 이 아니다 — 이름에 속지 않았다

`save_report_as_preset` 이 이름만 보면 딱 맞아 보인다. 실물을 봤더니 **본문 스냅샷**이다.
모듈 독스트링이 직접 말한다 — *"a preset is a filled-in starting point … carries a content
snapshot so a new report can be born pre-populated instead of blank."*

`create_report_from_run(run_id)` 의 "run" 도 **반입된 CAE 해석 1건**이지 절차 실행이 아니다.
그리고 **SED·적층·워피지 계산기는 실행을 만들지 않으므로 이 길로 못 간다** — 계산 결과의 길은
`create_report_draft` 쪽이다.

라이브 확인 — `list_presets()` 는 `count: 0`, `list_templates()` 는 3개뿐이다.

→ 이름이 겹친다고 재사용하면 엉뚱한 것을 물려받는다. **정작 가까운 것은 SmartTwinMCP 템플릿과
`saved_searches` 였다**(둘 다 "보고서" 와 무관한 자리에 있다).

## W-7. 자동화가 건드리면 안 되는 사람 자리가 셋 있다

전부 **의도된 설계**이고, 절차 기능이 편의로 건너뛰면 안 된다.

1. **`publish_report`** 는 `preview_publish` 가 발급한 `confirm_token` 을 요구한다 — 2단 확인.
2. **`risk_add_finding`** 은 `cites` 0건이면 **422** 다. `claim`·`warrant` 는 자유 산문이고
   설계 자체가 사람 등록(`origin='human'`)용이다.
3. **`pcb_warpage_surrogate`** 는 스스로 경고한다 — *"합성(synthetic) 데이터로 학습한 데모.
   절대값을 판정·양산 의사결정 근거로 쓰지 마라."*

→ 절차에 `gate: human` 을 두고, 실행 기록에 **모델 출처·경고를 반드시 싣는다.**
"A to Z 자동" 의 Z 는 게시가 아니라 **사람 앞에 놓는 것**이다.

## W-8. 절차 목적지에 이미 구멍이 둘 있다

"패턴화된 리스크 검토" 가 최종 목표인데, 거기로 가는 웹 경로가 막혀 있다.

둘 다 절차 기능과 **별개의 기존 결손**이라 이번에 손대지 않았다. P6 전에 닫아야 한다.

## W-9. 조사 방법에 대한 메모

이번 조사는 셋을 병렬로 돌렸고(오케스트레이션 기계 / 삼종세트 도구 / 독립 배치), 각자
**소스가 아니라 실물**을 봤다 — 게이트웨이 `tools/list` 로 스키마를, 대화 sqlite 로 활동
기록을, 감사 jsonl 로 호출 순서를 봤다.

그 덕에 두 가지를 피했다.

- **`describe_data_capability` 를 "능력 레지스트리" 로 과대평가할 뻔했다.** 실제로 불러 보니

- **RA 프리셋을 "절차 저장" 으로 오독할 뻔했다**(W-6).

이 폴더의 다른 교훈과 같은 줄에 있다 — **흉내 낸 데이터로 판정하면 코드가 아니라 흉내를
시험하게 된다.**

## W-10. 배치를 뒤집었다 — 별도 앱 → **포털 안의 격리 모듈**

개정 1에서 토폴로지 B(별도 HEAX 앱)를 **강하게** 권했다. 되돌린다. 늦게 확인한 사실 하나가
비용 구조를 바꿨다.

```python
# backend/app/agent/routes.py:223
def _chat_user_pat(keystore, settings, principal) -> str | None:
    """이 챗 한 번을 위한 단명 PAT. … 게이트웨이는 이 토큰을 포털 JWKS 로 검증하므로
       위조가 불가능하고, 도구 인가도 서비스 계정이 아니라 이 사람의 groups 로 이뤄진다"""
```

**포털은 이미 사용자 명의로 게이트웨이를 부를 수 있다.** 절차 실행기가 필요로 하는 것이
정확히 그것이다. 별도 앱으로 가면 이 한 줄을 얻으려고 HMAC 신원 단언 배선 + 새 리포 +
매니페스트 + apptainer + 배포 + Drive 를 새로 만들어야 한다.

**내가 "독립성" 을 프로세스 분리로 읽은 것이 틀렸다.** 조사가 실제로 말한 것은 그게 아니다 —
`agent_semaphore`·`agent_client`·`conv_store` 를 **공유하지 말라**는 것이었다. 자기 세마포어,
자기 httpx, 자기 sqlite 를 쓰면 같은 프로세스 안에서도 챗에 영향이 0이다. (개정 3) 런타임 자원
얘기다 — 기동 실패는 공유되므로 모듈 import·스토어 오픈 실패는 절차 기능만 끄고 포털은 뜬다.
게이트웨이 백엔드 영속 세션은 피할 수 없는 공유라 120초 규칙으로 막는다. W-19.

HWAXRisk 가 별도 앱으로 간 근거(장기 자산이 포털 릴리스에 묶이면 안 된다)는 **여전히 유효한
단점**이다. 그래서 저장소를 독립 sqlite 로 두어 **언제든 떼어낼 수 있게** 한다. 쓸모가
증명되면 그때 승격한다 — **지금 승격 비용을 선불하지 않는다.**

**교훈** — "무엇을 재사용하면 안 되나" 를 "어디에 살아야 하나" 로 번역할 때 한 칸 건너뛰었다.
제약은 자원 공유였지 주소가 아니었다.

## W-11. 학습을 선행 필수에서 **나중 보조**로 내렸다

개정 1은 P0(관측 충실도)을 전제로 뒀다 — "챗 기록으로는 절차를 복원할 수 없으니 먼저 고치자".
사실 판단은 맞지만(W-1 증거는 그대로다) **결론이 과했다.**

챗 기록을 해석해 절차를 복원하는 것은 어렵다. 그런데 **절차 안에서 한 일은 해석이
필요 없다** — 절차 기능이 자기 관측자라 기록이 곧 절차다. "하고 나서 저장" 이
처음부터 성립한다.

→ 관측 개선은 여전히 값어치가 있고(챗 활동 패널·핸드오프 근거가 정확해진다) **S5 의 전제**
지만, **핵심 기능의 선행 조건은 아니다.** 선행으로 두면 값어치가 먼 단계 하나를 맨 앞에
세우는 셈이다.

**교훈** — "이 방식은 불가능하다" 를 "이 일은 불가능하다" 로 넓혀 읽었다. 막힌 것은 **입구
하나**였고 다른 입구가 있었다.

## W-16. 성공 판정은 코드가 한다 — 실패 다섯 모양 중 셋이 `isError=false`

리포의 유일한 선례 `upload.mcp_call` 은 `isError` 를 버리고 `content[0]` 만 보며 파싱 실패를
`{"raw"}` 로 정상 반환한다 — **베끼면 실패가 성공으로 기록된다.**

→ PLAN §5-6 의 네 조건. 이 리포의 반복 패턴 "실패가 정상 응답과 똑같이 생겼다" 의 또 한 자리라,

## W-17. "사용자 명의" 의 실제 범위 — 16개 중 4개, RA 는 조용한 폴백, odb-hub 는 서비스 토큰

게이트웨이 원장에 호출자를 남기는 것은 한 줄이지만 §4 "순수 프록시" 와 별개 리포 수정이라 §7 #7

## W-18. `dry_run` 은 두 뜻 — 계획 모드 vs 도구 `dry_run`(16종)

체크리스트의 "`dry_run` 기본값" 은 뜻이 없었다. 도구 수준으로 읽으면 위험하다 — 게이트웨이에
dry_run 처리가 없고 465종 중 16종만 자기 인자로 가지며, 없는 도구에 얹으면 백엔드가 버리고
**실제로 실행**된다(실측 `list_parts`+`dry_run:true` → 정상 결과). 같은 리포 `docs/tool-entry` 는
이 말을 도구 수준 뜻으로 쓴다 — 어휘가 충돌하고 있었다.

→ 계획 모드(기본, 게이트웨이를 안 부름)와 도구 `dry_run`(스키마에 있을 때만 폼 노출, 없는 도구의
`args` 에 적혀 있으면 저장 거절)으로 가르고 단계마다 `mode` 를 남긴다.

## W-19. 실행은 요청 밖 · 세션은 실행당 하나 · 타임아웃은 게이트웨이보다 길게

절차 경로는 nginx catch-all(60초)이고 게이트웨이 상한은 120초라 동기로 두면 nginx 는 504,
uvicorn 은 완료 → 재시도 → 보고서 둘. **dev vite 프록시에선 재현되지 않는다.** → 202 + 폴링,
같은 단계 `running` 이면 409, 기동 시 in-flight 는 `unknown/failed(stage=restart)`.

**타임아웃 결정** — 발견 둘이 충돌했다. "실행기 타임아웃 ≤110초(게이트웨이보다 짧게)" 와
"≥260초(게이트웨이의 재연결 재시도까지 덮게)". 후자를 택했다 — 짧은 타임아웃은 게이트웨이 쪽
호출을 멈추지 못하고(그 발견 스스로 "보호 수단이 아니다" 라 했다) `unknown` 만 늘린다. 보호는
"120초를 넘길 수 있는 동기 도구를 절차에 안 넣는다" 로 한다.

비멱등 쓰기가 두 번 도는 경로가 둘이다 — 게이트웨이가 예외 뒤 재연결하고 같은 인자로 한 번 더
부른다, 실행기가 먼저 포기하면 쓰기는 그 뒤 완료된다. 그래서 클라이언트 타임아웃·프로세스 종료는
`failed` 가 아니라 `unknown` 이고 `done` 은 절대 재실행하지 않으며 `unknown` 쓰기 단계는 사람
확인 뒤에만 재실행한다.

세션 — `mcp_call` 은 호출마다 세션을 만들고 안 닫는다. 게이트웨이 SDK 는 유휴 만료가 없다. 실행당
하나 열고 `finally` 에서 닫는다. 기동 실패는 try/except 로 절차 기능만 끈다(`/procedures-api/health`).
`get_job`·`get_job_details` 를 게이트웨이 `_CACHE_DENY` 에 넣는 것은 별개 결손으로 **기록만**
한다 — 게이트웨이는 순수 프록시.

## W-20. 도구에 판본이 없다 — `backend`+`tool`+`schema_fp`

노출 이름은 다른 백엔드와 겹칠 때만 접두어가 붙어 **다른 앱의 가동 여부로 뒤집힌다**(StepForge
4개 도구 실측). `tools/list` 에 버전이 없고 백엔드는 영속 세션 하나라 옛 판본을 못 띄운다.
앞 라운드의 "노출 이름을 저장한다" 판정을 이 사실이 뒤집었다 — 별칭 `<백엔드>_<원본>` 은 항상
호출되고 파괴 차단은 원본 기준이라 우회가 없다. 판본 대신 지문(`sha1(desc+schema)[:16]`)을 박아
**변화를 잡아 멈추는 것까지**가 할 수 있는 전부다. `predict_sed` 의 `sample: dict` 는 지문이 못
잡는다 — 실행 기록과 게이트가 그 몫.

## W-21. 저장 모델·소유·저장 규칙·이관

- 표 다섯(`procedures`·`procedure_versions`·`runs`·`run_steps`·`run_gate_acks`). 실행은 판본 행 id FK
  (HEAXHub 방식), "하고 나서 저장" 은 `derived_from_run` 역참조, `inputs_json` 은 S4 비교표용.
- 소유 — `owner_sub` 강제(`conv_store` 선례). 실행은 공유하지 않는다 — PER_USER_SSO 백엔드의
  사용자별 시야가 결과에 담긴다. 공유 정책(포크 전용?)은 §7 #6.
- 크기 — 도구 결과 1건이 0.9MB(`list_agents`), 이미지는 base64. 절차 기능은 agent-server 절단을
  안 탄다. gzip BLOB + 2MB 상한 + 이미지 파일 + 90일(HWAXRisk `rr_snapshot_calls` 선례, stdlib 만).
  백업은 매일 통째로 7세대라 안 그러면 7배로 커진다.
- 등록 — `backup-local.sh` 는 튜플 1줄이 아니라 **세 줄**이다. 튜플만 늘리면 `zip` 이 짧은 쪽에서
  멈춰 다섯째 sqlite 가 **오류 없이** 백업에서 빠진다. `sync: mirror`(실행은 사용자 데이터) 라 dev
  절차는 동기화로 안 가고 YAML export/import 로 간다.
- sqlite — 단일 연결 + Lock 을 `to_thread` 로 감싸면 트랜잭션 경계가 스레드 사이에서 섞인다.
  스레드별 연결 + `busy_timeout=5000`(백업·이관이 `mode=ro` 로 동시에 여는 순간용).
- 비밀 — 465종 중 `api_key` 인자 8종·`confirm_token`·`brief_token` 이 실재한다. 상수로 저장되면
  공유 절차가 곧 유출이라 키 이름으로 거절하고 변수·`save` 만 허용한다.
- API prefix `/procedures-api` — `App.tsx` 가 `/changelog` API 와 `/updates` SPA 를 가른 것과 같은
  이유(SPA `/procedures/*` 와 겹치면 새로고침이 JSON 을 받는다).
- v1 실행은 대화 저장소에 쓰지 않는다 — `kind` Literal·`ConvKind` 를 넓히는 것은 S5 의 일이다.

### 절차 기능의 존재 이유를 도구가 직접 증명했다

`solve_prescribed_curvature` 설명 원문 — *"다른 도구는 전부 힘 제어(N/M)라 **에이전트가
M = D·κ 지름길을 쓰게 되는데, 비대칭 스택에서 실측 +244.8% 과대**다."* LLM 이 스스로 엮으면
2.4배 틀리고 절차로 굳히면 안 틀린다. 그동안 "재현성" 으로 뭉뚱그려 말하던 것에 **수치가
붙었다.**

### 사용자 전제 한 곳을 정정했다

"DynaForge 에서 scenario.json 을 도출" — `list_operations` 47개 전수 확인 결과 scenario·drop·
impact 계열 오퍼레이션이 **없다**. 만드는 쪽은 클러스터(`smarttwin_submit` 이 프리셋 base +
deep-merge)이고 DynaForge 는 `attach_report_scenario` 로 **되받는다.** 조립 주체만 다르고
사용자가 원한 그림은 그대로 선다.

### 조사가 바꾼 설계 판단 셋

1. **제출과 회수는 다른 절차다.** 드라이버 walltime 이 167시간(7일)이라 한 절차에 못 둔다.
   §4 의 "폴링·대기 없음, 잡을 거는 도구는 절차 밖" 이 제약이 아니라 **옳은 모양**이었다.
2. **R 스윕·각도 프리셋 비교는 분기가 아니라 S5 다.** "조건 분기가 필요하다" 고 보이던 자리가
   사실 "같은 절차 × 변수 N개" 였다. §4 가 분기를 뺀 결정이 여기서 값을 한다.
3. **파일을 나르는 단계가 절차 밖이라는 결정이 두 번 확인됐다** — `model_path` 는 클러스터
   헤드노드 공유 FS 절대경로, 리포트 HTML 은 8~10MB 라 REST intake(512MB) 전용이다.

### 새로 확인된 무음 실패 다섯

이 폴더의 반복 주제가 또 나왔다 — **실패가 정상 응답과 똑같이 생겼다.**

| 자리 | 모양 |

## W-27. 시간 정책과 심의 경계 — 사용자 지시 둘

### 오래 걸리는 도구를 상정한다

지시는 "각 툴마다 시간이 오래 걸릴 수 있는 걸 감안하자" 였다. 실측을 다시 보니 **이미 상한
위에 있는 것이 셋**이다 — `search_catalog_property` 세션 첫 호출 **120.3초**(3회 재현, 이후
0.1초) · `agent_search` hybrid 102~221초 · `list_materials` 120초. 게이트웨이 상한이 정확히
120초라 첫 호출이 잘리고, 잘리면 그 백엔드 **영속 세션이 재연결**되면서 챗·심의까지 흔든다.

→ PLAN §5-10. 단계가 `expect`(`fast`/`slow`/`job`)를 선언하고 `job` 은 저장 거절,
`warmup: true` 단계는 한 번 버리는 호출로 콜드스타트를 흡수한다. 실행기 타임아웃은 ≥260초로
게이트웨이보다 늦게 포기한다.

**설계상 중요한 자리 하나** — 선언은 사람이 하지만 **실행 기록의 `duration_ms` 가 쌓이면 실측
p95 를 옆에 보여 준다.** §1 의 "절차 기능이 자기 관측자" 원칙이 시간에도 적용된다. 선언과
실측이 어긋나는 것을 사람이 고치는 것이 아니라 **화면이 말한다.**

### 심의는 잡을 걸지 않는다

지시는 "심의에서는 낙하 결과 조회를 하자. 시뮬을 심의할 때 시작하면 전체 결과 정리가 쉽지
않을 거야" 였다. 맞고, 근거가 셋으로 갈린다.

1. **시간이 안 맞는다** — 드라이버 walltime 167시간 vs 심의 라운드 몇 분. 심의 중에 잡을 걸면
   그 심의는 **의도만 남은 근거**로 끝난다.
2. **집계가 좌석의 일이 아니다** — 전각도는 자식 잡을 26~10000개 만들고 그 집계가
   `sphere_report`·`impact_report` 의 일이다. 좌석이 라운드 중간에 모으려 들면 **부분 결과로
   결론을 낸다.**
3. **판독 도구가 이미 집계된 슬라이스를 준다** — `report_worst_cases` 최악 랭킹,
   `report_directional` 방향 롤업, `report_query` 서버 필터. 좌석이 받아야 할 모양 그대로다.

→ 심의 좌석에는 `report_*` 판독 도구만 주고 제출 계열(`smarttwin_submit`·`slurm_submit_job`·
`run_job`·`submit_lsdyna_job`)은 뺀다. 순서가 정해진다 — **절차 기능이 먼저 돌고(R2a → 잡 →
R2b), 심의는 그 뒤에 `report_id` 를 읽는다.**

**이것이 앞서 논의한 "절차를 도구로 등록해 심의가 부른다" 의 정확한 형태다** — 심의에 주는
것은 **R2b(회수·판독)** 쪽이지 R2a(제출)가 아니다. 그리고 제출/회수를 가른 결정에
**두 번째 독립적 근거**가 생겼다. 첫째는 walltime, 둘째는 심의 경계다. 같은 분리가 두 이유로
필요하면 그것은 우연이 아니라 구조다.

## W-29. 문서의 `save` 경로가 전부 틀렸다 — 회귀가 잡았다

적층 체인을 실물로 돌렸더니 응답이 `{status, data, errors, warnings, assumptions, metadata}`
봉투였다. 값은 `data.` 아래 있고 **경고는 최상위**에 있다.

| 값 | 개정 4 가 적은 것 | 실물 |
|---|---|---|
| 등가하중 | `equivalent_loads` | `data.equivalent_loads` |
| 파손 여유 | `min_tsai_wu_R` | `data.first_ply_failure.tsai_wu_R` |
| 수명 | `life_cycles` | `data.life_cycles` |

그대로 짰으면 **첫 실행에서 죽었다.** 잡은 것은 `test_procedures_r1.py` 다 — 씨앗 YAML 을
읽어 `save` 경로를 **실물 응답에 대고 풀어 본다.** 고정물은 2026-09-14 실호출이다.

**교훈** — 절차가 "저장된다" 와 "돈다" 는 다른 문제다. 저장 시점 검증은 스키마를 보지
**응답 모양**을 못 본다. 응답 고정물 없이 쓴 `save` 경로는 전부 가정이다.

**부수로 고친 것 셋.**
- 판정에 `status` 검사를 더했다 — 적층 해석기는 `ok|warning|error` 를 낸다. `error` 면
  `errors[]` 도 대개 차 있지만 비어 있어도 실패로 친다.
- 고정물을 만들며 **내가 고정물을 망가뜨렸다** — 배열을 앞 2개로 자르는 트림이
  `loads.M` 을 `[51.37, 0.0, "…(3건)"]` 로 바꿔 놨다. 등가하중은 숫자 3개여야 뜻이 된다.
  8개 이하 배열은 안 자르게 고쳤다. **짧은 배열은 모양이 곧 뜻이다.**
- 씨앗의 `save` 이름 `tsai_wu_R` 이 변수 이름 규칙(snake_case)에 걸렸다. 검증기가 옳고
  씨앗이 틀렸다 — 이름은 우리 것이고 경로만 응답 필드다.

## W-30. 라우트가 부르는 메서드가 **아예 없었다** — 셸 한 줄이 원인

사용자가 `/procedures` 를 열었더니 "도구 목록을 불러오지 못했습니다" 가 떴다. 로그가
한 줄로 말했다 — `AttributeError: 'ProceduresRunner' object has no attribute 'catalog'`.

**원인은 셸이다.** `cd backend && python3 - <<'PY' …` 를 이미 `backend` 안에서 돌려 `cd` 가
실패했고, `&&` 가 끊겨 **python 이 아예 실행되지 않았다.** 그런데 뒤이은 pytest 는 통과했고
(그 메서드를 아무도 안 썼다) 나는 "추가했다" 고 보고했다. 세 개가 통째로 없었다 —
`catalog` · `step_once` · `merge_inputs`.

**왜 219개가 못 잡았나.** 두 가지가 겹쳤다.
- `/procedures-api/tools` 를 **아무 테스트도 안 쳤다**. 권한 전수 테스트는 403 만 봤다.
- `POST /runs/{id}/steps` 는 202 라 실패가 **백그라운드 로거로만** 간다. 화면도 서버도
  조용하다 — 이 리포가 반복해서 겪는 "실패가 정상 응답과 똑같이 생겼다" 의 또 한 모양이다.

**가드를 세웠다.** `routes.py` 소스에서 `_runner(request).X(`·`_store(request).X(` 를 정규식으로
뽑아 `hasattr` 로 대조한다. 이름 하나가 없으면 **라우트를 안 쳐도** 잡힌다. 가드가 0건을
훑고 통과하지 않도록 "실제로 찾는지" 도 함께 시험한다.
그리고 `/tools` 를 MockTransport 로 실제로 쳐 보는 테스트와 `step_once`·`catalog` 회귀를 더했다.

**교훈 둘.**
- **`cd X && …` 는 이미 그 안에 있으면 통째로 안 돈다.** 편집 스크립트는 성공 출력을 반드시
  확인해야 한다 — 이번엔 출력에 "추가" 줄이 없었는데 내가 안 봤다.
- **202 + 폴링은 실패를 숨긴다.** 그 라우트는 "요청이 받아들여졌다" 만 말한다. 그래서
  백그라운드 경로일수록 **호출 계약을 정적으로** 지켜야 한다.

## W-31. 씨앗을 화면에서 가져온다 — 첫 화면이 비어 있으면 아무도 못 시작한다

도구 목록이 뜨기 시작하자 다음 구멍이 드러났다. **절차 목록이 비어 있었다.** R1 씨앗

`GET /procedures-api/seeds` 와 `POST /procedures-api/seeds/{name}/import` 를 붙였고,
절차 목록이 비면 씨앗 카드를 대신 보여 준다(제목·단계 수·백엔드·사람 확인 자리, 그리고

결정 세 가지.

- **깨진 씨앗은 목록을 죽이지 않는다.** 파싱이 실패하면 그 줄만 `broken` 으로 표시하고
  나머지를 낸다. 하나가 상하면 전부 못 보는 편이 더 나쁘다.

## W-32. SPA 폴백이 **API 404 를 200 + HTML 로** 바꾸고 있었다

씨앗 경로를 살아 있는 서버에서 확인하다 옆에서 발견했다.

```
GET /procedures-api/seeds → 401   (라우트 있음, 정상)
GET /procedures-api/zzz   → 200   ← text/html
```

백엔드가 SPA 를 함께 내므로 catch-all `@app.get("/{full_path:path}")` 가 하나 있다.
등록된 API 는 위에서 먼저 잡히지만 **없는 API 경로**는 그대로 SPA 로 새서 index.html 이
200 으로 돌아갔다. `/auth`·`/agent`·`/mcp` 전부 같았다 — 절차만의 문제가 아니다.

무엇이 나쁜가. `apiFetch` 는 `res.ok` 가 참이라 성공으로 넘기고, 호출부가 `.json()` 을
부르는 **한참 뒤 엉뚱한 자리**에서 `Unexpected token '<'` 로 터진다. 경로 오타 하나가
"서버가 이상하다" 로 보인다 — 이 리포가 반복해서 만난 **"실패가 정상 응답과 똑같이
생겼다"** 의 또 한 모양이다.

**접두사를 손으로 적지 않았다.** `app.routes` 에서 첫 칸을 유도한다 — 라우터를 더해도
목록이 어긋나지 않는다. 하드코딩했으면 다음 라우터에서 조용히 낡았을 자리다.

**고치면서 생긴 새 위험은 반대쪽이다.** 접두사를 잘못 잡으면 사용자의 **깊은 링크가
새로고침에서 404** 가 된다. 그래서 `test_spa_fallback.py` 가 둘을 같이 건다 — 없는 API 는
JSON 404 이고, **SPA 경로 11개와 API 접두사 15개가 한 칸도 겹치지 않는다**. 겹침이 없는
건 우연이 아니다. `/procedures`(SPA) ↔ `/procedures-api`(API), `/updates`(SPA) ↔
`/changelog`(API) 를 일부러 갈라 놓은 결과이고, 이제 그 규칙이 테스트로 고정됐다.
빈 집합끼리 비교해 통과하는 사고를 막으려고 "표를 실제로 읽었나" 도 함께 시험한다.

## W-34. 씨앗 ②~⑥ 도 살아 있는 게이트웨이에서 돌려 봤다 — 두 곳이 걸렸다

고정물은 "기록해 둔 응답" 을 시험한다. 그것만으로는 사용자가 화면에서 처음 돌릴 때
무엇에 걸릴지 모른다. 그래서 ②~⑥ 을 실제로 이어 불렀다.

**걸린 것 둘은 전부 `laminate` 스키마였다.**
- `material.type` 을 빼면 `E202 INVALID_MATERIAL_TYPE`.
- `fatigue.k` 를 1보다 크게 주면 `E100 … should be less than or equal to 1`(k 는 기울기다).

둘 다 도구가 `suggestion` 으로 고치는 법을 준다 — **이 서버의 오류는 자가 복구가 된다.**
다만 화면에서 처음 만나면 멈칫하므로 씨앗의 `why` 와 examples.md 에 붙여 넣을 판을 적었다.
정본은 도구가 들고 있다 — `get_reference_cases(case_id="fatigue_reversed_cycle")`.

**확인된 것 하나가 중요하다.** `equivalent_loads` 에는 `chain` 이라는 **설명 문자열**이
끼어 있다. 씨앗은 이 객체를 통째로 다음 단계에 넘기는데, 받는 쪽 둘이 **그대로 받아 준다**
(`load_state` 가 N·M 만 읽는다). 걷어내는 단계를 따로 두지 않아도 된다는 뜻이고,
이건 소스를 읽어 짐작한 것이 아니라 **실호출로 확인했다**.

`save` 경로 여섯이 살아 있는 응답에서 전부 풀렸다 — ① 셋 + `basis`, ③④ `equivalent_loads`,
⑤ `tsai_wu_R`·`governing_mode`, ⑥ `life_cycles`.

**미해결 마찰 하나를 남긴다.** `json` 형 변수에 **기본값 칸이 없다**(`Var` 에 `default`
없음, `extra: forbid`). 그래서 사람이 4겹 적층 JSON 을 화면에서 손으로 채워야 한다.
`default` 를 더하면 규격·지문·폼이 함께 바뀌므로 **혼자 정할 일이 아니라고 보고 안 했다.**
지금은 문서로 막아 뒀다.

## W-35. `Var.coerce` 가 **운영 경로에서 한 번도 안 불리고 있었다**

미결로 남겨 뒀던 "json 변수 기본값" 을 붙이려다 그 밑에서 더 큰 것이 나왔다.
`grep '\.coerce('` 이 테스트 네 줄과 방금 내가 쓴 한 줄만 찾았다 — **실행 경로에 없다.**

무슨 일이 일어나고 있었나. 화면의 입력칸은 문자열밖에 못 보낸다. `POST /runs` 는
`body.vars` 를 그대로 `inputs` 에 넣고, 치환기는 통째 리프의 **형을 그대로 보존**한다
(그게 `template.substitute` 의 설계다). 그래서 —
- 적층 정의가 `laminate` 인자에 **문자열**로 실린다 → 도구가 거절한다.
- `r_unfold` 가 `"1000"` 으로 실린다 → 같은 일.

즉 **R1 을 화면에서 처음 돌리면 깨졌다.** 고정물 테스트도 실호출도 이걸 못 봤다 —
둘 다 파이썬에서 이미 형이 맞는 값을 넣었기 때문이다. 사람이 브라우저에서 채우는
경로만 이 모양이었다.

`coerce_inputs(spec, raw)` 를 만들어 `start_run` 이 **실행을 만들기 전에** 부른다.
- `json` 은 문자열이면 `json.loads` 한다. 깨져 있으면 422 이고 실행이 안 만들어진다.
- `boolean` 은 `"true"/"false"` 를 받는다(칸이 문자열밖에 못 보낸다).
- 빠진 **필수** 변수를 여기서 잡는다. 안 잡으면 그 변수를 쓰는 **단계에 가서야** 터지고,
  그때는 앞 단계가 이미 게이트웨이를 부르고 난 뒤다 — 되돌릴 수 없는 것도 있다.
- 안 채운 선택 변수는 `""` 로 들어가지 않고 빠진다.

## W-36. 예시는 **기본값이 아니다** — 버튼으로 넣는다

원래 물음은 "`json` 변수에 기본값을 두자" 였다. 두지 않았다.

미리 채워 두면 4겹 적층이 **자기 부품의 값처럼** 보인 채 그냥 돌고, 결과는 정상으로
나온다. 이 리포가 반복해서 만나는 모양 그대로다. 그래서 `Var.example` 은 칸을 채우지
않는다 — 칸은 비어 있고, 사람이 **"예시 넣기"** 를 눌러야 들어간다. `required` 는 그대로
살아 있어서 안 누르면 시작에서 걸린다. 화면에도 "내 값이 아니다 — 넣고 **고쳐서** 쓴다"
를 붙였다.

곁들여 `json` 변수 칸을 **여러 줄**로 바꿨다. 4겹 적층을 한 줄 `input` 에 넣는 것은
가능해도 사람이 할 일이 아니다.

예시 값은 지어내지 않았다. 도구가 들고 있는 정본
`get_reference_cases("fatigue_reversed_cycle")` 을 **부품 두께 1.2mm 에 맞춰** 0.125 →
0.3mm 로 바꾼 것이고, 총두께가 ①이 준 `thickness_mm` 와 **같은지 테스트가 본다**
(다르면 다른 부품을 해석하는 것이다). 씨앗에서는 YAML 앵커(`&ply`/`*ply`)로 적어
234줄을 157줄로 줄였고, 앵커판과 펼친 판의 값이 같은 것을 확인하고 바꿨다.

## W-37. 게이트웨이 한 칸 어긋남의 정체 — **재집계가 이틀째 매달려 있었다**

W-33 에서 "원인을 못 짚었다" 고 남긴 것을 짚었다. 짐작이 아니라 로그로 갈랐다.

`_revive_once` 는 항상 `GET :4040/api/v1/mcp/servers` 로 시작한다. 그 호출이
재기동 전후 구간에 **딱 한 번**뿐이었고, 그 한 번이 내가 손으로 친 `POST /refresh`
였다. 60초 주기라면 그 사이 세 번 있어야 한다. 로테이션 로그를 열어 보니 —

```
9/12 00:17 ~ 18:07  → 1069 회 (정상)
9/12 18:07:43       → 마지막
9/13 · 9/14         → 0 회
```

**멈춘 자리도 로그에 있다.** 18:07:54 재집계가 백엔드를 차례로 돌다가
`smart-twin-mcp -> 18 tools` 다음에서 끊겼다. 다음 차례인 `heax-materialtwin_web` 은
POST 를 보낸 기록만 있고 응답이 없다. 그 직전에 같은 백엔드가 liveness 에서
TimeoutError 를 냈다 — 느려진 앱 하나가 재집계 안에서 응답을 멈춘 것이다.

`_aggregate()` 의 `await b._ready.wait()` 와 `await b.session.list_tools()` 에
**데드라인이 없었다.** liveness(`fail_after`)·재연결(`move_on_after`) 경로엔 이미
걸어 놨는데 여기만 비어 있었다. 그래서 `_revive_loop` 가 거기 선 채로 **이틀** 있었고,
그동안 죽은 백엔드 부활도 도구 목록 갱신도 없었다.

**최악인 것은 아무도 못 봤다는 점이다.** 게이트웨이는 옛 카탈로그로 정상 응답을 계속
냈다. 에러도 경고도 없다. StepForge 를 재배포했는데 새 도구가 안 보여서야 드러났다 —
W-33 에서 "게이트웨이가 105초 뒤 스스로 감지했다" 고 적은 것은 **틀렸다.** 그 재집계는
내 수동 `/refresh` 였다. (고쳤다. 아래가 그 기록이다.)

고친 내용은 HWAXMcpGateway 쪽이다 — 두 await 에 `LIVENESS_TIMEOUT_S`(10초) 데드라인을
걸고, 초과하면 그 백엔드만 건너뛰며 **ERROR 로 남기고** 세션을 죽은 것으로 표시해
다음 회차 재연결 루프가 집어 가게 했다(`session is None` 갈래와 같은 동작). 회귀
테스트 둘을 붙였는데, 고치기 전 코드로는 5초 데드라인에 걸려 **실제로 실패한다**.
재기동 뒤 주기 루프가 60초마다 도는 것을 로그로 확인했다(15:08·15:09·15:10·15:11).

**교훈.** 멈추는 것은 예외가 아니라 **행**이라 `except` 로는 안 잡힌다 — 데드라인만
잡는다. 그리고 "60초 내 자동 재집계" 같은 약속은 **그 약속이 지켜지는지 보는 눈**이
없으면 조용히 거짓이 된다.

## W-38. R1 을 끝까지 돌렸다 — 답은 **불리**, 첫 사이클에 파손

씨앗을 처음부터 끝까지 태웠다. 입력은 **화면이 보내는 모양 그대로** 전부 문자열로 넣고
`coerce_inputs` 를 태웠다(W-35 가 고친 자리를 실제로 지나간다).

| 단계 | 결과 |
|---|---|
| ① `bend_profile` | R 6.0 · 두께 1.2 · 폭 40.0 mm · `analytic_cylinder_pair` |
| ③ 굽힘 R=6 | Mx 3842.7 N·mm/mm · 표면 변형률 **±10.0 %** · W130 |
| ④ 펼침 R=1000 | Mx 23.1 N·mm/mm · 표면 변형률 ±0.06 % · W130 |
| ⑤ 파손 | Tsai-Wu **R = 0.0757** · 지배 `fiber_tension` · `fails: true` |
| ⑥ 수명 | **1 사이클** (4겹 전부 동률) |
| ⑦ 보고서 | `gate: human` — 멈췄다 |

**절차가 답해야 할 질문에 답했다.** 1.2mm CFRP 판을 R 6mm 로 굽는 설계는 성립하지
않는다. 0° 인장 파손변형률이 Xt/E1 = 1500/181000 = 0.83% 인데 표면이 10% 다 —
12배다. 같은 두께로 그 변형률에 들려면 R ≳ 72mm 여야 한다(도구가 준 값만으로 유도).
정답을 제대로 찾으려면 R 스윕(S5)이나 `solve_required_thickness_scale` 이다.

**교차 검증이 걸렸다.** 적층 총두께 1.2mm 가 ①이 형상에서 읽은 두께와 같다 — 같은
부품을 해석했다는 뜻이다. 씨앗의 `why` 가 경고하는 자리이고, 이번엔 맞았다.

**두 상태의 차이가 곧 사이클**이라는 설계도 확인됐다. 별도 하중 변수가 없는데
Mx 3842.7 ↔ 23.1 이 그대로 ⑥의 max·min 이 된다. `equivalent_loads` 에 끼어 있는
`chain` 설명 문자열도 받는 쪽 둘이 그대로 삼켰다(W-34 에서 실호출로 확인한 것).

**W130 이 두 번 떴고 둘 다 기록에 올라왔다.** 자유 폭(M_y=0) 가정이라는 경고다 —
실제 지그가 구속 폭이면 답이 9.6% 갈린다. 씨앗이 `width_mode` 를 사람에게 묻는 이유가
이것이고, 경고가 조용히 사라지지 않는 것을 이번 실행으로 봤다.

**어디까지 돌렸나(정확히).** 도구 호출은 게이트웨이를 **내 MCP 자격**으로 했고,
형 맞추기·치환·판정·`save` 는 절차의 **실제 모듈**(`coerce_inputs`·`template`·`judge`)로
돌렸다. 포털 HTTP 경로(PAT 발급 → `GatewaySession`)는 이번에 안 지나갔다 — 내 셸에
PAT 가 없고, **없는 신원으로 토큰을 만들지 않았다.** 그 경로는 라우트 테스트와
살아 있는 서버 확인으로 따로 덮여 있다. 브라우저 완주는 여전히 사람 몫이다.

## W-39. 예제가 **한 칸만** 채워져서 실행이 안 됐다

사용자가 화면에서 "예시 넣기" 를 누르고 재생을 눌렀더니 이렇게 떴다.

```
채워야 할 값이 비어 있습니다 — StepForge 과제 ID(project_id), 부품 이름(part),
펼친 상태 굽힘반경 R_max (mm)(r_unfold), 굽힘축(bend_axis), 폭 구속(width_mode)
```

검증(W-35)은 옳게 동작했다. 틀린 것은 **씨앗**이다 — `laminate` 한 칸에만 `example` 을
달아 놨다. 나머지 다섯은 "사람이 판단해야 하는 값이라 예시를 주면 안 된다" 고 내가
스스로 판단해 뺐는데, 그 판단이 **예제를 못 돌게 만들었다.**

바로잡은 방식이 중요하다. `example` 은 여전히 기본값이 아니다(안 누르면 안 들어간다).
여섯 칸 전부에 예시를 달고, **"예제 값 모두 넣기"** 를 한 번에 채우는 버튼으로 뒀다.
옆에 "함께 오는 예제로 한 번 돌려 보는 용도입니다. **내 부품의 값이 아닙니다.**" 를 적었다.
판단이 필요한 값(굽힘축·폭 구속·펼침 R)은 예시로 들어가되 `why` 가 그대로 붙어 있다.

**교훈.** 사람이 판단할 값이라고 예시까지 빼면, 예제가 예제가 아니게 된다. 막을 것은
"값이 몰래 들어가는 것" 이지 "예시가 있는 것" 이 아니다.

## W-40. 실행 이력이 절차에 안 묶여 있었다 — 만든 뜻이 반쯤 사라져 있었다

사용자가 짚은 것 셋이 전부 같은 뿌리였다.

1. **예제를 실제로 돌릴 수 있어야 한다** → W-39.
2. **이력을 그대로 다시 돌리면 그 데이터로 계산되는 게 보여야 한다.**
3. **한 절차로 돌린 것들의 이력이 다 있어야 한다.**

절차를 만드는 뜻은 **다시 돌리는 것**인데, 그 두 길이 다 막혀 있었다.

**② 다시 돌리기.** `POST /runs/{id}/replay` 를 붙였다. 지난 실행의 입력을 그대로 써서
**새 실행**을 만든다(덮어쓰지 않는다 — 덮으면 이력이 사라진다). 기록을 재생하는 것이
아니라 도구를 실제로 다시 부르므로 **지금 데이터로 계산된 값**이 나온다.

⚠ **함정 하나를 여기서 막았다.** 실행의 `inputs` 에는 앞 단계가 뽑은 `save` 값도
섞여 있다(`merge_inputs`). 그대로 물려주면 새 실행이 **옛 중간값을 쥔 채** 시작하고,
①이 굽힘반경을 다시 읽어도 옛 값이 이미 범위에 있어 무엇이 쓰였는지 알 수 없게 된다.
그래서 **선언된 변수만** 걸러서 넘긴다. 테스트가 이것을 지킨다.

**③ 절차별 이력.** 실행은 `procedure_version_id` 하나만 들고 있어서 화면에서 절차로
되짚을 수가 없었다 — 한 절차를 몇 번 돌렸는지 보는 것 자체가 불가능했다.
`list_runs` 가 `procedure_versions` 를 조인해 `procedure_id`·`version_no` 를 함께 내고,
`GET /runs?procedure_id=` 로 그 절차의 이력만 본다. 절차 상세 아래에 그 목록을 두고,
실행 상세에는 "← 이 절차 판본 N 에서 나왔습니다" 를 달았다.

**곁들여 — 씨앗을 다시 가져오면 사본이 아니라 판본이다.** 씨앗은 리포와 함께 자란다
(오늘만 해도 예시가 한 칸에서 여섯 칸으로 늘었다). 가져올 때마다 사본이 생기면 목록이
같은 이름으로 차고 어느 것이 최신인지 사람이 알 수 없다. `procedures.from_seed` 를
기록해 두고, 이미 있으면 `add_version` 한다 — **옛 판본과 그 이력은 그대로 남는다.**

⚠ `CREATE TABLE IF NOT EXISTS` 는 **이미 있는 표를 고치지 않는다.** 칼럼을 DDL 에만
더하면 새 DB 에서는 되고 돌고 있는 DB 에서는 조용히 없어서, 그 칼럼을 읽는 코드가
**운영에서만** 터진다. 멱등 `_migrate` 를 두고 옛 스키마 DB 에 실제로 붙는지 확인했다.

**남은 한 가지.** `from_seed` 가 생기기 전에 가져간 절차는 그 칸이 비어 있어 판본으로
안 올라가고 사본이 하나 생긴다. 제목으로 짐작해 입양하는 규칙은 두지 않았다 — 사람이
같은 제목으로 만든 자기 절차를 잘못 집어삼킬 수 있다. 한 번뿐인 일이라 그대로 둔다.

## W-41. 개명이 깨뜨린 낱말 하나가 **이틀 동안 화면에 떠 있었다**

남은 일을 정리하려고 "챗·심의 파일 0줄 변경" 을 diff 로 확인하다 걸렸다. 절차 코드
첫 커밋 이후 챗·심의 소스에서 바뀐 파일이 **1건** 있었고, 열어 보니 이것이었다.

> 심의 화면의 예시 질문에서 **`밸런스` 의 `런` 이 `실행` 으로 바뀌어** 있었다.
> (깨진 문자열 자체는 여기 안 적는다 — 검사기가 이 문서를 잡는다. 실물은 커밋 `731922a`
>  의 diff 와 그것을 되돌린 `c95a6ee` 에 있다.)

워크벤치 → 절차 개명에서 `런` → `실행` 을 통째로 치환한 자국이다. 그때 12개 파일을
되돌리고 **"전부 원복했다" 고 보고했는데** 이 파일이 빠져 있었다. 하필 그 줄이
심의 화면의 **예시 질문**이라 사용자 눈에 그대로 보였다.

무서운 점은 **아무것도 안 터진다는 것**이다. 타입도 맞고 테스트도 통과하고 화면도
그려진다 — 글자만 틀렸다. 사람이 읽기 전엔 아무도 모른다.

`tests/test_rename_scars.py` 를 세웠다. **규칙이 아니라 실제 낱말에서 깨진 꼴을 만들어**
찾는다 — 처음엔 정규식(`[가-힣]실행[가-힣]`)으로 짰다가 `선실행해`·`오실행된다` 같은
멀쩡한 낱말을 잡아서 버렸다. 깨진 문자열을 **소스에 안 적는 것**도 그래서다(적으면
자기를 잡는다). 일부러 깨뜨려 실제로 잡히는 것까지 확인했다.

**교훈 둘.**
- 일괄 치환은 **한국어 낱말 속을 지나간다.** `런`·`벤치` 같은 두 글자는 특히 그렇다.
- "전부 되돌렸다" 는 보고는 **diff 로 확인한 것만** 참이다. 이번에도 내 기억이 틀렸고
  git 이 옳았다.

## W-42. "이 플랫폼의 일은 하나가 아니다" — 계획의 무게중심을 옮겼다

사용자가 두 흐름을 들었다. ① 챗으로 VOC 를 찾아 불량 메커니즘으로 정리해 보고서를 만들고
심의에 건다. ② MaterialTwin 에서 물성을 찾아 교체안을 만들고 DynaForge 물성을 갱신한다.
그리고 요구가 셋이었다 — **재현이 안 되는 것을 그 역할의 앱에 추가할 것**, **사용 이력에서
절차가 도출될 것**, **하드코딩하지 말 것**.

맞는 지적이라 계획을 고쳤다(PLAN §9). 요지 셋.

**① 예제 셋은 증명이지 제품이다가 아니다.** R1·R2·R3 은 세 모양(단일앱 계산 · 오래 걸리는
잡 · 폐쇄망)을 증명한다. 제품은 "챗에서 한 일이 절차로 굳는 길" 이고, 그래서 **S7 을 선택에서
본선으로** 옮겼다.

**② 결손 찾기와 절차 도출은 두 일이 아니라 하나다.** 도출을 시도하면 안 펴지는 칸이 나오고
그게 곧 결손이다. **이 고리는 이미 한 번 돌았다** — R1 이 굽힘반경을 "사람이 채우는 칸" 으로
뒀다가, 물어보니 형상에 있어서 StepForge 에 `bend_profile` 을 만들었다(D-287). 그것을 재치가
아니라 **작업 방식**으로 적었다.

**③ 하드코딩하지 않는다 = 이름으로 분류하지 않는다.** 실제로 해 보고 버렸다(§9-7).

## W-43. 내가 결손을 하나 **오판했다** — 그래서 검사 순서가 생겼다

게이트웨이 도구 지도 466개를 앱별로 갈라 "DynaForge 에는 물성을 갱신하는 도구가 없다 →
그 앱에 만들어야 한다" 고 판단했다. **틀렸다.**

`list_operations` 를 부르니 DynaForge 는 **연산 47개**를 들고 있었고 그중 둘이 물성 교체였다
(`matdb` · `matswap`). 도구가 아니라 `run_operation` 하나 뒤에 있어서 —
`search_tools("물성 교체")` 로 **안 나오고**, 카탈로그에서 **47개가 1로 세어지고**,
절차는 도구 단위라 **단계로 못 적는다.**

그대로 갔으면 DynaForge 팀에 **없는 일감**을 보낼 뻔했다. 그래서 §9-3 에 결손을 네 종류로
가르고 **검사 순서(② 숨어 있음 → ③ 안 이어짐 → ① 도구 없음 → ④ 재현 불가)** 를 박았다.
②를 먼저 안 보면 ①로 오판한다 — 내가 그랬다.

**그런데 계약은 있었다.** `describe_operation("matdb")` 가 `required`·
`additionalProperties:false` 까지 갖춘 JSON Schema 를 준다. 없는 것은 역량이 아니라
**드러남**이었다.

## W-44. 2단 도구 — 등록부는 데이터, 어댑터는 한 줄, 등재는 사람

`docs/procedures/dispatchers.yaml` 에 **사람이 확정한 것만** 적는다. 검출기
(`dispatch.detect_candidates`)는 후보를 밀 뿐 등재하지 않는다 — 잘못 등재하면 엉뚱한 인자를
검증한다.

검출 신호를 **이름이 아니라 스키마 모양**으로 잡았다. 인자가 적고 · 하나가 고르는 문자열이고 ·
다른 하나가 **속성 없는 object**(자유 페이로드)이며 · 같은 카탈로그에 `describe_*` 짝이 있다.
속성이 적힌 object(`laminate` 같은)는 자유 페이로드가 아니다 — 그것까지 2단으로 보면
엉뚱한 것을 잡는다(테스트가 지킨다).

**두 번째 단의 형식이 앱마다 다르다.**

| 앱 | 계약 | 형식 |
|---|---|---|
| DynaForge | `describe_operation` | JSON Schema 그대로 |
| StepForge | `job_params_guide` | `{type, default, 설명}` — 어댑터가 옮긴다 |

어댑터는 `schema_kind` 한 줄로 고른다. 코드에 흩뿌리지 않는다. StepForge 가 **모르는 키를
거절한다**(D-278)는 사실을 `additionalProperties:false` 로 옮기는 것까지 어댑터의 일이다 —
그래야 저장 시점에 잡힌다.

**효과는 테스트 한 줄이 말한다.**
`run_operation(operation="matdb", args={model, outut})` 가 1단 검사만으로는 **그냥 통과**하고,
두 번째 단을 붙이면 `outut` 오타와 빠진 `output` 을 **저장 시점에** 잡는다.

⚠ **못 받아 오면 검사하지 않는다.** `describe` 호출이 실패하면 그 항목만 건너뛴다 —
**모른다와 틀렸다를 섞지 않는다.** 이 규율이 없으면 게이트웨이가 잠깐 흔들릴 때 멀쩡한
절차가 저장 거절된다.

## W-45. 관측 — 세 표면을 다 읽었고, **원장은 이미 있었다**

절차 도출이 되려면 "무엇을 어떤 인자로 불러 무엇을 받았나" 가 남아야 한다. 세 곳을 다 읽었다.

- **게이트웨이 감사** 12,787줄: `{ts, tool, backend, ok, ms}` 가 전부다. 인자도 결과도 상관
  ID 도 없고, MCP 경로엔 호출자도 없다(93%가 신원 0). `ts` 가 초 단위라 6,584줄이 키를 공유한다.
  ⚠ 성공 기록에 `error` 가 실린다(`ok:true` + `error:"as:…"`·`"cache-hit"`).
- **챗**: 인자는 시작 이벤트(220자), 결과는 완료 이벤트(220/4000자)로 **갈라져** 나가고
  **잇는 키가 없다**. LangGraph 가 `run_id` 를 주는데 코드가 안 읽는다. 성패·소요·앱도 없다.
  화면은 **도구 이름으로** 묶어 같은 도구 N번 호출이 한 줄로 합쳐진다 — §5-5 의
  `predict_sed` 다섯 번이 이 기계다. 핸드오프는 **결과 있는 항목마다 인자가 `undefined`** 다.
- **심의**: 짝이 **안에서는 맞는데**(`tool_call_id` 로 조인) 나갈 때 `status`(인자)와
  `evidence`(결과)로 갈라지고, 웹 경로는 `evidence` 를 **통째로 버린다**.

그리고 `agent/audit.py` 에 `event='tool_call'` 이 **스키마로 선언돼 있는데 아무도 안 쓴다.**

**답은 새 원장을 만드는 게 아니었다.** `procedures.sqlite` 의 `run_steps` 가 이미 정확한
모양이다 — 인자 원본 · 결과 gzip · 양쪽 sha256 · 성패 · 소요 · 순서. 챗과 심의가 **안 쓸 뿐**이다.
→ **하나의 원장, 세 생산자**(PLAN §9-9). 그러면 절차 도출이 "챗 기록을 해석하는 일" 이 아니라
**"이미 절차 모양인 기록을 읽는 일"** 이 된다.

⚠ 이것은 §3 의 "챗 파일 0줄" 원칙에 **예외**를 낸다. 그래서 계획에 명시했다 — 챗에 **기록만**
더하고, 읽는 쪽은 안 바꾸고, 쓰기가 실패해도 챗을 막지 않는다.

## W-46. 관측 배선 — 짝·성패·표식, 그리고 하나의 원장

PLAN §9-9 의 ①~⑤를 놓았다. **순서가 설계였다** — 짝과 성패 없이 원장에 쓰면 거짓이 쌓인다.

**① 짝.** `run_id` 가 도구 시작·완료 두 이벤트에 **같은 값으로 이미 오고 있었다.** 코드가
안 읽었을 뿐이다. `call` 로 실어 보낸다. 이 하나로 §5-5 가 풀린다 — `predict_sed` 다섯 번의
프리뷰가 같아도 이제 **다섯 줄로 남는다.**

**② 성패.** `_cap_tool` 이 예외를 문자열로 바꿔 돌려주는 것은 **의도다**(그래야 LLM 이
스키마를 보고 인자를 교정한다). 문제는 그러면서 **판단까지 버렸다**는 것이다. 전송 오류인지
인자 오류인지는 이미 그 자리에서 가르고 있었다. 표지(`✖`)를 달아 그 판단을 실어 나르고
완료 이벤트가 `ok` 를 싣는다.

**③ 표식 절단.** 네 갈래를 한 규약으로 모았다(`…#sha1[:6]`). 심의 쪽에만 있던 것이다.
표식 없이 자르면 n 자 뒤에서만 갈리는 두 호출이 **같은 서명**이 된다.
⚠ 포털이 에이전트의 4000자를 **2000자로 다시** 자르고 있었다(표식 없이) — 그것도 걷어냈다.

**④ 심의.** 짝은 **안에서는 맞았다**(`tool_call_id` 로 조인). 나갈 때 인자는 `status` 로,
결과는 `evidence` 로 갈라져 다시 못 붙었다. id 를 삼중항에 실어 두 이벤트에 같이 태우고,
`evidence` 에 **인자를 붙였다** — 핸드오프가 "결과는 있는데 인자가 없다" 이던 뿌리다.

**⑤ 하나의 원장.** `app/procedures/from_chat.py`. 챗 턴의 도구 호출을 `run_steps` 에 남긴다.
새 표를 안 만들었다 — 이미 정확한 모양이었다.

접는 규칙에 규율 하나를 박았다. **짝 키가 없으면 아예 안 접는다.** 이름으로 묶는 것은
화면이 하던 일이고 그게 §5-5 를 만들었다 — 원장이 그 거짓을 물려받으면 안 된다.
안 남기는 편이 낫다.

그리고 셋을 더 지켰다.
- **기록만 더한다** — 챗이 읽는 쪽은 안 바꿨다(화면 묶기만 짝 키로 고쳤고, 없으면 종전대로).
- **실패해도 챗을 막지 않는다** — `record` 가 모든 예외를 삼킨다(테스트가 지킨다).
- **모른다와 틀렸다를 안 섞는다** — `ok` 를 못 받으면 `None` 이다. `False` 가 아니다.

**⑥ 챗 실행은 자동으로 절차가 되지 않는다.** `procedure_version_id` 가 없는 빈 실행으로
남고, 사람이 보고 뽑을 때 판본이 생긴다(PLAN §7 "자동 저장 금지").

남은 것 — ⑥ 게이트웨이 얇은 색인(상관 ID·호출자)과 ⑦ 성공 기록의 `error` 오남용 제거.
그리고 그 위에 **도출**(실행 → 절차 초안 제안)이 올라간다.

## W-47. 게이트웨이를 얇은 색인으로 — 그리고 `error` 오남용을 걷어냈다

감사 12,787줄을 읽고 두 가지를 고쳤다(PLAN §9-9 ⑥·⑦).

**⑦ 먼저 — 성공 기록에 `error` 가 실리고 있었다.**

```
{"ok": true, …, "error": "as:someone@samsung.com"}
{"ok": true, …, "error": "cache-hit"}
```

위임 신원과 메모를 `error` 칸으로 날랐다(215줄). 그러면 `error` 는 실패 신호로 못 쓰고
`caller` 는 신원 질의로 못 쓴다. **성공이 실패처럼 생긴 것**이라 이 리포가 싫어하는 모양의
거울상이다. 칸을 갈랐다 — `caller`(누가) · `mode`(어느 명의) · `note`(실패 아닌 메모) ·
`corr`(어느 실행). `error` 는 실패에만 쓴다. 소스 정적 검사로 재발을 막는다.

**⑥ 신원과 상관 ID.** MCP 경로 10곳 전부에 `caller` 를 싣는다. 새로 만들 게 없었다 —
PAT 의 이메일이 이미 `X-HWAX-User` 로 주입되고 있었고(gateway.py:2183) `_request_user()` 가
그걸 읽는다. 종전에 93%가 신원 0이던 것은 **있는 값을 안 쓴 것**이었다.
`ts` 도 밀리초로 바꿨다 — 초 단위라 12,787줄이 7,879 키로 뭉갰다(최악 109줄/키).

**⚠ 상관 ID 를 챗에는 못 붙였다.** 챗은 도구 연결을 **그룹 집합으로 캐시한다**
(`agent_for`). 대화 id 를 연결 헤더에 넣으면 캐시가 대화마다 쪼개져 도구 로딩이 매 대화마다
새로 돈다. 절차는 **세션이 실행 단위**라 붙일 자리가 거기다 — `GatewaySession(corr=run_id)`.
실측으로 확인했다(`corr: "run-TEST123"`).

챗 쪽은 호출마다 헤더를 실을 길이 필요한데 MCP 클라이언트가 연결 단위라 간단하지 않다.
**억지로 붙이지 않고 미결로 남긴다** — 챗은 대신 `from_chat.record()` 로 원장에 직접 쓰므로
감사 색인 없이도 이어진다(그게 §9-9 의 "얇은 색인 · 살찐 기록" 이 갈라 놓은 이유다).

## W-48. 도출 — 값이 **어디서 왔는지**를 찾는다(키워드 목록이 아니라)

한 고리의 마지막 칸이다(PLAN §9-2). 챗에서 한 일이 원장에 남았으면 절차로 펴 본다 —
**안 펴지는 칸이 곧 결손이다.**

어려운 것은 "어느 인자가 변수인가" 였다. 키워드 목록(`*_id` 는 변수, `path` 는 변수…)으로
정하면 그게 하드코딩이고, §9-7 에서 이미 한 번 버린 방식이다. 대신 **출처를 찾는다.**

| 어디서 왔나 | 무엇인가 | 어떻게 아나 |
|---|---|---|
| 앞 단계 **결과 안에** 있다 | **체인** — `save` → `{{}}` | `find_path()` 가 경로를 역으로 찾는다 |
| 사람이 쓴 말 **안에** 있다 | **변수** | 대화 제목·질문에 그 값이 있다 |
| 둘 다 아니다 | **모른다** | 상수로 두고 `needs_human` 에 올린다 |

`find_path` 는 `template.extract` 의 역이다. `{"parts":[{"for_bending_analysis":
{"bend_radius_mm":6.0}}]}` 에서 `6.0` 을 주면
`parts[0].for_bending_analysis.bend_radius_mm` 를 돌려준다.

**R1 을 넣으면 R1 체인이 그대로 나온다.** ①이 읽은 굽힘반경을 ③이 인자로 썼다는 사실을
사람이 적어 주지 않아도 알아낸다 — 값이 거기 있다는 것으로 안다.

규율 넷.
- **찾은 경로는 대조한다.** `template.extract` 로 다시 풀어 같은 값이 나올 때만 체인으로
  인정한다. 짐작한 경로를 주면 **못 도는 절차**가 나온다.
- **짧은 값은 안 믿는다.** `"ok"`·`1`·`"mm"` 은 아무 데나 있다. 우연한 일치로 체인을
  만들면 엉뚱한 단계가 물린다(`MIN_MATCH_LEN=3`).
- **모르면 모른다고 한다.** 지어낸 변수는 절차를 조용히 망친다 — 매번 물어보는 칸이 되거나
  남의 값이 상수로 굳는다. 세 번째 갈래가 그래서 있다.
- **변수와 save 가 같은 이름 공간이다.** 둘 다 `{{이름}}` 으로 불리므로 따로 세면
  뒤엣것이 앞엣것을 조용히 덮는다(테스트가 지킨다).

**결손이 같이 나온다** — `backend` 를 도구 지도에서 못 찾았거나(챗 기록에 앱이 없다),
인자가 구조가 아니라 글이면(잘린 미리보기) `gaps` 에 올라간다. 도출과 결손 찾기가 한 일이라는
§9-2 가 코드로 성립한다.

**⚠ 인자를 날것으로 남기게 바꿨다.** 종전에는 챗이 인자를 220자 미리보기로만 남겨서
그걸로 만든 절차는 **인자가 손상돼 있었다**(적층 정의·시나리오는 통째로 잘린다).
결과에 `result_full` 을 두는 것과 같은 이유로 시작 이벤트에 `detail_full` 을 더했다.

**⚠ 자동 저장하지 않는다.** `GET /runs/{id}/draft` 는 초안과 **근거**를 낼 뿐이다.
`backend` 가 빈 초안은 저장 검증에 걸리는 것까지 시험한다 — 그게 "자동 저장 금지" 의 실질이다.

## W-49. 절차는 사실상 도구다 — 변수가 그 입력 스키마다

사용자가 짚었다. *"인자화해서 절차화되면 여러 변수 의미가 잘 노출되게 설명까지 LLM 이
잘 읽어야 할 것 같아, MCP 기능 만드는 것처럼."*

맞다. 그런데 도출이 붙이던 설명은 **"사람이 이번 대화에서 준 값이다"** 한 줄이었다.
그 절차를 받은 사람도, 그 절차를 부를 LLM 도 그 칸이 무엇인지 알 수 없다.

**설명을 지어낼 필요가 없었다 — 도구 스키마에 이미 있다.**

`bend_radius` 를 변수로 올릴 때 `solve_prescribed_curvature` 의 `inputSchema` 에서
그 인자의 `description`·`type`·`enum`·`default` 를 끌어온다. 그래서 —

| 끌어온 것 | 무엇이 달라지나 |
|---|---|
| `description` | 변수의 `why` 가 **뜻**을 말한다("굽힘반경, 길이 단위. unit_system 에 묶인다") |
| `enum` | 자유 입력이 **고르는 칸**이 된다 — `free\|constrained` 오타가 조용히 살지 않는다 |
| `type` | 형이 맞는다(화면이 문자열로 보내도 `coerce_inputs` 가 푼다) |
| `default` | "도구 기본값: free" 가 설명에 붙는다 |

여기에 **쓰이는 자리**를 더한다. 한 변수가 세 단계를 움직이는데 한 단계만 적혀 있으면
사람이 영향 범위를 오해한다 — 값을 바꿨을 때 무엇이 함께 바뀌는지가 절차의 요점이다.

**⚠ 설명 없는 인자는 결손이다.** 도구 스키마에 그 인자 설명이 없으면 `arg_undocumented`
로 `gaps` 에 올린다. 지어내지 않고 "설명이 없다" 고 적는다. 이것이 §9-3 ①의 새 얼굴이다 —
**그 앱의 문서 결손**이고, 고칠 자리는 그 앱의 도구 설명이다.

**그리고 도출이 결함 하나를 드러냈다.** 같은 인자에 같은 값이 두 단계에 쓰였는데 변수가
**둘로 갈라졌다**. 그러면 사람이 같은 값을 두 번 채우고, 한쪽만 바꾸면 절차가 조용히
어긋난다. `(인자 이름, 값)` 으로 묶어 하나로 만들었다. 다른 인자에 같은 값이 든 것은
안 묶는다 — `width="free"` 와 남의 `mode="free"` 가 합쳐지면 더 나쁘다.

## W-50. 절차를 **도구 계약**으로 낸다 — 등록의 다리

`GET /procedures-api/procedures/{id}/tool` 이 `{name, title, description, inputSchema,
human_gates}` 를 낸다. `to_input_schema()` 가 변수를 JSON Schema 로 옮긴다
(`additionalProperties:false`, `required`, `enum`, `examples`).

R1 을 그 계약으로 보면 이렇게 나온다.

```
*project_id   string              StepForge 과제 ID
*bend_axis    x | y               적층의 0° 방향을 기준으로 어느 축으로 굽는지…
*width_mode   free | constrained  답이 **9.6% 갈린다**(도구가 W130 으로 경고한다)…
*laminate     object              {unit_system, laminae:[{thickness, angle_deg, material}]}…
```

**⚠ 사람 확인 자리가 계약의 일부다.** `human_gates` 를 계약에 싣는다 — 부르는 쪽이
"이 절차는 보고서 초안에서 멈춘다" 를 모르면 **"왜 안 끝나지"** 가 된다. 도구처럼 부르게
하려면 멈추는 것이 정상이라는 사실도 계약으로 말해야 한다.

이것이 사용자가 맨 처음 말한 것으로 돌아간다 — *"프로젝트 중 하나가 이런 걸 자동화해 놓은
도구로 등록하고, 실제 심의를 돌릴 때는 자동화된 워크플로우로 돌리게끔"*. 등록 자체는 아직
사람 손이지만, **계약은 이제 도구와 같은 모양이다.**

## W-51. 대상을 **룰로 고른다** — 이름을 박으면 그 절차는 그 부품에만 쓴다

사용자가 짚었다. *"스텝이나 ODB 같은 경우는 대상이 되는 파트 이름을 정하는 룰 같은 것도,
파트 이름 같은 것도 룰 베이스로 필터하게끔 하는 게 있으면 좋을 거야."*

맞다. R1 은 `part: "UBEND_1"` 로 리터럴을 박아 뒀고, 그 절차는 **그 부품에만** 쓴다.
다른 과제에 재생하려면 대상을 고르는 규칙이 변수여야 한다.

역량은 이미 있다 — `find_parts`(이름 글롭·재질·부피 범위·메시 유무) · `find_reports` ·
`find_materials_by_metadata`. 없던 것은 **절차가 그 룰을 받고 결과를 다루는 칸**이다.

`Step.select` 를 더했다.

```yaml
- backend: heax-step_forge
  tool: find_parts
  args: {project_id: "{{project_id}}", name: "{{part_rule}}"}
  select: {from: parts, save: name, as: part, label: name}
```

**0/1/N 이 이 기능의 전부다.**

| 결과 | 무엇을 하나 |
|---|---|
| 0개 | **실패**. 조용히 건너뛰면 뒤 단계가 전부 헛도는데 **화면은 정상으로 보인다** |
| 1개 | 그것을 담는다(다시 돌릴 때 쓰도록 `inputs` 에도 남긴다) |
| N개 | **사람에게 묻는다** — 후보를 보이고 고르게 한다 |

⚠ **여럿에서 첫 번째를 조용히 집는 것이 가장 위험하다.** 엉뚱한 대상으로 절차 전체가
돌고 결과는 정상으로 나온다. StepForge 가 이미 그 자세를 잡아 뒀다 — *"이름이 겹치면
후보를 돌려주고 **고르지 않는다** — 엉뚱한 파트를 답하는 것이 가장 나쁘다"*(D-170).
그래서 기본이 `ask` 이고, `first` 는 사람이 명시해야 하며 **저장 시점에 경고한다.**
`on_none: skip` 도 같은 이유로 경고한다.

**고르기는 확인과 다르다.** 확인(`ack`)은 "이대로 해라" 이고 고르기(`pick`)는
**"이것으로 해라"** 다. 그래서 라우트를 따로 뒀다.

⚠ **보여 준 후보 중에서만 고를 수 있다.** 아무 값이나 받으면 룰을 우회해 엉뚱한 대상으로
절차가 돈다 — 그건 고르는 것이 아니라 박는 것이다(테스트가 지킨다).

⚠ `from` 경로가 안 풀리면 **후보 없음과 같게** 다룬다. 조용히 통과시키면 룰이 틀린 줄
모른 채 절차가 돈다.

## W-52. 저장이 스키마 대조를 우회하고 있었다 — 그리고 고치다 더 큰 것을 찾았다

스키마 대조가 `/validate` 에만 있었다. 그건 **권고**지 검증이 아니다 — API 를 직접 부르면
그대로 통과한다. 저장(`_validated`)에서도 같은 검사를 하게 했다.

**그러다 진짜 결함이 드러났다.** 테스트가 전부 깨졌는데, 원인이 둘이었다.

**① 빈 카탈로그를 "도구가 없다" 로 읽었다.** 게이트웨이는 465종을 들고 있으므로 0건은
**"못 물어봤다"** 는 뜻이다. 그걸 실패로 치면 게이트웨이가 잠깐 흔들릴 때 멀쩡한 절차가
저장 거절된다. 내가 docstring 에 "못 물어봤을 때와 틀렸을 때를 섞지 않는다" 고 적어 놓고
코드가 안 지켰다.

**② 더 큰 것 — 없는 것과 내 권한 밖인 것을 섞고 있었다.**
테스트가 **살아 있는 게이트웨이를 실제로 부르고 있었고**(lifespan 이 진짜 러너를 세운다),
그 신원의 시야에는 step_forge·laminate 도구가 없었다. 그래서 멀쩡한 R1 씨앗이
*"게이트웨이에 이 도구가 없다"* 로 저장 거절됐다.

**이건 테스트만의 일이 아니다.** `tools/list` 는 **부르는 사람의 권한으로 필터된다**.
남이 쓸 절차를 만드는 사람이 그 도구를 못 볼 수 있고, 그 앱이 잠깐 안 붙어 있을 수도 있다.
"안 보인다" 에는 **세 가지 뜻**이 있는데 하나로 뭉개고 있었다.

→ 갈랐다. **보이는 도구에서 확실한 것**(인자 오타·필수 누락)은 저장에서 막고,
**안 보이는 도구**는 만드는 화면에서는 알려 주되 저장은 막지 않는다. 문구도 바꿨다 —
*"없다"* → *"안 보인다 — 없거나, 내 권한 밖이거나, 그 앱이 지금 안 붙어 있다"*.

⚠ 곁가지로 알게 된 것 — **포털 테스트가 살아 있는 게이트웨이를 친다.** 지금은 통과하지만
게이트웨이가 내려가 있으면 결과가 달라진다. 그 자체가 결손이다(테스트는 공유 서비스를
치면 안 된다). 지금 고치지 않고 적어 둔다.

## W-53. 고르기 화면 — 내가 연 구멍을 막았다

`select: {on_many: ask}` 를 만들어 놓고 **화면에 고르는 자리를 안 만들었다.** 룰이 여럿을
고르면 실행이 `gated` 로 멈추는데, 화면에는 확인 버튼밖에 없어서 **이어갈 길이 없었다.**
기능을 더하면서 막다른 길을 만든 것이다.

실행 단계 화면에 후보 버튼을 붙였다. 고르면 `pick` 을 부르고 이어서 돈다.
문구로 이유를 적었다 — *"첫 번째를 자동으로 집지 않습니다 — 엉뚱한 대상으로 돌아도
결과는 정상으로 나오기 때문입니다."*

## W-54. 테스트를 오프라인으로 — 감사 줄수 0 증가로 확인했다

W-52 에서 찾은 것을 고쳤다. 포털 테스트가 **살아 있는 게이트웨이(:9110)를 실제로 치고**
있었다. lifespan 이 진짜 실행기를 세우기 때문이다. 그래서 —

- 게이트웨이가 내려가면 결과가 달라지고,
- 결과가 **그 신원의 권한**에 좌우되고(멀쩡한 R1 씨앗이 저장 거절됐다),
- 남의 게이트웨이에 세션이 쌓인다.

`_offline_runner()` 를 세웠다 — 도구 0개를 돌려주는 가짜 게이트웨이다. 0개는
"못 물어봤다" 로 다뤄지므로(W-52) 저장은 경고만 남기고 통과한다.

**확인은 감사 줄수로 했다.** 전체 스위트를 돌리기 전후로 `/data/svc/mcp-gateway/audit.jsonl`
이 12,803줄 그대로였다. "안 친다" 는 주장을 코드가 아니라 **바깥 흔적**으로 확인한 것이다.

## W-55. 2단 후보 넷을 실제로 물어봤다 — 셋이 각각 다른 답을 냈다

| 후보 | 결과 |
|---|---|
| `catalog_run` (SmartTwinMCP) | **등재.** 뒤에 도구 **44개**. `catalog_describe` 가 JSON Schema draft 2020-12 을 그대로 주고 `examples`·`how_to_call` 까지 있다 — 지금 등재한 셋 중 계약이 가장 잘 갖춰졌다 |
| `slurm_submit_job` (STC) | 2단은 맞는데 **계약이 산문이다.** `slurm_list_templates` 가 텍스트 한 덩이를 주고 필수 file_key 가 그 안에 적혀 있다 → **결손으로 등재**(`gaps/stc-template-schema.yaml`) |
| `create_report_from_preset` · `run_saved_search` | 이 박스에 항목이 **0건**이라 **확인 못 했다.** 없다는 뜻이 아니다 — 후보로 두고 `checked` 에 무엇을 봤는지 적었다 |

**세 번째 줄이 규율이다.** 0건을 "그 앱에 2단이 없다" 로 읽으면 W-52 에서 고친 것과 같은
잘못이다 — **확인 못 한 것과 없는 것은 다르다.** 테스트가 후보마다 `checked` 를 강제한다.

곁들여 — 잡 제출은 되돌리기 어려운 쪽이다. 계약이 산문이면 `file_key` 오타를 **저장
시점에 못 잡고**, 잡을 던진 뒤에야 안다. 그래서 결손으로 올렸다.

## W-56. 소요·시각 — 짝 키가 있으니 잴 수 있게 됐다

원장(`run_steps`)에 `duration_ms` 칸이 있는데 챗이 안 채우고 있었다(§9-8). 이제 짝 키가
있으니 **시작을 기억했다가** 완료에서 뺀다. 이름으로는 못 잰다 — 같은 도구를 N번 부르면
어느 시작이 어느 완료인지 모른다(§5-5 가 그 기계다).

## W-57. 룰이 고른 **전부**를 돌린다 — 배치는 새 실행 N개다

"디스플레이 패널에 해당하는 것" 처럼 **여럿이 답인** 물음이 있다. 하나만 고르면 나머지는
버려진다. `POST /runs/{id}/steps/{ix}/fan-out` 이 후보마다 **실행을 하나씩** 만든다.

**설계의 요점은 새 기계를 안 만든 것이다.** 배치는 그냥 **실행 N개**이고 `batch_id` 로
묶일 뿐이다. 그래서 기존 것이 전부 그대로 돈다 — 게이트·재개·다시 돌리기·도출·초안.

그 덕에 계획(S5)이 요구한 것이 **저절로** 지켜진다.

> "배치는 첫 `gate: human` 직전까지 돌고 표를 만든다. 이후는 표에서 골라 개별 재개
> (**초안 N개 금지**)"

각 실행이 자기 게이트에서 알아서 멈춘다. 보고서 초안이 한꺼번에 N개 만들어지는 일이 없다.
따로 막는 코드를 안 썼다 — 구조가 그렇게 되어 있다.

**규율 넷.**
- **기본이 계획 모드다.** N개를 live 로 던지는 것은 사람이 골라야 한다.
- **보여 준 후보 안에서만** 펼친다. 아무 값이나 받으면 룰을 우회한다(`pick` 과 같은 규율).
- **상한 50.** 넘으면 *"룰을 좁혀 주세요"* 라고 말한다 — 사람이 표로 볼 수 있는 크기까지다.
- **고른 값이 이미 범위에 있으므로 그 선택 단계 다음부터** 돈다. 룰을 N번 다시 풀지 않는다.

**비교표는 `inputs` 를 그대로 열로 편다**(S5 가 적어 둔 그대로). 단계 인자를 역파싱하면
치환된 뒤 값이라 무엇이 달랐는지가 흐려진다 — 표의 요점은 *"무엇을 바꿨더니 무엇이
달라졌나"* 다. 공통 변수(과제 id 등)는 원래 실행에서 물려받고 고른 값만 갈린다.

⚠ 동시성은 **실행기의 기존 상한**이 잡는다(세마포어 2 · 느린 단계는 백엔드별 잠금).
배치가 따로 상한을 두지 않는다 — 두 곳에서 세면 어긋난다.

## W-58. 도구 **인자 설명**이 1,348개 중 15개다 — 1%

사용자의 요구("변수 의미가 잘 노출되게, LLM 이 잘 읽게")를 따라가다 바닥을 쳤다.
`find_parts` 의 인자 설명을 보러 갔더니 **하나도 없었다.** 전수로 셌다.

| | |
|---|---|
| 도구 | 468종 |
| 인자 | 1,348개 |
| **설명 있는 인자** | **15개 (1%)** |

최악은 인자 21개에 설명 0개(`list_reports`·`find_reports`). 그런데 **내용이 없는 게
아니다** — 도구 **산문**에 있다. `find_parts` 의 `name` 이 글롭이라는 사실은
*"`name` 은 글롭이다(`bolt_*`)"* 라는 문장에만 있다. 이 허브의 도구 설명이 유난히 긴
이유가 그것이다 — **인자 설명을 산문이 대신하고 있다.**

**두 가지를 했다.**

**① 산문에서 인용한다.** `from_prose()` 가 도구 전체 설명에서 **그 인자 이름이 실제로
나오는 문장**을 찾아 쓴다. ⚠ 지어내지 않는다 — 인용이고, 인용이라는 사실을 밝힌다
("(도구 설명에서) …"). 아무 문장이나 붙이면 **틀린 설명**이 되므로 이름이 나오는
문장만 가져온다(테스트가 지킨다).

**② 검출기 눈금을 바꿨다.** 인자마다 결손을 올리면 **99%에서 울린다.** 그건 검출기가
아니라 잡음이고, 목록이 그것으로 덮여 **진짜 결손이 묻힌다.** 초안 하나당 한 줄로 모아
몇 개인지만 말한다.

결손 장부에 `hub-arg-descriptions.yaml` 로 올렸다. ⚠ **한 앱의 일이 아니다** — 전 앱이
조금씩 채울 일이고, 한 번에 다 할 것도 아니다. **절차에 실제로 쓰이는 도구부터**다.

## W-59. 초안 확정 화면 · 비교표의 "왜"

**초안 확정.** 도출이 펴 보기만 하고 끝나면 고리가 안 닫힌다. 사람이 정할 자리마다
체크상자와 이름 칸을 두고, 고른 것만 변수로 올려 저장한다. 화면에 왜 묻는지도 적었다 —
*"코드는 이 값들이 어디서 왔는지 모릅니다. 과제마다 바뀌는 값이면 변수로 올리고,
이 절차의 성질이면 그대로 둡니다."*

**비교표의 "왜".** 계획(S5)이 *"실패한 과제를 건너뛰고 계속 + 무엇이 왜 실패했는지 표에"*
라고 적어 뒀다. 상태만 보이면 "5건 중 2건 실패" 로 끝나고 사람이 실행을 하나씩 열어야 한다
— **표의 값어치가 거기서 사라진다.** 첫 실패 단계·도구·오류를 열로 싣고, 경고 코드도
함께 싣는다(W120 처럼 결과는 정상인데 경고만이 유일한 신호인 자리가 있다).

## W-60. 후처리가 DynaForge 로 온다 — 절차를 **읽는 쪽으로** 쓴다

사용자가 짚었다. *"낙하 충격은 최신의 KooD3plot 쪽이 후처리 모듈을 DynaForge 에 올려놓고
쓸 거잖아? 그걸 감안해서 잘 구성해 주면 좋을 것 같아."*

**지금 사슬을 실측으로 확인했다.**

```
제출   smarttwin_submit / slurm_submit_job        (STC)
후처리 job_postprocess(all|deep|sphere)           (smart-twin-mcp → KooChainRun → KooD3plotReader)
       → Run_*/Output/report/(deep) · sphere_report.html
운반   REST intake(512MB) / ingest_report(작은 것만)   ← **아픈 자리**
판독   report_summary · report_worst_cases · report_directional …   (DynaForge)
```

후처리기 실물은 **`KooDynaPostProcessor`**(Qt/VTK **실행 바이너리**, 오프스크린 가능) —
KooD3plotReader V1.3.0 `references/` 에 번들·standalone 로 들어 있다. 라이브러리가 아니라
실행 파일이라 "어디에 두든 그 자리에서 돈다" 가 된다.

**옮겨지면 운반이 통째로 사라진다.** `sphere_report.html` 9.8MB · `impact_report.html`
7.9MB 를 나르려고 REST intake 를 쓰고 `report_id` 를 사람이 변수로 넣고 있다 —
**그건 설계가 아니라 우회다.**

**그래서 절차를 반으로 갈랐다.**

| 반쪽 | 옮겨지면 |
|---|---|
| **얻는 쪽** — 잡 결과에서 리포트가 생기고 `report_id` 가 정해진다 | **바뀐다** |
| **읽는 쪽** — `report_*` 판독 도구 묶음 | **안 바뀐다** |

→ **읽는 쪽으로 절차를 쓰고, 얻는 쪽은 `report_id` 변수 하나로 좁힌다.** 그러면 옮겨
왔을 때 **앞에 단계 하나를 더하는 것**으로 끝난다. 반대로 지금 사슬(REST 명령·파일
경로·postprocess 인자)을 절차에 박으면 옮겨진 뒤 그 절차는 **전부 거짓말**이 된다.
R2b 가 `report_id` 를 변수로 받는 진짜 이유가 이것이다(운반 한계는 부차적이다).

**옮겨 올 때 필요한 것을 미리 적어 뒀다.**
- 연산으로 오면 — `run_operation(operation="postprocess")` + `describe_operation` 이
  계약을 준다. 등록부에 DynaForge 가 이미 있어 **한 줄도 안 고친다**.
- 직접 도구로 오면 — 인자 스키마가 필요하다. 지금 `job_postprocess` 는 `args` 자유 object
  하나이고 `mode` 가 산문에만 있어, 그대로 오면 오타를 저장 시점에 못 잡는다.
- 오래 걸리면 — 전각도 낙하는 Run 이 수십~수백이라 120초를 넘길 수 있다. `expect: job` 은
  저장 거절이라 **제출·회수가 자동으로 갈린다**(§5-10). 그 규칙이 여기서 값을 한다.

## W-64. 결손을 장부로 — **파일은 포털이 쓰지 않는다**

도출이 결손을 찾아내도 화면에만 떠 있으면 앱 팀에 안 간다. `POST /gaps/draft` 가 결손
하나를 §9-6 모양의 **YAML 초안**으로 만든다.

⚠ **파일을 쓰지 않는다.** 텍스트를 돌려줄 뿐이고 사람이 읽고 리포에 커밋한다. 포털이
리포에 직접 쓰면 —
- 검토 없이 결손이 늘고,
- 컨테이너가 리포를 쓰게 되고,
- **누가 등재했는지가 git 이 아니라 웹 세션에 남는다.**

셋 다 싫다. 테스트가 "파일을 안 쓴다" 를 실제로 확인한다(gaps 디렉터리 목록 대조).

초안에는 §9-3 의 **검사 순서를 일깨우는 줄**이 박혀 있다 — *"등재 전에 ② 숨어 있나 →
③ 안 이어지나 → ① 도구 없나 → ④ 재현 불가인가"*. 내가 그 순서를 안 밟아 DynaForge 에
없는 일감을 보낼 뻔했기 때문이다(W-43). `status: open` · `confirmed_by: null` 로 나가서
**사람이 확정하기 전에는 확정이 아니다.**

## W-65. 2단 도구를 화면에서 고른다 — 47개가 도구 하나로 보이던 자리

등록부(W-44)와 저장 시점 검증(W-52)은 있었는데 **만드는 화면에는 아무것도 없었다.**
`run_operation` 을 고르면 인자가 `operation`·`args` 두 칸으로 보일 뿐이라, 사람이
`operation` 에 무엇을 적을지 알 방법이 없다 — 뒤에 연산 47개가 있다는 사실 자체가
화면에 없다.

도구를 고르면 **등록부와 대조해** 2단이면 칸이 하나 더 뜬다.
- 뒤에 무엇이 있나(목록) → 고르면 **그 계약**(인자 이름·필수 표시)
- `operation` 으로 고르고 `args` 에 넣는다는 것도 화면이 말한다
- 계약을 못 받으면 *"이름이 틀렸거나 그 앱이 지금 안 붙어 있다"* — **없다고 하지 않는다**

⚠ **노출 이름이 접두어로 바뀔 수 있다.** 앱이 겹치면 게이트웨이가 `heaxkooremapper_mcp_`
를 붙인다. 이름이 정확히 같은지만 보면 그때 2단 칸이 조용히 사라진다 — `_<tool>` 로
끝나는지도 본다.

**목록 응답 모양이 앱마다 다르다.** DynaForge 는 `{name, category, summary}` 의 연속,
SmartTwinMCP 는 `{hits: […]}`. 하나로 가정하면 한쪽이 **조용히 빈 목록**이 된다 —
`_names_of()` 가 몇 가지 모양을 보고, 모르는 모양이면 **빈 목록**이다(지어내지 않는다).

정적 계약 가드도 넓혔다 — 라우트가 부르는 실행기 메서드가 실제로 있는지 본다(W-30 재발 방지).

## W-66. 하드코딩 점검 — 가드를 세우자 **첫 실행에서 둘을 잡았다**

사용자가 물었다. *"지금 만든 것들이 하드코딩이 불합리하게 들어가 있지는 않은지 잘
점검해 보도록."* 절차 모듈의 모듈 상수를 전수로 훑어 넷으로 갈랐다.

| 갈래 | 예 | 판정 |
|---|---|---|
| **A. 카탈로그에서 뽑은 목록** | `MUST_GATE`·`DRY_RUN_TOOLS`·`WARN_EXACT` | ⚠ **위험** — "바뀌면 다시 뽑는다" 고 적어 놓고 **확인하는 코드가 없었다** |
| **B. 남의 리포에서 베낀 값** | `CACHE_PREFIX`·`GW_DENY_*`·시간 상한 관계 | ⚠ **위험** — 그쪽이 바뀌면 조용히 어긋난다 |
| C. 판단 눈금 | `MIN_MATCH_LEN`·`BATCH_MAX`·`MAX_DEPTH` | 괜찮다 — 근거가 옆에 적혀 있고, 틀려도 조용하지 않다 |
| D. 어휘·문법 | `_KEY`·`RUN_STATES`·`_SCHEMA_TYPE` | 괜찮다 — 안 바뀐다 |

**A 를 데이터로 바꿨다.** `docs/procedures/fixtures/catalog-census.json` 이 **뽑은 시점**을
남기고, 테스트가 목록을 거기 대조한다. 갱신은 `backend/scripts/refresh-census.py` 로
**사람이 돌린다** — 테스트가 자동으로 뽑으면 어긋난 것이 조용히 정상이 된다.

**그 가드가 첫 실행에서 둘을 잡았다.**
1. 도구가 465 → **470종**이 됐다(`ligament_check`·`slenderness_check`). 읽기 전용이라
   게이트는 필요 없었지만, **몰랐다는 게 문제다.**
2. ⚠ **`publish_report_to_datahub` 가 게이트 없이 저장되고 있었다.** AI Data Hub 에
   **등재**하는 도구다 — 바깥으로 나가고 되돌리려면 남의 손이 필요하다. 465종에서 뽑을
   땐 없던 도구다. `MUST_GATE` 에 넣었다.

**B 도 대조하게 했다.** 테스트가 `../HWAXMcpGateway/gateway.py` 를 읽어
`_CACHEABLE`·`_INVOKE_DENY_*` 가 우리 사본과 같은지 보고, **시간 상한 관계**도 본다 —
단계 상한 < 게이트웨이 상한 < 워밍업. 그쪽이 바뀌면 그 관계가 조용히 뒤집혀 게이트웨이가
먼저 끊고 우리에겐 `unknown` 만 남는다. 리포가 없는 박스에서는 건너뛴다.

## W-67. 검출기가 **자기가 아는 것도 못 밀고 있었다**

점검하다 더 나왔다. 2단 후보 검출기(`_mate`)가 이름 접두만 봐서, **확정 등재된
`catalog_run` 을 못 찾았다** — `run_` 으로 시작하지 않아서다. 접두·접미를 둘 다 보게 고쳤다.

그래도 `run_job` 은 못 민다. 짝이 `job_params_guide` 라 어간(`job`) + 동사로 안 만들어진다.
**여기서 규칙을 늘리지 않았다** — 그게 지금 점검하는 바로 그 하드코딩이다.

대신 **못 민다는 사실을 등록부에 데이터로 적었다**(`detector_finds: false` + 이유).
테스트가 그 데이터와 검출기를 대조한다 — 민다고 적혀 있는데 못 밀면 실패, 못 민다고
적혀 있는데 밀어도 실패다. 새 2단을 등재하는 사람이 **둘 중 하나를 고르게** 된다.

## W-68. **세 겹 감사** — 고친 자리 옆에서 새 결함이 난다

사용자 지시는 "문제가 없어질 때까지 점검" 이었다. 한 번 훑고 끝내지 않고 **라운드를
돌렸고**, 라운드마다 **앞 라운드의 수정 자체를 대상으로** 삼았다. 그게 이 기록의 요점이다.

- **1차** — 네 갈래(무음 결함·권한/주입·테스트 품질·화면) 병렬. 40여 건.
- **2차** — **1차 수정이 남긴 것**만. 8건. 그중 셋은 1차가 **없던 결함을 새로 만든** 것이다.
- **3차** — 2차 수정 대상.

2차가 무엇을 잡았는지가 중요하다. 예를 들어 —

- 재개를 고치려고 `save` 를 원장에 남기기 시작했더니, **펼치기(fan-out) 자식이 전부 즉사**했다.
  자식은 고른 단계 *다음부터* 도는데 `fan_out` 은 선언 변수만 물려줬기 때문이다.
  그리고 그게 **보이게 된 것 자체**가 같은 라운드의 `_spawn` 수정 덕이다 — 전에는
  `running` 으로 매달려 있어 아무도 몰랐다. 결함을 고치면 다음 결함이 드러난다.
- `"0012" == 12` 를 막으면서 `str(int(float(n)))` 을 썼는데, 그것이 **2^53 위에서 다른 수**를
  만든다. 막으려던 사고가 위쪽 끝에 그대로 남았다.
- 챗 원장의 절단 표식이 `finish_step` 을 다시 불러, **직전 커밋이 고친 것을 경계 한 칸에서
  되돌렸다**("성패를 못 받았다" → `ok=1`).

**교훈으로 남길 것.** 수정은 그 자리에서 검증하지 말고 **한 라운드 뒤에 다시 본다.**
그리고 감사가 짚은 것은 전부 **직접 재현한 뒤에만** 고친다 — 3차에서 하나는 실측으로
전제가 뒤집혔다(§W-69).

## W-69. 감사가 그린 시나리오가 **실물에서는 안 일어나는** 경우

1차 감사가 "맨이름 폴백이 남의 앱 계약으로 검증한다" 고 짚었다. 시나리오는 이랬다 —
두 앱이 `get_report` 를 내고, 게이트웨이가 A 것을 맨이름으로 노출하면, `reportarchive`
단계가 A 의 계약으로 검사되고 드리프트 가드까지 통과한다.

**실측하니 전제가 틀렸다.** 게이트웨이는 한 앱만 가진 도구를 맨이름으로 내고,
**겹치면 전부 앱 접두로** 낸다 — 겹칠 때 맨이름은 **아예 사라진다**
(`whoami`·`list_reports`·`register_material`·`system_status`·`cancel_job` 확인).
그 시나리오는 이 게이트웨이에서 안 일어난다.

남는 좁은 위험은 `backend` 를 잘못 적은 경우인데, 그건 `schema_fp` 드리프트로 멈추거나
실행이 `unknown tool` 로 터진다 — **조용히 틀리지는 않는다.** 코드는 그대로 두고
**측정 결과를 주석으로** 남겼다. 다음 사람이 이걸 "고치려다" 맨이름 폴백을 떼면,
한 앱만 가진 도구(대다수)의 검증이 통째로 꺼진다.

**규칙.** 감사의 지적은 가설이다. 재현해서 통과하면 고치고, 전제가 틀렸으면
**왜 안 일어나는지를 코드 옆에 적는다** — 안 적으면 다음 사람이 같은 지적을 다시 하고,
이번엔 "고쳐" 버린다.

## W-70. '없는 확신' 을 주는 가드 — 하한이 통과시킨다

정적 가드(`routes.py` 를 훑어 실행기·저장소 메서드가 실제로 있는지 보는 것)가
`_store(request).x()` 형만 찾고 있었다. 라우트가 흔히 쓰는 `store = _store(request)` →
`store.x()` 형이 통째로 빠져, **12개를 보고 5개를 놓쳤다.** 놓친 것이 하필 가장 최근에
추가된 것들이다 — 이 가드가 존재하는 이유가 바로 그 재발 유형(W-30)인데.

더 나쁜 것은 **반증 가드**였다. `len(_called("_store")) >= 6` 이 12개를 "충분하다" 고
통과시켰다. 가드가 절반만 도는데 **그 사실을 가드가 확인해 주고 있었다.**

고치면서 하한을 실측값(15)으로 올렸다. 그리고 넓힌 가드가 곧바로 진짜 헷갈림을 찾아냈다 —
`_ra_precheck` 가 user_store 를 `store` 라고 부르고 있었다(같은 파일에서 `store` 는
절차 저장소다). 이름을 `users` 로 바꿨다.

**규칙.** 반증 가드의 하한은 "0이 아니다" 가 아니라 **실측 전수**여야 한다.
느슨한 하한은 가드가 죽은 것을 감춘다.

## W-71. 검사가 **빌드 산출물에** 매여 있으면 평소엔 꺼져 있다

`test_spa_fallback.py` 가 `frontend/dist/index.html` 이 없으면 `skip` 했다. `dist` 는
gitignore 다 — 즉 **이 리포에서 API 404 대 SPA 200 을 보는 유일한 자리**가, 누가
`pnpm build` 를 돌렸는지에 따라 켜지고 꺼졌다. 그 사고(SPA 폴백이 API 오탈자를 200+HTML 로
삼킨 것)가 이 기능을 만든 계기였는데, 그 회귀 검사가 기본적으로 안 돌았다.

`FRONTEND_DIST` 환경변수로 **두 줄짜리 가짜 dist** 를 만들어 쓰게 고쳤다. 폴백이 보는 것은
파일의 **존재**이지 내용이 아니다. `dist` 를 감추고 돌려 확인했다.

같은 부류로, 인구조사 대조가 이름이 바뀌면 `pytest.skip` 을 했다 — **쫓는 사건이 났을 때
조용히 통과**한다는 뜻이고, 첫 바퀴에서 skip 이 나면 나머지 둘은 아예 안 본다. 모아서
끝에 따지게 고쳤다.

**규칙.** skip 은 "이 박스에 그 리포가 없다" 처럼 **환경**에만 쓴다.
**찾으려는 것이 발견됐을 때** 도는 skip 은 검사를 뒤집는다.

## W-72. 3차에서 나온 것 — **판정기 자신이 실패를 성공으로 만들고 있었다**

1·2차가 배선과 권한을 봤다면 3차는 `judge.py` 를 봤고, 거기서 가장 무거운 둘이 나왔다.
둘 다 **실패를 성공으로** 바꾸는 방향이라 이 리포가 쫓는 바로 그 모양이다.

**① 목록형 도구 응답이 전부 `not_json` 이었다.** 항목마다 TextContent 로 오는데
(`list_agents` 796개) `join_content` 가 줄바꿈으로 잇고, 판정기는 그 한 덩이를 한 번만
파싱했다. 실호출 확인 — `list_operations` 47 · `list_agent_domains` 23 ·
`list_agents` 408 블록이 **셋 다 실패**였다. PLAN §79 가 "다중 text 항목은 각각 파싱해
리스트로" 라고 적어 둔 것이 구현에 없었다.

소비처가 그것을 **조용히** 받고 있었다. `dispatcher_items` 는 `ok` 를 버리고 `.parsed`
만 쓰므로 `GET /dispatchers/…/items` 가 **200 + `items: []`** 를 냈다 — "연산 47개" 라고
적힌 `note` 와 나란히. 그 엔드포인트가 존재하는 이유("이게 없으면 사람이 `operation` 에
무엇을 적을지 알 방법이 없다")가 사라진 상태였다.

**② `unwrap` 이 봉투보다 먼저 돌았다.** SmartTwin 계열은 **실패해도 `stdout` 이 채워져
온다**(`{ok:false, exit_code:2, stderr:…, stdout:"{…}"}`). 먼저 벗기면 바깥의
`ok:false`·`errors[]`·`exit_code` 가 통째로 사라지고 **잡이 죽었는데 부분 결과가
성공으로** 기록된다. 하필 PLAN §79 가 `unwrap: stdout` 을 지정한 그 조합이다.

봉투 검사를 앞으로 옮기고, 벗길 칸이 없으면 조용히 바깥을 쓰지 않게 했다.
`exit_code != 0` 도 실패로 센다 — 프로세스를 돌리는 앱은 성패를 그것으로 말한다.

**덧붙여 배운 것.** 판정기는 **모든 단계가 지나는 자리**다. 여기서 한 방향으로 틀리면
그 위의 검증·기록·화면이 전부 그 거짓을 물려받는다. 앞 두 라운드가 배선을 고치는 동안
이 층은 아무도 안 봤다.

## W-73. 깊이 상한은 **공용 순회기**에 둔다

깊은 인자(`{"a":{"a":{…}}}` 2000단)를 보내면 `RecursionError` 가 라우트 밖으로 새어
**500** 이 됐다. pydantic 은 `dict[str, Any]` 속을 안 보므로 모양 검증(422)이 이걸 못 잡는다.

처음엔 `_scan_args` 에만 가드를 달았는데 `template.refs` 가 먼저 터졌고, 그걸 고치니
반복문 **밖의** `_all_refs` 가 또 터졌다. 호출부마다 재는 방식은 하나를 빼먹는다.

**상한을 `template` 에 두고 `TemplateError` 로 냈다** — 순회기를 부르는 쪽이 여럿이라
(저장 검증 · 미사용 변수 계산 · 실행 시 치환) 거기가 정본이다. 저장 검증은 그와 별개로
**재귀 없이** 한 번 재서 거절 사유를 사람 말로 낸다.

## W-74. 완화는 **한쪽만** 해야 했다 — 한국어 경계

2차에서 `_in_prose` 경계를 ASCII 기준으로 바꿨다. 근거는 전부 **뒤**쪽이었다 —
한국어는 조사를 값에 붙여 쓴다(`PANEL_1을`·`BRKT부품`). 그런데 **앞**까지 함께 풀었다.

그러자 합성어의 접미가 값으로 잡혔다 — `고전압배터리팩` 에서 `배터리`,
`리어BRKT` 에서 `BRKT`, `이차전지셀` 에서 `전지셀`. `draft()` 의 결론이 실제로 뒤집혔고
(`constant` → `asked`), 이유 문구는 "사람이 쓴 말 안에 이 값이 있다" 고 **단언**한다.
모듈 머리말의 "모르면 모른다고 한다 — 지어낸 변수는 절차를 조용히 망친다" 가 깨진 자리다.

앞 경계만 유니코드로 되돌리니 2차가 고정한 6건이 **전부 그대로** 통과하고 거짓 양성
3건이 막혔다. **고칠 때 건드린 범위가 근거보다 넓지 않은지 본다.**

## W-75. **인공 고정물로 고정하면 고친 줄 알고 넘어간다** — 4차에서 가장 아픈 것

3차가 "목록형 도구 응답이 전부 `not_json` 이다" 를 고쳤다. 검사도 달았다. 초록이었다.
**그런데 프로덕션에서는 한 번도 안 돌았다.**

이유는 하나다. 고정물을 `json.dumps({...})` **compact** 로 만들었는데, 게이트웨이가 실제로
보내는 블록은 **pretty-print** 다. 파서를 줄 단위로 짰으니 `{` 한 줄이 JSON 이 아니라
영영 안 걸린다. `indent=2` 하나만 붙이면 즉시 깨지는 검사였다.

4차가 살아 있는 게이트웨이로 실호출해서 잡았다 — `list_operations` 47블록 · 423줄,
`dispatcher_items` 여전히 **0건**. 고쳤다고 적어 둔 그 화면이 그대로였다.

**규칙.** 외부 응답을 다루는 코드의 고정물은 **실물에서 줄인 것**이어야 한다. 내가 만든
모양으로 고정하면 내 가정을 검사할 뿐이다. 이 리포는 그걸 알고 있었다 —
`test_procedures_dispatch.py` 머리말이 "아래 고정물은 **실물 응답 모양**이다(실호출에서
줄인 것)" 라고 적어 뒀는데, 정작 내가 새로 단 검사가 그 규율을 안 지켰다.

덧붙여, 같은 커밋이 **자기 자신을 지우고 있었다.** 다중 파싱이 성공하면 곧바로 반환해
같은 커밋이 고친 다른 것(봉투를 unwrap 보다 먼저 보기)이 그 경로에서만 무효였다.
한 함수 안에 두 수정을 넣을 때 **경로가 갈라지는지**를 본다.

## W-76. 저장은 **모델이 보장하는 모양**으로 한다

절차 저장 아홉 경로가 받은 dict 를 **그대로** 넣고 있었다. `vars` 는
`default_factory=list` 라 YAML 에 없어도 검증을 통과하는데, 그대로 저장되면 화면이
`spec.vars.length` 를 읽다 `TypeError` 로 죽는다. 그리고 이 리포에는 ErrorBoundary 가
**하나도 없어** 라우트가 아니라 **앱 전체가 흰 화면**이 된다. 도달 경로는 "YAML 가져오기" 다.

검증은 통과시키고 저장은 원본을 넣으면, **검증이 보장한 것과 저장된 것이 다르다.**
`_validated` 가 정규화된 dict 를 돌려주게 하고 모든 저장 경로가 그것을 쓴다(왕복 확인).
화면과 타입도 없는 칸을 방어한다 — 서버가 채워도 **그 전에 들어간 판본**이 DB 에 남는다.

## W-77. 판정기가 **셋인데 답이 달랐다** — 5차

리포가 셋이고 도구 결과를 판정하는 자리가 셋이다.
`HWAXPortal/judge._envelope_fail` · `HWAXAgentServer/_result_ok`(챗) ·
`HWAXAgentServer/_delib_tool_result_ok`(심의). 셋이 **서로 다른 부분집합**을 보고 있었다.

실호출로 확인된 어긋남 —

| 실물 본문 | 포털 | 챗 | 심의 |
|---|---|---|---|
| `{"status":"error","errors":[…]}` (analyze_laminate) | 실패 | **성공** | 실패 |
| `{"error":"not_visible",…}` (risk_get_coverage) | 실패 | **성공** | 실패 |
| `{"status":"error","errors":[]}` | 실패 | **성공** | **성공** |
| `{"refused":true}` (허브 관례) | 실패 | **성공** | **성공** |
| `{"exit_code":2}` | 실패 | **성공** | **성공** |

챗이 성공으로 보면 활동 패널의 '실패' 배지가 안 붙고(실패한 호출이 성공과 똑같이 보인다),
절차 원장에도 성공으로 적혀 **검증된 단계인 양** 굳는다.

에이전트 서버 쪽 둘을 `envelope_failed` 하나 위에 세웠다. 포털 것과는 리포가 달라 코드를
공유할 수 없으니 **같은 목록을 본다는 것을 주석으로 묶었다**(status·ok·refused·error·
errors·exit_code).

**왜 네 라운드가 못 봤나.** 1~4차가 포털만 봤다. 같은 개념이 여러 리포에 흩어져 있으면
**한 리포만 보는 감사는 그 불일치를 구조적으로 못 본다.** 6차부터 리포를 가로질러 본다.

## W-78. 인공 고정물은 **한 번 고쳐도 다른 자리에 또 있다**

4차가 "compact 고정물이라 프로덕션에서 안 돌았다" 를 잡았다(W-75). 5차가 **같은 파일의
다른 상수**에서 같은 것을 또 찾았다 — `GW_DENIED = "invoke-denied"` 는 게이트웨이
**감사 로그**에만 있고 응답 본문에는 없다. 그 갈래는 죽은 코드였고, 관문에 막힌 호출이
`tool_error`(그냥 에러)로 기록됐다. 테스트는 손으로 지어낸 `"invoke-denied: delete_report"`
를 단언해 초록이었다.

**한 번의 수정으로 끝내지 않고 가드를 세웠다** — 게이트웨이 소스를 읽어 네 상수가 전부
`TextContent(... text=...)` 자리(= 호출자가 받는 본문)에 있는지 본다. 로그 줄이나 주석에만
있으면 실패한다. 이런 문자열은 앞으로도 늘 테니, 고친 것보다 **못 고치게 한 것**이 중요하다.

## W-79. 6차 — **아무도 안 본 자리**에 가장 큰 것이 있었다

1~5차가 "고친 자리 옆"을 봤다면 6차는 **한 번도 안 본 경로**를 봤고, 거기서 셋이 나왔다.

**① 업로드가 게이트웨이 거절을 `created: true` 로 냈다.** `judge.py` 모듈 머리말이 다섯
라운드 내내 `agent/upload.py:mcp_call` 을 **이름까지 적어** "베끼면 안 되는 이유" 로 들고
있었는데, 정작 그 함수는 아무도 안 고쳤다. 셋이 전부 실패를 성공으로 만든다 —
`result.isError` 미독 · `content[0]` 만 · 파싱 실패를 `{"raw": …}` 로 정상 반환.
실물로 `unknown tool:` 과 파괴 도구 관문이 `created: true` 로 나가는 것을 확인했다.

**교훈.** *경고를 적어 둔 것과 고친 것은 다르다.* 주석이 "이건 틀렸다" 고 말하고 있으면
그 자리를 **고칠 대상 목록에 올려야** 한다 — 안 그러면 주석이 면죄부가 된다.

**② 계정을 정지해도 SSO·기존 세션·PAT 이 전부 살았다.** `status` 를 인증 판단에 쓰는
자리가 백엔드 전체에서 **로컬 비밀번호 경로 하나**뿐이었다. 살아 있는 박스는
`AUTH_PROVIDER=oidc` 라 **실제로 쓰이는 경로가 뚫린 쪽**이다. 형제 모듈에는 이미 있었다
(`main.py` 의 `is_active`, 실행기의 `owner_inactive`) — auth/access 에만 없었다.

**③ REST 프록시가 자격 체계를 통째로 우회했다.** 소스 주석이 위험을 알고 `inject` 있는
사이트를 GET/HEAD 로 좁혀 뒀는데, 전제 하나가 틀렸다 — "inject 없는 사이트는 권한 상승이
없다". 상류 AIDataHub 가 **인증 없이 200** 이라 이 프록시가 유일한 관문이었다.

**규칙으로 남길 것.** 한 개념이 여러 리포·여러 경로에 흩어져 있으면, **한 곳만 보는
감사는 그 불일치를 구조적으로 못 본다.** 5차가 판정기 셋에서 그것을 배웠고(W-77),
6차가 인증·인가에서 같은 것을 다시 만났다.

## W-80. 게이트웨이 본체 — 근거 원장이 **환각 방어를 무력화**하고 있었다

`verify_answer` 는 이 허브 안내문이 지시하는 **마지막 방어선**이다("수치를 사용자에게
보내기 전에 대조하라"). 그 원장이 이렇게 새고 있었다.

- **칸이 섞였다.** 신원이 없으면 그룹 문자열, 그것도 없으면 `_anon` **한 칸을 모두가 공유**.
  도구를 하나도 안 부른 새 세션에서 불러도 **남이 조회한 목록**이 나왔다(실측).
  → 신원 → 세션 순으로 가르고, 둘 다 없으면 **안 쌓고 안 조회한다.** 섞느니 없는 게 낫다.
- **캐시가 맞으면 안 쌓았다.** 반환 경로 여섯 중 캐시 적중만 빠져서, 캐시가 데워진 뒤에는
  **방금 제대로 조회한 수치**를 지어낸 값이라고 고발했다. 간헐적이라 모양이 가장 나쁘다 —
  사람이 도구를 못 믿게 된다.
- **만료가 부활했다.** 저장된 exp 를 무시하고 다시 도장을 찍어, 30분 지난 수치가 무관한
  호출 하나로 재인증됐다.

같은 파일에서 **카탈로그 출렁임**도 고쳤다. 레지스트리가 200 인데 앱이 빠지면 즉시
제거였다 — 87종이 61초 사라진 기록이 로그에 4회 있다. 폴링 **실패**는 이미 지키고 있었는데
"200 인데 빠짐" 은 안 지켰다. **부분 실패와 진짜 변경을 가르는 것**이 이 리포의 반복 주제다.

## W-81. 재기동은 사람이 고른다

게이트웨이는 챗·심의가 함께 쓴다. 코드를 고쳐도 **도는 프로세스는 옛 것**이라,
반영에는 재기동이 필요하고 그 순간 진행 중인 SSE 가 끊긴다. 그래서 사람에게 물었고,
`./start.sh restart --bg`(포트 점유자를 정확히 내린다 — 포트킬 오살 방지)로 올린 뒤
**16/16 백엔드·472종 복귀**를 확인하고 실물 네 가지를 다시 태웠다.

덤으로 인구조사 가드가 **세 번째**로 잡았다 — 재기동으로 SignalForge 조회 도구 9종이
합류했다. 재기동이 카탈로그를 바꾼다는 것을 가드가 즉시 알려 준 셈이다.

## W-82. 7차 — **PAT 위조로 임의 신원·권한**이 됐다 (선재, 일곱 라운드가 못 봤다)

`pat_verify` 가 토큰 헤더의 `kid` 를 그대로 `keystore/<kid>.pub` 경로에 넣었다.
`kid` 는 **검증 전** 값이다 — 공격자가 정한다. `../` 로 keystore 밖의 아무 `.pub` 를
검증키로 쓸 수 있고, 자기 공개키를 아무 데나 심으면(업로드 스테이징이 첨부 내용·파일명을
그대로 저장한다) **자기 개인키로 서명한 PAT 가 통과한다.**

실측으로 완전 재현했다 — 계정도 없는 `intruder@evil.com` 이 `email=hwax.demo@…`,
`groups=['portal-admin']` 으로 수락됐다. 그 신원이 `principal_pat_or_session` 을 쓰는
전부(챗·업로드·대화·심의·docx)를 지난다.

게이트웨이는 **JWKS**(발행 키목록과 대조)라 안 뚫렸다. 포털만 로컬 검증이라 뚫렸다.
**같은 개념의 두 구현 중 한쪽만 안전했고, 여섯 라운드가 그 쪽만 봤다.**

**규칙.** 외부가 준 값이 **경로·키·이름**으로 쓰이는 자리를 따로 훑어라. 이 리포는
`_seed_path`(씨앗)·`_SEED_NAME` 에서 같은 것을 이미 한 번 막았는데, **인증 쪽엔 없었다.**

## W-83. 정지는 **세 곳**에서 동시에 들어야 한다

6차가 정지 검사를 포털 `deps.entitled` 에 넣었다. 7차가 재현해 보니 —
- 게이트웨이는 `/internal/access/entitlements` 를 읽는데 그건 `compute()` 를 지나고,
  **`compute` 는 `status` 를 아예 안 봤다** → 정지 계정 PAT 로 MCP·REST 둘 다 200.
- `set_status` 가 PAT 을 폐기하지 않아 **서명 자체는 계속 유효**했다.

`compute()` 가 원장 행을 권한으로 바꾸는 **유일한 자리**다 — 거기서 끊으면 포털도
게이트웨이도 함께 닫힌다. 그리고 **토큰까지 죽인다** — 권한 계산만 막으면, 자격을 안 보는
경로가 생기는 순간 다시 뚫린다(REST 프록시가 정확히 그랬다).

**규칙.** "막았다" 는 **그 개념을 소비하는 경로 전수**로 확인한다. 한 곳에 넣고 끝내면
그건 절반이다.

## W-84. 한 자리를 고치면 **형제 자리**를 같이 본다

7차가 6차 수정 자체에서 셋을 찾았는데, 전부 같은 모양이다.
- 6차가 `/health` **본문**에서 권한 지도를 뺐는데, 형제 `/tools-map` 은 nginx 로
  **외부에 그대로** 열려 있었다(실측 200·43KB).
- 6차가 `mcp_call` 을 판정기로 바꿔 502 를 던지게 했는데, 각 분기의 감사 한 줄이
  **마지막에** 있어 중간 실패가 **부분 부작용 + 무기록**이 됐다. 고치기 전에는 실패가
  `created:true` 로 위장된 덕에 (틀리게라도) 감사가 남았다 — 이 항목만 보면 관측을 잃었다.
- 5차가 단 인구조사 가드가 **문자 거리**로 판정해, 감사 줄 바로 다음이 `TextContent(` 라
  로그 전용 문자열이 통과했다 — 그 가드가 잡으려던 회귀를 못 잡았다.

**규칙.** 고친 자리의 **형제**(같은 파일의 같은 종류, 같은 경로의 다음 홉)를 한 번 더 본다.
