## W-1. 착수 전에 구상을 한 군데 고쳤다 — **기록이 절차를 복원하지 못한다**

사용자 구상의 절반은 "챗으로 한 일을 기억했다가 재생" 이다. 만들 수 있는지 보려고
**지금 무엇이 기록되고 있는지**부터 전수로 봤다. 여섯 갈래가 있는데 **어느 하나도 단독으로
절차를 복원하지 못한다.**

| 갈래 | 순서 | 도구명 | 인자 | 결과 | 짝짓기 |
|---|---|---|---|---|---|
| 포털 `meta.activity[]` | 배열 순서만 | O | 220자 | 220/2000자 | **없음** |
| SSE `status` | 스트림 순서 | O | 140~220자 | 1개 지점만 | **없음**(`run_id` 버림) |
| 게이트웨이 `audit.jsonl` | **벽시계+ms** | O | **없음** | **없음** | 없음 |
| 포털 `agent_audit` | — | 컬럼만 존재 | — | — | **미배선** |
| 워크플로 `journal.jsonl` | started/result | **없음** | **없음** | 문자열 | agentId |
| `delib-jobs/*.json` `steps[]` | 최근 30개 | 버림 | 버림 | 버림 | 없음 |

(개정 3) 게이트웨이 `audit.jsonl` 은 MCP 경로에서 **호출자도** 안 적는다 — caller 는 REST
프록시만 넘긴다. W-17.

**결정적 증거.** 실제 대화 저장소에서 한 메시지에 `predict_sed` 가 `ap_cx=50.1 … 50.5` 로
다섯 번 병렬 호출됐는데, 기록은 `호출×5 → 완료×5` 순서이고 **결과 다섯의 프리뷰가 전부
같다.** 어느 결과가 어느 입력의 것인지 알 수 없다.

부족한 것은 넷이다 — ① 호출 식별자 ② 시각·소요시간 ③ 절단 안 된 인자 ④ 앱 귀속.
**①과 ④는 이미 방출 지점에 있는 값이다.** LangGraph `astream_events(version="v2")` 의
`on_tool_start`/`on_tool_end` 훅에 `event["run_id"]` 가 손에 있는데 싣지 않는다
(`app.py:2607`·`:2633`).

→ **P0 을 절차보다 앞에 뒀다.** 관측할 수 없는 절차는 기록할 수 없다. 이 순서를 뒤집으면
나머지가 전부 짐작 위에 선다. 그리고 P0 은 절차 기능이 취소돼도 **그 자체로 값어치가 있다** —
챗 활동 패널이 정확해지고 핸드오프 근거의 인자가 살아난다.

## W-2. 막힌 곳은 계산기가 아니라 추출기다 — 그리고 그 조각은 **이미 있다**

`predict_sed` 의 필수 입력 10개가 전부 기판 레이아웃·패키지 배치 치수다. STEP 에 솔더볼이
없고 k파일에도 없다. **`ball_size`·`pad_size` 는 ODB++ 전용**이고, `pkg_type` 은 어떤 형상
데이터로도 유도할 수 없다. 게다가 **465종 중 SedInput 을 만들어 주는 어댑터가 0개다.**

그런데 조사 중 예상 밖의 것을 찾았다.

```
/home/koopark/claude/ODB     dev 에 실재 — 파서 14종 · 체크리스트 룰 39개 · FastAPI
                             서비스 계층이 CLI·REST·MCP 공용으로 이미 설계됨
documents/MCP_INTEGRATION.md 447줄 규격서 — 도구 13종 제안까지 합의돼 있음
```

규격서가 직접 말한다 — *"서비스 계층은 MCP를 염두에 두고 이미 인터페이스 독립적으로
설계되어 있습니다. 서버를 얹기만 하면 됩니다."*

제안된 도구가 막힌 슬롯과 정확히 맞물린다(`odb_list_components` → 좌표,
`odb_interposer_ratio` → `board_type`, `odb_extract_parts` → `ball_size`·`pad_size`,
`odb_copper_ratio` → 워피지 3인자). (개정 3) 이 화살표는 전부 **가정**이다 — 특히 `board_type`
은 인터포저 비율로 INT 만 가려지고 HALF/FULL 은 못 가른다. W-25.

→ **ODB 부재를 "나중에 해결할 전제" 가 아니라 "설계로 흡수할 제약" 으로 뒀다.** 공급자 없는
슬롯은 실패가 아니라 **사람에게 묻는 칸**이다. 나중에 도구가 붙으면 **같은 절차가 손대지
않고** 무인으로 돈다. 이게 §4 슬롯 모델의 존재 이유다.

⚠ cae00 에는 `odb-hub` 가 붙어 있지만 **무엇을 내주는지 확인 못 했다**(dev 에서 도달 불가,
페르소나 `key_tools` 비어 있음, 매니페스트에 `mcp:{}` 없음). 로컬 엔진이냐 cae00 허브냐는
결정 대기다.

## W-3. A→Z 가 끊기는 진짜 이유는 엔진이 아니라 **과제 키**다

```
StepForge      project_id    24-hex
DynaForge      session_id    user 스코프
ThermalShock   project       그냥 문자열 메타(README 가 명시)

```

이 다섯을 묶는 것이 **없다.** 문서 자체가 열린 질문으로 남겨 놨다 —
`docs/design-risk-review/plan.md:4760` *"크로스도메인 부품 명명 규칙(ECAD refdes ↔ MCAD
파트명 ↔ Dyna `Group\Name`)이 조직에 있는가 → **없음 가정**"*.

→ **P1 을 절차보다 앞에 뒀다.** 절차가 아무리 정교해도 단계 사이에서 키가 끊기면 사람이
손으로 잇는다. 그리고 키 레지스트리는 **절차가 없어도 쓸모가 있다** — 사람이 앱을 오갈 때
찾아 주는 것만으로. (개정 2 에서 "작다·병렬" 로, 개정 3 에서 **S3 뒤**로 — W-22.)

## W-4. 토폴로지 B — agent-server 에 붙이지 않는 이유는 취향이 아니다

사용자 요구가 "챗·심의에 지장 없는 독립 구성" 이라 붙일 자리를 전수로 봤다.

**agent-server 는 탈락이다.**

- 인증이 아예 없다 — `Depends`/`Security`/`HTTPBearer` 0개. `start.sh:37-49` 가 의도라고
  적어 놓았고 방어는 `127.0.0.1` 바인드뿐이다.
- 전역 가변 상태가 12개 넘고 **그중 둘은 이미 교차오염 사고가 났다** — `tool_degraded` 가
  다른 요청의 스트림에 가짜 배너를 주입했고 `ContextVar` 로 고쳤다(`deliberation.py:983-986`).
  여기 쓰면 **이미 두 번 고친 버그를 세 번째로 낸다.**
- **아티팩트 정리에 생산자 네임스페이스가 없다** — 오래된 것부터 500개로 깎으므로
  절차 산출물을 챗이 지우고, 반대도 된다.

**포털 공유 자원도 탈락이다.**

- `agent_semaphore`(64)는 큐 없이 **429 즉시 거절**이다.
- `agent_client` 는 풀 64에 read 타임아웃이 없어, 먹히면 챗이 429 가 아니라 **조용히 멈춘다** —
  더 나쁜 고장 모양이다.
- **실증이 있다.** HWAXRisk 의 예외 클래스 이름이 그대로 *"엔진 슬롯이 없다(포털
  agent_semaphore 429)"* 이고, 패널 하나가 챗 슬롯을 **최대 40분** 쥔다.

→ **리스크 심사가 간 길(토폴로지 B)을 그대로 간다.** 그 결정의 근거가 이번 구상과 같다 —
*"과제 수십 개·수년치가 쌓이는 장기 자산이라 포털 릴리스·박스 수명에 묶이면 안 된다"*.
비용도 이미 측정돼 있다(커밋 `943252f`) — **포털 백엔드 0줄**, 기존 파일 3개 + 새 페이지 1개.

## W-5. 절차 모델을 새로 발명하지 않는다 — **부품이 거의 다 있다**

범용 워크플로 엔진은 스택 어디에도 없다(게이트웨이·포털·agent-server 에서
`workflow|pipeline|procedure|macro|playbook` grep **히트 0건**). `infra/pipeline/*.js` 1,801줄은
**심의 전용**이고 도메인 프롬프트가 파일의 22%다.

그런데 인벤토리에 필요한 조각은 흩어진 채로 이미 있다.

| 자산 | 왜 정답에 가까운가 |
|---|---|
| **KooRemapper `catalog_data.json`** | 스택에서 **유일하게 완성된 선언형 능력 카탈로그**. 47 ops × {타입·필수·기본·enum·전제조건·검증된 예제·함정} + JSON Schema 파생 + Draft2020 검증 |
| **SmartTwinMCP `audit_events`** | 절차 기록의 정답 모양 — `(occurred_at, actor, tool@version, action, target, detail=args)`. **`pipeline_step` 액션까지 이미 있다** |
| **SmartTwinMCP 템플릿** | `{name, applies_to[], args{}}` — "이름 붙인 인자 세트 + 적용 가능 도구". 레코드 형식을 발명할 필요가 없다 |
| **HEAXHub `POST /jobs/{id}/rerun`** | **판본(`app_version_id`)을 박아** 인자+입력파일까지 복원하는 유일한 구현 |
| **ReportArchive 잡 큐** | 운영급 — 우선순위·백오프·dedup·reaper·하트비트·스케줄러. 새 절차 = 핸들러 파일 하나 |
| **`saved_searches`** | 스냅샷이 아니라 **조건 저장 + 라이브 재실행 + 구독 + 워터마크** |
| **`invoke_tool`** | 이름으로 실행하는 통로. 인가·캐시·사용자 위임·감사를 **그대로 탄다** |

→ **빠진 것은 이들을 엮는 순서 모델과, 호출을 짝지을 식별자 한 필드다.** 그래서 계획이
"엔진을 만든다" 가 아니라 "모델을 정하고 부품을 엮는다" 가 됐다.

**함정 하나 — "템플릿" 이라는 말이 스택에서 서로 무관한 세 뜻으로 쓰인다.** 보고서 양식(RA) ·
잡 인자 프리셋(SmartTwin) · 클러스터 제출 템플릿. 절차 문서에서 이 말을 쓸 때 어느 뜻인지
반드시 밝힌다.

## W-6. RA 프리셋은 "절차 저장" 이 아니다 — 이름에 속지 않았다

`save_report_as_preset` 이 이름만 보면 딱 맞아 보인다. 실물을 봤더니 **본문 스냅샷**이다.
모듈 독스트링이 직접 말한다 — *"a preset is a filled-in starting point … carries a content
snapshot so a new report can be born pre-populated instead of blank."*

`create_report_from_run(run_id)` 의 "run" 도 **반입된 CAE 해석 1건**이지 절차 실행이 아니다.
그리고 **SED·적층·워피지 계산기는 실행을 만들지 않으므로 이 길로 못 간다** — 계산 결과의 길은
`create_report_draft` 쪽이다.

라이브 확인 — `list_presets()` 는 `count: 0`, `list_templates()` 는 3개뿐이다.

→ 이름이 겹친다고 재사용하면 엉뚱한 것을 물려받는다. **정작 가까운 것은 SmartTwinMCP 템플릿과
`saved_searches` 였다**(둘 다 "보고서" 와 무관한 자리에 있다).

## W-7. 자동화가 건드리면 안 되는 사람 자리가 셋 있다

전부 **의도된 설계**이고, 절차 기능이 편의로 건너뛰면 안 된다.

1. **`publish_report`** 는 `preview_publish` 가 발급한 `confirm_token` 을 요구한다 — 2단 확인.
2. **`risk_add_finding`** 은 `cites` 0건이면 **422** 다. `claim`·`warrant` 는 자유 산문이고
   설계 자체가 사람 등록(`origin='human'`)용이다.
3. **`pcb_warpage_surrogate`** 는 스스로 경고한다 — *"합성(synthetic) 데이터로 학습한 데모.
   절대값을 판정·양산 의사결정 근거로 쓰지 마라."*

→ 절차에 `gate: human` 을 두고, 실행 기록에 **모델 출처·경고를 반드시 싣는다.**
"A to Z 자동" 의 Z 는 게시가 아니라 **사람 앞에 놓는 것**이다.

## W-8. 절차 목적지에 이미 구멍이 둘 있다

"패턴화된 리스크 검토" 가 최종 목표인데, 거기로 가는 웹 경로가 막혀 있다.

둘 다 절차 기능과 **별개의 기존 결손**이라 이번에 손대지 않았다. P6 전에 닫아야 한다.

## W-9. 조사 방법에 대한 메모

이번 조사는 셋을 병렬로 돌렸고(오케스트레이션 기계 / 삼종세트 도구 / 독립 배치), 각자
**소스가 아니라 실물**을 봤다 — 게이트웨이 `tools/list` 로 스키마를, 대화 sqlite 로 활동
기록을, 감사 jsonl 로 호출 순서를 봤다.

그 덕에 두 가지를 피했다.

- **`describe_data_capability` 를 "능력 레지스트리" 로 과대평가할 뻔했다.** 실제로 불러 보니

- **RA 프리셋을 "절차 저장" 으로 오독할 뻔했다**(W-6).

이 폴더의 다른 교훈과 같은 줄에 있다 — **흉내 낸 데이터로 판정하면 코드가 아니라 흉내를
시험하게 된다.**

## W-10. 배치를 뒤집었다 — 별도 앱 → **포털 안의 격리 모듈**

개정 1에서 토폴로지 B(별도 HEAX 앱)를 **강하게** 권했다. 되돌린다. 늦게 확인한 사실 하나가
비용 구조를 바꿨다.

```python
# backend/app/agent/routes.py:223
def _chat_user_pat(keystore, settings, principal) -> str | None:
    """이 챗 한 번을 위한 단명 PAT. … 게이트웨이는 이 토큰을 포털 JWKS 로 검증하므로
       위조가 불가능하고, 도구 인가도 서비스 계정이 아니라 이 사람의 groups 로 이뤄진다"""
```

**포털은 이미 사용자 명의로 게이트웨이를 부를 수 있다.** 절차 실행기가 필요로 하는 것이
정확히 그것이다. 별도 앱으로 가면 이 한 줄을 얻으려고 HMAC 신원 단언 배선 + 새 리포 +
매니페스트 + apptainer + 배포 + Drive 를 새로 만들어야 한다.

**내가 "독립성" 을 프로세스 분리로 읽은 것이 틀렸다.** 조사가 실제로 말한 것은 그게 아니다 —
`agent_semaphore`·`agent_client`·`conv_store` 를 **공유하지 말라**는 것이었다. 자기 세마포어,
자기 httpx, 자기 sqlite 를 쓰면 같은 프로세스 안에서도 챗에 영향이 0이다. (개정 3) 런타임 자원
얘기다 — 기동 실패는 공유되므로 모듈 import·스토어 오픈 실패는 절차 기능만 끄고 포털은 뜬다.
게이트웨이 백엔드 영속 세션은 피할 수 없는 공유라 120초 규칙으로 막는다. W-19.

HWAXRisk 가 별도 앱으로 간 근거(장기 자산이 포털 릴리스에 묶이면 안 된다)는 **여전히 유효한
단점**이다. 그래서 저장소를 독립 sqlite 로 두어 **언제든 떼어낼 수 있게** 한다. 쓸모가
증명되면 그때 승격한다 — **지금 승격 비용을 선불하지 않는다.**

**교훈** — "무엇을 재사용하면 안 되나" 를 "어디에 살아야 하나" 로 번역할 때 한 칸 건너뛰었다.
제약은 자원 공유였지 주소가 아니었다.

## W-11. 학습을 선행 필수에서 **나중 보조**로 내렸다

개정 1은 P0(관측 충실도)을 전제로 뒀다 — "챗 기록으로는 절차를 복원할 수 없으니 먼저 고치자".
사실 판단은 맞지만(W-1 증거는 그대로다) **결론이 과했다.**

챗 기록을 해석해 절차를 복원하는 것은 어렵다. 그런데 **절차 안에서 한 일은 해석이
필요 없다** — 절차 기능이 자기 관측자라 기록이 곧 절차다. "하고 나서 저장" 이
처음부터 성립한다.

→ 관측 개선은 여전히 값어치가 있고(챗 활동 패널·핸드오프 근거가 정확해진다) **S5 의 전제**
지만, **핵심 기능의 선행 조건은 아니다.** 선행으로 두면 값어치가 먼 단계 하나를 맨 앞에
세우는 셈이다.

**교훈** — "이 방식은 불가능하다" 를 "이 일은 불가능하다" 로 넓혀 읽었다. 막힌 것은 **입구
하나**였고 다른 입구가 있었다.

## W-16. 성공 판정은 코드가 한다 — 실패 다섯 모양 중 셋이 `isError=false`

리포의 유일한 선례 `upload.mcp_call` 은 `isError` 를 버리고 `content[0]` 만 보며 파싱 실패를
`{"raw"}` 로 정상 반환한다 — **베끼면 실패가 성공으로 기록된다.**

→ PLAN §5-6 의 네 조건. 이 리포의 반복 패턴 "실패가 정상 응답과 똑같이 생겼다" 의 또 한 자리라,

## W-17. "사용자 명의" 의 실제 범위 — 16개 중 4개, RA 는 조용한 폴백, odb-hub 는 서비스 토큰

게이트웨이 원장에 호출자를 남기는 것은 한 줄이지만 §4 "순수 프록시" 와 별개 리포 수정이라 §7 #7

## W-18. `dry_run` 은 두 뜻 — 계획 모드 vs 도구 `dry_run`(16종)

체크리스트의 "`dry_run` 기본값" 은 뜻이 없었다. 도구 수준으로 읽으면 위험하다 — 게이트웨이에
dry_run 처리가 없고 465종 중 16종만 자기 인자로 가지며, 없는 도구에 얹으면 백엔드가 버리고
**실제로 실행**된다(실측 `list_parts`+`dry_run:true` → 정상 결과). 같은 리포 `docs/tool-entry` 는
이 말을 도구 수준 뜻으로 쓴다 — 어휘가 충돌하고 있었다.

→ 계획 모드(기본, 게이트웨이를 안 부름)와 도구 `dry_run`(스키마에 있을 때만 폼 노출, 없는 도구의
`args` 에 적혀 있으면 저장 거절)으로 가르고 단계마다 `mode` 를 남긴다.

## W-19. 실행은 요청 밖 · 세션은 실행당 하나 · 타임아웃은 게이트웨이보다 길게

절차 경로는 nginx catch-all(60초)이고 게이트웨이 상한은 120초라 동기로 두면 nginx 는 504,
uvicorn 은 완료 → 재시도 → 보고서 둘. **dev vite 프록시에선 재현되지 않는다.** → 202 + 폴링,
같은 단계 `running` 이면 409, 기동 시 in-flight 는 `unknown/failed(stage=restart)`.

**타임아웃 결정** — 발견 둘이 충돌했다. "실행기 타임아웃 ≤110초(게이트웨이보다 짧게)" 와
"≥260초(게이트웨이의 재연결 재시도까지 덮게)". 후자를 택했다 — 짧은 타임아웃은 게이트웨이 쪽
호출을 멈추지 못하고(그 발견 스스로 "보호 수단이 아니다" 라 했다) `unknown` 만 늘린다. 보호는
"120초를 넘길 수 있는 동기 도구를 절차에 안 넣는다" 로 한다.

비멱등 쓰기가 두 번 도는 경로가 둘이다 — 게이트웨이가 예외 뒤 재연결하고 같은 인자로 한 번 더
부른다, 실행기가 먼저 포기하면 쓰기는 그 뒤 완료된다. 그래서 클라이언트 타임아웃·프로세스 종료는
`failed` 가 아니라 `unknown` 이고 `done` 은 절대 재실행하지 않으며 `unknown` 쓰기 단계는 사람
확인 뒤에만 재실행한다.

세션 — `mcp_call` 은 호출마다 세션을 만들고 안 닫는다. 게이트웨이 SDK 는 유휴 만료가 없다. 실행당
하나 열고 `finally` 에서 닫는다. 기동 실패는 try/except 로 절차 기능만 끈다(`/procedures-api/health`).
`get_job`·`get_job_details` 를 게이트웨이 `_CACHE_DENY` 에 넣는 것은 별개 결손으로 **기록만**
한다 — 게이트웨이는 순수 프록시.

## W-20. 도구에 판본이 없다 — `backend`+`tool`+`schema_fp`

노출 이름은 다른 백엔드와 겹칠 때만 접두어가 붙어 **다른 앱의 가동 여부로 뒤집힌다**(StepForge
4개 도구 실측). `tools/list` 에 버전이 없고 백엔드는 영속 세션 하나라 옛 판본을 못 띄운다.
앞 라운드의 "노출 이름을 저장한다" 판정을 이 사실이 뒤집었다 — 별칭 `<백엔드>_<원본>` 은 항상
호출되고 파괴 차단은 원본 기준이라 우회가 없다. 판본 대신 지문(`sha1(desc+schema)[:16]`)을 박아
**변화를 잡아 멈추는 것까지**가 할 수 있는 전부다. `predict_sed` 의 `sample: dict` 는 지문이 못
잡는다 — 실행 기록과 게이트가 그 몫.

## W-21. 저장 모델·소유·저장 규칙·이관

- 표 다섯(`procedures`·`procedure_versions`·`runs`·`run_steps`·`run_gate_acks`). 실행은 판본 행 id FK
  (HEAXHub 방식), "하고 나서 저장" 은 `derived_from_run` 역참조, `inputs_json` 은 S4 비교표용.
- 소유 — `owner_sub` 강제(`conv_store` 선례). 실행은 공유하지 않는다 — PER_USER_SSO 백엔드의
  사용자별 시야가 결과에 담긴다. 공유 정책(포크 전용?)은 §7 #6.
- 크기 — 도구 결과 1건이 0.9MB(`list_agents`), 이미지는 base64. 절차 기능은 agent-server 절단을
  안 탄다. gzip BLOB + 2MB 상한 + 이미지 파일 + 90일(HWAXRisk `rr_snapshot_calls` 선례, stdlib 만).
  백업은 매일 통째로 7세대라 안 그러면 7배로 커진다.
- 등록 — `backup-local.sh` 는 튜플 1줄이 아니라 **세 줄**이다. 튜플만 늘리면 `zip` 이 짧은 쪽에서
  멈춰 다섯째 sqlite 가 **오류 없이** 백업에서 빠진다. `sync: mirror`(실행은 사용자 데이터) 라 dev
  절차는 동기화로 안 가고 YAML export/import 로 간다.
- sqlite — 단일 연결 + Lock 을 `to_thread` 로 감싸면 트랜잭션 경계가 스레드 사이에서 섞인다.
  스레드별 연결 + `busy_timeout=5000`(백업·이관이 `mode=ro` 로 동시에 여는 순간용).
- 비밀 — 465종 중 `api_key` 인자 8종·`confirm_token`·`brief_token` 이 실재한다. 상수로 저장되면
  공유 절차가 곧 유출이라 키 이름으로 거절하고 변수·`save` 만 허용한다.
- API prefix `/procedures-api` — `App.tsx` 가 `/changelog` API 와 `/updates` SPA 를 가른 것과 같은
  이유(SPA `/procedures/*` 와 겹치면 새로고침이 JSON 을 받는다).
- v1 실행은 대화 저장소에 쓰지 않는다 — `kind` Literal·`ConvKind` 를 넓히는 것은 S5 의 일이다.

### 절차 기능의 존재 이유를 도구가 직접 증명했다

`solve_prescribed_curvature` 설명 원문 — *"다른 도구는 전부 힘 제어(N/M)라 **에이전트가
M = D·κ 지름길을 쓰게 되는데, 비대칭 스택에서 실측 +244.8% 과대**다."* LLM 이 스스로 엮으면
2.4배 틀리고 절차로 굳히면 안 틀린다. 그동안 "재현성" 으로 뭉뚱그려 말하던 것에 **수치가
붙었다.**

### 사용자 전제 한 곳을 정정했다

"DynaForge 에서 scenario.json 을 도출" — `list_operations` 47개 전수 확인 결과 scenario·drop·
impact 계열 오퍼레이션이 **없다**. 만드는 쪽은 클러스터(`smarttwin_submit` 이 프리셋 base +
deep-merge)이고 DynaForge 는 `attach_report_scenario` 로 **되받는다.** 조립 주체만 다르고
사용자가 원한 그림은 그대로 선다.

### 조사가 바꾼 설계 판단 셋

1. **제출과 회수는 다른 절차다.** 드라이버 walltime 이 167시간(7일)이라 한 절차에 못 둔다.
   §4 의 "폴링·대기 없음, 잡을 거는 도구는 절차 밖" 이 제약이 아니라 **옳은 모양**이었다.
2. **R 스윕·각도 프리셋 비교는 분기가 아니라 S5 다.** "조건 분기가 필요하다" 고 보이던 자리가
   사실 "같은 절차 × 변수 N개" 였다. §4 가 분기를 뺀 결정이 여기서 값을 한다.
3. **파일을 나르는 단계가 절차 밖이라는 결정이 두 번 확인됐다** — `model_path` 는 클러스터
   헤드노드 공유 FS 절대경로, 리포트 HTML 은 8~10MB 라 REST intake(512MB) 전용이다.

### 새로 확인된 무음 실패 다섯

이 폴더의 반복 주제가 또 나왔다 — **실패가 정상 응답과 똑같이 생겼다.**

| 자리 | 모양 |

## W-27. 시간 정책과 심의 경계 — 사용자 지시 둘

### 오래 걸리는 도구를 상정한다

지시는 "각 툴마다 시간이 오래 걸릴 수 있는 걸 감안하자" 였다. 실측을 다시 보니 **이미 상한
위에 있는 것이 셋**이다 — `search_catalog_property` 세션 첫 호출 **120.3초**(3회 재현, 이후
0.1초) · `agent_search` hybrid 102~221초 · `list_materials` 120초. 게이트웨이 상한이 정확히
120초라 첫 호출이 잘리고, 잘리면 그 백엔드 **영속 세션이 재연결**되면서 챗·심의까지 흔든다.

→ PLAN §5-10. 단계가 `expect`(`fast`/`slow`/`job`)를 선언하고 `job` 은 저장 거절,
`warmup: true` 단계는 한 번 버리는 호출로 콜드스타트를 흡수한다. 실행기 타임아웃은 ≥260초로
게이트웨이보다 늦게 포기한다.

**설계상 중요한 자리 하나** — 선언은 사람이 하지만 **실행 기록의 `duration_ms` 가 쌓이면 실측
p95 를 옆에 보여 준다.** §1 의 "절차 기능이 자기 관측자" 원칙이 시간에도 적용된다. 선언과
실측이 어긋나는 것을 사람이 고치는 것이 아니라 **화면이 말한다.**

### 심의는 잡을 걸지 않는다

지시는 "심의에서는 낙하 결과 조회를 하자. 시뮬을 심의할 때 시작하면 전체 결과 정리가 쉽지
않을 거야" 였다. 맞고, 근거가 셋으로 갈린다.

1. **시간이 안 맞는다** — 드라이버 walltime 167시간 vs 심의 라운드 몇 분. 심의 중에 잡을 걸면
   그 심의는 **의도만 남은 근거**로 끝난다.
2. **집계가 좌석의 일이 아니다** — 전각도는 자식 잡을 26~10000개 만들고 그 집계가
   `sphere_report`·`impact_report` 의 일이다. 좌석이 라운드 중간에 모으려 들면 **부분 결과로
   결론을 낸다.**
3. **판독 도구가 이미 집계된 슬라이스를 준다** — `report_worst_cases` 최악 랭킹,
   `report_directional` 방향 롤업, `report_query` 서버 필터. 좌석이 받아야 할 모양 그대로다.

→ 심의 좌석에는 `report_*` 판독 도구만 주고 제출 계열(`smarttwin_submit`·`slurm_submit_job`·
`run_job`·`submit_lsdyna_job`)은 뺀다. 순서가 정해진다 — **절차 기능이 먼저 돌고(R2a → 잡 →
R2b), 심의는 그 뒤에 `report_id` 를 읽는다.**

**이것이 앞서 논의한 "절차를 도구로 등록해 심의가 부른다" 의 정확한 형태다** — 심의에 주는
것은 **R2b(회수·판독)** 쪽이지 R2a(제출)가 아니다. 그리고 제출/회수를 가른 결정에
**두 번째 독립적 근거**가 생겼다. 첫째는 walltime, 둘째는 심의 경계다. 같은 분리가 두 이유로
필요하면 그것은 우연이 아니라 구조다.

## W-29. 문서의 `save` 경로가 전부 틀렸다 — 회귀가 잡았다

적층 체인을 실물로 돌렸더니 응답이 `{status, data, errors, warnings, assumptions, metadata}`
봉투였다. 값은 `data.` 아래 있고 **경고는 최상위**에 있다.

| 값 | 개정 4 가 적은 것 | 실물 |
|---|---|---|
| 등가하중 | `equivalent_loads` | `data.equivalent_loads` |
| 파손 여유 | `min_tsai_wu_R` | `data.first_ply_failure.tsai_wu_R` |
| 수명 | `life_cycles` | `data.life_cycles` |

그대로 짰으면 **첫 실행에서 죽었다.** 잡은 것은 `test_procedures_r1.py` 다 — 씨앗 YAML 을
읽어 `save` 경로를 **실물 응답에 대고 풀어 본다.** 고정물은 2026-09-14 실호출이다.

**교훈** — 절차가 "저장된다" 와 "돈다" 는 다른 문제다. 저장 시점 검증은 스키마를 보지
**응답 모양**을 못 본다. 응답 고정물 없이 쓴 `save` 경로는 전부 가정이다.

**부수로 고친 것 셋.**
- 판정에 `status` 검사를 더했다 — 적층 해석기는 `ok|warning|error` 를 낸다. `error` 면
  `errors[]` 도 대개 차 있지만 비어 있어도 실패로 친다.
- 고정물을 만들며 **내가 고정물을 망가뜨렸다** — 배열을 앞 2개로 자르는 트림이
  `loads.M` 을 `[51.37, 0.0, "…(3건)"]` 로 바꿔 놨다. 등가하중은 숫자 3개여야 뜻이 된다.
  8개 이하 배열은 안 자르게 고쳤다. **짧은 배열은 모양이 곧 뜻이다.**
- 씨앗의 `save` 이름 `tsai_wu_R` 이 변수 이름 규칙(snake_case)에 걸렸다. 검증기가 옳고
  씨앗이 틀렸다 — 이름은 우리 것이고 경로만 응답 필드다.

## W-30. 라우트가 부르는 메서드가 **아예 없었다** — 셸 한 줄이 원인

사용자가 `/procedures` 를 열었더니 "도구 목록을 불러오지 못했습니다" 가 떴다. 로그가
한 줄로 말했다 — `AttributeError: 'ProceduresRunner' object has no attribute 'catalog'`.

**원인은 셸이다.** `cd backend && python3 - <<'PY' …` 를 이미 `backend` 안에서 돌려 `cd` 가
실패했고, `&&` 가 끊겨 **python 이 아예 실행되지 않았다.** 그런데 뒤이은 pytest 는 통과했고
(그 메서드를 아무도 안 썼다) 나는 "추가했다" 고 보고했다. 세 개가 통째로 없었다 —
`catalog` · `step_once` · `merge_inputs`.

**왜 219개가 못 잡았나.** 두 가지가 겹쳤다.
- `/procedures-api/tools` 를 **아무 테스트도 안 쳤다**. 권한 전수 테스트는 403 만 봤다.
- `POST /runs/{id}/steps` 는 202 라 실패가 **백그라운드 로거로만** 간다. 화면도 서버도
  조용하다 — 이 리포가 반복해서 겪는 "실패가 정상 응답과 똑같이 생겼다" 의 또 한 모양이다.

**가드를 세웠다.** `routes.py` 소스에서 `_runner(request).X(`·`_store(request).X(` 를 정규식으로
뽑아 `hasattr` 로 대조한다. 이름 하나가 없으면 **라우트를 안 쳐도** 잡힌다. 가드가 0건을
훑고 통과하지 않도록 "실제로 찾는지" 도 함께 시험한다.
그리고 `/tools` 를 MockTransport 로 실제로 쳐 보는 테스트와 `step_once`·`catalog` 회귀를 더했다.

**교훈 둘.**
- **`cd X && …` 는 이미 그 안에 있으면 통째로 안 돈다.** 편집 스크립트는 성공 출력을 반드시
  확인해야 한다 — 이번엔 출력에 "추가" 줄이 없었는데 내가 안 봤다.
- **202 + 폴링은 실패를 숨긴다.** 그 라우트는 "요청이 받아들여졌다" 만 말한다. 그래서
  백그라운드 경로일수록 **호출 계약을 정적으로** 지켜야 한다.

## W-31. 씨앗을 화면에서 가져온다 — 첫 화면이 비어 있으면 아무도 못 시작한다

도구 목록이 뜨기 시작하자 다음 구멍이 드러났다. **절차 목록이 비어 있었다.** R1 씨앗

`GET /procedures-api/seeds` 와 `POST /procedures-api/seeds/{name}/import` 를 붙였고,
절차 목록이 비면 씨앗 카드를 대신 보여 준다(제목·단계 수·백엔드·사람 확인 자리, 그리고

결정 세 가지.

- **깨진 씨앗은 목록을 죽이지 않는다.** 파싱이 실패하면 그 줄만 `broken` 으로 표시하고
  나머지를 낸다. 하나가 상하면 전부 못 보는 편이 더 나쁘다.

## W-32. SPA 폴백이 **API 404 를 200 + HTML 로** 바꾸고 있었다

씨앗 경로를 살아 있는 서버에서 확인하다 옆에서 발견했다.

```
GET /procedures-api/seeds → 401   (라우트 있음, 정상)
GET /procedures-api/zzz   → 200   ← text/html
```

백엔드가 SPA 를 함께 내므로 catch-all `@app.get("/{full_path:path}")` 가 하나 있다.
등록된 API 는 위에서 먼저 잡히지만 **없는 API 경로**는 그대로 SPA 로 새서 index.html 이
200 으로 돌아갔다. `/auth`·`/agent`·`/mcp` 전부 같았다 — 절차만의 문제가 아니다.

무엇이 나쁜가. `apiFetch` 는 `res.ok` 가 참이라 성공으로 넘기고, 호출부가 `.json()` 을
부르는 **한참 뒤 엉뚱한 자리**에서 `Unexpected token '<'` 로 터진다. 경로 오타 하나가
"서버가 이상하다" 로 보인다 — 이 리포가 반복해서 만난 **"실패가 정상 응답과 똑같이
생겼다"** 의 또 한 모양이다.

**접두사를 손으로 적지 않았다.** `app.routes` 에서 첫 칸을 유도한다 — 라우터를 더해도
목록이 어긋나지 않는다. 하드코딩했으면 다음 라우터에서 조용히 낡았을 자리다.

**고치면서 생긴 새 위험은 반대쪽이다.** 접두사를 잘못 잡으면 사용자의 **깊은 링크가
새로고침에서 404** 가 된다. 그래서 `test_spa_fallback.py` 가 둘을 같이 건다 — 없는 API 는
JSON 404 이고, **SPA 경로 11개와 API 접두사 15개가 한 칸도 겹치지 않는다**. 겹침이 없는
건 우연이 아니다. `/procedures`(SPA) ↔ `/procedures-api`(API), `/updates`(SPA) ↔
`/changelog`(API) 를 일부러 갈라 놓은 결과이고, 이제 그 규칙이 테스트로 고정됐다.
빈 집합끼리 비교해 통과하는 사고를 막으려고 "표를 실제로 읽었나" 도 함께 시험한다.

## W-34. 씨앗 ②~⑥ 도 살아 있는 게이트웨이에서 돌려 봤다 — 두 곳이 걸렸다

고정물은 "기록해 둔 응답" 을 시험한다. 그것만으로는 사용자가 화면에서 처음 돌릴 때
무엇에 걸릴지 모른다. 그래서 ②~⑥ 을 실제로 이어 불렀다.

**걸린 것 둘은 전부 `laminate` 스키마였다.**
- `material.type` 을 빼면 `E202 INVALID_MATERIAL_TYPE`.
- `fatigue.k` 를 1보다 크게 주면 `E100 … should be less than or equal to 1`(k 는 기울기다).

둘 다 도구가 `suggestion` 으로 고치는 법을 준다 — **이 서버의 오류는 자가 복구가 된다.**
다만 화면에서 처음 만나면 멈칫하므로 씨앗의 `why` 와 examples.md 에 붙여 넣을 판을 적었다.
정본은 도구가 들고 있다 — `get_reference_cases(case_id="fatigue_reversed_cycle")`.

**확인된 것 하나가 중요하다.** `equivalent_loads` 에는 `chain` 이라는 **설명 문자열**이
끼어 있다. 씨앗은 이 객체를 통째로 다음 단계에 넘기는데, 받는 쪽 둘이 **그대로 받아 준다**
(`load_state` 가 N·M 만 읽는다). 걷어내는 단계를 따로 두지 않아도 된다는 뜻이고,
이건 소스를 읽어 짐작한 것이 아니라 **실호출로 확인했다**.

`save` 경로 여섯이 살아 있는 응답에서 전부 풀렸다 — ① 셋 + `basis`, ③④ `equivalent_loads`,
⑤ `tsai_wu_R`·`governing_mode`, ⑥ `life_cycles`.

**미해결 마찰 하나를 남긴다.** `json` 형 변수에 **기본값 칸이 없다**(`Var` 에 `default`
없음, `extra: forbid`). 그래서 사람이 4겹 적층 JSON 을 화면에서 손으로 채워야 한다.
`default` 를 더하면 규격·지문·폼이 함께 바뀌므로 **혼자 정할 일이 아니라고 보고 안 했다.**
지금은 문서로 막아 뒀다.

## W-35. `Var.coerce` 가 **운영 경로에서 한 번도 안 불리고 있었다**

미결로 남겨 뒀던 "json 변수 기본값" 을 붙이려다 그 밑에서 더 큰 것이 나왔다.
`grep '\.coerce('` 이 테스트 네 줄과 방금 내가 쓴 한 줄만 찾았다 — **실행 경로에 없다.**

무슨 일이 일어나고 있었나. 화면의 입력칸은 문자열밖에 못 보낸다. `POST /runs` 는
`body.vars` 를 그대로 `inputs` 에 넣고, 치환기는 통째 리프의 **형을 그대로 보존**한다
(그게 `template.substitute` 의 설계다). 그래서 —
- 적층 정의가 `laminate` 인자에 **문자열**로 실린다 → 도구가 거절한다.
- `r_unfold` 가 `"1000"` 으로 실린다 → 같은 일.

즉 **R1 을 화면에서 처음 돌리면 깨졌다.** 고정물 테스트도 실호출도 이걸 못 봤다 —
둘 다 파이썬에서 이미 형이 맞는 값을 넣었기 때문이다. 사람이 브라우저에서 채우는
경로만 이 모양이었다.

`coerce_inputs(spec, raw)` 를 만들어 `start_run` 이 **실행을 만들기 전에** 부른다.
- `json` 은 문자열이면 `json.loads` 한다. 깨져 있으면 422 이고 실행이 안 만들어진다.
- `boolean` 은 `"true"/"false"` 를 받는다(칸이 문자열밖에 못 보낸다).
- 빠진 **필수** 변수를 여기서 잡는다. 안 잡으면 그 변수를 쓰는 **단계에 가서야** 터지고,
  그때는 앞 단계가 이미 게이트웨이를 부르고 난 뒤다 — 되돌릴 수 없는 것도 있다.
- 안 채운 선택 변수는 `""` 로 들어가지 않고 빠진다.

## W-36. 예시는 **기본값이 아니다** — 버튼으로 넣는다

원래 물음은 "`json` 변수에 기본값을 두자" 였다. 두지 않았다.

미리 채워 두면 4겹 적층이 **자기 부품의 값처럼** 보인 채 그냥 돌고, 결과는 정상으로
나온다. 이 리포가 반복해서 만나는 모양 그대로다. 그래서 `Var.example` 은 칸을 채우지
않는다 — 칸은 비어 있고, 사람이 **"예시 넣기"** 를 눌러야 들어간다. `required` 는 그대로
살아 있어서 안 누르면 시작에서 걸린다. 화면에도 "내 값이 아니다 — 넣고 **고쳐서** 쓴다"
를 붙였다.

곁들여 `json` 변수 칸을 **여러 줄**로 바꿨다. 4겹 적층을 한 줄 `input` 에 넣는 것은
가능해도 사람이 할 일이 아니다.

예시 값은 지어내지 않았다. 도구가 들고 있는 정본
`get_reference_cases("fatigue_reversed_cycle")` 을 **부품 두께 1.2mm 에 맞춰** 0.125 →
0.3mm 로 바꾼 것이고, 총두께가 ①이 준 `thickness_mm` 와 **같은지 테스트가 본다**
(다르면 다른 부품을 해석하는 것이다). 씨앗에서는 YAML 앵커(`&ply`/`*ply`)로 적어
234줄을 157줄로 줄였고, 앵커판과 펼친 판의 값이 같은 것을 확인하고 바꿨다.

## W-37. 게이트웨이 한 칸 어긋남의 정체 — **재집계가 이틀째 매달려 있었다**

W-33 에서 "원인을 못 짚었다" 고 남긴 것을 짚었다. 짐작이 아니라 로그로 갈랐다.

`_revive_once` 는 항상 `GET :4040/api/v1/mcp/servers` 로 시작한다. 그 호출이
재기동 전후 구간에 **딱 한 번**뿐이었고, 그 한 번이 내가 손으로 친 `POST /refresh`
였다. 60초 주기라면 그 사이 세 번 있어야 한다. 로테이션 로그를 열어 보니 —

```
9/12 00:17 ~ 18:07  → 1069 회 (정상)
9/12 18:07:43       → 마지막
9/13 · 9/14         → 0 회
```

**멈춘 자리도 로그에 있다.** 18:07:54 재집계가 백엔드를 차례로 돌다가
`smart-twin-mcp -> 18 tools` 다음에서 끊겼다. 다음 차례인 `heax-materialtwin_web` 은
POST 를 보낸 기록만 있고 응답이 없다. 그 직전에 같은 백엔드가 liveness 에서
TimeoutError 를 냈다 — 느려진 앱 하나가 재집계 안에서 응답을 멈춘 것이다.

`_aggregate()` 의 `await b._ready.wait()` 와 `await b.session.list_tools()` 에
**데드라인이 없었다.** liveness(`fail_after`)·재연결(`move_on_after`) 경로엔 이미
걸어 놨는데 여기만 비어 있었다. 그래서 `_revive_loop` 가 거기 선 채로 **이틀** 있었고,
그동안 죽은 백엔드 부활도 도구 목록 갱신도 없었다.

**최악인 것은 아무도 못 봤다는 점이다.** 게이트웨이는 옛 카탈로그로 정상 응답을 계속
냈다. 에러도 경고도 없다. StepForge 를 재배포했는데 새 도구가 안 보여서야 드러났다 —
W-33 에서 "게이트웨이가 105초 뒤 스스로 감지했다" 고 적은 것은 **틀렸다.** 그 재집계는
내 수동 `/refresh` 였다. (고쳤다. 아래가 그 기록이다.)

고친 내용은 HWAXMcpGateway 쪽이다 — 두 await 에 `LIVENESS_TIMEOUT_S`(10초) 데드라인을
걸고, 초과하면 그 백엔드만 건너뛰며 **ERROR 로 남기고** 세션을 죽은 것으로 표시해
다음 회차 재연결 루프가 집어 가게 했다(`session is None` 갈래와 같은 동작). 회귀
테스트 둘을 붙였는데, 고치기 전 코드로는 5초 데드라인에 걸려 **실제로 실패한다**.
재기동 뒤 주기 루프가 60초마다 도는 것을 로그로 확인했다(15:08·15:09·15:10·15:11).

**교훈.** 멈추는 것은 예외가 아니라 **행**이라 `except` 로는 안 잡힌다 — 데드라인만
잡는다. 그리고 "60초 내 자동 재집계" 같은 약속은 **그 약속이 지켜지는지 보는 눈**이
없으면 조용히 거짓이 된다.

## W-38. R1 을 끝까지 돌렸다 — 답은 **불리**, 첫 사이클에 파손

씨앗을 처음부터 끝까지 태웠다. 입력은 **화면이 보내는 모양 그대로** 전부 문자열로 넣고
`coerce_inputs` 를 태웠다(W-35 가 고친 자리를 실제로 지나간다).

| 단계 | 결과 |
|---|---|
| ① `bend_profile` | R 6.0 · 두께 1.2 · 폭 40.0 mm · `analytic_cylinder_pair` |
| ③ 굽힘 R=6 | Mx 3842.7 N·mm/mm · 표면 변형률 **±10.0 %** · W130 |
| ④ 펼침 R=1000 | Mx 23.1 N·mm/mm · 표면 변형률 ±0.06 % · W130 |
| ⑤ 파손 | Tsai-Wu **R = 0.0757** · 지배 `fiber_tension` · `fails: true` |
| ⑥ 수명 | **1 사이클** (4겹 전부 동률) |
| ⑦ 보고서 | `gate: human` — 멈췄다 |

**절차가 답해야 할 질문에 답했다.** 1.2mm CFRP 판을 R 6mm 로 굽는 설계는 성립하지
않는다. 0° 인장 파손변형률이 Xt/E1 = 1500/181000 = 0.83% 인데 표면이 10% 다 —
12배다. 같은 두께로 그 변형률에 들려면 R ≳ 72mm 여야 한다(도구가 준 값만으로 유도).
정답을 제대로 찾으려면 R 스윕(S5)이나 `solve_required_thickness_scale` 이다.

**교차 검증이 걸렸다.** 적층 총두께 1.2mm 가 ①이 형상에서 읽은 두께와 같다 — 같은
부품을 해석했다는 뜻이다. 씨앗의 `why` 가 경고하는 자리이고, 이번엔 맞았다.

**두 상태의 차이가 곧 사이클**이라는 설계도 확인됐다. 별도 하중 변수가 없는데
Mx 3842.7 ↔ 23.1 이 그대로 ⑥의 max·min 이 된다. `equivalent_loads` 에 끼어 있는
`chain` 설명 문자열도 받는 쪽 둘이 그대로 삼켰다(W-34 에서 실호출로 확인한 것).

**W130 이 두 번 떴고 둘 다 기록에 올라왔다.** 자유 폭(M_y=0) 가정이라는 경고다 —
실제 지그가 구속 폭이면 답이 9.6% 갈린다. 씨앗이 `width_mode` 를 사람에게 묻는 이유가
이것이고, 경고가 조용히 사라지지 않는 것을 이번 실행으로 봤다.

**어디까지 돌렸나(정확히).** 도구 호출은 게이트웨이를 **내 MCP 자격**으로 했고,
형 맞추기·치환·판정·`save` 는 절차의 **실제 모듈**(`coerce_inputs`·`template`·`judge`)로
돌렸다. 포털 HTTP 경로(PAT 발급 → `GatewaySession`)는 이번에 안 지나갔다 — 내 셸에
PAT 가 없고, **없는 신원으로 토큰을 만들지 않았다.** 그 경로는 라우트 테스트와
살아 있는 서버 확인으로 따로 덮여 있다. 브라우저 완주는 여전히 사람 몫이다.

## W-39. 예제가 **한 칸만** 채워져서 실행이 안 됐다

사용자가 화면에서 "예시 넣기" 를 누르고 재생을 눌렀더니 이렇게 떴다.

```
채워야 할 값이 비어 있습니다 — StepForge 과제 ID(project_id), 부품 이름(part),
펼친 상태 굽힘반경 R_max (mm)(r_unfold), 굽힘축(bend_axis), 폭 구속(width_mode)
```

검증(W-35)은 옳게 동작했다. 틀린 것은 **씨앗**이다 — `laminate` 한 칸에만 `example` 을
달아 놨다. 나머지 다섯은 "사람이 판단해야 하는 값이라 예시를 주면 안 된다" 고 내가
스스로 판단해 뺐는데, 그 판단이 **예제를 못 돌게 만들었다.**

바로잡은 방식이 중요하다. `example` 은 여전히 기본값이 아니다(안 누르면 안 들어간다).
여섯 칸 전부에 예시를 달고, **"예제 값 모두 넣기"** 를 한 번에 채우는 버튼으로 뒀다.
옆에 "함께 오는 예제로 한 번 돌려 보는 용도입니다. **내 부품의 값이 아닙니다.**" 를 적었다.
판단이 필요한 값(굽힘축·폭 구속·펼침 R)은 예시로 들어가되 `why` 가 그대로 붙어 있다.

**교훈.** 사람이 판단할 값이라고 예시까지 빼면, 예제가 예제가 아니게 된다. 막을 것은
"값이 몰래 들어가는 것" 이지 "예시가 있는 것" 이 아니다.

## W-40. 실행 이력이 절차에 안 묶여 있었다 — 만든 뜻이 반쯤 사라져 있었다

사용자가 짚은 것 셋이 전부 같은 뿌리였다.

1. **예제를 실제로 돌릴 수 있어야 한다** → W-39.
2. **이력을 그대로 다시 돌리면 그 데이터로 계산되는 게 보여야 한다.**
3. **한 절차로 돌린 것들의 이력이 다 있어야 한다.**

절차를 만드는 뜻은 **다시 돌리는 것**인데, 그 두 길이 다 막혀 있었다.

**② 다시 돌리기.** `POST /runs/{id}/replay` 를 붙였다. 지난 실행의 입력을 그대로 써서
**새 실행**을 만든다(덮어쓰지 않는다 — 덮으면 이력이 사라진다). 기록을 재생하는 것이
아니라 도구를 실제로 다시 부르므로 **지금 데이터로 계산된 값**이 나온다.

⚠ **함정 하나를 여기서 막았다.** 실행의 `inputs` 에는 앞 단계가 뽑은 `save` 값도
섞여 있다(`merge_inputs`). 그대로 물려주면 새 실행이 **옛 중간값을 쥔 채** 시작하고,
①이 굽힘반경을 다시 읽어도 옛 값이 이미 범위에 있어 무엇이 쓰였는지 알 수 없게 된다.
그래서 **선언된 변수만** 걸러서 넘긴다. 테스트가 이것을 지킨다.

**③ 절차별 이력.** 실행은 `procedure_version_id` 하나만 들고 있어서 화면에서 절차로
되짚을 수가 없었다 — 한 절차를 몇 번 돌렸는지 보는 것 자체가 불가능했다.
`list_runs` 가 `procedure_versions` 를 조인해 `procedure_id`·`version_no` 를 함께 내고,
`GET /runs?procedure_id=` 로 그 절차의 이력만 본다. 절차 상세 아래에 그 목록을 두고,
실행 상세에는 "← 이 절차 판본 N 에서 나왔습니다" 를 달았다.

**곁들여 — 씨앗을 다시 가져오면 사본이 아니라 판본이다.** 씨앗은 리포와 함께 자란다
(오늘만 해도 예시가 한 칸에서 여섯 칸으로 늘었다). 가져올 때마다 사본이 생기면 목록이
같은 이름으로 차고 어느 것이 최신인지 사람이 알 수 없다. `procedures.from_seed` 를
기록해 두고, 이미 있으면 `add_version` 한다 — **옛 판본과 그 이력은 그대로 남는다.**

⚠ `CREATE TABLE IF NOT EXISTS` 는 **이미 있는 표를 고치지 않는다.** 칼럼을 DDL 에만
더하면 새 DB 에서는 되고 돌고 있는 DB 에서는 조용히 없어서, 그 칼럼을 읽는 코드가
**운영에서만** 터진다. 멱등 `_migrate` 를 두고 옛 스키마 DB 에 실제로 붙는지 확인했다.

**남은 한 가지.** `from_seed` 가 생기기 전에 가져간 절차는 그 칸이 비어 있어 판본으로
안 올라가고 사본이 하나 생긴다. 제목으로 짐작해 입양하는 규칙은 두지 않았다 — 사람이
같은 제목으로 만든 자기 절차를 잘못 집어삼킬 수 있다. 한 번뿐인 일이라 그대로 둔다.

## W-41. 개명이 깨뜨린 낱말 하나가 **이틀 동안 화면에 떠 있었다**

남은 일을 정리하려고 "챗·심의 파일 0줄 변경" 을 diff 로 확인하다 걸렸다. 절차 코드
첫 커밋 이후 챗·심의 소스에서 바뀐 파일이 **1건** 있었고, 열어 보니 이것이었다.

```
- '… 대칭 적층과 동박 밸런스 중 무엇이 먼저인가',
+ '… 대칭 적층과 동박 밸실행스 중 무엇이 먼저인가',
```

워크벤치 → 절차 개명에서 `런` → `실행` 을 통째로 치환한 자국이다. 그때 12개 파일을
되돌리고 **"전부 원복했다" 고 보고했는데** 이 파일이 빠져 있었다. 하필 그 줄이
심의 화면의 **예시 질문**이라 사용자 눈에 그대로 보였다.

무서운 점은 **아무것도 안 터진다는 것**이다. 타입도 맞고 테스트도 통과하고 화면도
그려진다 — 글자만 틀렸다. 사람이 읽기 전엔 아무도 모른다.

`tests/test_rename_scars.py` 를 세웠다. **규칙이 아니라 실제 낱말에서 깨진 꼴을 만들어**
찾는다 — 처음엔 정규식(`[가-힣]실행[가-힣]`)으로 짰다가 `선실행해`·`오실행된다` 같은
멀쩡한 낱말을 잡아서 버렸다. 깨진 문자열을 **소스에 안 적는 것**도 그래서다(적으면
자기를 잡는다). 일부러 깨뜨려 실제로 잡히는 것까지 확인했다.

**교훈 둘.**
