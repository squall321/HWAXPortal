# LLM 서버 둘 나눠 쓰기 — 결정과 까닭

**LP-D1 사용자 결정(2026-10-15).** "지금은 끝이 137로 끝나는 서버 하나가 vLLM 이 연결되어있는데 이거를 두개 서버(136, 137로 끝나는 서버)에 llm을 배치하려고 하거든. 이거를 자원 상황에 따라 유동적으로 쓸수 있게끔 할 수 있어?" — 물음에 대한 답: 두 서버에 **같은 모델**, 기준은 **자원 보고 분배**(vLLM 지표를 읽는 라우터 — nginx 연결 수 방식은 GPU 상태를 모른다), 차례는 **M3 끝나고 바로**.

**LP-D2 붙임을 둔다.** 카드 대조는 한 전문가의 카드 묶음을 셀마다 다시 싣는다 — 같은 서버로 가면 vLLM 접두 캐시가 미리 채우기를 줄인다. 무작위로 흩으면 두 서버 모두 캐시가 덜 맞는다. 그래서 '덜 바쁜 쪽' 위에 '같은 열쇠는 같은 서버(확실히 바쁘지 않으면)' 를 얹는다.

**LP-D3 흐르기 시작한 스트림은 다시 보내지 않는다.** 넘김은 연결 실패(요청이 서버에 닿지 않은 것)만이다 — 생성 중에 끊긴 것을 다른 서버에 다시 보내면 같은 답을 두 번 만들고 부르는 쪽(엔진의 재시도·차감 규칙)과 겹친다. 그 끊김은 지금처럼 부르는 쪽의 인프라 실패로 둔다.

**LP-D4 주소가 여러 `.env` 에 사본으로 있다.** 설정 킷은 없는 키만 더하므로 정본만 바꾸면 조용히 옛 주소로 돈다(무음 결함 다섯째 '앱은 정상, env 만 빠졌다' 와 같은 꼴). 그래서 주소 바꾸기는 사본을 함께 바꾸는 단계로 하거나, 라우터가 지금 주소를 이어받아 클라이언트를 안 고치는 길로 한다.

**LP-D5 라우터는 cae00 에 둔다(사용자, 2026-10-15).** 열린 물음 1 의 답. HWAX 박스에 작은 서비스로 두고 우리가 관리한다 — GPU 서버는 건드리지 않는다. 그래서 클라이언트 주소를 라우터로 바꾸는 update-all 단계(백업 · 바뀐 파일 목록 · 되돌리기)를 함께 넣는다(LP-D4).

**LP-D6 …136 은 …137 과 같다(사용자, 2026-10-15).** 열린 물음 2 의 답 — 같은 GLM · 1M 창 · 같은 기동 인자. 라우터는 두 서버를 똑같이 다루고, 기동 때 `/v1/models` 로 모델·창이 정말 같은지 대조해 다르면 크게 알린다(사람이 답한 것을 코드가 다시 확인한다 — 한쪽만 재기동하다 인자가 갈리는 날을 대비).

**LP-D7 동시 수는 자동으로 올리지 않는다(2026-10-15).** 계획의 L-4 는 '카드 대조 관문 8 → 16' 이었다. 들여다보니 처리량을 두 배로 쓰려면 세 곳이 함께 움직여야 한다 — 에이전트 서버 `.env` 의 관문 · 리스크 앱 `knobs.env` 의 워커(데이터 디렉터리에 있다) · 포털 중계의 스트림 상한. 하나만 오르면 사슬이 어긋난다(워커 > 관문이면 거절과 재시도, 스트림 < 관문이면 중계에서 기다림). 또 …136 을 정비하는 날 풀은 하나로 줄어드는데, 자동으로 올린 16 이 남은 서버를 두 배로 누른다. 그래서 라우터로 두 서버를 함께 쓰는 것(8 개가 4·4 로 나뉘고 바쁜 쪽을 피한다)까지만 자동으로 하고, 처리량 두 배는 절차서의 세 줄로 사람이 `/stats` 를 보고 올린다. 코드 기본값과 시간 한도 사슬 시험(P3-3)은 그대로다.

**LP-D8 붙임 열쇠는 메시지 앞부분의 해시다(2026-10-15).** 계획 초안은 '요청 머리의 붙임 열쇠(대화 id · 전문가 키)' 였다 — 그러면 클라이언트 다섯 곳을 고쳐야 한다. 앞부분 해시는 클라이언트를 안 고치고 같은 효과를 낸다 — 카드 대조는 시스템 프롬프트(역할 + 카드 묶음)가 앞에 오고, 대화는 앞이 같은 채 뒤로 자란다. vLLM 접두 캐시가 맞는 것도 정확히 '앞이 같은' 요청이다. 앞이 같은 서식 요청이 한 서버에 몰리는 것은 붙임 문턱(`STICKY_SLACK`)이 푼다.

**LP-D9 라우터는 손님 키를 그대로 넘긴다(2026-10-15).** 라우터가 `LLM_API_KEY` 를 끼워 넣으면 이 박스(cae00 — 여러 계정이 쓰는 서버)의 누구든 루프백 9130 으로 키 없이 GLM 을 쓴다. 넘기기만 하면 키 검사는 지금처럼 vLLM 이 한다. 라우터 자신은 `/v1/models` 대조에만 키를 쓴다.

**LP-D10 라우터의 지문은 라우터 파일뿐이다(2026-10-15).** 포털 리포 안에 있으므로 매니페스트 기본 지문(git HEAD)을 쓰면 문서 커밋 하나에도 라우터가 재기동돼 몇 시간 도는 카드 대조·심의의 LLM 호출이 끊긴다. 그래서 `fp_git: false` 로 라우터 코드만 지문에 넣고, 서버 목록은 라우터가 `infra/.env` 를 다시 읽어 재기동 없이 바꾼다. 그래도 코드가 바뀌어 재기동할 때 도는 호출이 있으면 미룬다(에이전트 서버와 같은 규율).

**LP-D11 구현에서 정한 것 — 라우터(L-1, 2026-10-15, `63be0e9`·`32b3581`·`1f4a037`).** ① 위로 가는 연결은 keep-alive 를 끈다(`max_keepalive_connections=0`) — 그래야 '연결 실패' 가 곧 '요청이 서버에 닿지 않았다' 이고, 다시 보내도 같은 답을 두 번 만들지 않는다(LP-D3). ② 연결이 안 된 서버는 `COOLDOWN_S` 뒤 저절로 돌아온다(지표를 다시 읽기 전에도 쓴다) — 지표 읽기가 실패할 때마다 그 시계를 다시 건다. ③ 띄우는 스크립트는 `_common.sh` 를 소싱하지 않는다 — 그 파일은 infra/.env 를 통째로 `set -a` 로 내보내 키가 라우터 환경에 든다. 대신 `--cleanenv` 로 띄우고 라우터가 infra/.env 를 직접 읽는다. 두 클라이언트 모두 `trust_env=False` 다(운영자 셸의 프록시를 타지 않는다). ④ 다시 읽은 목록이 비거나 전부 틀리면 마지막 목록으로 계속 보낸다(`/health.kept_last_list`) — 풀을 끄는 것은 update-all 이다(사본을 되돌린 뒤 §4 뒤에 라우터를 내린다). 심의 때문에 재기동을 미룬 서비스가 아직 라우터를 가리키는 동안 LLM 을 잃지 않게. ⑤ `services.py` 의 `health:` 도 `${KEY:-기본}` 을 푼다 — 안 그러면 매니페스트에 적은 라우터 health 주소가 끝내 'up' 으로 읽히지 않는다.

**LP-D12 구현에서 정한 것 — 배선(L-2·3, 2026-10-15, `279983a`·`7fe321d`·`35d5820`·`ffb31fd`).** ① 1i 는 1h(비우기) 바로 뒤 · §2 앞이다 — 라우터 재기동도 비우기 창 안에서 하고, 바꾼 사본은 §2·§4 의 재기동 지문(.env 가 든다)으로 그 자리에서 이어진다. 비우기 시험의 '1h 바로 뒤가 §2' 단언은 '1h 와 §2 사이에는 1i 만' 으로 바꿨다. ② 풀을 끄면 라우터는 §4 **뒤에** 내린다 — 미룬 재기동이 장부에 있거나 §2·§4 가 0 이 아니거나 도는 요청이 확실히 있거나 사본이 아직 라우터를 가리키면 내리지 않고 ○('LLM 라우터 내리기 미룸'). 장부 이름은 '재기동 건너뜀' 으로 끝나지 않게 했다 — 비우기 끝맺음이 그것을 심의 미룸으로 읽어 새 패널을 멈춘 채 두지 않게. ③ apply-envs 의 새 키는 라우터가 서버 하나 이상 올라왔다고 답할 때만 라우터 주소, 아니면 직접 주소다(1i 가 사본을 바꾸는 조건과 같다 — 새 키가 죽은 라우터를 가리키지 않게). ④ `LLM_UPSTREAMS` 는 따옴표 밖 공백을 거절한다 — start.sh 가 infra/.env 를 bash 로 소싱하므로 그 줄 하나로 기동이 죽는다. 주소마다 `/v1` 로 끝나야 하고, 겹침·라우터 자기 포트·IPv6·자격·쿼리는 거절한다. ⑤ 사본 목록은 apply-envs 의 MAP 과 `@FROM_RA:LLM_BASE_URL@` 킷 줄에서 유도하고, 코드에서 확인한 둘(AIDataHub `LLM_BASE_URL` — chat 이 `OPENAI_BASE_URL` 보다 먼저 읽는다 · MXWhitePaper `LLM_BASE_URL`)을 더했다. PaperIngest `.env` 는 이번 실행이 다시 읽게 하는 자리가 없어 ⚠ 로 말한다(허브 앱은 HEAXHub 의 `HEAX_APP_LLM_BASE_URL` 을 받는다). 관리 밖 둘 — AIDataHub 챗 화면이 저장하는 주소 덮어쓰기(`chat_llm_config.json`)와 HEAXHub 자신의 `LLM_LOCAL_ENDPOINT`(OpenAI `/v1` 이 아니다).
