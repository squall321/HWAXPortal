# LLM 서버 둘 나눠 쓰기 — 결정과 까닭

**LP-D1 사용자 결정(2026-10-15).** "지금은 끝이 137로 끝나는 서버 하나가 vLLM 이 연결되어있는데 이거를 두개 서버(136, 137로 끝나는 서버)에 llm을 배치하려고 하거든. 이거를 자원 상황에 따라 유동적으로 쓸수 있게끔 할 수 있어?" — 물음에 대한 답: 두 서버에 **같은 모델**, 기준은 **자원 보고 분배**(vLLM 지표를 읽는 라우터 — nginx 연결 수 방식은 GPU 상태를 모른다), 차례는 **M3 끝나고 바로**.

**LP-D2 붙임을 둔다.** 카드 대조는 한 전문가의 카드 묶음을 셀마다 다시 싣는다 — 같은 서버로 가면 vLLM 접두 캐시가 미리 채우기를 줄인다. 무작위로 흩으면 두 서버 모두 캐시가 덜 맞는다. 그래서 '덜 바쁜 쪽' 위에 '같은 열쇠는 같은 서버(확실히 바쁘지 않으면)' 를 얹는다.

**LP-D3 흐르기 시작한 스트림은 다시 보내지 않는다.** 넘김은 연결 실패(요청이 서버에 닿지 않은 것)만이다 — 생성 중에 끊긴 것을 다른 서버에 다시 보내면 같은 답을 두 번 만들고 부르는 쪽(엔진의 재시도·차감 규칙)과 겹친다. 그 끊김은 지금처럼 부르는 쪽의 인프라 실패로 둔다.

**LP-D4 주소가 여러 `.env` 에 사본으로 있다.** 설정 킷은 없는 키만 더하므로 정본만 바꾸면 조용히 옛 주소로 돈다(무음 결함 다섯째 '앱은 정상, env 만 빠졌다' 와 같은 꼴). 그래서 주소 바꾸기는 사본을 함께 바꾸는 단계로 하거나, 라우터가 지금 주소를 이어받아 클라이언트를 안 고치는 길로 한다.
