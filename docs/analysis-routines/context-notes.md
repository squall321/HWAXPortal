# 분석 루틴 — 판단과 까닭

계획 `PLAN.md` · 체크리스트 `checklist.md`. 새 판단은 맨 아래에 덧붙인다.

## C-1 조사는 넷으로 나눠 읽기만 했다(10-29)

사용자 요청 '서브에이전트로 계획을 세워보자'. 절차 기능 · 챗 루틴 모드 · MCP 길 · 예시 연쇄의 플랫폼 지도를 따로 맡겼고, 아무것도 고치거나 다시 띄우지
않았다. 에이전트의 보고는 가설로 읽고 계획의 바탕이 되는 사실(왕복 상한 80 · 핀은 셋까지 우선순위 · 대화 종류 셋 · 절차 저장소 · `from_chat.record` ·
`feat:procedures`)은 코드에서 다시 봤다. 플랫폼 지도의 cae00 전용 도구 이름은 QA 기록 · 문서에서 왔다 — dev 에서 스키마를 못 봤다.

## C-2 절차에 LLM 단계를 넣지 않는다(AR-D1)

절차의 보증(schema_fp · 모르는 인자 거부 · MUST_GATE · 비밀 검사)은 전부 '저장 때 고정된 인자' 위에 선다. LLM 이 실행 때 도구와 인자를 고르면 그 보증이
하나도 서지 않는다. 그래서 같은 저장소의 다른 표 · 다른 스펙이다. 거꾸로 절차는 루틴의 한 단계로 들어올 수 있다 — 결정적인 부분은 결정적으로 돈다.

## C-3 한 턴 ReAct 로는 안 된다(AR-D2)

8 ~ 9단계가 한 턴에 들어가지 않는다 — 왕복 상한 약 39, 10-29 QA EX-03 은 여러 허브 질문 하나가 호출 25 · 541초였다. 핀은 우선순위일 뿐이고
`invoke_tool` 이 늘 묶여 있어 단계가 다른 플랫폼으로 샌다(10-29 QA 의 코어 질문 샘이 그 길이다). 한 맥락에 결과가 쌓이고(단일 응답 약 100k자),
건너뛴 단계가 보이지 않으며 이어 갈 수 없다. 코드가 단계를 돌고 단계마다 그 플랫폼 도구만 묶으면 이 넷이 함께 풀리고 고정비(도구 설명)도 준다.

## C-4 면제의 덫(AR-D4)

절차 PAT(`purpose=procedure`)는 게이트웨이가 `invoke_tool` 정확이름 차단을 면제하는 유일한 자격이다 — 전제는 '사람이 이 인자를 승인했다'(W-100).
LLM 이 고른 호출이 이 PAT 로 나가면 그 전제가 거짓이 된다. 루틴은 챗 PAT · 개인 PAT 로만 부르고, 시험으로 잠근다.

## C-5 하나의 계약, 두 실행자(AR-D3)

MCP 조사는 상태를 포털에, 챗 조사는 에이전트 서버 파일 원장을 권했다. 둘로 두면 Claude 길과 Qwen 길의 기록이 갈라진다. 포털이 정의 · 실행 · 원장 · 렌더를
쥐고, 게이트웨이 `routine_call` 한 곳이 울타리와 기록을 맡으면 두 길이 같은 검사 · 같은 원장 · 같은 보고서 꼴을 탄다. 에이전트 서버는 상태를 쥐지 않는
순서 실행자다 — 재기동되면 interrupted 이고 '이어서' 는 포털 원장에서 끝난 단계를 건너뛴다.

## C-6 예시 연쇄는 cae00 에서만 판정한다(AR-D10)

코어 허브 · FailureTrace · PLM · FMEA · ODB 가 dev 에 없고 RA 는 내려가 있다. dev 는 계약과 꼴을 보고, 결과의 옳고 그름은 cae00 실주행으로 본다 —
request-1029 C-31(dev 의 QA 는 기준이 아니다)과 같은 판단이다.

## C-7 사용자 결정 셋(10-30 KST)

- **Q1 RA 초안은 저절로 만든다.** 루틴이 끝나면 그 사람 이름으로 `create_report_draft` 를 부른다. RA 토큰이 없으면 서비스 계정으로 떨어지지 않고 건너뛰며
  보고서 끝과 화면에 '토큰을 등록하면 올라간다' 를 적는다. 게시(publish)는 MUST_GATE 라 늘 사람이 RA 에서 한다. 스펙의 `report.ra.upload` 기본값이 `auto` 다
  (`ask` · `off` 는 루틴마다 고를 수 있게 남긴다).
- **Q2 · Q4 끝까지 돈다.** 권한 없음 · 토큰 없음 · 이 박스에 없음 · 결과 없음인 단계는 사유를 커버리지에 적고 다음 단계로 간다. 멈추는 것은 둘 —
  기준 키 후보가 여럿일 때(사람이 고른다)와 기준 키 단계 자체가 안 될 때다.
- **Q7 시장불량은 둘 다.** FailureTrace `pd_defect` 와 PLM 문제점을 따로 부르고(PLM 은 보류 중이라 `enrich=0`), 잇는 키(모델 · 과제 · 고장 모드)와 그 규칙은
  R0 계약에서 정한다. 조사 메모 — `pd_defect` 는 검사자 · 작업자 칸이 있어 생산 불량일 수 있다(보고서에 원천을 나눠 적는다).
- 남은 결정(Q3 울타리는 플랫폼 · Q5 새 권한 키 `feat:routines` · Q6 공유 기본 '나만' · Q8 PLM 은 enrich=0 으로만 · Q9 시뮬레이션은 있는 결과만 ·
  Q10 Claude 길 반출은 개인 MCP 와 같게)은 권고 기본값으로 짓는다 — 사용자가 바꾸라면 그때 바꾼다.

## C-8 R0 · R1 에서 정한 것(10-30)

- **울타리는 게이트웨이 백엔드 키다**(권한표 플랫폼 id 가 아니라). 허브 앱(`heax-*`)처럼 권한표에 행이 없는 백엔드가 있고, FailureTrace · FMEA 처럼 플랫폼 id 가
  박스마다 다른 것도 있다. 호출이 실제로 막히는 단위가 백엔드라 그것으로 묶고, 라벨은 /tools-map 의 앱 라벨을 보이기용 사본(`label`)으로 남긴다.
- **막혔을 때의 정책 칸은 `blocked` 다**(`on` 이 아니다). PyYAML(YAML 1.1)은 `on` · `off` 를 참 · 거짓으로 읽어, 손으로 쓴 YAML 의 `on:` 이 `True:` 키가 됐다
  (예시 YAML 을 검증하는 시험이 잡았다). 옛 `on:` 이 들어오면 고칠 것을 말하고, `upload: off`(거짓으로 읽힘)는 'off' 로 받는다.
- **`insight` · `cite` 는 보고서 절 이름으로 예약**이라 단계 id 로 쓰지 않는다 — 예시의 인용 단계는 `refs` 다.
- **저장은 막지 않는 것과 막는 것을 가른다** — 이 박스에 없는 백엔드는 저장된다(cae00 에서 짠 루틴을 dev 로 가져올 수 있다). 준비도가 실행 때 단계 상태로 말한다.
- 짜기 · 판 더하기 · 보관 · 가져오기는 세션 + CSRF 만, 읽기 · 준비도 · 검증은 PAT 도 받는다(게이트웨이 `routine_list` · `routine_get` 이 호출자 PAT 를 넘긴다).
- 메뉴 '절차' 는 `feat:procedures` 또는 `feat:routines` 면 보이고, 루틴만 가진 사람에게는 절차 탭 셋을 숨기고 루틴 탭으로 보낸다.

## C-9 R3 설계 — 챗 실행도 에이전트가 게이트웨이로 만든다 · 쓰기 분류는 게이트웨이가 정본(10-30)

정본 계약은 [R3-design.md](R3-design.md)(결정 D1 ~ D12). 코드 지도 여섯(에이전트 턴 · 떼어 낸 작업 · 선례 · 포털 중계 · 화면 · R2 계약 실물)을 읽고 정했다.

- **D1 뒤집기** — 처음 계약(§5)은 '포털 중계가 실행을 만들고 계획을 붙여 넘긴다' 였다. 중계가 만들면 `start_run` 이 이벤트 루프에서 sqlite 와 게이트웨이 왕복을 하고,
  실패 까닭(422 입력 · 403)이 화면에서 'Request failed (4xx)' 로 뭉개진다(화면은 배열 detail 만 그린다). 에이전트 서버가 `routine_run_start` 로 만들면 Qwen 길과 Claude 길이
  같은 도구 · 같은 계약을 탄다. 게이트웨이 도구에 없던 `conversation_id` 를 인자로 더했다.
- **쓰기 분류의 빈틈** — R2 의 `is_write_tool`(절차 MUST_GATE · WARN · 게이트웨이 차단 접두)은 이름 몇 개만 막는 목록이라, 도구를 비운 단계에 dev 의
  `create_document` · `update_block` · `run_operation` · `recipe_run` · `save_result_to_path` · `set_job_sync` 가 '읽기' 로 묶였다(R2 계약 지도). Qwen 이 그 도구로 잡을 낼
  수 있었다 — AR-D5 위반. 게이트웨이에는 검색 순위용 분류 `_tool_is_write`(readOnlyHint · destructiveHint → 이름 낱말 · 읽기 낱말 예외)가 이미 있어 그것을 정본으로 삼고
  `/tools-map` 에 싣는다. 울타리(`routine_call`)도 같은 판정으로 막는다 — 계획이 낡았거나 포털이 옛 판이어도 쓰기가 안 나간다.
- **RA `ask` 결함** — `routine_report_submit` 이 `ra_next` 로 'upload=true 로 다시 내라' 고 하는데 보고서를 내면 실행이 `done` 이 되어 다시 낸 요청이 늘 409 였다.
  게이트웨이 시험은 포털을 가짜로 세워 이것을 못 봤다(포털 시험은 409 를 단언하고 있었다 — 결함을 계약으로 굳힌 셈). 렌더한 RA 블록을 실행에 저장하고 끝난 실행의
  `/report` 는 저장본을 돌려준다.
- **심의 단계와 상한** — 상태 조회를 `routine_call` 로 하면 줄마다 원장 한 줄 · 예산 하나(기본 8)를 쓰고, 시간 상한(기본 60분)이 심의(분 ~ 시간)보다 먼저 닿아 결정문을
  못 받는다. 진행은 `deliberate_status` 를 직접 부르고, 결과 읽기(`deliberate_result`)는 시간 상한 뒤에도 연다.
- **떼어 낸 작업의 셈** — 루틴을 `delib_active` 에 더해 update-all · start.sh · deploy-all 의 기다림 다섯 곳이 고침 없이 루틴을 기다리게 했다. 카드 검토를 반으로 줄이는
  `_delib_human` 에는 세지 않는다(루틴은 Qwen 이고 그 반감은 GLM 보호다).
- **대화 종류** — `kind=routine` 을 만들지 않았다. 세 곳(포털 `ConvCreate` · 화면 `ConvKind` · 게이트웨이 enum)을 함께 고쳐야 하고 하나만 빠져도 사이드바 필터가 대화를 숨긴다.
  체크리스트 R4 의 '대화 kind=routine' 은 이 판단으로 바뀐다.

## C-10 R3 은 여럿이 나눠 지었다 — 독립 블랙박스 시험 · 맞대기(10-30)

사용자 지시('울트라 코드로 꼼꼼히' · '서브에이전트 많이 나눠서'). 리포 · 파일 단위로 나눴다 — 게이트웨이 · 에이전트 실행기 · 포털 /routines-api · 포털 중계 · 화면 상태 ·
화면 UI. 에이전트 실행기와 화면 순수 함수는 **설계서만 읽고 쓴 독립 블랙박스 시험**을 따로 두고, 맞대기 단계가 두 쪽을 함께 돌려 설계서 기준으로 틀린 쪽을 고친다
(구현자의 시험만으로는 구현자의 오해가 시험에도 들어간다 — '일치 시험은 둘 다 틀리면 통과'). 블랙박스가 실행기를 몰고 갈 수 있게 시험 이음매(`GW_TRANSPORT` ·
`_routine_llm` · `_user_tools` · `_tool_backends`)를 설계 단계에서 이름까지 정했다. 화면 둘은 TypeScript 인터페이스를 미리 고정해 같이 짓게 했다.

## C-11 짓다가 드러난 것(10-30 — 맞대기 · 알려진 결함 고침)

설계에서 바뀐 결정은 [R3-design.md](R3-design.md) §8 에 있다. 여기는 그렇게 바꾼 까닭이다.

- **내 도구 목록이 비면 실행이 `done` 으로 끝났다.** `app._get_tools_retry` 는 마지막 시도의 빈 목록을 돌려주고(예외가 아니다), 건강한 게이트웨이는 안내대 도구를 늘
  싣는다 — 그래서 빈 목록은 '일시 고장' 이다. 처음 구현은 열린 단계를 전부 건너뜀으로 닫고 보고서까지 내 이어갈 수 없는 실행을 만들었다. 이제 running 으로 멈추고 '이어서' 를 말한다.
  맞대기 단계가 찾았다(설계는 401 만 말했다).
- **보고서에 발견이 두 번 찍혔다.** 설계 §4.7 은 실행기가 단계 절(요약 + 발견)을 짓게 했고, 포털 렌더는 실행기가 준 글 뒤에 저장된 발견을 또 붙인다. 포털의 실제 렌더로
  재현했다. 단계 절의 정본을 포털 한 곳으로(실행기는 인사이트만), 포털은 준 글에 이미 있는 발견을 다시 붙이지 않는다(Claude 길 대비).
- **호출 원장 쓰기의 경합은 실제였다.** 개수 세기와 넣기 사이에 다른 호출이 끼면 `UNIQUE constraint failed: routine_calls.run_id, routine_calls.call_id` 가 난다(변이 시험
  6번 중 6번). `BEGIN IMMEDIATE` 한 트랜잭션 안에서 실행 상태 · 단계 닫힘 · 예산 · 상한을 다시 본다 — 취소와 엇갈려 닫힌 단계를 다시 여는 일도 막는다.
- **상한 판정 차례** — 시간 상한 예외(D5 의 결과 읽기)가 호출 상한까지 넘기지 않게, 둘 다 닿았으면 `limit_kind` 는 `calls` 다.
- **고르기 화면과 실행이 다른 말을 했다** — 준비도(`/readiness`)는 게이트웨이 쓰기 분류를 몰라 '됨' 이라 하고, 실행을 시작하면 계획이 그 도구를 빼 '이 박스에 없음' 으로
  닫혔다. 둘이 같은 함수(`allowed_tools` · `write_reason`)를 쓴다.
- **중계 셋** — 답 글이 비면 대화에 아무것도 안 남는 규칙 때문에 루틴의 run_id 를 잃었다(중계 시간 초과 · 에이전트가 안내 글 전에 죽음). 두 탭이 같은 실행을 끝까지 읽으면
  보고서가 두 번 남았다. 떼어 읽는 펌프는 끝날 때까지 챗 허가를 쥐므로(연결 풀 = 허가 수) 다시 붙기를 되풀이하면 64 허가를 다 쥘 수 있다 — 8개로 묶었다.
- **RA 초안 두 번** — 끝난 실행의 저장 보고서를 돌려주는 길(D12)이 생기자, 게이트웨이가 다시 낸 요청마다 초안을 또 만들 수 있게 됐다. 저장 보고서에 `ra_report_id` 를 싣고
  게이트웨이는 있으면 다시 안 만든다.
- **앞 프로세스가 남긴 단계** — 재기동 뒤 '이어서' 는 running 단계를 처음부터 다시 돌렸다. 심의 단계면 두 번째 `deliberate_start` 를 냈다(첫 잡은 원장에 있다). 원장의
  마지막 성공한 `deliberate_start` 의 job_id 를 다시 쓰고(반대 검토가 '첫 호출만' 은 두 번 끊기면 셋째 심의를 세운다고 짚었다), 플랫폼 단계는 앞 호출을 원장에서 읽어 봉투 근거에 싣는다.
- **다시 붙기는 같은 사람만** — 처음 구현의 판단을 받았다. 새어 나간 run_id 로 남의 단계 글(조회 결과 미리보기)을 보지 못하게.
- **덤으로 고친 옛 결함** — 챗 `sendMessage` 의 useCallback 의존성에 `searchSources` 가 빠져, 웹 검색 원천을 켜고 곧바로 보내면 옛 원천이 나갔다(09-11 부터). 루틴 줄을 고치던
  자리라 함께 고쳤다.
- 고친 것마다 **사본에서 그 고침을 되돌려 시험이 깨지는 것**을 보였다(변이 시험) — 구현자 시험만으로는 구현자의 오해가 시험에도 들어간다.

## C-12 반대 검토 — 여섯 렌즈 · 70 에이전트 · 확인 40(10-30)

렌즈 여섯(신원 · 울타리 / 수명 · 실패 / 리포 사이 계약 / LLM 실행기 / 화면 / 시험의 진짜 꼴)이 찾고, 찾은 것마다 회의론자가 둘(낮음은 하나, 갈리면 셋째)이 반박했다.
43건 중 40건 확인 · 3건 반박. 렌즈가 달라도 같은 결함을 여럿이 찾았다(심의 단계 멈춤 · 이어서의 덧붙인 말 · RA ask — 셋씩).

- **높음 하나 — 울타리가 이름 동사 규칙이었다.** R3-D6 은 게이트웨이 `_tool_is_write`(검색 순위의 감점용 — 주석이 '막지 않는다' 고 적는다)를 울타리 정본으로 삼았다. 앱들이
  readOnlyHint 를 달지 않아(실측 — MXWP 위키만 단다) 동사가 아닌 이름(`risk_job_action` · `single_drop_simulation` · `job_postprocess` · `docforge_convert` · `meeting_close`)이
  '쓰기 아님' 으로 묶이고 `routine_call` 을 통과했다(게이트웨이 사본에서 재현 — 취소 · 잡 제출이 실행하는 사람 이름으로 나간다). 공개 루틴이면 남이 짠 단계 글이 그 쓰기를 시킬 수

  쓰기 동사 없음). 모르는 이름은 막히고, 읽기인데 막히면 앱이 readOnlyHint 를 달거나 cae00 이 `read_tools.local.json` 에 더한다(커밋 없이 — 검색 손잡이와 같은 박스 덧씌우기).

  심의를 못 시작해 실패하거나(영구 실패) 줄 선 심의를 기다리며 셈에 남았다(기다림이 안 끝난다). 잠깐의 거절은 기다렸다 다시, 기다리는 동안은 셈에서 뺀다.
