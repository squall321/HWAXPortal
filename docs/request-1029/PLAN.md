## 0. 한눈에

목표는 셋이다.
1. **코어 질문이 코어 정본으로 간다.** 고장모드 · 시험항목 · 가상검증 · 관리 기준 · 물성 질문(OT-06 ~ 10)이 FMEA · ARP · MatNexus · 리포트 아카이브로 새지 않게 한다.
2. **한 질문의 LLM 비용을 줄인다.** 지금 요청 하나의 프롬프트가 평균 108,275 토큰이고, 그중 약 80% 가 도구 설명이다. 접두 캐시 적중은 11.9% 이고, 자기검증은 27번 중 19번 답을 다시 썼다.
3. **숨은 탭에서 답이 멈추지 않는다.** 화면이 스트림을 읽지 않으면 포털 중계와 에이전트 응답까지 함께 멈췄다(OT-07 은 25분).

원칙도 셋이다.
- **어휘는 한 곳에 둔다.** 코어 낱말이 세 곳의 손 표에 따로 있었다 — 에이전트 프롬프트의 발동 낱말(`app.py:183`), 게이트웨이 검색 동의어(`gateway.py:2814-2818`), 에이전트 분야 힌트(`_AREA_HINT`). 그래서 R-1 과 R-4 가 같은 낱말을 서로 다르게 틀렸다. 코어 어휘표 하나를 정본으로 두고 셋을 거기서 만든다(2.1 B-1).
- **재고 나서 바꾼다.** 같은 16문항(cae00 점검기 `~/ontology-test/`)과 게이트웨이 검색 평가로 전후를 잰다. 박스 값을 바꾸는 시험(W-2 · W-6)은 사람이 정한다.
- **앞선 결정을 뒤집는 것은 묻는다.** W-2 는 '창에서 유도한 예산으로 전량 바인딩' 결정(`app.py:2049-2056` 주석)을, R-6 은 '시험 앱은 라벨만 바로잡는다'(10-27 D-1)를 건드린다.

⚠ dev 에는 코어 허브 셋 · FMEA · ARP · ODB 허브가 없다. 그래서 길 찾기(2.1)는 dev 에서 단위 시험 · 가짜 도구 지도로만 확인하고, 실제 효과는 cae00 재시험으로 본다(4절).

## 1. 진단 — 요청서와 조사를 맞대 보면

- **묶이는데 부르지 않는다.** 10-28 의 HA-02 로 코어 도구 16개는 턴마다 묶인다. 그런데 OT-06 ~ 10 은 코어를 0번 불렀다. 모델이 고를 근거가 없기 때문이다.
  - 발동 낱말이 '부품 · 모델 · 과제 · 불량' 뿐이다(`app.py:183`).
  - 규칙 ⑦ 의 '보내지 말 곳' 에 FMEA · ARP · ODB 허브가 없다(`app.py:191`).
  - 허브 도구 설명은 일반문인데, FMEA 도구 설명에는 '규격 · 시험 · 고장모드' 가 있다.
  - 검색 동의어가 도구 이름이 아니라 타입 이름(`failure_mode` · `sim_capability` · `criterion`)에 이어져 있어 점수가 0 이다(`gateway.py:2814-2818`).
- **일반 챗은 전문가를 자동으로 고르지 않는다.** 사용자가 핀할 때만 쓴다. 그래서 이번 실패는 전문가 고르기가 아니라 **도구 · 앱 고르기** 문제다. 페르소나 쪽 연결(2.4 E-5)은 띵킹 · 심의 좌석 고르기에 효과가 나는 다음 단계다.
- **낭비의 큰 몫은 고정비다.** 무캡 경로가 창의 45%(88,473 토큰)까지 도구 설명을 싣는다(`app.py:2056`). 부하분산기는 같은 질문의 호출을 매번 다른 복제본으로 보낸다(`least_conn` — 117쌍 중 1쌍만 같은 복제본). 턴마다 묶음 순서도 바뀐다.
- **숨은 탭 문제는 중계 구조 탓이다.** 포털 중계(`backend/app/agent/routes.py` `chat()` 의 `gen()`)는 상류 프레임을 하나 읽고 브라우저로 내보내는 한 루프다. 브라우저가 읽기를 멈추면 상류 읽기도 멈추고, 서버 사본 저장(루프 끝)도 미뤄진다. 챗은 심의와 달리 에이전트의 분리 실행(`_detach_stream`) · ping 도 타지 않는다.

**① 손잡이 파일(게이트웨이)** — `HWAXMcpGateway/search_tuning.json`(추적 — 기본값, 지금 코드 상수를 옮긴 것) + `search_tuning.local.json`

재기동 없이 다시 읽는다. 덧씌우기가 깨지면 버리고 기본값으로 돌며 까닭을 낸다.
