# 챗 전용 LLM(stcx) — 결정과 까닭

**CL-D1 받은 것(2026-10-17).** 사용자 — "stcx 의 그래픽 카드를 chat 에서 사용하고, 심의에서 GLM 을 사용하게끔". 근거 문서는 사용자가 붙인
「stcx GPU LLM 사용 가이드 v1.1」(Qwen3.8-Flash-Next 10벌 · cae00 `127.0.0.1:18700/v1` · 262,144 토큰 · 도구 호출 qwen3_xml · 생각 모드
기본 켬). 사용자 결정 셋(10-17) — ① 띵킹은 GLM ② stcx 가 죽으면 챗은 GLM 으로 자동 넘김 ③ 챗에서 Qwen 생각 모드는 끔.

**CL-D2 '방법 B'(VLLM_BASE_URL 교체)를 쓰지 않는다.** 에이전트 서버의 두 클라이언트(`llm` · `delib_llm`)가 같은 주소를 보므로 심의까지
stcx 로 간다. `llm` 만 바꿔도 심의 준비(전문가 고르기 축 · VOC · 되묻기 · 주제 뽑기)와 띵킹이 따라간다. 그래서 챗 전용 클라이언트를 따로
두고 챗 흐름(`_agent_stream`)에서만 쓴다.

**CL-D3 넘김은 LLM 호출 단위다.** 턴 전체를 다시 돌리면 이미 실행한 도구(RA 저장 · 잡 제출)가 두 번 돈다. LangChain `with_fallbacks` 는
호출마다 앞 클라이언트가 실패하면 다음으로 보내고, 스트림이 첫 조각을 낸 뒤의 실패는 넘기지 않는다(가이드 6장의 한계와 같다).
langgraph 1.2.5 `create_react_agent` 는 받은 모델에 `bind_tools` 를 부르고, `RunnableWithFallbacks` 는 그 메서드를 앞 · 뒤 클라이언트
둘 다에 적용한다. 넘기는 예외는 연결 실패 · 시간 초과 · 5xx 만이다 — 400(잘못된 요청)은 GLM 에서도 같은 까닭으로 실패할 수 있고, 404
(모델 이름)는 설정 오류라 숨기지 않는다.

**CL-D4 챗 턴은 모델 호출마다 글을 낸다.** 챗 경로는 '비스트리밍인가' 를 서버 전체 값(`llm_nostream`) 하나로만 봤다. 챗 서버를 스트리밍으로
열고(`CHAT_LLM_DISABLE_STREAMING=0`) 넘겨받는 GLM 이 비스트리밍(cae00 의 tool_calls 유실 우회)이면, 넘겨받은 답은 조각 없이 끝나 글이 버려지고
턴이 '빈 답' 으로 끝나 확정 종결 절차가 돌았다(시험으로 재현 — 변이가 '글이 있다' 만으로는 안 잡혀, 확정 종결이 돌지 않았다는 것을 단언했다).
조각을 흘리지 않고 끝난 호출은 끝 이벤트의 글을 낸다. 챗 서버 스트리밍의 기본값은 `LLM_DISABLE_STREAMING` 을 따른다 — stcx 의 스트리밍 도구
호출은 cae00 에서 확인한 뒤 연다(server-setup 6절).

**CL-D5 챗 턴의 창은 두 서버 중 작은 값이다.** 챗 경로의 예산(이력 · 문서 · 도구 결과 · 도구 설명)은 `_model_context_tokens()` 하나를 보는데
그 값은 GLM 1M 이다. 그대로면 Qwen(262,144)에 넘치는 요청이 가 400 이 난다 — 400 은 넘기지 않으므로 챗이 실패한다. 외부 응답자가 쓰는 문맥
변수(`ctx_override`)를 챗 턴의 태스크에만 걸고 턴이 끝나면 되돌린다. 작은 값이라 GLM 으로 넘겨도 맞는다. 챗 서버 창은 그 서버
`/v1/models` 에서 답을 받았을 때만 굳힌다(못 물으면 `CHAT_LLM_CONTEXT_TOKENS` — 기본 128,000 — 으로 잡고 다시 묻는다).

**CL-D6 포털은 update-all 3.5c 가 맞춘다 — 적은 값은 기록한다.** 정본은 포털 `infra/.env`(LLM 설정의 정본 규칙). 킷은 없는 키만 더하므로
3.5c 가 매 실행 `_upsert_kv` 로 맞춘다. 키가 없으면 손대지 않는다(사람이 에이전트 서버 `.env` 에 직접 적은 값을 지키려고). 그러면 운영자가
되돌리려고 줄을 **지웠을** 때 사본이 남는다 — 3.5c 가 적은 주소를 `infra/.state/chat-llm.url` 에 남기고, 줄이 빠졌는데 사본이 그 값이면 끈다.
빈 값은 늘 끈다. 그 서버가 모델을 내는지는 보기만 한다(못 닿아도 ⚠ — 넘김이 있으니 배포를 막을 일이 아니다). 키는 argv · 출력에 싣지 않는다.

**CL-D7 시험.** 에이전트 서버 `tests/test_chat_llm.py` 8(실제 lifespan · 가짜 서버 — 닫힌 포트 · 5xx · 400 · 스트리밍 챗 서버가 비스트리밍
GLM 으로 넘기는 실제 챗 턴 · 창 덮어쓰기 · /health) · 변이 8/8 · 전체 2,459 통과(`fd110a6`). 포털 `tests/test_update_all_chat_llm.py` 8
(update-all 원문 구획을 임시 포털에서 — 없음 ○ · 적기 · 모델 확인 · 경고 · 끄기 · 지운 줄 · 모양 · 키) · 변이 6/6. 실제 stcx 서버로는 돌려 보지
못했다(dev 에서 닿지 않는다) — cae00 확인은 server-setup 4절.

**CL-D8 401 · 403 과 첫 조각 전 침묵도 넘긴다(2026-10-17, cae00 리뷰 A1 · A2 · A3 · P3).** CL-D3 의 넘김은 연결 실패 · 시간 초과 · 5xx 였다.
cae00 첫 적용에서 둘이 드러났다. ① stcx LLM 은 키가 있어야 하는데(안내서가 '키는 없다' 로 틀렸다) 401 은 넘기지 않아 키 없이 켜면 챗이 전부
실패하고, 키를 바꾸는 rolling(약 20분) 동안 일부 챗이 실패한다. 401 · 403 은 그 서버의 키 문제라 VLLM_* 는 자기 자격이 따로 있어 같은 까닭으로
실패하지 않는다 — 400(같은 요청이면 GLM 도 실패) · 404(모델 이름 — 설정 오류)와 다르다. 그래서 넘기되, 설정 오류가 숨지 않게 /health 의
`chat_llm.last_error` · 넘김 횟수 · `ctx_probe_error`(창 조회가 200 이 아니면 그 사유)와 update-all 3.5c 의 '키를 거절했다' 가 말한다.
② 스트리밍에서 첫 조각 전에 멈추면 langchain-openai 의 StreamChunkTimeoutError(TimeoutError 계열)라 넘기지 못했다 — 복제본 하나가 받고
멈추면 300초 뒤 챗 오류였다. 이제 넘긴다. 조각이 흐른 뒤의 실패는 여전히 넘기지 못한다. 창 조회는 처음 답을 영원히 굳히던 것을 200 일 때만
받아 10분마다 다시 묻게 했다(키를 고치면 재기동 없이 /health 가 따라온다).

**CL-D9 Qwen 도 1M 창 — YaRN factor 4 · 1,010,000, 벌이 섞인 동안의 '창이 모자라다' 400 은 넘긴다(2026-10-18).** 사용자 — "100만토큰으로
해야할것 같은데 큐웬 모델도". 배경 — 10-17 챗을 stcx(262,144)로 옮기자 챗 턴의 창이 min(Qwen, GLM) = 262,144 가 되어 도구 예산(창의 45%)이
117,964 토큰으로 줄었다. 무캡 경로(`TOOL_MAX=0`)는 게이트웨이 순서 뒤에서부터 떨어뜨린다(dev 실측 — 519종 약 162K 토큰, 262K 창이면
87종 잘림: StepForge 77 · 게이트웨이 자체 8 · REST 2, 1M 창이면 0). cae00 은 665종이고 RA · ODB 가 heax 앱 앞이라 더 앞(heax 앱 —
MaterialTwin 쪽)까지 잘렸을 것으로 본다 — 사용자가 본 'MaterialTwin 이 연결돼 있는데 없다' 의 유력한 까닭이다(cae00 로그의
`[agent] tool budget:` 줄로 확인할 일 — 아직 안 봤다). 2026-10-17 전 GLM 챗은 도구를 전부 붙였다 — 1M 은 그때로 돌아간다.

- **방법** — YaRN factor 4. vLLM 은 yarn 이면 원래 창 × factor(262,144 × 4 = 1,048,576)를 스스로 유도하고, 띄우는 길이는 Qwen 계열 카드가
  검증한 1,010,000 이다. 포털 · 에이전트 서버는 고칠 것이 없다(창은 10분마다 `/v1/models` 에서 읽는다 — `_chat_context_tokens`).
- **`VLLM_ALLOW_LONG_MAX_MODEL_LEN` 을 쓰지 않는다** — 모델 카드는 함께 적지만, 덮어쓰기가 맞으면 필요 없고 틀리면 그 env 가 없어야 기동이
  거부된다. 켜 두면 틀린 채로 떠 학습한 위치 너머를 쓴다(vLLM 스스로 NaN 을 경고한다). vLLM 0.23.0(GLM 과 같은 판, dev 의 SIF)의 실제 함수
  (`ModelConfig._apply_dict_overrides` · `_get_and_verify_max_len`)로 확인했다 — VLM 꼴(Qwen3_5Moe, `text_config.rope_parameters` + mrope)과
  옛 꼴(Qwen3Next, 맨 위 `rope_theta`) 모두 덮어쓴 뒤 1,010,000 이 env 없이 통과하고, 덮어쓰기 없음 · 자리 틀림(VLM 에 맨 위)은 기동을 거부한다.
- **덮어쓰기를 손으로 쓰지 않고 config.json 에서 만든다** — vLLM 0.23 은 dict 덮어쓰기를 둘로 가른다. 중첩 설정(`text_config`)은 재귀로 합치고
  맨 위의 dict 칸(`rope_parameters`)은 통째로 바꾼다. 바꾸는 쪽에서 `rope_theta` · `partial_rotary_factor` · `mrope_section` 을 빠뜨리면 기동은
  되는데 위치 인코딩이 조용히 달라진다. 그래서 지금 값을 읽어 세 칸만 바꾼다(server-setup 9.2). stcx 이미지는 10-15 판 파생이라 시범이 가린다.
- **섞인 동안** — 시범 · rolling 동안 부하분산기 뒤에 262,144 벌과 1,010,000 벌이 섞인다. 에이전트가 10분마다 묻는 창이 새 벌에서 오면 그
  창으로 만든 긴 요청이 옛 벌에 가 400 이다. CL-D3 은 400 을 넘기지 않는다 — 다른 400 은 GLM 도 같은 까닭으로 실패할 수 있어서다. 이 400 은
  다르다 — 챗 턴의 창은 두 서버 중 작은 값이라 그 요청은 GLM 창 안이다(CL-D8 의 401 · 403 과 같은 논리). 그것만 넘긴다(에이전트 서버
  `35c048b` — 챗 서버 클라이언트를 ChatOpenAI 하위 클래스로, 네 길에서 vLLM 의 두 문구와 OpenAI 의 `context_length_exceeded` 만
  `ChatCtxOverflow` 로 올린다). `with_fallbacks` 는 `except 튜플` 로 잡아 `__instancecheck__` 꼼수가 안 먹는다 — 진짜 하위 클래스로 올려야
  한다. 되돌릴 때 · 벌 하나가 옛 sbatch 로 떴을 때도 같은 길이 덮는다.
- **남는 비용** — 정적 YaRN 은 짧은 글에도 늘인 위치를 쓴다(Qwen 카드의 주의 — 시범에서 짧은 답을 견준다). 1M 에 가까운 요청의 prefill 은 분
  단위일 수 있고 그동안 그 벌의 다른 요청이 느려진다. 매 챗 호출에 도구 설명 전부가 실린다(GLM 챗 때와 같다). KV 는 벌마다 약 5.0M 토큰
  (가이드 — 50.3 GiB 에 262K 대화 19개)이라 1M 대화는 벌마다 약 4.9개를 동시에 담는다. 짧은 요청의 동시 처리는 그대로다.
- **stcx 쪽은 사람 몫이다** — dev 에서 stcx 에 닿지 않는다(CL-D7). 시범 수치(needle 200K · 500K · 900K 의 시간 · 찾음, 짧은 글 비교)는 시범한
  사람이 여기 적는다 — 아직 없다.
