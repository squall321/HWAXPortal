# 리스크 심사 20만 토큰 창 — 결정과 까닭

> 계획 [PLAN.md](PLAN.md) · 체크리스트 [checklist.md](checklist.md). 앞선 맥락은 재설계 [D-22](../risk-review-redesign/context-notes.md)(작은 창 장치를
> 만들지 않는다) · D-57(쟁점 패널 카드 절을 번갈아) · 메모리 'GLM 1M 창 · 잘라내지 않는다'(10-10).

**W-D1 목표는 '누락 0 · 멈춤 0' 이다 — 크기를 넘으면 나눠 여러 번 부른다(사용자, 2026-10-20).**
사용자 지시 그대로다 — "거절이 아니라 여러번 핑퐁을 치더라도 다 고려해야지". 그래서 재설계 D-22('창이 모자라면 잡을 멈추고 까닭을
말한다')를 뒤집는다. D-22 는 운영이 1M(GLM-5.2)이라는 전제(10-10)에서 '작은 창 박스는 설계 목표가 아니다' 로 내린 결정이었고,
그 전제가 20만으로 바뀌면 멈춤이 일상이 된다(W-D2 — 표본 전문가의 59%). 1M 박스의 동작은 바꾸지 않는다 — 1M 에서는 한계를 넘는
카드가 없어 조각 · 쪽이 생기지 않는다(표본 0장).

**W-D2 실측 — 20만에서 새는 곳은 '판정' 이 아니라 '멈춤' 과 '제목만' 이다(2026-10-20, dev).**
방법은 이렇다. dev AIDataHub 전문가 796명 가운데 무작위 30명(시드 20261020)과 두 명(xd-yield-ramp · material-twin-analyst)의
`/api/agents/{agent}/records` 를 읽어 엔진의 `normalize_card` · `assign_aliases`(= `render_card` 길이)로 펼쳤다. 한계는
`limits()` 와 `plan()` 의 식 그대로다(판정 한 장 자리 = `p_hard − verdict.fixed − unit_body_max`, 훑기 = `p_hard − sweep.fixed −
manifest_page_max`). 20만은 Claude 길 기본(창 200,000 · 출력 32,000)으로 셈했다.
- 카드는 짧은 메모가 아니라 문서다 — 한 장 중앙값이 전문가마다 2만~5만 자, 가장 긴 것 51.7만 자. 전문가 한 명의 전문 합 중앙값 244만 자.
- 한 장 자리(20만: 판정 131,560 · 훑기 126,012자)를 넘는 카드가 143장(2.5%), 그런 카드를 가진 전문가가 19/32명 — 지금은 그 전문가의
  잡이 `ctx_too_small` 로 선다. 1M 에서는 0장이다.
- 입력 결손 셀의 전문 몫 24,648자를 31/32명이 넘는다 — 지금은 넘는 카드가 제목으로만 실린다(`bg_dropped`).
- 판정 단계는 점검 카드 전부를 살아 있는 단위마다 대보므로(빠진 카드 재질의 포함) 카드를 빠뜨리지 않는다. 호출만 는다 —
  셀당 중앙값 2.6배(26 → 65), 최대 4.9배. 훑기는 4.5배(470 → 2,120).
표본은 dev 의 카드다. 운영 명단 전원의 분포는 W0 에서 cae00 에서 같은 방법으로 잰다(dev 리스크 원장에는 실제 실행이 없다).

**W-D2 덧붙임(2026-10-31, B32 — 리스크 앱 `111b34e`).** 같은 표본을 읽기 전용 셈 스크립트로 다시 쟀다 — 19/32 · 31/32 는 재현되고, 한 장 자리를 넘는 카드 143장은 지금 200장이다(AIDataHub `539d06b` 가 10-30 에 기록 목록의 원천을 바꿨다). 다만 W-D2 의 셈에는 지식카드가 아닌
기록(특허 · 논문 — 명단 전원에서는 규격도)이 섞여 있었다. 카드 팩이 실제로 싣는 지식카드만 세면 20만 한 장 자리를 넘는 카드는 0 이다 — 위 '멈춤' 의
크기는 그 기록이 팩에 들 때의 이야기다. 명단 전원 표는 리스크 앱 context-notes W-D 절, cae00 한 번은 사람 몫(리스크 앱 checklist 2장).

**W-D3 '검토했다' 는 전문으로 실린 것만 센다.**
제목 · 목록 줄 · 다른 쪽의 제목 목록으로 실린 것은 커버리지에 넣지 않는다. 조각으로 실렸으면 그 카드의 모든 조각이 실려야 그 카드를
'전문 노출' 로 센다. 증명은 원장이다 — 잡을 닫을 때 '범위 안 살아 있는 셀에서 전문 노출 0인 카드 = 0' 을 불변식으로 본다.
어기면 조용히 끝내지 않고 목록을 단 partial 로 닫는다(무음 결함 규율 — '실패가 정상처럼 보인다' 를 만들지 않는다).

**W-D4 조각 경계는 결정적이고, 절 번호는 원래 것을 쓴다.**
같은 카드면 같은 조각이어야 다시 돌기(셀 지문)와 vLLM 접두 캐시가 산다. 경계는 절 → 문단 → 문장 차례이고, 한도 안에서 가장 큰 덩이를
먼저 쓴다. 인용 대조는 원래 절 번호(`§3`)와 원문 위치로 하므로 조각 때문에 인용이 틀리지 않는다. 조각에는 카드 틀(머리 · 제목 ·
전체 목차 · 조각 위치)을 실어 모델이 카드 전체의 모양을 안다.

**W-D5 나눠 부른 결과는 코드로 합치고, 갈릴 때만 한 번 더 부른다.**
합치기 규칙은 결정적이다 — 해당은 '어느 조각 · 쪽이든', 판정은 가장 무거운 것, 인용은 다 모은다. 같은 카드의 조각끼리 판정이
갈리면(한쪽 FAIL, 다른 쪽이 반박 근거) 두 조각에서 인용된 절만 모아 그 카드 하나를 다시 판정한다. 배경 · 입력 결손의 쪽이 둘 이상이면
셀마다 합치기 호출을 한 번 더 부르되, 합치기는 새 지적을 만들지 못하게 한다(출력 인용이 입력 지적의 인용 안이어야 받는다).

**W-D6 열린 물음은 사용자 몫이다(PLAN 4절).** 20만 모델의 길(GLM 자리 · 사내 모델 · Claude 길 — 비용과 시간이 갈린다), G3 기준값,
패널 좌석의 다시 읽기 도구(E2), 카드 수천 장 전문가의 처리, 1M 박스에도 켤지.

## 2026-10-20 사용자 결정 · 다듬은 것

**W-D7 모델은 GLM 5.3 Flash(20만 창)로 바꾼다 — 확정. 장치는 에이전트 서버의 창 값에서 저절로 켜진다(사용자).**
"에이전트 서버 설정이 20만이면 자동으로 저렇게 동작하게 하면 돼". 따로 스위치를 두지 않는다 — 조각 · 쪽은 그 박스의 `limits()`
(창 · 출력 상한)에서 셈하고, 1M 박스에서는 한계를 넘는 카드가 없어 저절로 생기지 않는다(PLAN 4절 5번의 답 — 같은 코드가 창을 따른다).
GLM 5.3 Flash 의 출력 상한은 아직 모른다 — 모르면 엔진 기본(출력 16,000 토큰 가정, 창 20만이면 `p_hard` 179,676)으로 셈하고,
알게 되면 `CARD_REVIEW_MAX_TOKENS` 를 명시한다(재설계 E3-13 과 같은 자리).

**W-D8 패널 좌석이 카드 절을 다시 읽는 도구를 연다(사용자 — PLAN 4절 3번 "그래").** GLM 길 좌석의 자유 조회에 카드 절 읽기를 둔다(W4 · E2).

**W-D9 카드가 아주 많은 전문가는 막지 않고 다 돌린다 — 잡 안에서 맨 뒤로(사용자 — "상황에 따라서지, 흔하지 않으니 합리적으로").**
흔하지 않다(표본 32명 중 한 명이 2,693장). 확인을 받으려고 잡을 세우면 그 사이 다른 전문가까지 늦는다. 그래서 막지 않되 ① 잡 안에서
그 전문가를 맨 뒤 차례로 두어 다른 전문가 결과가 먼저 나오게 하고 ② 잡을 열 때 어림에 그 전문가 몫(호출 수 · 전체 대비 비율)을 따로
보인다. 기준은 '그 전문가의 어림 호출이 잡 전문가 중앙값의 10배 이상'. 사람은 어림을 보고 잡을 취소하거나 범위에서 뺄 수 있다(종전 기능).

**W-D10 '고려했다' 의 정의를 다듬는다 — 훑기의 전문 대조도 센다(W-D3 보강).**
훑기는 그 전문가의 카드 전부를 전문으로 모든 단위의 목록 줄에 대본다(묶음 × 목록 쪽). 그러니 카드마다 '이 단위에 걸리나' 를 전문으로
한 번 판단받는다 — 이것을 그 (카드, 단위)의 고려로 센다. 그 위에 ① 점검 카드는 살아 있는 단위마다 판정이 전문으로 한 번 더(종전 그대로)
② 카드 밖 · 입력 결손 호출은 **훑기에 걸린 카드와 훑기 결과가 없는 카드(그 쪽 훑기가 실패)** 를 전문으로 싣고(넘치면 쪽으로 나눈다),
나머지는 제목만 둔다 — 이미 훑기에서 전문으로 고려됐다. 까닭은 비용이다 — 20만 창에서 입력 결손 몫은 2.5만 자인데 카드 한 장이
보통 2만~5만 자라, 모든 카드를 전문으로 다시 실으면 셀 하나에 수백 번을 부른다. 그래서 G1 의 증명은 (카드, 단위)마다
'훑기 전문 대조' 와 해당하면 '판정 · 쪽 전문' 이 다 있는지로 본다. 훑기가 실패해 고려가 빈 (카드, 단위)는 그 셀의 호출이 전문으로 메운다.

**W-D11 조각은 엔진이 run 안에서 만들고 부르고 합친다 — 앱에는 한 카드 = 한 행 그대로(구현 중 고침, 10-20).**
처음 안은 엔진의 새 요청 `POST /card_review/chunk`(긴 카드 → 조각 카드들)로 앱이 `oversize.cards` 를 조각 내 다시 계획하고 결과를 앱이
합치는 것이었다. 앱을 읽어 보니 판정 원장 `rr_card_verdicts` 의 열쇠가 (대상, 단위, 전문가, record_id, 변형)이고, `check_pack` 이
record_id 가 겹치는 팩을 거절하며, 실효 판정 · 불변식 G4 · G5 가 record_id 로 카드를 고른다 — 조각을 앱에 드러내면 원장 · 팩 검사 ·
불변식 · 보고서를 다 손대야 한다. 그래서 조각을 엔진의 run 안에 가뒀다. 계획(`plan`)은 한 장 자리(`card_room` — 판정 · 훑기 자리 중
작은 것)를 넘는 카드를 혼자 한 묶음(`chunked` · 조각 수 어림 `chunks`)으로 내고, 앱은 원래 카드를 그대로 보낸다. run 은 조각(`K12.1` …)마다
보통 run 을 차례로 돌려(`status{chunk, of}`) 카드 한 장의 행으로 합치고(W-D5), 갈리면 인용 둘레(앞뒤 3,000자)만 모아 한 번 더
묻는다(`status{step: reconcile}`). 계획의 선과 run 의 선이 같아(둘 다 card_room) 계획과 실행이 갈리지 않는다. 조각 크기는 한 장 자리의
90%(`CHUNK_SHARE`)이고, 단위가 커서 조각과 함께 창을 넘으면 넘친 만큼 줄여 다시 나눈다(세 번, 바닥 2,000자). 관문 자리는 조각마다 잡고
놓는다 — 조각 사이에 `review_busy` 면 기다렸다 그 조각부터 잇는다(합 900초 안).

**W-D12 계획의 조각 수는 하한에 가까운 어림이고, `CHUNK_SHARE` 는 판에 넣지 않는다.**
계획이 읽는 상수는 `limits_rev` 에 들어야 한다(시험이 대조한다). `CHUNK_SHARE` 를 판에 넣으면 1M 박스의 판까지 바뀌어 모든 셀 지문이
바뀐다 — 1M 에서는 조각이 생기지 않는데 다시 돈다. 그래서 계획은 `ceil(글자 / card_room)` 만 내고(실제는 절 경계 · 틀 몫으로 하나둘
많을 수 있다 — 실제 수는 결과의 `meta.chunked.n`), 조각 상수는 run 에서만 읽는다. 기존 계약 예제 전부가 바이트 그대로인 것으로
1M 동작이 같음을 확인했다.

**W-D13 나눠 부른 결과가 '판정함' 으로 보이는 길을 막는다.**
① 조각 하나가 끝내 실패하면(첫 시도 LLM 실패 등) 받은 조각을 합치지 않고 그 오류(`chunk` · `of` 를 단)로 끝낸다 — 앱이 그 호출을 종전
규칙으로 다시 낸다. ② 보충까지 묻고도 판정 행이 없는 조각이 있으면(solo 의 조건 줄만 냈다 등) 나머지 조각의 OK 로 카드를 세우지 않고
판정 행을 빼 빠진 카드(`missing`)로 낸다(`meta.chunked.unjudged`). ③ 재판정은 `ok` · `failed`(물었는데 답이 안 섰다 — 가장 무거운 판정이
남는다) · `skipped`(갈렸는데 두 쪽 근거를 한 번에 못 실었다)로 적는다. ④ 조각 호출에 모델이 틀 줄의 원래 별칭(`K12`)으로 답하면 그 조각의
답으로 읽는다 — 버리면 세 번 묻고 `no_rows` 로 조각째 실패한다(실제로 재현했다). 원래 카드가 같은 요청에 따로 실렸거나 조각이 둘이면
접지 않는다.

**W-D14 조각 호출의 벽시계는 늘리지 않는다 — 실패한 조각이 그 자리에서 호출을 끝내므로 안쪽 사유가 먼저 선다.**
호출 하나가 조각 수만큼 길어진다(보통 조각당 수 분). 그래도 앱의 벽시계(`HWAXRISK_REVIEW_CALL_TIMEOUT_S` 18,000초)를 조각 수만큼 늘리지
않는다. 조각 하나가 끝내 실패하면 run 이 그 오류로 바로 끝나므로(W-D13 ①) 최악 사슬은 '성공한 조각들 + 실패한 조각 하나(요청 최악 약
10,824초)' 다. 앱 벽시계가 먼저 걸리는 것은 성공한 조각들이 합쳐 7,000초 넘게 걸린 경우뿐이고, 그때도 `review_timeout` 으로 다시 낸다
(조용하지 않다). 벽시계를 늘리면 PAT 수명 여유(벽시계 + 600초)까지 함께 커져 자격 만료로 잡이 서는 일이 늘어난다. 침묵 한도(300초)는
조각 사이에도 ping · status 가 흘러 걸리지 않는다.

**W-D15 카드 밖 · 입력 결손(W2-B) — 훑기에 걸린 카드는 '몫' 이 아니라 '창' 까지 전문으로 싣고, 그래도 넘칠 때만 쪽으로 나눈다(10-21).**
실측(엔진 `limits()`) — 20만 창에서 카드 밖 · 입력 결손 호출의 '몫 안 카드 자리'(본문 몫 − 단위 상한)는 21,497 · 24,648자뿐인데 창이 허용하는
카드 자리는 122,549 · 125,700자(출력 32,000)다. 카드 한 장 중앙값이 2만~5만 자라 지금은 훑기에 걸린 카드 한 장도 몫에 못 들어 제목으로
내려간다(`bg_dropped`). 1M 에서도 몫 안 자리는 12만~14만 자라 큰 전문가는 이미 제목으로 내린다. 그래서 —
① 앱이 호출마다 반드시 전문이어야 할 카드를 `extra.must_full` 로 알린다 — 그 단위의 훑기에 걸린 카드, 그 단위의 훑기 결과가 없으면(훑기
실패) 그 호출의 카드 전부(W-D10).
② 엔진은 `must_full` 카드를 몫이 아니라 창 한도까지 전문으로 싣는다(넘으면 `soft_over` — 판정의 '혼자 넘는 한 장' 과 같은 관대함). 남은
몫 안 자리는 종전처럼 다른 카드를 차례로 채우고 나머지는 제목이다(`bg_dropped` 는 `must_full` 밖 카드만 센다).
③ `must_full` 이 창 한 번에 안 들면 쪽으로 나눠 쪽마다 부른다 — 다른 쪽의 카드는 제목으로 싣는다. 창 한 번보다 긴 카드 한 장은 W1 의
조각으로 쪽에 나눠 싣는다. 결과는 코드로 합친다(카드 밖 f · 입력 결손 q1/q2 는 정체가 같은 줄을 하나로, '없음' 자리 줄은 실제 줄이 있으면
뺀다, more 는 어느 쪽이든 '더 있다' 면 더 있다). LLM 합치기 호출(W-D5 의 둘째 문장)은 두지 않는다 — 쪽마다 다른 카드라 지적이 겹치기
어렵고, 합치기는 새 지적을 못 만드니 얻는 것이 중복 정리뿐인데 실패할 자리가 하나 는다. W5 에서 겹친 지적이 보이면 다시 본다.
④ `must_full` 이 없으면 종전 그대로다. 앱의 호출 캐시는 시도 안에서만 쓰여(같은 시도에 이미 받은 답) 새 칸 때문에 도는 셀이 다시 묻는 것은
배포 때 한 번이다.

**W-D16 단위가 커서 넘치면 단위를 쪼개지 않고 카드를 그 단위에 맞게 조각 낸다(W2-C, 10-21).**
계획(PLAN 2절 C)은 단위를 변경 줄 기준으로 쪽 내는 것이었다. 들여다보니 큰 단위가 멈추는 까닭은 '단위 + 카드 한 장' 이 창을 넘는
것이고(20만 창에서 한 장 자리 안의 카드는 최대 14만 자라, 큰 카드를 가진 전문가는 단위 2만여 자부터 oversize 였다), 카드는 이미 W1 로
조각 낼 수 있다. 그래서 — ① run 은 카드 한 장의 verdict · sweep 이 창을 넘으면(OverBudget) 그 카드를 조각 낸다. 조각 크기는 한 장
자리와 '이 단위와 함께 들 자리'(카드 − 넘친 만큼 − 보충 지적 블록 몫) 가운데 작은 것의 90% 다. 통째로 드는 카드는 조각 내지 않는다(한 장
자리를 넘어도 작은 단위와는 한 번에 — W1 의 '한 장 자리를 넘으면 늘 조각' 보다 호출이 준다). 보충 지적 블록 몫을 남기지 않으면 자리가
좁을 때 보충 시도가 창을 넘는다(시험으로 확인했다). ② 조각 자리가 돌릴 바닥(RUN_FLOOR 1,000자) 밑이면 나누지 않는다 — 아주 작은 조각
수십 개로 부르지 않는다. 자리가 좁으면 조각 틀에서 전체 목차(최대 1,500자)를 뺀다. ③ 계획은 조각을 켠 창에서 단위가 돌릴 바닥만큼의 카드
자리도 못 남길 때만 oversize 다 — 그래서 계획이 '돈다' 고 한 단위는 run 도 돈다(over_budget 은 앱에서 사람 손 보류라 실행에서 처음 알면
안 된다). ④ 카드 밖 · 입력 결손 호출은 종전대로 단위가 홀로만 들면 된다 — 반드시 전문인 카드를 쪽으로도 실을 자리가 없으면(단위가 창을
거의 다 쓴다) 멈추지 않고 제목으로 내리고 `meta.must_dropped` 로 센다. 그 카드는 훑기에서 이미 전문으로 그 단위와 맞대어졌고(W-D10),
남는 빈칸은 W3 원장이 '전문 노출 없음' 으로 드러낸다. 단위 하나가 홀로 창을 넘는 경우(20만에서 14만 자 남짓)만 여전히 oversize 다 —
그때가 단위 쪽 나누기의 몫인데, 운영 단위 크기(W0)를 본 뒤 정한다.

**W-D17 커버리지는 스키마를 올리지 않고 셀의 extras_json 에 적는다 — 놓침은 불변식 G10, 증명 줄은 품질 블록(W3, 10-21).**
계획(F)은 '커버리지 원장(스키마 v6)' 이었다. v6 은 재설계 M4(RA 쓰기)의 몫으로 비워 둔 번호이고, 스키마를 올리면 반출 · 들이기 판
(schema_version) · 굳은 DDL 지문 시험이 함께 움직인다. 그런데 필요한 것은 셀마다 '카드가 어떤 길로 전문으로 읽혔나' 하나이고, 셀에는
이미 JSON 칸(extras_json)이 있다. 그래서 — ① 러너가 카드 밖 · 입력 결손 호출의 마지막 답에서 셀의 커버리지를 적는다
(`extras_json.coverage = {cards, judged, full, swept_only, missed[], hit_title[]}`). 판정은 점검 카드의 실효 판정, full 은 그 셀의
카드 밖 · 입력 결손 호출이 전문으로 실은 카드(엔진 `meta.aliases.cards` — 제목으로 내린 카드는 빠진다 · 쪽 실행도 같은 뜻으로 맞췄다,
8731e19), 훑기 대조는 그 카드의 묶음 × 그 단위의 목록 쪽이 답했고 그 단위가 답에서 빠지지 않은 것이다(sweep_json.gaps · missing_in).
② 셋 다 없는 카드가 놓침(missed)이고 불변식 G10 이 잡는다 — 불변식이 서면 종합의 완결(C1)이 서지 않는다(조용히 닫지 않는다, W-D3).
③ 훑기에 걸렸는데 판정도 호출 전문도 없는 카드(hit_title — 단위가 커서 자리가 없었다, 엔진 must_dropped)는 놓침이 아니다(훑기에서 전문으로
맞대어졌다) — 품질의 '[누락 0 증명]' 줄에 따로 센다. ④ 이 기능 전에 닫힌 셀은 커버리지가 없어 '모름' 으로 세고 G10 이 보지 않는다 —
도는 잡의 옛 셀을 거꾸로 위반으로 만들지 않는다. 거른 셀(na_irrelevant)은 훑기 답으로만 거르므로(G8) 늘 훑기 대조가 있다.

**W-D18 패널 근거 — 압축 줄은 이미 있다(I4 · I5). 긴 절은 인용 둘레로(E1), 좌석은 절 단위 읽기를 늘 쥔다(E2) — 10-21.**
쟁점 패널의 제기 · 반대 측 항목(I4 · I5)이 카드마다 판정 행 한 줄(카드 표지 · 판정 · 인용 원문 · 사유 · 경로)을 이미 싣는다 — 계획 E1 의
'결정적 압축 줄' 이 그것이다. 빈틈은 인용된 카드 절 원문(I6)이 칸보다 긴 절을 통째로 건너뛰는 것이었다(좁은 창에서는 그 카드의 원문이
패널에 하나도 안 실린다). 그래서 E1 은 절이 I6 칸의 1/3(바닥 400자)을 넘으면 인용 둘레만 싣고(`절 n자 가운데 인용 둘레 m자`), 몇 절이
원문 · 인용 둘레 · 원문 없음 · 칸에서 빠짐인지 브리프 meta 에 센다(`cited_sections`). E2 는 새 도구를 만들지 않는다 — AIDataHub 의
`get_record_sections(record_id, sections=[절])` 가 절 단위 읽기이고 읽기 전용 접두사(get_)라 자유 조회 검문을 지난다. 리스크 심사의 앱
제한(어댑터 앱)에서 잘려 나가던 것을 유지 도구(_RISK_KEEP_TOOLS)에 넣고 좌석 도구 순위 맨 앞에 세운다(27d7d8c). 좌석의 조회 단계는
근거 발췌에서 `[card:<record_id>#<절>]` 표지를 보므로 따로 안내 문구를 더하지 않았다(프롬프트 지문 불변). Claude 길의 패널은 자유 조회가
없어 이 통로가 닿지 않는다 — Claude 길을 20만으로 쓸 때 다시 본다.

**W-D19 호출 어림의 20만 보정은 실측(W5) 뒤로 미룬다.**
앱의 호출 어림(`calls_estimate`)은 이 박스의 마지막 계획에서 묶음당 카드 수(k)를 읽어 판정 묶음 수를 셈하므로 창이 작아져 k 가 줄면 이미
따라 는다. 더해지는 것 — 조각(카드당 2~5) · 쪽(넘친 셀의 카드 밖 호출) · 재판정 — 은 카드 길이 분포와 훑기 걸림 비율에 달려 dev 표본으로는
배수를 못 박는다. W5(cae00 A/B)에서 실제 호출 수를 재 그 배수로 보정하고, 그때 '카드가 아주 많은 전문가는 맨 뒤 · 어림 따로'(W-D9)도
같은 수로 가른다(지금은 잡 시작 때 그 전문가의 카드 수를 모른다 — 팩은 세션이 열 때 받는다).

**W-D20 요약 계층(map-reduce, PLAN 2절 D)은 미룬다 — 카드 누락이 아니라 서술의 질이고, 넘치면 이미 '코드 조립본' 으로 드러난다.**
영역 · 종합 요약의 입력은 지식카드가 아니라 등록부 행(걸림)이다. 20만 창에서 요약은 몫(본문 89,600자)을 넘어도 창 한도(약 16.4만 자 —
행 400자면 400행 남짓) 안이면 그대로 돌고(soft_over), 창마저 넘는 영역만 over_budget 으로 LLM 요약 대신 서술 없는 코드 조립본이 되고, 보고서에 '서술 없이 코드 조립본이다 — 까닭' 이 적힌다(조용하지 않다). 등록부의
행은 그대로 다 보고서에 있다. 그래서 '모든 카드를 본다' 는 목표(G1)와는 떨어져 있고, 새 호출 종류(부분 요약 · 합치기)와 꼭 다룰 행 추적을
더하는 일이 크다. W5(cae00)에서 영역마다 행 수를 재 보고 몫을 넘는 영역이 흔하면 그때 만든다.

**W-D21 1M 에서도 바뀌는 곳을 밝힌다 · E1 은 칸이 모자랄 때만 줄인다(검증 중 고침, 10-21).**
'1M 박스는 동작이 그대로다' 는 엔진의 계획 · 판 · 계약 예제(바이트 그대로)에는 맞지만 앱까지 이은 동작에는 다 맞지 않았다. 1M 에서도
달라지는 곳 — ① 카드 밖 · 입력 결손 호출에 앱이 `must_full` 을 보낸다(엔진이 features 로 알리므로). 훑기에 걸린 카드가 몫 안 자리(1M 에서
약 12만~14만 자)에 다 들던 칸은 프롬프트가 같고, 넘던 칸은 예전에 제목으로 내리던 카드를 이제 전문으로 싣는다(토큰이 는다 — 잘라내지 않는다는
1M 원칙 쪽이다). 훑기가 실패한 칸은 그 묶음의 카드가 반드시 전문이 된다. ② 50만 자 남짓 넘는 단위는 보류 대신 카드를 조각 낸다(W-D16).
③ 리스크 심사 좌석의 도구 순위에 `get_record_sections` 가 맨 앞에 선다(E2 — 얹지 않고 순위만, 도구 예산이 빠듯하면 맨 뒤 하나가 밀린다).
④ E1 을 처음에는 'I6 칸의 1/3 을 넘는 절은 늘 인용 둘레로' 로 지어 1M 에서도 원문이 다 들어가는 긴 절을 잘랐다 — 1M 에서는 잘라내지
않는다는 지침(10-10)에 어긋나는 회귀였다. 이제 인용된 절의 원문이 I6 칸에 다 들어가면 그대로 싣고, 넘칠 때만 긴 절을 1/3 로 줄인다
(넘칠 때는 종전에도 뒤의 줄이 빠졌다 — 그 대신 더 많은 절이 서게 한다). 시험이 두 경우를 함께 본다.
