## CK-3 SRC-15 — REST 다리의 정해진 쓰기 경로에만 단언을 싣는다. MCP 길과 GET 은 그대로 둔다

- `per_user_sso.step_forge` 를 그대로 켜면 REST 다리만이 아니라 StepForge 의 MCP 호출 전부(도구 94)가 사람별 세션으로 바뀐다.
  게이트웨이의 MCP 목록 · 호출 갈래가 그 표를 함께 보기 때문이다. 운영 중인 앱의 신원 모델이 통째로 바뀌는 일이라 하지 않는다.
- REST 다리의 StepForge 칸을 통째로 사람 명의(`per_user`)로 바꾸면 읽기(GET)도 사람 명의가 된다. 그러면 리스크 앱 캡처처럼 지금 서비스
  계정으로 읽는 흐름의 보이는 범위가 바뀐다. 그래서 GET · HEAD 는 지금처럼 서비스 토큰(`inject`)으로 둔다. 정해진 쓰기 경로
  (`write_paths`)만 단언을 싣고, 그 밖의 쓰기 메서드는 405 로 막는다.
- 요청서가 물은 '셋만 여는 것' 이 이 꼴이다. 메서드를 사이트마다 여는 지금 규칙(`allowed_methods`)을 경로까지 좁힌다.
- 버린 것 — MCP 적용(`onto_link(dry_run=false)`)을 사람 단언으로 받는 길. 챗에는 더 자연스럽지만 StepForge 의 MCP 계층이 요청 머리를
  읽어야 하고, 게이트웨이의 StepForge MCP 세션 모델이 바뀐다.

## CK-4 SRC-13 — 서비스 신원은 패널 PAT 꼴을 베낀다

- 지금은 서비스 신원이 없다. 게이트웨이 공유 토큰(GW_TOKEN)은 `x-hwax-user` 를 믿어 아무 사람으로나 행세할 수 있다. 포털 `/internal/*`
  등도 연다. 그래서 박스 작업에 내줄 수 없다.
- 패널 PAT(청중 `mcp-app-panel` · `purpose` · jti 접두 · 꼴 전체 검사)가 가장 가까운 선례다. 새 청중 `mcp-gateway-service` 로 두면 포털 챗 ·
  REST 프록시 · 그림 받기 · 옛 게이트웨이가 모두 이 토큰을 거절한다. 실수로 다른 데 쓰여도 열리지 않는다.
- 사람 신원을 싣지 않는다(`x-hwax-user` 없음). 그래서 사람별 위임 앱(리스크 · MX 백서 · DynaForge · ste)은 서비스 계정으로 불린다.
  허용 목록에 넣을지는 운영자가 정한다. RA · TestScope 는 서비스 세션이 실제 사람의 토큰이라 허용 목록에 넣지 않는다고 적어 둔다.
- 허용 목록은 게이트웨이 박스 파일(`service_tools.local.json`, gitignore)이다. 포털을 거치지 않고, 집행이 이미 푸는 `백엔드:원래 이름` 키를
  그대로 쓴다. 다시 읽기는 `read_tools.local.json` 과 같은 mtime 꼴이다.

## CK-5 SRC-14 — 쓰기 낱말 셋(link · edit · sync)과 읽기 목록 둘

- 목록 규칙(`_WRITE_NAME`)에 `unlink` 는 있고 `link` · `edit` · `sync` 는 없었다(93cda53, 10-28). 일부러 뺀 기록은 없다.
- 울타리가 열린 것은 아니었다. 읽기 토큰 · 루틴 · 패널은 모두 '모르면 막는다' 라 이 도구들을 막았다. 빈 곳은 운영자 동기화의 '목록 밖
  쓰기' 알림이었다(write − routine_read). 이 도구들을 짚지 못해 챗 확인 카드에 올릴 기회가 없었다.
- dev 카탈로그에서 셋을 더하면 새로 걸리는 읽기는 ste `get_sync_settings` 하나다. 이것은 읽기 목록에 넣어 루틴 · 읽기 토큰을 지킨다.
  tools-map `write` 에는 남는데(이름 규칙은 읽기 목록을 보지 않는다), 이는 AIDataHub `get_record` 셋과 같은 지금의 꼴이다.
- DynaForge `plan_task_links` 는 쓰지 않는 미리 보기다(GET). 쓰기로 만들지 않고 읽기 목록에 넣는다.
- cae00 에만 있는 앱은 dev 에서 대조할 수 없다. 받은 편지함에 update-all 앞뒤의 tools-map `routine_read` 차이를 보라고 싣는다. 새로 쓰기가
  된 도구는 막는 쪽으로만 움직인다(루틴에서 빠진다).

## CK-6 SRC-12 — 끝맺음 뒤, ○ 요약 앞, 줄은 따로

- 자리는 끝맺음 셋(비우기 · 새 심의 멈춤 · 상태판 경보) 뒤, `hwax_skip_summary` 앞이다. 모든 배포 뒤이고 ○ 가 요약에 든다. § 머리(`hr`)는
  부르지 않는다. 남의 비우기 깃발이 있으면 그 틱이 새 깃발을 세우는데 내릴 곳이 없다.
- 실패는 `fail`(종료코드)도 `bad`(경고 수)도 아닌 따로 줄이다. 요청서가 '종료코드에 섞지 않고 요약에 줄 하나로 따로' 라 했다.
- 바쁨은 사전 점검과 update-all 이 이미 쓰는 셈을 그대로 쓴다 — 에이전트 `/health` · DynaForge 로컬 작업 · StepForge(pending · running) ·
  DocForge(queued · running). MX 백서 위키 작업은 lease 로 이어 집으므로 넣지 않는다. 셀 수 없으면 '바쁘다' 와 같이 건너뛴다(모름 ≠ 없음).
- 훅 파일은 `.gitignore` 로 지킨다. 지금은 무시 규칙이 없어 §1 · deploy-all 의 `git stash -u` 가 치운다. 이 판을 받기 전에는 훅이 없으니
  첫 실행 문제(옛 .gitignore 로 도는 §1)는 생기지 않는다. 훅은 이 판을 받은 뒤에 만든다.

## CK-8 챗 쪽 — 쓰기 메서드의 rest_call 은 늘 카드, StepForge 운영자에게 rest_call 을 입구로 묶는다(에이전트 서버 가지 wt1109/core-link)

- 관문(HA-29)은 이름만 봤다. 그래서 `rest_call` 의 POST 에 카드가 서지 않았다. 이제 메서드가 GET · HEAD 가 아니면 운영자 목록보다 먼저
  `confirm` 부류다(주문 낱말 · 핀으로 지나가지 않는다).
  - 메서드를 읽는 규칙은 게이트웨이 `_rest_call` 과 같다. 비었거나 공백이면 GET 이다.
  - 카드에는 사이트 · 메서드 · 경로 · 본문 앞 400자, 그리고 있으면 `query=` 를 싣는다. DELETE · PUT 의 대상이 query 에만 있을 때도 카드에
    보이게 하려는 것이다.
- StepForge 운영자를 고르면 StepForge 도구가 입구 상한(dev `TOOL_MAX=40`)을 채워 `rest_call` 이 묶이지 않았다. 그래서 앱 키 `heax-step_forge`
  에 `rest_catalog` · `rest_call` 을 입구 도구로 붙인다. 입구 도구는 상한과 예산 자르기를 넘긴다.
  - 운영자 정의(`he-team.json` 의 `key_tools`)가 아니라 에이전트 서버 표다. 동기화가 그 앱의 것이 아닌 `key_tools` 를 막는다.
  - 심의 좌석 · 띵킹에는 붙지 않는다.
- 게이트웨이 `/tools-map` 에는 `rest_call` 이 없어 카드에 앱 꼬리표가 없다. 승인 때의 '같은 앱인가' 대조도 `rest_call` 은 건너뛴다. 그대로 둔다 —
  대상은 `site` 인자(카드에 보인다)이고, 게이트웨이가 쓰기 경로와 신원을 한 번 더 막는다.

## CK-10 박스 훅 적대 검토 1차 — 훅은 제 세션에서, Ctrl-C · 종료 요청은 훅만 끊고 요약으로(가지 a5ff0f2b)

막는 결함은 없었고 작은 결함 다섯 · 시험 빈틈 여섯이 나왔다. 재현한 것만 고쳤다.

- `timeout --foreground` 는 훅을 update-all 과 같은 프로세스 묶음에 둔다. 그래서 훅의 `kill -INT 0` 이 본문을 130 으로 끝내 종료코드가
  FAIL 을 따르지 않았다. `kill 0`(TERM)이면 STOP 이 섰다(재현). 이제 `setsid` + `--foreground` 없는 `timeout` 으로 띄우고 `wait` 로 기다린다.
  상한은 그 묶음을 통째로 끝낸다(TERM, 삼키면 10초 뒤 KILL).
- 표식으로 거두던 `_reap_step` 은 걷었다. 훅의 마지막 명령이 스스로 124 를 내면, 일부러 띄운 데몬까지 죽였다(재현). 상한 판정은 걸린
  시간도 본다.
- 훅 도중 Ctrl-C 는 끝 요약을 통째로 잃었다(재현). 이제 훅이 도는 동안만 INT · TERM · HUP 을 받아 그 훅을 끊고, 남은 훅을 건너뛴 뒤
  요약을 낸다. 종료코드는 배포 결과(FAIL)다 — 배포는 이미 끝났다. update-all 의 트랩은 되돌린다.
- 훅이 update-all 의 조율 변수(`HWAX_DELIB_PAUSE_BY=update-all` 등)를 물려받았다. 그래서 훅이 부른 update-sites 가 'update-all 의 멈춤' 을
  세우면 끝맺음이 이미 지나 내릴 곳이 없었다(코드 읽기). 이제 걸러 넘긴다.
- DynaForge 셈에 30초 상한을 둔다(사전 점검과 같다).
- 시험 11개를 더해 살아남던 변이 여섯을 잡는다. 이름이 틀린 훅 경고는 대개 보이지 않는다(§1 stash 가 먼저 치운다) — README 에 되찾는
  법을 적었다.

## CK-11 서비스 PAT — 화면 · 원장 · 게이트웨이에서 정한 것(포털 가지 wt1109/core-link-svcpat · 게이트웨이 가지 wt1109/core-link)

- **원장.** `note` 칸도 더했다(목록에 메모를 보이려고). 시각은 기존 PAT 처럼 epoch 초다.
- **화면.** 관리자 칸은 토큰 화면의 따로 탭이고 '외부 연결' 앞에 둔다(e2e 가 마지막 탭을 외부 연결로 본다).
- **exchange · 챗.** 서비스 청중이라 둘 다 청중 검사에서 먼저 거절된다. 패널 PAT 처럼 따로 purpose 가드를 더하지 않고, 기본 청중에 서비스
  청중이 없다는 것을 시험이 못 박는다.
- **발급한 관리자를 정지해도 그 서비스 토큰은 살아 있다.** 박스 작업의 것이라 사람과 수명을 같이하지 않는다. 목록에 `issued_by` 가 있어
  다른 관리자가 회수한다.
- **남은 빈 곳.** 이용 통계(`/admin/usage`)는 서비스 PAT 를 '개인' 으로, 주인을 `system:<작업>` 으로 센다. 따로 셀지는 쓰임을 본 뒤 정한다.
- **게이트웨이.**
  - 서비스 토큰에는 resources · prompts 를 내주지 않는다(허용 목록이 다루지 않는다 — 막는 쪽).
  - 작업 허용 목록의 RA · TestScope 도구는 읽을 때 버리고(⚠), 부르면 `service-denied(impersonation)` 이다. 그쪽 서비스 세션은 실제 사람의
    토큰이다.
  - 감사 꼬리표는 `svc:` + jti 의 `svc-` 뒤 8자다.
  - jti 접두(`svc-`)는 '서비스 토큰이라 주장한다' 의 방아쇠에서 뺀다. 사람 PAT jti(`token_urlsafe`)가 그렇게 시작할 확률이 약 6e-8 이라,
    그 토큰이 영영 401 을 받는다. 접두는 꼴 검사에만 남긴다.

## CK-12 STEPFORGE_SSO_SECRET 은 provision.env 에, update-all 이 넘기고 어긋남을 본다(가지 f2930226)

- 다른 provision.env 손잡이처럼 §5 가 소싱한 값을 재프로비저닝 대입 사슬에 싣는다. 비밀이 있는데 게이트웨이 칸(`rest_sso.step_forge` ·
  `rest.step-forge` 의 `delegate` · `write_paths`)이 없거나 다르면 재프로비저닝하고, 뒤에서 다시 본다.
- 허브가 있는 박스에서 비밀이 없으면 ○ 를 남긴다. 그때 챗의 StepForge 적용 · 박스 작업의 규칙 잇기는 꺼져 있다(미리 보기는 된다).

  지운다(절차서).

## CK-14 StepForge 답(11-09) — 위임 비밀 따로 · 쓰기 경로 다섯 · 서비스는 셋만 · 훅은 plm-sync 하나

- StepForge 세션이 그쪽 R2(온톨로지 쓰기 적용은 포털 신원 길만)를 바꾸는 일이라 그쪽 사용자에게 한 번 더 물었고, 같은 답이었다.
- **위임 비밀은 `secrets.env` 의 새 줄 `STEPFORGE_SSO_SECRET`** 이다. 기존 `STEPFORGE_GATEWAY_SECRET` 은 포털 신원 검증용(허브
  `gateway_shared_secret`)이라 섞지 않는다. 섞으면 허브가 그 머리를 싣지 않는 박스에서 웹 화면 적용이 깨진다.
- **쓰기 경로는 다섯**이다(onto-link · onto-put · onto-define · onto-fill · plm-sync). 뒤의 둘은 이번에 새로 둔 고정 경로다.
  - `onto-fill` 은 지금 잡 걸기가 과제 경로라 따로 두었다.
  - `plm-sync` 는 포털이 청했다. 훅이 MCP `run_job` 을 쓰면 허용 목록이 도구 단위라 같은 토큰으로 mesh · pipeline 도 걸 수 있었다.
    경로 한 줄이면 허용이 받기 하나로 좁혀진다.
- **서비스 단언은 셋만** 받는다. plm-sync(대량 소실 넘기기 `allow_mass_absence` 는 막음), 규칙 단 onto-link, 증명 규칙 onto-fill 이다.
  strong 자동 확정 규칙은 사람만 돌린다. 거절 코드는 틀린 단언 401 · 허용 밖 403 · 그 밖의 도구 거절 400 이다.
- **박스 훅은 plm-sync 하나로 준다.** 규칙 잇기(SRC-03 · 04 · 05)는 앱 안에서 받기 · 파싱 · 대응 잡 뒤에 스스로 돈다. 서비스 단언의 onto-link ·
  onto-fill 은 훅이 규칙 단 선을 바깥에서 직접 이을 때만 쓴다.
