# 여러 전문가를 한 목소리로 — 계획과 근거

사용자 요청(2026-09-12): "둘 이상의 전문가를 선택하고 챗하는 것 — 도구 특화와 전문지식을
조합해서 한 명으로서의 의견이 되게. 최대 5명. 유효성부터 생각해봐."

## 유효한가 — 그렇다, 단 조합을 제한해야 한다

- **값이 나는 조합은 '도메인 전문가 + 도구 운영자'다.** 열충격 SED 운영자는 predict_sed 를
  어떻게 부르는지 알지만, 그 결과가 이 제품에서 위험한지는 신뢰성 전문가가 안다. 지금은 둘 중
  하나만 고를 수 있어 운영자를 고르면 해석이 얕고 전문가를 고르면 도구를 못 썼다.
- **같은 층을 여럿 겹치면 해롭다.** 도메인 전문가 3~5명을 한 목소리로 합치면 모델이 평균을 내
  각자의 날카로운 판단이 일반론으로 무너진다. 더 나쁜 건 **갈리는 의견을 한 목소리가 숨기는
  것**이다(거짓 합의). 갈리는 것을 세우는 자리는 심의다.
- **예산이 실제로 부딪힌다.** 역할 문서 4,000자 × 5 = 2만 자가 도구 스키마 앞에 깔리고,
  운영자 1명이 앱 하나(11~81개 도구)를 끌고 온다. TOOL_MAX=40·스키마 예산 12,000 이고
  dev 16K 에서는 77개로 이미 400 이 났다. 이 시스템 실측으로 '상위 40개가 호출의 79%'라
  도구를 늘릴수록 선택 정확도가 떨어진다.

## 형태

| 자리 | 인원 | 하는 일 |
|---|---|---|
| 주 전문가(lead) | 1 | 답의 목소리·판단 기준. 지식카드 선조회도 이 사람 것 |
| 보조 | ≤4 | 운영자면 앱 도구·입구 도구를, 도메인 전문가면 역할(판단 기준)만 빌려준다 |

- 상한은 5명(PERSONA_MAX)이되 **실효 제약은 앱 3개·도구 캡**이다.
- 보조의 역할 문구는 1,200자로 줄여 싣는다(PERSONA_HELPER_ROLE_MAX) — 전문을 실으면 도구
  스키마 예산을 그만큼 밀어낸다.
- 보조의 지식카드는 **선조회하지 않는다**. 필요하면 모델이 agent_search("<키>", 질의) 로
  직접 부른다(선조회하면 사람 수만큼 지연·예산이 곱해진다).
- 답은 한 목소리다. 다만 **갈리면 숨기지 않는다** — 끝에 '이견: …' 한 줄을 붙이고, 판단이
  갈려 결론을 못 내면 '/심의' 를 권한다. 이게 거짓 합의를 막는 장치다.

## 계약

- 에이전트서버 `ChatRequest.pinned_agents: list[str]` — 첫 명이 주 전문가. 구 계약
  (`pinned_agent` 하나)도 그대로 받는다(`_persona_keys` 가 둘을 합쳐 정규화).
- 포털 `ChatRequest.pinned_agents` (≤5) → agent_guard 가 **각자** 권한을 본다. 한 명만
  검사하면 못 쓰는 운영자를 둘째 자리에 끼워 그 앱 도구를 얻을 수 있다(우회).
- 프론트는 대화/드래프트에 `pinnedHelpers` 로 영속하고, 보낼 때 [주, ...보조] 로 싣는다.

## 남은 것

- MCP(클로드) 쪽 선택 — 프로토콜에 UI 표면이 없다. `prompts/list` + `completion/complete`
  (슬래시 명령 + 인자 자동완성)이나 `browse_experts` 텍스트 도구로 같은 일을 할 수 있다.
- 조합 추천(이 질문엔 누구+누구) 은 아직 없다 — 사람이 고른다.
