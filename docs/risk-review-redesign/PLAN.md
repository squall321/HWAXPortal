# 리스크 심사 재설계 — 전 전문가가 자기 지식카드 전부로 검토한다

> 2026-10-09 세움. 구현 전이다. 대조 시점의 코드는 HWAXRisk `7248651` · HWAXAgentServer `7683125` · HWAXPortal `00d5565` 다.
> 이 문서가 가장 위다 — 이 문서 > [problems.md](problems.md) > [reference/04-contract.md](reference/04-contract.md) > `reference/spec-*.md` 순으로 이긴다.
> 결정과 그 까닭은 [context-notes.md](context-notes.md), 할 일은 [checklist.md](checklist.md) 에 있다.

## 1. 무엇을 왜

사용자의 목표는 넷이다(말 그대로).

- "변경점이 많이 있으면 그 과제를 영역별로 분석하게끔 하고 싶었다."
- "모든 전문가들에게서 다 디테일한 보고서가 나오게 하고 싶었다."
- "모든 전문가에 대한 지식카드를 이용해서 대답하게" 한다.
- "리스크 심사는 모든 전문가가 고려할 수 있는 리스크를 최대한 고려해주는게 중요하다."

지금 구조는 이 목표와 어긋난다(코드를 읽고 반박 검증한 것이고, 표시한 것은 실행으로 재현했다).

| 지금 | 무엇이 문제인가 |
|---|---|
| 같은 과제의 두 번째 패널부터 저장이 실패한다(실행 재현) | 매 패널에 앉는 지정 반대석의 의견이 중복 제약에 걸린다. 패널이 `running` 에 굳고 그 과제는 재기동까지 멈춘다 |
| 모든 패널이 같은 질문·같은 변경 요약을 받는다 | 변경이 수백 건이어도 좌석에 닿는 것은 6~12건이고 나머지는 '…(N줄 생략)' 이다 |
| 잘리는 순서가 부호 있는 크기순이다 | 얇아짐·간극 축소 같은 감소 변화가 먼저 잘리고, 설계와 무관한 격자 수 증가가 앞에 선다 |
| 치수·결과 칸과 좌석 기억 칸이 비어 나간다 | 값을 찾는 자리와 좌석 이름 필드가 어긋나 있다 |
| 좌석 선정이 변경 내용을 보지 않는다 | 변경이 어디에 몰렸든 편성이 같다 |
| 좌석당 지식카드는 검색된 몇 줄뿐이다 | 한 전문가의 카드 전부(평균 57,000자)의 6% 남짓이고, 검색어에 변경 내용이 없다 |
| 인용한 카드가 실재하는지 확인하지 않는다 | 카드 번호를 적기만 하면 근거 등급이 '문헌·규격' 으로 오른다 |
| 기본 완료 기준이 114명에서 끝난다 | 359명 가운데 32% 다. ECAD 가 없으면 회로 110명 중 104명은 아예 앉지 않는다 |
| 산출물이 전문가 단위가 아니다 | 보고서는 의장이 뽑은 리스크 묶음 단위이고, 전문가별 보고서는 없다 |

재 본 값(dev AIDataHub, 2026-10-08)은 이렇다.

- 심사 대상 전문가 359명(15개 영역), 지식카드 10,774장. 전문가당 30장 안팎(0장 3명 — `material-twin-analyst`·`sim-structural-calc`·`sim-thermal-sed`).
- 한 사람의 카드 전부는 평균 57,072자·최대 91,780자다. 도구 없는 단독 호출이면 한 번에 들어간다. 토의 좌석의 근거 예산(약 18,000자)에는 들어가지 않는다.
- 점검형 카드(설계 규칙·실패 사례·규격 요약)는 약 43% 다(전문가당 약 13장).
- 논문·특허·규격 약 28,700건은 건당 4만~10만 자라 검색으로만 쓴다.

## 2. 목표 구조

일의 단위를 패널에서 **(전문가 × 검토 단위)** 로 바꾼다. 검토 단위는 변경을 부위·계면으로 묶은 것이다.

| 단계 | 하는 일 | 누가 |
|---|---|---|
| 0. 변경 정리 | 전 변경을 빠짐없이 검토 단위로 나눈다(잘림 0·미배정 0). | 코드 |
| 1. 전수 훑기 | 전문가가 자기 카드 전부와 전 단위를 본다. 배경 카드가 전문으로 읽히는 자리다. | 전문가 혼자, 도구 없는 호출 |
| 2. 카드 대조 | 점검형 카드를 6~8장씩 끊어 카드마다 적용 여부와 준수 여부를 적는다. 카드 문구와 변경을 함께 인용한다. 카드에 없는 리스크는 따로 적는다. | 전문가 혼자 |
| 3. 검증 | 인용한 카드가 그 호출에 실은 카드인지, 인용 문구가 원문에 있는지 대조한다. 빠진 카드는 다시 묻는다. | 코드 |
| 4. 전문가별 보고서 | 전문가의 결과를 한 건으로 묶는다. | 코드 |
| 5. 쟁점 토의 | 판정이 갈리거나 영역이 만나는 곳만 지금 방식의 패널로 토의한다. | 그 쟁점에 걸린 영역 |
| 6. 종합 | 영역별 요약 → 과제 종합 보고서. 무엇을 못 봤는지를 수치로 싣는다. | 코드와 의장 |

토의를 잘게 나누는 것은 답이 아니다 — 빠짐없이 고려하는 것은 토의가 아니라 대조에서 나온다. 제 안을 보지 않고 따로 설계한 쪽도 같은 구조로 왔다([reference/02-rival.md](reference/02-rival.md)).

## 3. 마일스톤

설계서 일곱 편을 그대로 따르면 걸음이 120개(겹친 것을 합쳐 107개)이고 사용자가 새 흐름의 첫 보고서를 읽는 것이 7~8주째다. 그래서 순서를 꾸러미가 아니라 마일스톤으로 잡는다. 원칙은 셋이다.

- 재는 것이 만드는 것보다 먼저다. 호출 시간·글자/토큰 비·단위 수는 전부 가정이고 한 번도 잰 적이 없다.
- 사용자가 '이것이 원하던 상세 보고서인가' 를 답하는 시점(M2)을 가장 빨리 낸다.
- 문제를 막는 장치(선저장·복구·잠금·인용 재대조·정직한 수치)는 앞에 두고, 호출 수를 줄이는 장치와 검증 안 된 단계는 잰 뒤로 보낸다.

걸음 이름은 설계서의 것이다(예: `WP1 S2` 는 `reference/spec-wp1-repairs.md` 4절의 S2).

### M1 지금 패널이 제대로 돈다

뒤 단계 없이도 값이 있고 가장 먼저 나간다. 꼭 필요한 걸음은 이렇다.

- 시험 바닥 — `WP5b C1·C2·C3·C4`(합성 다건 변경 생성기는 `app/devseed.py` 한 벌이고 `WP1 S0`·`WP2 1` 과 같은 것이다).
- 리스크 앱 — `WP1 S1~S14·S17` 과 `S15` 가운데 `raised` 분기만. `WP4 0a·0d`. `WP5a R1·R2·R3·R10`.
- 에이전트 서버 — `WP1 E1·E2·E3·E4`.
- 포털 — `WP1 P1·P3`, `WP5a P2`.

설계서에서 바꾸는 것(반대 검토 반영)은 이렇다.

- **두 번째 패널 수리를 끝까지 한다.** 원장 밖 좌석의 회차는 `100000 + panel_no` 다. 발언이 0건인 원장 좌석은 의견 행을 만들지 않고, 옛 발언 0 행이 남은 DB 에서도 재착석 저장이 돼야 한다(WP1 `P-01`).
- **같은 과제의 두 번째 리비전에서 브리프가 죽는 결함을 같이 고친다.** 선례 줄 앞의 접두 때문에 판단어 검사에 걸린다(WP1 `P-03`). 운영 경로에서는 검사 위반이 나도 죽지 않고 그 줄을 방패로 싸서 싣고 기록한다.
- **프롬프트 문구는 M1 에서 바꾸지 않는다.** 좌석 계약의 카드 인용 문장(`S16·E5·P2`)과 카드 묶음 배선은 M2 로 미룬다. 대신 '확인 안 된 카드 인용은 등급을 올리지 못한다' 만 넣는다. 세 리포의 같은 날 변경과 파리티 상수를 건드리지 않게 된다.
- **스키마 v3 는 `rr_panels` 의 세 열뿐이다**(`result_gz·result_hash·result_saved_at`). 보고서 저장 열은 넣지 않는다.
- **포털 선언은 한 번에 맞춘다.** `knowledge_query` 는 `str | dict[str, str] | None`, `save_report` 도 같이 선언한다(쟁점 패널이 패널마다 RA 보고서를 만들지 않게).
- 그 밖의 WP1 문제 `P-02·P-04~P-20` 은 M1 을 시작할 때 걸음의 수용 기준으로 옮긴다.

나갈 기준.

- dev — 합성 다건 변경 타깃에서 패널 셋이 연속 `done`. 이름에 판단어가 든 부품으로도 `brief_error` 0. 변경 목록에 실명과 값이 실리고 감소 변화가 앞자리에 있다. 저장 실패 → 다시 저장 → `done`. 세 리포 시험 전체 통과.
- cae00(사용자) — `schema_version: 3`, 실제 타깃에서 영역별 대표 세 패널이 `done`.

### M2 한 과제에서 전문가 몇 명이 카드 대조를 끝까지 돌고 보고서가 나온다

- 에이전트 서버 — `WP3a 1~7`(새 모듈 `card_review`, 엔드포인트 `limits·pack·plan·run`, 호출 종류는 `sweep·verdict·offcard` 셋).
- 포털 — `WP3a P1`(중계 넷).
- 리스크 앱 — `WP2 2·3·4·6·7(동결 발췌만)·11` 과 `9` 가운데 순서 함수만. `WP3b 1·3~11`. `WP5a R5` 의 최소분. 품질 수치 모듈의 격자·카드·절단·인용·뒤집힘·호출 초.
- 시험 — `WP5b C5·C7·C8·C9·C15`.

쓰지 않는 것 — 관련성 신호와 거르기, 현황 타깃의 단위, 근거 꾸러미의 실호출, 입력 결손 호출, 2차 영향, 긴 문서 검색, 전원 포함, 쟁점·종합 전부, 비우기, 밤 창, 지표.
실행 설정 — 훑기 켬, 거르기 끔(모든 셀이 대조로 간다), 순서를 뒤집은 이중 판정 전량.

나갈 기준(cae00 실제 변경 비교 타깃 1건, 영역별 대표 가운데 입력 결손이 아닌 9명 × 검토 대상 단위 전부).

1. 격자가 완전하고 `reviewed` 셀에 카드 누락 0·절단 0 이다.
2. 저장된 판정의 카드는 전부 그 호출에 실은 카드이고, 대조 통과 인용은 얼린 원문에 있다.
3. 포털 대화 목록에 새 대화가 없다. 도는 중에 앱을 한 번 내렸다 올려도 차감 없이 스스로 이어 돈다.
4. 전문가 보고서 9편이 읽힌다. **사용자가 3편을 읽고 인용 10개를 카드 원문과 대조한 뒤 '이 형식이 원하던 상세 보고서인가' 를 답한다.** 아니면 보고서 조립을 고치고 M3 로 가지 않는다.
5. 실측표를 갱신했다 — 호출 초, 셀당 호출 수, 뒤집힘 비율, 양성 비율, 훑기의 '무관' 비율, DB 증가분, 그동안의 챗 첫 응답 지연.

### M3 전원·쟁점 토의·종합

- 리스크 앱 — `WP2 9`(전원 포함·입력 결손·보류 해제)·`7`(실호출)·`12`. 실패 셀 처분 REST. `WP4 1·2·3(택소노미 1.1 만)·7·8·9·10·12(도구 둘)·14`. `WP5a R7`(상한·동의·다시·넘김)·`H1`. `WP5b C10~C12·C14·C16`.
- 에이전트 서버 — 입력 결손 호출(`noinput`), `WP3a 8`(긴 문서 검색 — 카드 0장 3명), 요약 호출 한 종류. `WP5a A1·A2·A3`(관문·`/drain`).
- 포털 — `WP5a P1`(update-all 비우기)·`P3·P4`.

나갈 기준(cae00 실제 타깃 1건, 359명 전원 — 회로 110명은 입력 결손 두 질문이고 보고서가 그 사실을 적는다).

1. 모든 셀이 종결이거나 사유 있는 `failed` 다. 그 수와 사유가 종합 보고서 머리에 있다.
2. 전문가 보고서가 359편이다.
3. 쟁점 패널이 상한 안에서 전부 끝났고 상한 밖은 '미토의 쟁점' 으로 보고서에 있다.
4. 영역 요약 15건과 종합 보고서가 있고 그 수치가 완결 판정과 같다.
5. 완결 표기가 잔여(입력 결손·실패·사람 넘김·미토의·2차 영향 미실행·결손 사냥 미실행)를 달고 나온다. 잔여가 있으면 맨 `C3` 로 적히지 않는다.
6. 도는 중에 update-all 한 번이 비우기로 지나가고 심사가 이어 돈다. 챗 첫 응답 지연이 평소의 2배 안이다.

### M4 잰 뒤에 정한다

관련성 신호·거르기·'해당 없음' 표본 재검토, 2차 영향, 결손 사냥, 현황 타깃의 단위, RA 저장, 지표, 쟁점 패널 자동 재개, AIDataHub `get_agent_cards`, 밤 창, 기본값 켬.

## 5. 이번에 빼거나 미루는 것

| 무엇 | 처분 | 까닭 | 잃는 것 |
|---|---|---|---|
| 변경→영역 신호와 훑기 거르기 | M4 | 호출 수를 줄이는 장치인데 줄어드는 양을 잰 적이 없다 | 호출이 는다(빠짐은 줄지 않는다 — 더 본다) |
| '해당 없음' 표본 재검토 | M4 | 거르기가 꺼져 있으면 모집단이 0 이다 | 없음 |
| 2차 영향·결손 사냥 | M4 | 방법이 검증된 적이 없고 상한이 추정이다 | 영역 간 영향을 체계적으로 되묻지 않는다. M3 는 넘김 줄과 메커니즘 집계를 표로만 싣고 '미실행' 잔여로 적는다 |
| 현황 타깃의 단위 | M4 | 목표는 '변경이 많을 때' 다 | 현황 타깃은 옛 흐름으로만 심사한다 |
| RA 저장 | M4 | RA 쪽 한도·쓰기 자격이 미확인이고 과제 기본값이 비공개다 | 종합 보고서를 앱과 MCP 도구로만 읽는다 |
| 밤 창·챗 밀림 감지 | 뺀다 | 기본 꺼짐으로 정했고 챗 경로를 건드려야 한다 | 밤에 동시 수가 저절로 오르지 않는다 |
| 실행 전 추정 장치 | 줄인다 | 셀 수는 정확히 셀 수 있다 | 토큰·벽시계 범위 표시. 상한 하나와 동의 한 번은 남긴다 |
| 운영 코드의 가짜 엔진 손잡이 | 뺀다 | 잘못 켜지면 실패가 정상 응답과 같은 모양이다 | 배포된 SIF 위의 리허설. 시험의 가짜 엔진으로 대신한다 |
| 지표 12종 | M4 | 타깃별 수치는 품질 모듈과 진행 응답이 낸다 | 타깃을 가로지른 추세 |
| AIDataHub `get_agent_cards` | M4 | 없어도 돈다. 다른 리포·다른 배포 길이다 | 카드 받기가 전문가당 목록 1회 + 카드 N회다 |
| 좌석 계약의 카드 인용 문구(M1 분) | M2 | 세 리포 같은 날 변경을 M1 에서 피한다 | M2 전까지 패널 좌석의 카드 인용이 등급을 올리지 못한다 |

과하지 않은 것(꼭 있어야 한다) — 결과 선저장과 다시 저장, 러너 잠금, 카드 묶음 동결과 앱 쪽 재대조, 줄 단위 파서와 빠진 행만 다시 묻기, 창 초과 사전 거절, 판 어긋남 보류, 인프라 탓과 내용 탓의 구분, 차단기, 옛 타깃 얼리기, 이중 판정, 완결 표기의 잔여, 비우기 신호(M3).

## 8. 크기

정직한 어림이다(반대 검토 X3 — 걸음 크기는 설계서의 '바뀌는 파일' 로 매긴 것이다).

- 새로 쓰는 양은 약 30,000줄(시험 포함)이다. 지금 리스크 앱 전체의 6할이고, 그 앱은 커밋 100개·6주가 걸렸다.
- 마일스톤별(재작업 포함) — M0 약 15시간 · M1 약 70시간 · M2 약 110시간 · M3 약 80시간 · M4 약 65시간.
- 달력으로는 cae00 왕복 다섯 번과 전원 실주행을 얹어 10~14주다. 사용자가 새 흐름의 첫 보고서를 읽는 것은 4~5주째다.
- 호출 시간이 가정의 3배면 달력이 한 달 는다.

## 9. 진행 규율

- 마일스톤을 시작할 때 걸음 하나를 먼저 한다 — 그 마일스톤 걸음이 닿는 설계서 절과 [problems.md](problems.md) 의 문제를 읽어 걸음의 수용 기준으로 옮기고, 고칠 자리의 닻(함수 이름·문자열)을 `grep` 으로 다시 확인한다. 설계서의 줄 번호 505건 가운데 196건이 M1 이 고치는 파일을 가리킨다.
- 소비자 시험의 입력은 손으로 쓰지 않는다 — 생산자의 실제 함수를 거쳐 만든다('시험은 통과하는데 운영 경로가 빈다' 가 여섯 군데서 같은 원인으로 났다).
- 걸음마다 그 리포의 시험 전체를 돌리고 논리 단위로 커밋한다. 끝난 리포부터 올린다.
- HWAXRisk `frontend/` 는 다른 세션 몫이다 — 백엔드 계약(응답 필드)까지만 한다. ReportArchive·TestScope 리포는 고치지 않는다.
- LLM 을 부르는 실주행은 임시 데이터 디렉터리·임시 포트에서 한다. 하네스는 절대경로를 쓰고 `pkill -f` 를 쓰지 않는다.
- cae00 에서 사람이 할 일은 마일스톤마다 절차서에 적는다(`docs/cae00-deploy-guide.md` 와 같은 규율 — 줄 번호 대신 출력 문구).
