# 리스크 심사 재설계 — 결정과 그 까닭

계획은 [PLAN.md](PLAN.md), 할 일은 [checklist.md](checklist.md) 에 있다. 이 문서는 날짜가 박힌 기록이다 — 그때의 사실을 적은 것이라 뒤에 고쳐 쓰지 않고 덧붙인다.

## 경위 (2026-10-08 ~ 10-09)

사용자가 리스크 심사의 라운드 수를 물은 데서 시작했다. 답을 찾다가 구조가 사용자의 뜻과 다르다는 것이 드러났다.

1. 패널은 3라운드 고정이고 전문가는 과제마다 한 번 앉는다는 것을 확인했다.
2. 사용자가 "변경점이 많이 있으면 그 과제를 영역별로 분석하게끔 하고 싶었다" 고 했다. 코드를 읽어 보니 모든 패널이 같은 변경 요약을 받고 있었다(읽는 에이전트 다섯 + 반박 검증 다섯).
3. 사용자가 "모든 전문가들에게서 다 디테일한 보고서가 나오게 하고 싶었다", "모든 전문가에 대한 지식카드를 이용해서" 라고 했다. dev AIDataHub 를 재 보니 전문가당 지식카드가 30장 안팎이고 한 번의 호출에 들어가는 크기였다.
4. '카드 대조는 혼자 먼저, 토의는 쟁점만' 이라는 안을 네 관점에서 공격시키고 독립 대안을 하나 받았다. 독립 대안도 같은 구조로 왔다.
5. 사용자가 네 부분 전부를 승인하고 "계획을 좀더 꼼꼼히 세워 발생할만한 문제는 이번에 다 고치고싶다" 고 했다(10-09).
6. 상세 설계서 일곱 편 → 계약 조정 → 문제 사냥 열한 갈래(250건)를 거쳐 계획서를 썼다.

## 결정

**D-1 일의 단위를 패널에서 (전문가 × 검토 단위)로 바꾼다.**
토의 좌석 하나의 근거 예산은 128K 창에서 약 18,000자다(직전 라운드 몫과 도구 스키마를 먼저 뗀다). 한 전문가의 카드 전부는 평균 57,072자라 토의 좌석에는 구조적으로 들어가지 않는다. 토의를 몇 번으로 나누어도 좌석당 예산은 그대로다. 도구 없는 단독 호출이면 약 109,000자를 쓸 수 있다.

**D-2 토의는 끝에, 쟁점에만 둔다.**
3라운드 가운데 두 라운드가 반박과 표결이다. 같은 요약을 본 좌석들이 좁혀 가는 구조라 '각자 자기 카드로 빠짐없이' 와 방향이 반대다. 독립 판정을 먼저 받아야 서로의 말에 끌려가기 전의 생각이 남는다. 토의는 정밀도를 맡는다.

**D-3 순서를 꾸러미가 아니라 마일스톤(M0~M4)으로 잡는다.**
설계서 순서대로면 120걸음이고 사용자가 첫 보고서를 읽는 것이 7~8주째다. 그 형식이 원하던 것이 아니면 그 위에 선 종합까지 다시 쓴다. 마일스톤 순서로는 4~5주째에 M2 의 보고서가 나온다(반대 검토 X3-17).

**D-4 재는 걸음(M0)을 맨 앞에 둔다.**
호출 시간·글자/토큰 비·모델 창·단위 수가 전부 가정이고 설계서의 작업 순서 어디에도 재는 걸음이 없었다. 에이전트 서버에는 토큰 사용량을 읽는 코드가 0건이다. 호출이 5분이 아니라 15분이면 전원 1회가 동시 4 에서 3주다(X3-01).

**D-5 M1(지금 패널 수리)을 가장 먼저 내보낸다.**
같은 과제의 두 번째 패널부터 저장이 실패하는 결함은 새 구조와 무관하게 지금 심사를 멈춘다. 설계자 셋이 따로 재현했고 코드로도 확인했다 — `rr_seat_opinions` 의 `UNIQUE(target_key, agent_key, cycle)` 인데 원장에 없는 반대석의 회차가 늘 1 이다. cae00 에서 이미 났는지는 M0-a 가 로그로 확인한다.

**D-6 M1 에서는 프롬프트 문구를 바꾸지 않는다.**
좌석 계약의 카드 인용 문장은 엔진·JS 파이프라인·앱 자산 세 곳이 바이트 동일해야 하고 파리티 검사기가 본다. 세 리포를 같은 날 올려야 하는 변경을 수리 묶음에 섞지 않는다. '확인 안 된 카드 인용은 등급을 올리지 못한다' 하나로 지어낸 인용이 등급을 올리는 구멍은 닫힌다(WP1 반대 검토의 cuts).

**D-7 스키마 버전은 마일스톤마다 하나, v4 는 dev 리허설 전에는 push 하지 않는다.**
이행기가 허용하는 연산은 표 생성·열 추가·인덱스 생성뿐이라 한 번 나간 PK 와 열 이름은 못 바꾼다. 새 표가 15개인데 계약 조정에서만 PK 가 세 번 바뀌었다. 실측이 표 모양을 바꾸라고 할 때 고칠 길을 남긴다(X3-03).

**D-8 러너의 주인은 WP3b 하나다. 선점 단위는 전문가 세션이다.**
두 설계서가 같은 파일(`review_runner.py`)을 다른 뼈대로 설계했다. 훑기·묶음 계획·마감·보고서가 전문가 단위라 셀을 하나씩 집는 러너에는 훑기가 설 자리가 없다. 운영 쪽 설계는 러너가 부르는 순수 함수 모듈로 줄인다.

**D-9 실패한 칸은 잡을 세우지 않고 완결을 막는다.**
전원 실행은 셀이 수천 개다. 합격선 안의 실패율로도 수십 건이 남는다. 그때마다 사람을 기다리면 종합 보고서가 나오지 않는다. 잡은 끝나고, 실패는 보고서의 '보지 못한 것' 과 완결 표기의 잔여로 남는다(X3-07).

**D-10 '자리 없음' 은 실패가 아니라 기다림이다.**
공유 LLM 의 관문이 자리가 없다고 즉답하는 것은 평소의 일이다. 이것을 인프라 실패로 세면 챗·심의와 같이 도는 낮에 셀이 `failed` 로 굳고 차단기가 계속 튄다(WP3b P-02).

**D-11 거르기('해당 없음')는 M4 로 미루고, M2·M3 는 전원이 전 단위를 대조한다.**
거르기는 호출 수를 줄이는 장치인데 줄어드는 양을 잰 적이 없다. 카드 제목만 보고 거르면 조용한 누락 통로가 된다. 검색 적중은 묶인 기록이 있으면 늘 같은 건수를 돌려줘 제외 신호로 쓸 수 없다(WP3a 가 코드에서 확인). 미루면 빠짐은 줄지 않고 호출만 는다.

**D-12 2차 영향과 결손 사냥은 M4 로 미루되, 안 돌았다는 것을 완결 표기에 싣는다.**
설계자 스스로 방법이 검증된 적이 없다고 적었다. M3 는 전문가가 적은 넘김 줄과 검토한 메커니즘을 코드로 세어 표로만 싣는다. 완결 표기에는 '2차 영향 미실행'·'결손 사냥 미실행' 이 잔여로 붙는다 — 안 한 것을 한 것처럼 보이게 하지 않는다.

**D-13 완결 표기는 모든 레벨에서 잔여를 단다.**
설계대로면 회로 6영역 전원이 입력 결손이어도 '심층 완료' 가 서고, 사람이 넘긴 칸이 잔여 목록에 없어 사라지고, 후속 단계가 한 번도 안 돌았어도 '없다' 조건이 공허하게 참이 됐다. 사용자 목표가 '빠짐없이' 이므로 못 본 것은 숫자로 보여야 한다(X1-01·02·07).

**D-14 카드를 받는 길과 카드의 정규 글은 하나다.**
에이전트 서버가 게이트웨이 도구로 받아 정규화하고, 앱은 그 응답을 통째로 얼린다. 인용 대조는 서버와 앱이 같은 벡터 파일로 파리티를 시험한다. 길이 둘이면 '카드 0장' 과 '못 받았다' 가 섞인다.

**D-15 운영 코드에 가짜 엔진 손잡이를 두지 않는다.**
잘못 켜지면 LLM 없이 정해진 판정이 원장에 쓰이고 그 실패는 정상 응답과 같은 모양이다. 이 리포에서 여러 번 난 무음 결함의 패턴이다. 리허설은 시험의 가짜 엔진으로 한다.

**D-16 기본 마감은 전원(C3)으로 한다(M3 앞에서 사용자 확인).**
사용자의 말이 "모든 전문가" 다. 지금 기본값(114명·32%)은 그 뜻과 다르다. 15명·114명은 중간 점검 지점으로 남긴다.

**D-17 회로 전문가를 새 흐름에 넣고, 입력 결손을 '해당 없음' 과 가른다.**
지금은 ECAD 가 없으면 104명이 시작할 때 보류로 닫혀 다시 열리지 않는다. 기구 변경이 회로에 주는 영향(보드 휨·간극·접지 금속)은 ECAD 없이도 말할 수 있다. 두 질문(기구 → 회로 영향 / ECAD 가 오면 확인할 것)으로 묻고, 영향을 못 낸 칸은 `no_input` 으로 따로 센다.

## 권고값으로 정한 것 (설계자들이 사용자 결정으로 올린 48건 가운데)

사용자에게 묻지 않고 권고값으로 간다. 바꾸고 싶으면 말하면 된다.

- 배경 카드(개념·FAQ·데이터)는 카드별 판정 대상에서 빼고 훑기에서 전문으로 읽힌다.
- '문제없음' 판정에도 사유와 카드 인용을 남긴다(행으로 둔다).
- 순서를 뒤집은 이중 판정은 M2 파일럿에서 전량, 그 뒤 비율은 실측으로 정한다.
- 카드 0장 전문가 3명과 물성 전문가의 '검색 근거만으로 한 검토' 는 검토함으로 세되 `basis=search_only` 로 따로 표기한다.
- 웹 경로 브리프의 상한은 24,000자, MCP 보충 경로의 옛 한도는 올리지 않는다.
- 통합 보고서는 M4 전까지 앱 안에서만 본다. 비공개 과제는 RA 에 올리지 않는다(지금 관례).
- MCP 보충 회차(Claude Code 에서 패널 돌리기)는 새 흐름 타깃에서 막는다. 옛 흐름 타깃은 그대로다.
- 보고서 본문에서 '참고' 등급은 건수만 싣고 접는다. 치명·FAIL 은 어떤 경우에도 접지 않는다.
- 입력 결손이 남은 타깃을 닫는 확인은 과제 소유자와 관리자가 한다.
- 운영에 이미 열린 타깃의 보류 104명은 그대로 두고 원하는 타깃만 사람이 푼다.
- 비교 잣대가 불확실해 제외된 수치 변화는 단서를 달아 보여 준다.
- 근거 꾸러미에서 지금 상태를 읽는 실호출은 캡처에 없던 도구만 허용한다.
- 이미 패널이 돈 옛 타깃에 검토를 얹는 것은 허용한다(원장의 종결 행은 건드리지 않는다).
- 예산 문턱은 추정 호출 1,500회 초과에 명시 동의, 30,000회 초과는 거절이다.
- 품질 지표가 기준 밖이면 완결을 보류하고 그 영역을 한 번 다시 돈다. 그래도 밖이면 사람이 사유와 함께 받아들여야 닫힌다.
- 기능 기본값은 꺼짐이다. dev 리허설과 cae00 시범 뒤에 켠다.
- 'sh' 영역은 센서·음향이다(게이트웨이 조직도에서 확인 — 설계서 둘이 뜻을 몰라 물음으로 올렸다).

## 계획 중에 새로 찾은 지금의 결함

새 구조와 무관하게 지금 도는 심사에 있는 것들이다. 전부 M1 에 들어 있다.

- 같은 과제의 두 번째 패널부터 저장이 실패한다(D-5).
- 발언이 0건이라 다시 앉는 원장 좌석도 같은 제약에 걸린다(WP1 P-01, 실행 재현).
- 같은 과제의 두 번째 리비전은 선례 줄의 접두 때문에 브리프가 판단어 검사에서 죽는다(WP1 P-03, 실행 재현).
- 부품 이름에 HOOK·PASSIVE·강화 같은 낱말이 들면 브리프 조립이 죽고 좌석 재시도까지 차감된다.
- 패널 기각이 등록부에 반영되지 않는다(`status` 열이 `open` 고정).
- 통합 보고서는 생성 분기가 죽어 있고(`level.get('raised')` 인데 그 키가 없다) 저장·전송 코드도 없다.
- 앱이 발언의 줄인 판만 받아 뒤쪽 인용을 잃는다(원문은 `say_full` 로 오는데 읽지 않는다).
- 자동 주입된 지식카드와 실패한 조회가 '도구 성공' 으로 세진다.
- 변경 파라미터의 절반가량(부피·bbox 등)은 의미 이벤트가 없어 좌석에 가지 않는다.
- 게이트 실패로 막힌 변경 비교는 다시 계산하는 길이 없다.

## 확인하지 못한 것

- cae00 의 사실 넷 — 리스크 앱에 실제 변경 비교 타깃이 있는지, 모델 창을 어떻게 읽는지, 출력 상한 값, LLM 응답에 사용량이 실리는지. M0 이 답한다.
- 호출 시간과 글자/토큰 비. 일정 어림은 5분에 기댄다.
- 사용자가 기대하는 '상세 보고서' 가 코드가 조립한 점검표 + 양성 판정의 본문과 같은 것인지. M2 가 처음 묻는다.
- 실제 변경이 여러 건인 비교 결과의 모습. dev 에는 자기 자신과 비교한 빈 건뿐이다.
- 문제 250건은 한 번의 사냥 결과다. 사냥꾼 한 명이 낸 것을 다른 눈이 다시 검증하지는 않았다(막는 16건 가운데 일부만 실행으로 재현됐다). 마일스톤을 시작할 때 그 마일스톤의 문제를 걸음으로 옮기면서 다시 본다.
- 프런트 세션의 일정. M3 의 실패 칸 처분과 잔여 확인이 화면 없이 REST 로만 될 수 있다.

## 2026-10-10 덧붙임 — cae00 재고와 사용자 결정

**D-18 좌석은 같은 과제의 등록부(앞 패널의 판정)를 도구로 보지 못한다(사용자 결정).**
여는 것은 변경 전체와 스냅샷 둘뿐이다. 앞 판정을 보면 뒤 패널이 그 결론을 따라 말해 지지 수가 독립 근거 없이 오른다.

**D-19 엄격해진 등급 규칙은 이미 저장된 패널에 소급하지 않는다(사용자 결정).**
새로 저장하는 패널부터 적용한다. 소급하면 사람이 확정한 판정 옆의 숫자가 움직인다.

**D-20 cae00 재고가 가정 셋을 바꿨다.**
- 모델 창이 1,048,576 토큰이다(GLM-5.2, 에이전트 서버가 엔드포인트에서 읽은 값). 설계는 128,000 을 가정했다. **D-21 전부 GLM-5.2 의 1백만 토큰 창을 가정한다. 잘라내지 않는다(사용자 지침, 10-10).**

## 2026-10-12 덧붙임 — M2 P1 포털 중계

**D-28 포털 중계는 엔진이 `code` 를 실은 오류를 상태·본문 그대로 넘기고, `code` 가 없는 것만 중계 어휘로 바꾼다.** (HWAXPortal `0f66999`) 계획(m2-wp3a P1)과 다른 곳과 그 까닭이다.
- 계획은 '5xx → 502 `agent_5xx`' 였다. 그러면 엔진이 내는 팩 오류 `tools_unavailable`(503)·`card_list_failed`·`card_list_unstable`·`card_fetch_failed`(502)가 `agent_5xx` 로 덮여, 앱이 팩 재시도(M2.md 4.4)와 인프라 백오프를 가를 수 없다. 그래서 상류 본문에 `code`(최상위 또는 FastAPI `detail` 안)가 있으면 상태·본문을 그대로 넘긴다. `code` 가 없는 5xx 만 502 `agent_5xx`(상류 본문은 되싣지 않는다), `code` 가 없는 404 만 404 `agent_outdated` 다. 엔진의 404 `agent_not_found` 는 `code` 가 있어 그대로 간다. M2.md 4.4 표 아래에 한 줄로 적었다.
- 전용 풀이 차서 연결을 못 얻으면(httpx `PoolTimeout`) 502 가 아니라 429 `engine_busy`(`retry_after_s` 30, `Retry-After`)다. 엔진에 닿지도 않았으니 기다림 부류다.
- 본문 상한(413)의 code 는 `body_too_large` 다. M2.md 4.4 의 '내용 탓' 칸에 더했다(같은 본문은 다시 보내도 넘는다). 상한은 받은 원 본문의 **바이트**로 잰다. Content-Length 가 있으면 읽기 전에, 없으면 읽으면서 멈춘다(앞단 nginx 는 2GB 까지 받는다). 리스크 앱은 본문을 UTF-8 그대로 보내야 한다 — httpx `json=` 은 이미 `ensure_ascii=False` 다. `\uXXXX` 로 보내면 한글 한 자가 6바이트라 1M 토큰 창 근처의 sweep 본문이 엔진 예산 검사 전에 413 이 될 수 있다.
- 신원 칸 넷은 run 만이 아니라 pack·plan 본문에도 덮어쓴다(설계서 3.2 — 중계 넷 전부). 엔진의 `plan` 요청 모델이 `extra="forbid"` 라면 네 칸을 선언해야 한다. 안 하면 포털을 거친 plan 이 전부 422 `unknown_fields` 다(E7 몫). `limits` 는 GET 이라 본문이 없다.
- run 은 상류를 응답 전에 연다. 422·409 를 상태 그대로 넘기려면 응답을 시작하기 전에 상류 상태를 알아야 해서다. 그래서 끊김 정리를 두 곳에 둔다 — 생성기의 finally 와 응답(`_CrStream.__call__`)의 finally 다. 생성기는 한 번도 돌지 않으면(헤더를 보내다 끊김) finally 도 돌지 않는다. 한 곳만 두면 퍼밋이 새고 엔진은 듣는 이 없는 LLM 호출을 끝까지 돈다(사본 변이 — 둘 다 지우면 8건, 응답 쪽만 지우면 1건이 붉다). 닫기는 `anyio.CancelScope(shield=True)` 로 가린다.
- 끊겼을 때 중계가 내는 프레임은 둘뿐이다. 침묵 한도는 `error{agent_stream_idle, infra, retryable, knob, idle_s}`, 도중 끊김은 `error{agent_unreachable, infra, retryable}` 이고 둘 다 뒤에 `done` 이다. 반쯤 온 프레임이 있으면 `\n\n` 으로 먼저 닫는다(안 닫으면 조각과 붙어 앱이 둘 다 못 읽는다). 엔진이 `done` 을 낸 뒤면 덧붙이지 않는다. 끝 프레임 없이 끝난 스트림에는 아무것도 지어내지 않는다(앱의 `engine_stream_cut`).
- 감사 — `card_review_{limits|pack|plan}_{done|error}`·`card_review_run_{start,done,error}`. 칸은 `kind`·`agent`·`unit`(각 200자에서 끊는다)·`bytes`·`sha256`(받은 원 본문)·`upstream`·`code` 뿐이다. run 의 끝 code 는 지나간 `error` 프레임의 code 이고, 없으면 `engine_stream_cut`(끝 프레임 없이 끝남)이나 `client_closed`(앱이 떠남, status `cancelled`)다. 포털이 막은 것(413·422·429)은 status `rejected` 다. 계획은 pack·run 만 적었지만 limits·plan 도 한 줄씩 남긴다 — 옛 판(`agent_outdated`)·시간 초과를 뒤에서 찾게 한다.
- 포털 403(권한 문, `ensure`)의 본문은 포털 공통 `{"detail": …}` 이고 `code` 가 없다. 앱은 상태 403 으로 가른다.
- 시험 — `backend/tests/test_card_review_relay.py` 77건. WP5b C7 ①~⑤, P-14(챗 세마포어 0·챗 클라이언트가 실패해도 카드 대조는 제 풀로 간다), 나갈 기준 3(대화 수 불변), 끊김 두 길(ASGI spec 2.3 의 `http.disconnect` — uvicorn 이 이것이다 — 와 2.4 의 헤더 전송 OSError). 사본 변이 일곱 가지(신원 덮어쓰기 뒤집기·권한 문·본문 상한·감사에 본문·code 실은 5xx 덮기·정리 두 곳)가 전부 붉다.
