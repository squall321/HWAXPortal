# 설계안 반박 검토 결과 (2026-10-08)

## LLM 신뢰도 (reliability)

**판정** 방향(카드 대조를 토의 앞에 두고 토의는 쟁점만)은 맞다. 지금은 좌석이 자기 카드의 약 6%(3,500자 / 평균 57,072자)만 받고 그 검색어에 변경 내용도 없으니, 카드를 전부 대조시키는 쪽이 사용자 목표에 가깝다. 그러나 2단계를 '한 호출에 30장 원문 + 판정 30개' 로 두면 서지 않는다. 입력은 평균에서는 창에 들어가지만 도구를 붙이면 p95 전문가부터 창을 넘고(130,071 > 128,000토큰, 넘치면 절단이 아니라 400), 출력은 지금 엔진이 다루는 발언(중앙 2,000자)의 4.5~6배라 형식 붕괴·'문제없음' 쏠림·건너뛰기가 한꺼번에 온다. 더 근본적으로 4단계 코드는 '카드가 실재하고 인용이 원문에 있다' 까지만 잡고 '문제없음 이 맞는가' 는 못 잡는데, 완결 기준(빈 칸 없음)은 호출이 있었는지만 재므로 도배된 '문제없음' 으로도 100% 가 된다. 점검 카드만 6~8장씩 끊고, 판정마다 카드·변경 양쪽 인용을 강제하고, 순서를 뒤집은 이중 판정과 표본 재질의로 뒤집힘률을 재서 보고서에 싣는 장치까지 넣으면 선다.

### 치명 결함과 고치는 법
- **결함** 한 호출에 30장·판정 30개 — 입력보다 출력 쪽이 먼저 무너진다. 형식이 깨지면 30행이 1행으로 조용히 줄고, 판정 칸의 과반이 구조적으로 '문제없음' 이라 그것이 기본 답으로 굳는다.
  - 근거: 판정 1건을 300~400자로 보면 30건 = 9,000~12,000자(약 8,571~11,428토큰)로 발언 중앙값 2,000자의 4.5~6배다. 엔진은 JSON 을 자유 텍스트로 요구하고 파싱 재시도는 1회다(HWAXAgentServer/deliberation.py:131, HWAXPortal/docs/GLM-DELIB-TUNING-REVIEW.md 20·80행). _parse_json(deliberation.py:1611-1637)은 바깥 객체가 깨지면 안쪽 객체를 차례로 읽어 마지막 것을 돌려준다. 같은 로직을 떼어 재현했더니 17번째 행의 이스케이프 안 된 따옴표 하나로 30행이 K30 한 행으로, 중간 절단은 K15 한 행으로 돌아왔다(dict 라 파싱 성공으로 보인다). 카드의 57.2%(13,369/23,378)가 점검 항목이 아닌 concept·faq·data 라 30칸 중 약 17칸은 처음부터 '문제없음' 이다. LLM_MAX_TOKENS 를 주석의 권장값 8192 로 건 박스라면 11,428토큰 출력은 절단된다(app.py:293). 가운데 카드 건너뛰기는 일반적으로 알려진 거동이고 이 박스의 GLM 에서는 미측정이다(실제 입력은 19,710~54,354토큰, 창의 15~42% 사이로 추정).
  - 고침: 판정 대상은 점검 카드(design-rule·failure-case·standard-summary, 전문가당 약 12.8장 추정)만으로 하고 6~8장씩 끊는다(전문가×묶음당 2호출). 배경 카드(concept·faq·data)는 판정 칸을 주지 않고 제목+요약 다이제스트(약 2,550자)로만 싣는다. 카드는 K01~K08 별칭으로 부르게 하고 코드가 record_id 로 되돌린다(지어낸 번호가 구조적으로 생기지 않는다). 행 수와 별칭 집합을 코드가 대조해 빠진 카드만 다시 묻는다.
- **결함** 4단계가 못 잡는 것이 바로 목표의 핵심(놓친 리스크)인데, 완결 기준이 그것을 재지 않는다. '빈 칸 없음' 은 호출이 있었다는 뜻이지 카드가 고려됐다는 뜻이 아니다.
  - 근거: 코드가 대조할 수 있는 것은 존재와 문자열 일치뿐이다. '문제없음'·'해당 없음' 은 대조할 원문이 없어 틀려도 조용하다. 1단계는 카드 제목만 보고 묶음을 걸러내므로 거기서 떨어진 (전문가×묶음)은 2단계에 가지도 않고 표에는 '해당 없음(사유)' 로 채워진다. ECAD 의존 6영역(pcb 19·pwr 18·rf 19·soc 20·passive 18·mem 16 = 110명, 30.6%)은 회로 변경 이벤트가 없어 구조적으로 '해당 없음' 이 된다(HWAXRisk/backend/app/assets/seat-contract.v1.json notes). 기본 temperature 가 0 이라(app.py:342·351) 같은 프롬프트를 한 번 더 돌리는 식의 재확인은 같은 답을 돌려줄 뿐이다.
  - 고침: 커버리지 셀을 (카드×묶음)으로 내리고 상태를 '양쪽 인용 검증됨 / 형식만 채움 / 미검토 / 입력 결측' 넷으로 나눈다. 판정을 적용 여부(적용됨·적용 안 됨·정보 부족)와 준수 여부 두 칸으로 가르고, '문제없음' 에도 카드의 조건 문구 인용과 변경 쪽 참조(c:·e:·d:)를 함께 요구한다. 점검 카드는 카드 순서를 뒤집은 두 번째 판정을 돌려 불일치만 카드 1장 단독 재질의로 가른다. '문제없음·적용 안 됨' 의 10~15% 를 무작위 단독 재질의해 뒤집힘률을 재고 보고서에 싣는다(임계를 넘으면 그 전문가×묶음을 단독 판정으로 다시 돈다). 1단계 탈락은 띵킹 예심처럼 AND 로 한다(LLM '무관' 이고 어휘·태그 신호도 0 일 때만, thinking.py:156-161).
- **결함** 카드 인용은 지금 코드에서 무검증으로 통과하고 등급을 '문헌·규격' 으로 올린다. 2단계가 카드 인용을 주 근거로 만들면 등급 열 전체가 의미를 잃고, 지어낸 카드 번호·인용문이 가장 잘 먹히는 자리가 된다.
  - 근거: narrative.py:644-646 은 external_check 가 None 이면 ok=True·verified=False 로 돌려준다. external_check 를 넣는 곳은 tests/test_atoms.py:309 뿐이고 _panel_scope(narrative.py:1502-1508)는 넣지 않는다. canonical_text_for(496-580)에 card 분기가 없어 None 이 되고, 719행의 quote 대조는 canonical 이 None 이면 건너뛰어 grade_ok=True 가 된다. 768행은 card 인용이 하나라도 있으면 '문헌·규격' 이다. 730행의 수치 대조는 모델이 직접 쓴 quote 문자열에 부분 문자열로 있기만 하면 통과한다('5' 가 '0.15' 에 걸린다). 카드의 67.9%(15,877/23,378)가 heuristic 인데 등급 판정은 confidence 태그를 보지 않는다. 좌석 계약(seat-contract.v1.json)에는 카드 인용 규칙 자체가 없다.
  - 고침: ① 실재 확인은 DB 존재가 아니라 '그 호출에 실은 카드 집합' 소속으로 한다(남의 카드·다른 배치 카드도 걸린다). ② card 분기를 넣어 sections[].content_text 를 정규 표기로 삼고, 공백 정규화 뒤 15자 이상·실질 문자 10자 이상 일치를 본다(엔진 _quote_validator, deliberation.py:2022-2075 방식. 지금 719행은 정규화 없는 정확 부분문자열이라 줄바꿈 하나로 오탐한다). ③ 수치는 모델의 quote 가 아니라 카드 원문·묶음 원문에서 토큰 단위로 대조한다. ④ 등급은 카드의 confidence 로 정한다 — fact·standard-summary(standard_refs 있음)만 '문헌·규격', heuristic·expert-judgement 는 '경험칙'.
- **결함** '카드 전부 + 묶음 전량 + 도구' 는 창의 꼬리에서 넘치고, 엔진의 좌석 경로로는 애초에 실을 수 없다. 넘치면 잘리는 것이 아니라 400 이라 그 전문가가 통째로 빠진다.
  - 근거: 엔진의 최악 기준 1.05자/토큰(deliberation.py:199)으로 카드 전부는 평균 54,354 · p95 74,071 · 최대 87,409토큰이다. 도구 스키마 40,000 + 시스템·출력 16,000(202행)을 더하면 p95 130,071 · 최대 143,409 로 묶음을 싣기도 전에 128,000 을 넘는다. 넘치면 400 이고 좌석이 유실된다(160-166행 주석). 엔진 좌석 예산은 128,000 − 45,714(_SEAT_CTX 48,000자) − 56,000 = 26,286토큰이라 사전 근거 17,967자(카드 9.4장분, 리스크 브리프 11,000자를 빼면 3.7장분)·지식카드 3,500자(4071행, 줄당 700자 2404행)뿐이다. 큰 묶음(가정 300이벤트×120자 = 36,000자)에 카드 평균을 더하면 88,640토큰, 도구를 붙이면 144,640토큰이다.
  - 고침: 2단계는 엔진 패널이 아니라 띵킹처럼 별도 호출기로 만든다. 조회 턴(도구 있음)과 판정 턴(도구 없음)을 가른다 — 엔진이 이미 그렇게 한다(_free_gather_one 독스트링, deliberation.py:3003-3005 '도구 호출 모델은 왕복 후 스키마 계약을 곧잘 어긴다'). 프롬프트 상한을 식으로 못박는다 — K×1,902 + 묶음 B + 고정 5,050 ≤ 약 33,600자(창의 25%). K=8 이면 B ≤ 약 13,300자다. 묶음이 B 를 넘으면 자르지 말고 0단계에서 subject_key·asm 롤업으로 더 쪼갠다.

### 개선
- 카드 종류별로 계약을 가른다. design-rule·standard-summary 는 적용 조건과 한계 대조, failure-case 는 조건 일치도(일치·부분·불일치·정보 부족)와 일치한 조건 인용, data 는 판정 없이 수치 근거로만(코드가 수치 대조), concept·faq 는 다이제스트로 싣고 '카드에 없는 리스크' 의 배경으로만 쓴다.
  - 이유: 배경 카드에 판정을 강제하면 30칸 중 약 17칸이 의미 없는 '문제없음' 이 되어 진짜 점검 카드의 판정까지 같은 쪽으로 끌려간다. 판정 대상이 30장에서 약 13장으로 줄어 묶음 크기 문제도 같이 풀린다.
  - 비용: 프롬프트 틀 3종과 종류 태그 파싱. 호출 수는 늘지 않는다.
- 점검 카드에 순서를 뒤집은 이중 판정을 돌리고, 불일치만 카드 1장 단독 재질의로 가른다.
  - 이유: 위치 때문에 건너뛴 카드와 쏠림을 잡는 유일한 수단이다. 기본 temperature 가 0 이라 프롬프트를 바꾸지 않으면 같은 답이 나온다.
  - 비용: 2단계 호출 2배. 관련 묶음이 전문가당 3개라는 가정에서 2,136 → 4,272회(지금 전원 72패널 3,500~6,800회와 같은 자릿수).
- '문제없음·적용 안 됨' 판정의 10~15% 를 무작위로 단독 재질의해 뒤집힘률을 전문가별·영역별로 재고 종합 보고서에 싣는다.
  - 이유: 코드가 못 잡는 거짓 '문제없음' 의 크기를 추정값으로라도 보이게 한다. 수치가 없으면 커버리지 100% 가 품질로 읽힌다.
  - 비용: 판정 약 13,717건(가정)의 15% = 2,057건. 4건씩 묶으면 약 514호출.
- 어휘 인계철선을 코드로 둔다. 카드의 제목·태그·standard_refs 와 묶음의 부품명·change_kind 겹침이 큰데 판정이 '적용 안 됨' 이거나 변경 쪽 인용이 없으면 단독 재질의로 올린다.
  - 이유: 거짓 음성이 가장 나기 쉬운 자리를 LLM 없이 좁힌다. 임베딩 코사인 절대값은 쓰지 않는다(이 코퍼스는 무관한 문장도 0.87~0.90).
  - 비용: 코드와 소수의 재질의.
- 양성 판정(위반 가능·주의)은 5단계 토의에 올리기 전에 카드 1장과 해당 변경 항목만으로 단독 확인한다.
  - 이유: 토의 패널이 헛쟁점으로 3라운드를 쓰는 것을 막고, 등록부에 들어가는 finding 의 인용을 한 번 더 좁힌다.
  - 비용: 양성 건수만큼의 호출(소수일 것으로 추정).
- 3단계 보고서는 검증된 2단계 행을 코드가 표로 조립하고, LLM 은 양성 행에 대한 서술만 행 id 를 달아 쓴다. 코드가 양성 행이 전부 보고서에 있는지, 보고서 수치가 행에 있는지를 본다.
  - 이유: 요약 호출은 검증을 통과한 내용을 빠뜨리거나 새 수치를 만든다. 띵킹의 종합이 코드 조립인 선례가 있다(thinking.py:265).
  - 비용: 조립 코드. 호출 수는 그대로다.
- K 를 정하는 파일럿을 먼저 돈다. 같은 (전문가, 묶음) 20쌍에 K=1·4·8·15·30 을 돌려 단독 판정(K=1)을 기준으로 일치율·누락률·위치별 '문제없음' 비율을 잰다.
  - 이유: 6~8장은 산수와 일반 거동에서 나온 값이고 이 박스의 GLM 에서 잰 값이 아니다. 30장이 실제로 견디면 호출을 줄일 수 있고, 8장도 못 견디면 더 줄여야 한다.
  - 비용: 약 420호출(쌍당 13+4+2+1+1 = 21회 × 20).
- ECAD 결측을 '해당 없음' 과 다른 상태(입력 결측)로 적는다.
  - 이유: 110명(30.6%)이 회로 변경 이벤트가 없어 판정할 재료가 없는데, 표에는 '검토했고 걸리는 것이 없다' 로 읽힌다.
  - 비용: 상태 한 개와 사유 코드.
- 5단계 토의 패널에는 agent_search(q=패널 질문) 대신 2단계의 쟁점 카드 판정·인용을 근거 항목으로 직접 싣는다. 리스크 앱 브리프 상한(11,000자)을 엔진 유도 예산(128K 에서 17,967자)에 맞춰 재배분한다.
  - 이유: 지금 토의 좌석은 변경 내용이 없는 질문으로 찾은 3,500자만 받는다. 2단계에서 찾은 쟁점 카드가 토의에 안 실리면 토의가 다시 기억으로 돈다.
  - 비용: brief.py CAPS 재배분과 시험 갱신.
- 판정 출력은 서버가 guided_json·response_format 을 받으면 그것으로, 아니면 행 단위 고정 형식과 행 수 검사로 받는다.
  - 이유: 자유 텍스트 JSON + 재시도 1회는 긴 배열에서 깨지고, 깨진 결과가 마지막 한 행짜리 정상 객체로 보인다.
  - 비용: 운영 LLM 서버 지원 여부 확인 1회.

### 확인하지 못한 것
- 카드 token_estimate(657토큰/장)의 산식을 AIDataHub 코드에서 찾지 못했다. 2.89자/토큰은 엔진의 최악 기준 1.05자/토큰과 2.8배 차이라, 카드 30장의 실제 GLM 토큰 수는 19,710~54,354 사이 어디인지 미측정이다. 예산 산수는 넘치면 400 이므로 1.05 로 잡았다.
- 운영 GLM 이 긴 입력의 가운데 카드를 얼마나 건너뛰는지, K 별 판정 일치율·'문제없음' 쏠림이 얼마인지는 재지 않았다. 본문의 해당 주장은 일반적으로 알려진 LLM 거동과 이 리포 주석의 실측 기록에 기댄 추정이다. 6~8장이라는 값도 파일럿으로 확인해야 한다.
- 리스크 심사 대상 전문가 359명의 카드 종류 분포를 모른다. 점검 카드 약 12.8장/명은 코퍼스 전체(23,378장) 분포를 그대로 적용한 추정이다. 영역마다 크게 다를 수 있다.
- 변경 묶음의 수·묶음당 글자 수·전문가당 관련 묶음 수(관련률)를 모른다. 호출 수는 관련 묶음 2·3·5개 가정으로만 냈고, 큰 묶음 예(300이벤트×120자)도 가정이다.
- 운영 박스의 LLM_MAX_TOKENS·DELIB_MAX_TOKENS·temperature 실값과 도구 스키마의 실제 토큰 수를 확인하지 못했다(.env 를 열지 않았다). 기본값 기준으로 적었다.
- 운영 LLM 서버가 guided_json·response_format(json_schema)을 받는지 모른다.
- 카드 record_id 의 형식과 카드 한 장의 최대 길이, sections 의 content_text 에 줄바꿈·표·수식이 얼마나 섞여 있는지(인용 대조의 정규화 수준을 정한다)를 보지 못했다(DB 미접속).
- 카드의 review_status·causal_status 실분포를 모른다. 주석은 causal_status 가 전부 validated 로 온다고 적지만 리스크 전문가 카드에서 직접 확인하지는 못했다.
- LLM 호출 1회의 실제 소요 시간을 몰라 벽시계 시간은 내지 않았다(동시 2 기준으로 호출 수에 비례한다).
- 논문·특허·규격을 묶음 내용으로 만든 검색어로 찾을 때의 재현율은 미측정이다. agent_search 는 절(섹션) 단위 발췌를 돌려주므로 여기서 빠진 문서는 4단계가 알 길이 없다.
- '카드에 없는 리스크' 는 대조할 원문이 없어 코드 검증이 불가능하다. 이중 판정·누락 점검(택소노미 38종)으로 줄일 수는 있어도 얼마나 줄어드는지는 재 봐야 안다.
