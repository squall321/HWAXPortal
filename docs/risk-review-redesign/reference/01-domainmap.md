### 바로잡은 것
- '브리프 E2 이벤트 표는 이벤트 전부를 싣는다' 는 틀리다. HWAXRisk/backend/app/brief.py:29 `"E0": 500, "E0c": 1000, "E1": 1650, "E2": 1100, "E3": 700, "E4": 600,` 이고 1357행 `item["result"] = clip_lines(item["result"], min(CLAMP_RESULT, cap - line_overhead(item)))` 가 넘는 줄을 뒤에서부터 버리고 '…(n줄 생략)' 만 남긴다. 라인 오버헤드 75자·프레이밍 53자를 빼면 이벤트 줄에 약 960자가 남아, 줄당 77~126자로 잡으면 7~12건이다(줄 길이는 추정). 변경이 많을수록 대부분이 어느 좌석에도 가지 않는다.
- E2 의 '정렬은 층·크기' 는 정확히는 부호 있는 원값 내림차순이다. brief.py:487 `-(r["magnitude"] if isinstance(r["magnitude"], (int, float)) else 0.0),` 이고 magnitude 는 after−before 다(diff.py:399 `delta = a - b`). 그래서 두께·간극이 줄어든 변경(음수)은 크기 없는 이벤트보다도 뒤로 가고, 단위가 섞여(mm·mm2·rank·MPa·G·무단위 요소 수) 숫자가 큰 단위가 앞을 차지한다. design_relevant 를 거르지 않아 설계 변경이 아닌 mesh.density_changed(요소 수 delta, diff.py:1396~1401)가 맨 앞에 설 수 있다. 1100자 절단과 겹치면 '무엇이 남는가' 가 영역도 중요도도 아닌 숫자 크기로 정해진다.
- '좌석별로 달라지는 것은 E0c 와 E7 뿐' 은 층이 틀리다. 근거(evidence)는 패널에 한 벌이고 전 좌석이 같은 것을 받는다 — E0c 는 그 패널에 앉은 도메인 전부의 계약 행을 한 칸에 모은 것이고(runner.py:427 `evidence.insert(1 if evidence else 0, seat_contract_evidence([s["domain"] for s in seats]))`), E7 도 좌석 전원의 줄을 한 칸에 싣는 구조다. 실제로 좌석마다 갈리는 것은 엔진 쪽 둘이다 — role 뒤에 붙는 자기 도메인 계약(HWAXAgentServer/deliberation.py:3990~3991)과, 역할 낱말로 자유 도구 순서를 매기는 `_tools_for_seat`(deliberation.py:2985, 호출 4493).
- E7 은 '비어 나올 수 있다' 가 아니라 코드상 러너 경로에서 늘 빈다. brief.py:1016 `agent_keys = [_s(s.get("agent_key")) for s in seats` 인데 러너가 넘기는 좌석은 planner.py:425 `"key": row["agent_key"],` 모양 그대로다(runner.py:414·422~423). 따라서 '자기 기억' 은 지금 좌석별 차이를 만들지 못한다(실행 미확인, 코드 대조).
- 완결 기준 서술이 한 조건 빠졌다. C1 은 도메인마다 1석에 더해 Tier A 완료 패널 3건을 요구한다 — registry.py:944~945 `tier_a_done = sum(1 for p in panels if p["tier"] == "A" and p["status"] == "done")` / `c1 = bool(c1_domains_ok and tier_a_done >= 3)`. C2 의 need 는 활성 좌석이 3 미만이면 전원이다(954행).

### 놓쳤던 사실
- 엔진에는 '영역' 개념이 이미 있다 — 다만 변경이 아니라 좌석 역할을 도구 영역에 잇는다. HWAXAgentServer/deliberation.py:2874 `# 좌석 역할 → 도구 영역. 전문가가 쓸 법한 것을 **쥐어 준다**` 아래 `_AREA_HINT` 가 10영역(material·calc·sim·result·mesh·cad·voc·quality·report·knowledge)의 낱말표이고, 2936행 `return 3 * len(rtok & hint) + len(qtok & hint)` 로 역할 낱말(가중 3)과 질문 낱말(가중 1)을 센다. 질문은 전 좌석 공통 문장이라 변경 내용은 여기에도 들어가지 않는다.
- 자산 안에 변경→도메인으로 이을 수 있는 간접 사슬이 하나 있는데 소비처가 없다. taxonomy.v1.json 의 메커니즘 38개마다 `default_tools` 가 있고(예: 38행 interface.interference → list_interfaces·interface_graph, 27행 mechanical.drop_stress → report_part_risk·report_worst_cases, 52행 material.property_uncertain → get_material, 59행 process.warpage → pcb_warpage_surrogate), seat-contract.v1.json 의 table 이 도메인별 required·recommended 도구를 갖는다. rr_delta_priors(change_kind→메커니즘)와 이으면 change_kind→메커니즘→도구→도메인이 되지만, `default_tools`·`default_detectability`·`failure_map` 을 읽는 앱 코드는 0건이다(grep).
- 변경이 많을 때 좌석이 잘린 이벤트를 스스로 당겨 올 길도 없다. 러너가 엔진에 주는 apps 는 어댑터 앱키뿐이고(runner.py:302~310, adapters/registry.py:27~29 → heax-step_forge·heax-kooremapper_mcp), 전체 diff 를 주는 risk_get_diff 는 `heax-hwax_risk` 앱 소속이라(deliberation.py:733) 3757행의 앱 조건을 통과하지 못한다(코드 대조, 실행 미확인).
- diff 타깃 브리프의 E3(명명 치수)·E4(결과 delta)는 키가 어긋나 비어 나온다. brief.py:514 `for item in _j(ctx["diff"]["diff_json"], {}).get("dims_delta") or []:` 와 551행이 diff_json 최상위에서 찾는데, 실제로는 `parametric` 아래에 있다(diff.py:590 `"parametric": parametric,`, 1017 `"dims_delta": dims_delta, "result_delta": result_delta, "rollup_delta": rollup_delta}`). 필드명도 base·target·rel 대 before·after·rel_delta 로 다르다. 그래서 diff 심사에서 좌석이 변경을 보는 창은 E1(요약 1650자)과 E2(1100자) 둘뿐이다(코드 대조, 실행 미확인).
- 사람이 지금 쓸 수 있는 손잡이가 넷 있고, 영역·도메인·subject 로 패널을 좁히는 인자는 없다. ① POST /targets 본문 agents 가 게이트웨이 조회보다 우선한다(routes.py:1902~1903, 2029~2034) — 호출자가 로스터와 relevance 를 정해 줄 수 있다. ② Settings HWAXRISK_ROSTER_DOMAINS(config.py:205) — 단 C1 이 같은 목록 전부를 요구한다(registry.py:942). ③ 잡의 user_memo(routes.py:2121)가 브리프 M 칸(CAPS 400)으로 전 좌석에 간다. ④ PUT /targets/{key}/coverage/{agent_key} 로 좌석을 skipped 처리(routes.py:2164~2167). - (mechanism, subject_key, change_kind) 묶음에 어느 도메인들이 제기했는지는 등록부에 이미 모인다 — registry.py:258~260·320 `"domains": domains,`(rr_registry.merged_json). rr_metrics 에도 expert·domain 차원이 있다(metrics.py:57). 둘 다 planner 가 읽지 않는다(planner.py:9~11 import).

### 확인하지 못한 것
- Tier A 세 패널 고정 구성((cam·disp·material·mech+xd)·(mem·passive·pcb·pwr+soc)·(rel·rf·sh·sim+std))은 planner.py 의 _pick_seats·_domain_cap·_reserve_non_xd 소스를 AST 로 떼어 메모리에서만 돌린 결과다(앱 import·파일 쓰기 없음). 전제는 15개 도메인 모두 rank 1 pending 좌석이 하나씩 있다는 것이고, 실제 로스터에서 어떤 도메인이 비면 구성이 달라진다.
- 변경이 여러 건인 실제 diff 의 summary_text 는 보지 못했다. 운영 DB(/data/appdata/hwax_risk/risk_review.db)를 immutable 읽기 전용으로만 열어 WAL 미반영분은 안 보였고, 보인 것은 self-diff 1행(이벤트 0건)뿐이다. 그래서 '500자 안에 이벤트가 몇 건 드는가'(코드상 헤더 약 285자 뒤 2~3건으로 추정)는 추정이다.
- 실제 로스터의 relevance 분포(0 인 좌석 비율, 도메인 안에서 순위가 얼마나 갈리는지)는 확인하지 못했다(같은 불변 읽기에서 rr_roster 0행). 코드상으로는 top 60 밖은 전부 0 이라 키 이름순으로 순위가 매겨진다. 로스터가 약 350석이라는 수치는 plan.md 의 기록이지 이번에 잰 값이 아니다.
- recommend_agents 구현은 지정된 세 리포 밖(AIDataHub)에 있다. 소스는 읽었으나 게이트웨이에 떠 있는 판이 그 소스와 같은지, _DESC_WEIGHT 등 환경변수 실값은 확인하지 않았다(네트워크 호출 금지).

- render.py 의 summarize/_summarize_diff(이벤트를 change_kind 별로 묶는 더 풍부한 요약)가 diff.py 에 배선되지 않은 것이 의도인지 누락인지는 코드에서 알 수 없다.
