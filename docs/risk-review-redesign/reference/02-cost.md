# 설계안 반박 검토 결과 (2026-10-08)

## 비용·운영 (cost)

**판정** 운영 관점에서 이 설계안은 조건부로 선다. 사용자의 질문(나눠서 해야 하지 않느냐)에 대한 답은 '그렇다, 다만 토의를 더 잘게 나누는 것이 아니라 카드 대조를 (전문가 × 묶음) 단일 호출로 나눠 심의 엔진 밖에서 돌리고 토의는 충돌한 묶음에만 쓴다' 이다. 그렇게 하면 묶음 20개·전문가당 관련 묶음 3개 기준으로 호출은 2,321~2,816회(지금 3,528~6,840회의 약 40~65%)이고 1~3단계 벽시계는 동시 6에서 약 18시간, 동시 2에서 약 54시간이다(호출 시간은 추정값이다). 그러나 지금 코드에는 그 가벼운 호출 경로도, (전문가 × 묶음) 단위를 담을 상태기계도 없다. 개별 검토를 '지금 패널 그대로' 돌리면 단위당 15~27회 호출에 타깃당 직렬과 일일 상한 24가 걸려 같은 조건이 45일이 되고, 관련성 판정 없이 전부 대조하면 묶음 20개에서 4.3~12.8일, 50개에서 10.5~31.5일이라 둘 다 성립하지 않는다. 토큰은 줄지 않는다(카드 원문 57,072자가 호출마다 실려 지금과 같은 자릿수다) — 줄어드는 것은 호출 수와 끊겼을 때 잃는 양이고, 늘어나는 것은 카드가 실제로 읽히는 비율(지금 좌석당 3,500자 = 카드 전량의 6.1% → 100%)이다.

### 개선
- 착수 전에 시범 측정을 한다 — 전문가 10명(카드 수 평균 5명 + 상위 5명) × 묶음 2개 = 2단계 20회.
  - 이유: 이 검토의 벽시계·토큰 표는 호출 시간(5분)과 자/토큰 비(1.05~2.9)를 추정으로 놓았다. 실제 값에 따라 1~3단계가 18시간일 수도 3일일 수도 있고, 분할이 필요한 전문가 수도 달라진다. 호출 시간, 실제 토큰 수, 출력 절단, JSON 파싱 실패율, 카드 번호 집합 일치율을 한 번에 얻는다.
  - 비용: LLM 호출 20회(약 2시간). 가벼운 호출 경로의 최소 구현이 먼저 있어야 한다.
- 3단계(전문가 보고서)를 LLM 호출이 아니라 코드 조립으로 바꾸고, '위반 가능·주의·판단 불가' 가 하나라도 있는 전문가에게만 요약 호출을 한 번 쓴다.
  - 이유: 2단계 산출은 이미 구조화돼 있어 표로 그리면 된다. 호출 359회를 아끼고, 관련 묶음이 많은 전문가에서 입력이 창을 넘는 문제(묶음 20개 전부면 183,500자, 50개 전부면 453,500자)가 사라진다. LLM 이 다시 쓰면서 판정이 바뀌는 일도 없다.
  - 비용: 렌더 코드 하나. 보고서가 산문보다 표에 가까워진다.
- (카드 묶음 해시, 묶음 내용 해시, 모델)로 단위 결과를 재사용한다 — 지금의 carried(바뀐 ckey 와 안 겹치면 이전 의견 승계)를 단위로 내린 것.
  - 이유: 재심사에서 가장 크게 줄고 누락은 0이다. 묶음 20개 중 3개만 바뀐 개정이면 2단계가 1,077회에서 약 160회로 준다(관련 묶음이 고르게 퍼졌다고 가정).
  - 비용: 해시 열 둘과 조회 한 번. 카드가 개정되면 해당 전문가는 전부 다시 돈다.
- 심사 시작 시 카드 스냅샷을 동결한다(전문가별 카드 묶음 해시 + 원문 gzip).
  - 이유: 심사가 며칠 걸리는 동안 카드가 고쳐지면 4단계의 '인용 문구가 카드 원문에 있는가' 대조가 거짓 불일치를 낸다. 패널 브리프를 동결하는 지금 관행과 같은 이유다.
  - 비용: 목록 359회 + 본문 10,774회 조회(본문은 한 장씩만 받을 수 있다)를 백그라운드 잡으로 한 번. 원문 약 20.5MB(10,774 × 1,902자), 압축하면 수 MB.
- 프롬프트를 [시스템 → 전문가 역할 → 카드 전부(고정 순서) → 묶음] 순으로 짜고, 같은 전문가의 묶음들을 연달아 돌린다.
  - 이유: LLM 서버가 접두 캐시를 쓰면 전문가당 카드 20,000~54,000토큰의 프리필을 관련 묶음 수만큼이 아니라 한 번만 낸다.
  - 비용: 순서만 바꾸면 된다. 효과는 서빙 설정에 달렸다(미확인).
- 단위 워커의 동시 수를 시간대로 바꾼다 — 낮 2, 밤 6. 세마포어는 챗·심의와 따로 둔다.
  - 이유: 동시 6은 지금 패널 하나(6석이 라운드마다 한꺼번에 호출)와 같은 순간 부하다. 다만 지금은 패널이 10~18분이고 이 작업은 18시간 이상 이어진다 — 심의가 공유 LLM 을 차지하면 챗이 청크 침묵 한도(300초)로, 띵킹 좌석이 600초 한도로 끝난다는 것이 코드 주석에 적혀 있다.
  - 비용: 설정 둘과 시계 분기. 낮에는 3분의 1 속도로 돈다(관련 3개 기준 전체 약 1.2~1.5일).
- 5단계 발동 조건을 '둘 이상 영역이 지적' 이 아니라 '판정 충돌 또는 심각도 상위' 로 좁히고, 패널 수에 상한과 우선순위를 둔다.
  - 이유: 전문가 359명이 카드 30장씩 대조하면 위험이 있는 묶음은 거의 전부 둘 이상 영역이 지적한다 — 그러면 쟁점 패널 수가 묶음 수와 같아진다. 묶음 50개면 2,450~4,750회로 지금 구조 전체의 약 70% 다.
  - 비용: 임계 조정이 필요하다. 충돌 없는 영역 간 상호작용은 묶음별 누락 점검(택소노미 38종 대조 — 차집합은 코드, 판단만 LLM 1회)이 받아야 한다.
- 6단계 영역 요약을 12명 안팎씩 나눠 요약한 뒤 합친다. 전문가별 보고서 부록은 종합 보고서 한 건에 넣지 않고 영역별 별도 문서로 낸다.
  - 이유: xd 는 122명이라 보고서 5,000자씩이면 610,000자로 한 호출에 안 들어간다. RA 는 rich_text 항목당 2,000자가 상한이라 359명 × 5,000자(약 1.8M자)는 항목 900개 이상이 된다.
  - 비용: 호출 16회 → 약 51회(조각 37 + 영역 병합 13 + 종합 1).
- 2단계 출력을 압축한다 — '문제없음' 은 카드 번호만, 나머지 판정만 인용과 이유를 쓴다.
  - 이유: 출력 생성이 호출 시간의 대부분이다. 30장 중 24장이 문제없음이면 9,000자가 약 2,900자로 줄어 호출 시간이 그만큼 준다.
  - 비용: '왜 문제없는가' 가 남지 않는다. 사용자가 그 이유까지 원하면 줄이면 안 되는 곳이다 — 사용자 결정이 필요하다.
- 줄이면 안 되는 곳을 못박는다 — (가) 2단계의 카드 전량 원문(상위 k 검색으로 바꾸면 지금의 6.1% 로 돌아간다) (나) 카드별 명시 회계(번호 집합 일치) (다) '해당 없음' 을 코드만으로 찍지 않는 것 (라) 4단계 코드 검증 (마) 묶음별 누락 점검 (바) 호출 한도 1800초와 패널 12시간.
  - 이유: 사용자 우선순위가 호출 수가 아니라 '빠짐없이 고려했는가' 다. 위 여섯은 비용 대비 누락 방지 효과가 가장 큰 자리이고, (가)는 전체 토큰의 대부분(관련 3개 기준 입력 81.4M자)이지만 이 설계의 목적 자체다.
  - 비용: 토큰은 지금 구조와 같은 자릿수로 유지된다(절감 없음).

### 숫자
- [가정 — 아래 표의 추정값] 2단계 1회 입력 75,572자(역할 1,500 + 카드 57,072 + 묶음 전량 4,000 + 검색 발췌 6,000 + 도구 결과 5,000 + 지시 2,000) · 출력 9,000자(30장 × 250 + 카드 밖 리스크 1,500). 호출 시간은 1단계 1분 · 2단계 5분 · 3단계 2분. 쟁점 패널 수 P = 묶음의 절반(올림). 토큰은 [하한 = 카드 표본비 1,902자 ÷ 657토큰 = 2.9자/토큰, 상한 = 엔진 보수 계수 1.05자/토큰]. 전부 실측이 아니라 추정이다.
- [지금 구조 — 호출] 패널 수 = Tier A 3 + B 20 + C 49 = 72(좌석 15 · 99 · 245명 ÷ 5 올림). 패널당 호출 하한 = S·R + S·(R−1)·2 + T + 3 = 49, 상한 = S·R·2 + S·(R−1)·4 + 2T + 3 = 95(S=6, R=3, T=4). 72 × 49 = 3,528, 72 × 95 = 6,840.
- [지금 구조 — 벽시계] 계획 상수 패널당 10~18분 → 72 × 10~18분 = 12~21.6시간(순 실행). 타깃당 직렬이라 동시 2는 한 타깃을 빠르게 하지 못하고, 일일 상한 24라 72 ÷ 24 = 최소 3일(하루 4~7.2시간 돌고 자정까지 쉰다). 공유 LLM 이 밀려 패널이 1시간이면 72시간, 2시간이면 6일.
- [지금 구조 — 실제로 전원에게 가는가] 기본 마감은 C2 라 Tier A+B 23패널 · 114명(359명의 32%)에서 끝나고 Tier C 는 명시 동의가 필요하다. ECAD 가 스텁이면 ECAD 의존 6영역(pcb 19 · pwr 18 · rf 19 · soc 20 · passive 18 · mem 16 = 110명) 중 104명이 deferred 로 내려가 실제 착석은 255명 · 51패널(3 + 14 + 34) · 2,499~4,845회다.
- [지금 구조 — 카드가 읽히는 비율] 좌석당 주입 3,500자 ÷ 전문가 카드 전량 평균 57,072자 = 6.1%.
- [엔진 근거 예산, 128K 창] 사전 예산 = int((128,000 − int(48,000 ÷ 1.05) − 56,000) × 1.05 × 0.93) = 25,668자, 그중 근거 몫 70% = 17,967자. 카드 전량 57,072자는 그 3.2배. (같은 식의 15% = 3,850자가 엔진 주석의 '128K 에서 3,850자' 와 일치한다.)
- [2단계 1회 토큰] 입력 26,105~71,973 · 출력 3,109~8,571. 카드만 — 평균 19,714~54,354 · p95 26,865~74,071 · 최대 31,703~87,410.

- [순간 LLM 부하] 지금 패널 1개 = 좌석 6석이 라운드마다 동시 호출, 타깃 2개면 12. 단위 워커 W6 은 패널 1개와 같은 동시 수다. 다만 호출당 입력이 26,000~72,000토큰으로 좌석 발언(추정 8,000~33,000토큰)보다 크다.

### 확인하지 못한 것
- 운영 LLM(GLM)의 실제 호출 시간과 생성 속도 — 2단계 1회가 5분이라는 것은 추정이다. dev 박스의 잡 기록 15건(/data/svc/agent-server/delib-jobs)은 2~7석 · 2라운드 시험 주행(52~547초)이라 대표값으로 쓸 수 없다. 벽시계 표 전체가 이 값에 비례한다.
- 실제 자/토큰 비 — 카드 표본은 1,902자에 657토큰(2.9자/토큰)인데 token_estimate 가 JSON 전체를 센 것인지 본문만 센 것인지 확인하지 못했다. 엔진은 1.05자/토큰을 가정한다. 이 비에 따라 2단계가 창에 넉넉히 들어가는지(하한), p95 부터 분할이 필요한지(상한)가 갈린다.
- 운영 박스의 DELIB_MAX_TOKENS · LLM_MAX_TOKENS 값(.env 를 열지 않았다). 8192 면 2단계 출력이 잘릴 수 있다.
- LLM 서버가 견디는 동시 요청 수와 접두 캐시 사용 여부 — 동시 6이 실제로 6배 빠른지, 같은 전문가의 연속 호출에서 카드 프리필이 재사용되는지 모른다.
- 쟁점 패널 수 P — 묶음의 절반으로 가정했다. 전문가 359명이 대조하면 거의 모든 묶음이 '둘 이상 영역 지적' 에 걸릴 수 있어 상한은 묶음 수 전체다. 발동 조건을 정해 실데이터로 재야 한다.
- 전문가당 관련 묶음 수의 실제 분포 — 1 · 3 · 전부는 과제가 준 가정이다. xd(122명)는 성격상 더 많은 묶음에 걸릴 가능성이 있으나 확인하지 못했다.
- 묶음 하나의 '전량 요약' 길이 — 4,000자로 가정했다. 지금 브리프의 변경 칸은 6~12건에 1,650자이고 0단계가 만들 묶음 요약은 아직 없다. 묶음이 매우 크면 2단계 입력이 그만큼 는다.
- 지금 구조에서 패널 하나가 실제로 쓰는 토큰 — 자유 조회 스텝의 도구 스키마 크기(천장 40,000토큰, 앱 3개 범위에서의 실제 값 미확인)에 민감하다. 스텝당 10,000토큰으로 가정해 패널당 0.51~1.40M 로 추정했다.
- 실제 타깃에서 ecad_absent 가 참으로 고정돼 있는지, 그래서 지금 로스터가 359명이 아니라 255명 활성으로 도는지 — DB 를 열지 않아 코드 경로로만 확인했다.
- 리스크 앱(HEAXHub 통합 SIF) 자체의 재배포가 update-all 에서 언제 일어나는지, 그때 심의 보호가 걸리는지 확인하지 못했다. 앱이 재기동하면 도는 패널이 닫히고 잡이 멈춘다는 것만 확인했다.
