## Q2. 알고 받을 것(가이드 1-4 요약 — 자세한 것은 그 절)

동작이 바뀌는 것 여덟(사용자 결정).

1. boundary · rbe 는 `output` 이 필수다 — 비우면 rc 1.
2. assemble 밖의 연산은 `output` 이 model · 그 인클루드 · 설정 · 다른 입력과 같은 파일이면 rc 1(입력에 손대지 않는다).
3. YAML op 여덟과 battery output · warpage `debug_prefix` 는 경로를 YAML 폴더 기준으로 푼다.
4. extract-parts · apply_carryover_plan 은 실패 · 거절해도 앞 실행의 출력을 지우지 않는다(보고에 `ok` · `output_written`).
5. battery 배치에 `model_types` 가 둘 이상이면 파일 이름에 종류가 든다 · 조합 하나라도 실패하면 rc 1.
6. offset 은 `material_card(s)` 가 없으면 거절한다(rc 1) — 예전엔 없는 MID 를 가리키는 덱을 rc 0 으로 냈다.
7. extract-parts 는 고른 파트에 칸으로 못 읽는 보 족 줄이 있으면 거절한다(`unreadable_aux`).
8. `info --strict` 가 같은 종류 절점 · 요소 번호 중복을 짚는다(연산 동작은 그대로).

해석 결과가 바뀌는 것(고친 결함) — battery 덱의 접촉(PENMAX 기본값 · 충격체 접촉에 IGNORE 가 실제로 걸린다) · tetremesh · unfold 가 셸 · 두꺼운
셸을 제 꼴로 쓴다 · hfdamp 가 구조 재질을 읽는다 · 뒤집은 map → prestress 체인이 재질을 싣는다. 같은 입력이라도 결과가 달라질 수 있으니 이 넷을 쓰는
사람에게 알린다.

> 덧붙임(11-11) — 위 `d0cd6b65…` 는 **파일 내용 해시**(`sha256sum step_forge.sif`)다. 허브의 `.sif.hash` 는 **빌드 캐시 열쇠**(효과 매니페스트 전체의
> 해시)라 값이 다르다. 둘을 견주면 맞지 않는 것이 정상이다. 내려받은 파일이 온전한지는 `sha256sum` 으로, 허브가 그 판을 받아들였는지는 앱이 떴는지로
> 본다(README 'SIF 의 숫자 둘').

알고 받을 것 — 바깥 꼴이 늘었을 뿐 예전 호출은 그대로다. 새 도구 · 잡을 거는 새 도구는 없다.

- 새 인자 `fold`(사람이 준 접힘 — 축 · 각 · 움직이는 쪽)가 견주기 · 짝짓기 도구 아홉과 match 잡에 붙었다.
- `set_revision` 에 `fold_angle_deg` · `fold_label` — 같은 리비전에 각도가 다른 과제 여럿을 받는다(각도 모름도 등록 · match 잡이 자동 각도를 채우고 사람 값은
  덮지 않는다). `revision_history` 에 리비전 아래 각도별 `states`.
- 몸체가 둘 이상인 판에만 새 칸(`bodies` · `articulation` 등)이 생긴다 — 몸체가 하나인 판은 응답이 예전과 바이트까지 같다.
- `compare_stackup` 은 두 과제가 접힘 쌍이면 적층을 견주지 않고 그 근거를 준다. 단면 SVG 에서 번호표를 못 놓은 파트는 `untagged` 로 댄다.
- 채우기 규칙 strong 은 그 짝이 든 몸체의 프레임이 선 경우만 자동이다 · 같은 입력의 `onto_fill` 잡도 다시 계획한다(엔진 판 3).

- StepForge SRC-02 — 부품 역할 16 → 코어 `part`(BOX-12 에서 운영 사용자가 확인).
- SignalForge(Q-2 다시 엶) — VOC 부품 16 → 코어 `part`, 증상 32 → 코어 `failure_mode`.
- KooRemapper SRC-08 — `cae_part` → `part` · `cae_finding` → `failure_mode` · `cae_campaign` → `analysis_method`(정확 일치만 — 사용자 결정 Q-5).

정본 허브의 읽기 도구로(쓰기 0) 세 타입마다 다음을 뽑아 사용자에게 넘긴다. 리포에는 싣지 않는다.

1. 타입 정의 — 칸 이름과 뜻, 그리고 **이 타입이 '종류' 어휘인지 개별 물건(인스턴스)인지**다. 예를 들어 `part` 가 '배터리' 같은 부품 종류인지,
   품번 하나하나인지다. 인스턴스면 VOC 'battery' 하나를 key 하나에 다대일로 잇는 꼴이 맞지 않아 대응표 꼴이 바뀐다.
2. 객체 목록 — key · 이름 · 별칭 · (있으면) 상위 분류, 그리고 타입별 건수. 건수가 수천을 넘으면 이름 · 별칭이 든 첫 500 개와 전체 건수만 낸다.

돌려받을 것 — 세 타입의 1 · 2(파일로, 사용자를 거쳐).

## Q7. 운영 사본(`stepforge-prod` · `dynaforge-prod`)이 새 판을 받는 길 — 사용자 결정 Q-4

사용자가 제안서 Q-4 에 '두 인스턴스를 같이' 를 골랐다(포털 [`../core-link/context-notes.md`](../core-link/context-notes.md) CK-2). 운영 사본 둘은 이
박스의 허브 앱이 아니라 박스 권한표 `connect:` 로 붙은 선언 백엔드다. 그래서 이 박스의 update-all 이 새 판을 넣지 못하고, 서비스 신원 ·
박스 훅 · 챗의 REST 단언 쓰기(SRC-13 · 15)도 이 박스 허브의 StepForge 에만 걸린다. 선언 백엔드는 신원 없는 호출을 막고, 사람이 등록한
토큰으로만 불린다.

사람 손 없이 도는 규칙 잇기(StepForge SRC-03 · 04 · 05, DynaForge SRC-09)는 앱 안에서 돈다. 그래서 운영 사본도 새 판을 받으면 같이 돈다.
알려 줄 것은 다음 셋이다.

1. 두 운영 사본은 누가 새 판을 넣나(이 박스 운영 · 다른 팀), 어떤 판(같은 Drive dist · 같은 git 판)을 어떤 길로 받나.
2. 이번 코드(StepForge · KooRemapper 의 코어와 잇기 판 — 다음 업데이트 라운드에 받은 편지함으로 알린다)를 두 사본에도 같은 때 넣을 수 있나.
3. 운영 사본의 StepForge 웹 화면(포털 신원 길)에서 사람이 후보를 확정 · 거절할 수 있나. 챗의 적용 길은 이 박스 허브 인스턴스에만 열린다.

돌려받을 것 — 1 ~ 3 의 답(사용자를 거쳐).
