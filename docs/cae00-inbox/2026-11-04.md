## Q1. 허브 셋의 판

까닭 — SP 0.4.68 ~ 0.4.71 에 MCP 도구 일곱이 새로 생겼다(계보 · BOM 전개 · 영향 범위 · 관계 제안). 포털은 그 가운데 쓰기를 확인 카드 목록에 넣었다(SL-2). 허브가
옛 판이면 도구가 없어 목록은 그 도구만 빼고 돈다 — 올릴지는 판을 보고 정한다. 0.4.72 는 앱 · DB 가 0.4.71 과 같아 0.4.71 이면 그대로 둬도 된다.

```bash
curl -s http://127.0.0.1:9110/tools-map | python3 -c '
import json, sys
d = json.load(sys.stdin); m, o = d["map"], d.get("orig") or {}
new = {"object_explode", "object_lineage", "lineage_repin", "graph_reach", "relation_propose", "relation_proposals", "relation_proposal_decide"}
for h in ("rootdesigndatahub", "failuretrace", "caegroupdatahub"):
    names = {o.get(n, n) for n, a in m.items() if a == h}
    print(h, "도구", len(names), "· 새 도구", len(names & new), "/ 7")'
```

- 0.4.71 · 0.4.72 면 새 도구가 7/7 이다. 도구 수는 게이트웨이가 감춘 것만큼 110 보다 적을 수 있다.
- 판 숫자는 개인 Claude 에서 그 허브의 `server_status` 로 볼 수 있으면 함께 적는다(일부 칸은 시스템 관리자만 — 못 보면 '못 봄').
- 허브가 이 게이트웨이에 없으면 그 줄은 '도구 0' 이다 — 그렇게 옮긴다.

## Q3. StepForge a78 — 새 그래프 도구 셋이 게이트웨이에 보이는가

까닭 — StepForge 가 SP 0.4.72 의 그래프 기능을 옮겼다(그쪽 a78 — main `ec721ef` · Drive `dist-20261103-234515Z`, 도구 183). 새 읽기 셋 `onto_reach`(영향 범위) ·
`onto_explode`(BOM 총수량) · `onto_lineage`(원천 → 파생물)이 게이트웨이에 읽기로 보여야 챗 · 루틴 · 심의 좌석이 쓴다. dev 에서는 셋 다 읽기로 보였다(11-04).
준비 — request-1030 `server-setup.md` 0절의 맨 아래 StepForge 줄(a79 — a78 을 품는다)대로 step_forge 를 받는다.

```bash
curl -s http://127.0.0.1:9110/tools-map | python3 -c '
import json, sys
d = json.load(sys.stdin); m, o = d["map"], d.get("orig") or {}
rr, w = set(d.get("routine_read") or []), set(d.get("write") or [])
for app in sorted({a for a in m.values() if "step" in a.lower()}):
    names = [n for n, a in m.items() if a == app]
    print(app, "도구", len(names))
    for t in ("onto_reach", "onto_explode", "onto_lineage"):
        hit = [n for n in names if o.get(n, n) == t]
        print("  ", t, "있음" if hit else "없음", *[("읽기" if n in rr else "읽기 아님") + (" · 쓰기" if n in w else "") for n in hit])'
```

- 기대 — StepForge 앱의 도구 183 · 셋 다 '있음 · 읽기'. 운영 사본이 따로 붙어 있으면 그 줄도 같은 꼴이다(접두 이름으로 보일 수 있다).
- 개인 Claude 로 `onto_lineage` 를 아무 객체에나 한 번 불러 답의 첫 줄을 옮긴다. 운영 허브의 PLM 정의가 계보 칸(`lineage_source`)을 아직 안 켜서
  '계보 관계 종류가 없다' 가 지금의 정상이다 — 다른 오류면 그 글을 옮긴다.

## Q4. StepForge a79 — 단면 지도가 보이고 새 반입에서 저절로 지어지는가

까닭 — StepForge 가 파싱 뒤 단면 지도(`section_atlas` — 축마다 고르게 자른 단면 그림 묶음)를 스스로 짓고, 새 읽기 도구 `section_atlas` 로 장을 꺼내게 했다(그쪽 a79 —
Drive `dist-20261104-135504Z`, 도구 184). dev 게이트웨이에서는 읽기로 보였다(11-04). 준비는 Q3 과 같다(같은 Drive 판이 a78 을 품는다).

- 도구 — Q3 의 명령을 다시 돌리되 셋 대신 `section_atlas` 를 본다(이름만 바꾼다). 기대 — StepForge 앱 도구 184 · `section_atlas` 있음 · 읽기.
- 지도 — 이 박스에서 **이 판을 받은 뒤 새로 반입된** 과제가 있으면 하나를 골라 개인 Claude 로 `section_atlas(project_id=…)` 를 인자 없이 부른다(읽기 — 상태 · 장 목록만).
  돌려받을 것 — 상태(ready · building · stale · none) · 장 수 · 걸린 초(있으면). 반입을 일부러 하지 않는다 — 새 반입이 아직 없으면 '아직 없음' 으로 적는다.
- `none` 이고 파싱 결과의 `section_atlas` 칸에 `why` 가 있으면 그 글을 옮긴다(작업량 어림이 900초를 넘으면 걸지 않는 것이 정상이다).
