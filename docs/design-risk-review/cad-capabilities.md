# 심사가 리스크를 뽑으려면 ECAD·MCAD 에 무엇이 있어야 하나

> 2026-10-07 · 질문: "심사 기능을 제대로 쓰려면 ECAD 쪽과 MCAD 쪽에 어떤 기능이 들어가 있어야 전문가 에이전트가 평가하고 리스크를 도출할 수 있나."
> 방법: 심사 엔진이 설계 사실을 소비하는 자리·좌석 계약·StepForge 141도구·ODB 리포·해석 어댑터를 읽고, 15개 도메인 좌석이 답해야 하는
> 리스크 질문 495개에서 필요한 능력을 뽑아 행마다 반박 검증한 뒤 합쳤다(능력 178건). 전체는 [cad-capabilities-catalog.md](cad-capabilities-catalog.md).
> 상태는 **2026-10-07 dev 게이트웨이 실호출** 기준이다. cae00 의 odb-hub(문서상 MCP 27도구)는 dev 에서 확인할 수 없어 `unverified` 다.

## 1. 결론

1. **심사는 아직 실제 설계로 돈 적이 없다.** 원장의 스냅샷 4건은 전부 시험 픽스처(10×10×1 mm 판 3장) 하나를 네 번 뜬 것이고, 패널·좌석 의견·요구·명명
   치수는 0행이다. 오늘 좌석이 받는 브리프를 그대로 재현하면 3,667자이고 내용은 "판 3장 · 접합 계면 2개" 가 전부다.
2. **MCAD 쪽은 재는 도구가 이미 대부분 있다. 막힌 곳은 StepForge 가 아니라 심사 쪽 배선이다.** 심사 어댑터가 싣는 것은 트리·상자 치수·계면 표뿐이고,
   좌석이 직접 부를 수 있는 StepForge 도구는 141종 중 32종(좌석당 3회)이다. 벽 두께·간극 분포·적층·체결·낙하 지표를 재는 도구 109종은 스냅샷으로도
   좌석 호출로도 닿지 않는다. StepForge 에 정말 없는 것은 열하나다(§3.3).
3. **ECAD 쪽은 dev 게이트웨이에 도구가 0종이다. 그런데 값은 ODB 리포에 이미 대부분 있다.** 부품 좌표·핀·넷·패키지·규칙 결과·리비전 변경이 파싱되거나
   계산돼 있고 REST 는 요약과 HTML 만 내보낸다. 48건 중 27건이 "리포에 있음 · 미노출" 이다. 막힌 곳은 파싱이 아니라 노출이다.
4. **ECAD 가 주는 것은 "무엇이 어디에 있고 어느 넷에 물렸나" 까지다.** ODB 의 체크리스트 38규칙은 전부 배치·이격·여백(보드 레벨 기계 신뢰성)이고
   SI·PI·EMI·열 규칙은 없다. 넷 전류·전압, 부품 소비전력, 패키지 사양, 언더필은 ECAD 어디에도 없다 — 그래서 전원·RF·SoC 좌석은 ECAD 만 붙여서는
   전기적 판정을 못 하고, **사람이 표로 넣는 입력 채널**이 따로 있어야 한다(§6).
5. **둘을 잇는 것이 통째로 없다.** 보드 좌표를 어셈블리 좌표로 옮기는 변환, refdes 와 기구 파트를 같은 것으로 묶는 키, 과제와 보드(여러 장)를 묶는 결속 —
   이 셋이 없으면 "실드캔 아래 부품 상면 간극", "발열원에서 배터리 셀까지 거리", "안테나 아래 동박" 같은 교차 사실이 한 건도 나오지 않는다(§5).
6. **판정 기준이 없다.** 요구 원장이 0행이라 OK·WARNING·FAIL 의 기준이 좌석 경험이다. CAD 를 아무리 붙여도 한계값이 없으면 "얼마나 위험한가" 는 안 나온다.
7. **해석 쪽은 없어서가 아니라 안 이어져서 비어 있다.** CAD 파트와 해석 PID 를 잇는 브리지가 응답 키 불일치로 0건이다(§6).

## 2. 숫자로 본 현황

| | 건수 | 있음 | 도구는 있음 · 스냅샷 미수집 | 부분 | 리포에 있음 · 미노출 | 계약에만 | 없음 | P0 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| MCAD(StepForge) | 63 | 2 | 24 | 26 | — | — | 11 | 32 |
| ECAD(ODB hub) | 48 | 0 | 0 | 14 | 27 | 3 | 4 | 24 |
| 교차·해석·기타 | 67 | 1 | 3 | 27 | 1 | 1 | 34 | 35 |

상태의 뜻 — **있음**: 도구가 값을 내고 스냅샷도 실어 리비전 비교·인용이 된다 · **도구는 있음 · 스냅샷 미수집**: 좌석이 직접 불러야 하고 리비전 비교가 안 된다 ·
**부분**: 칸이나 정밀도가 모자라다 · **리포에 있음 · 미노출**: 소유 리포가 이미 내는데 게이트웨이 도구가 없다 · **계약에만**: 심사 ECAD 계약에 이름만 있다.
**P0** 는 없으면 그 도메인 좌석이 핵심 메커니즘을 경험칙으로만 말하는 것이다.

스냅샷에 실리는 것과 좌석이 불러서 보는 것은 다르다. 스냅샷에 얼린 사실만 리비전 사이에 비교되고(무엇이 얇아졌나, 무엇이 가까워졌나), 다음 과제의 선례로 회수된다.
좌석이 부른 도구 결과는 그 패널 안에서만 인용되고, 얼린 판이 아니라 소스의 **지금** 상태를 읽는다.

## 3. MCAD 쪽 — StepForge

### 3.1 이미 재는데 심사에 닿지 않는 것 (StepForge 를 안 고치고 되는 것)

값이 이미 응답에 와 있는데 심사 어댑터가 버리거나, 도구는 있는데 좌석 통로가 닫힌 자리다. 전부 심사 앱·심의 엔진 쪽 일이다.

| 무엇 | 지금 | 고치면 |
|---|---|---|
| 검출 잣대(tol) 해시 | 어댑터가 받는 응답에 값이 있는데 안 읽는다 | 간극·접착 띠·관통의 **리비전 변화 이벤트가 살아난다**(지금은 전부 제외) |
| 재질명 | 사람이 지정한 재질이 응답에 오는데 id 대응에만 쓴다 | 재료 신호·질량 추정·이종재료 계면·물성 조회 키가 선다 |
| CAD↔해석 브리지 | 응답 키가 `parts` 인데 `rows` 를 읽어 0건 | 파트별 해석 결과를 CAD 파트에 묶는다 |
| MCP 폴백 | 단위·월드 좌표·잣대를 안 읽어 차단 게이트(G6)에 걸린다(스냅샷 3/4) | diff·타깃이 만들어진다 |
| 계면 행의 신뢰 칸 | 부분 측정·측정 방법·관통 두께를 버린다 | "잰 값" 과 "못 잰 값" 이 구별된다 |
| 역할·태그 | StepForge 의 역할 16종을 안 싣는다 | "무엇이 배터리·프레임·실드캔인가" 를 이름 대신 역할로 잡는다 |
| 체결·조인트·구조 | graph 잡 산출물을 안 싣는다 | 스크류·보스 위치와 분포가 스냅샷에 든다 |
| 못 잰 것 목록 | `list_unknowns` 를 안 싣는다 | "값이 없다" 와 "위험하지 않다" 가 갈린다 |
| 좌석 통로 | 141종 중 32종만 열림, 좌석당 3회 | 벽 두께·축방향 간극·간극 분포·적층·체결·누설·굽힘 도구를 좌석이 부른다 |

### 3.2 좌석이 필요로 하는데 스냅샷에 없는 측정 (도구는 있음 · P0)

0.5 mm 밖 파트 쌍의 정밀 거리 · 축방향 부호 간극 · 면 기준 간극과 밀착의 분포 · 실제 최소 벽 두께(지금 스냅샷의 "두께" 는 상자 최소 변이다) · 적층 환원 ·
체결 위치와 분포 · 굽힘 형상 · 단면 성질과 강성 급변 · 닫히지 않은 틈 · 낙하 방향별 사전 지표 · 치수 기록부(명명 치수). 도메인 9~10개가 각각 이것을 묻는다.

### 3.4 리비전 비교의 토대와 데이터

- **인스턴스 대응이 약하다.** 합동 파트는 형상 지문이 같고 대응 단계에 위치 항이 없어, 같은 스크류 여럿 중 어느 것이 옮겨졌는지 못 가린다. 실제 리비전 쌍으로
  검증된 적도 없다(변화 이벤트 0행).
- **재질·밀도가 전부 비어 있다.** STEP 이 재질을 안 실어 온다 — 사람이 지정하거나 사이드카로 넣어야 한다. 이것이 비면 물성 DB(값은 있다)를 물을 키가 없다.
- **실물 과제가 없다.** dev 의 과제는 전부 픽스처다.

## 4. ECAD 쪽 — ODB hub

### 4.1 실물이 둘이고 서로 다르다

| | dev 의 ODB 리포 | cae00 의 odb-hub |
|---|---|---|
| 가진 것 | ODB++ 파서 14종 · 체크리스트 38규칙 · REST 32개 | MCP 27도구(2026-09-16 실측 문서) |
| MCP | 없음(계획 문서만) | 있음 — dev 에서 확인 불가 |
| 게이트웨이 | dev 에는 백엔드 없음 → 도구 0종 | cae00 에서만 등록 |

**먼저 할 일은 cae00 게이트웨이의 도구 목록을 한 번 뜨는 것이다.** 문서대로라면 그것만으로 10건이 "도구는 있음 · 스냅샷 미수집" 으로 오르고, 심사 어댑터가
읽을 실제 도구 이름이 정해진다.

### 4.2 리포가 이미 내는 것 — 감싸서 내보내기만 하면 된다 (P0 만 17건)

| 무엇 | 지금 | 필요한 것 |
|---|---|---|
| **부품 배치 목록**(좌표·회전·면·미러·핀 수) | 추출 파일에는 있고 REST 는 이름·면만 준다. 분류가 Unknown 인 부품은 빠진다(샘플 692개 중 388개) | 보드 전체를 한 번에, **빠진 수를 밝혀서**(완결성 선언) |
| **체크리스트 규칙별 결과** | 규칙 id·위반 부품·표가 내부에 있는데 REST 는 합계와 HTML 만 | 규칙별 JSON |
| 핀 표와 넷 → 핀 역조회 | 파싱돼 있다 | 조회 |
| 보드 전체 넷 목록 | dev·cae00 어디에도 조회가 없다 | 이름·핀 수·경유 층 |
| 패키지 기하(피치·외형·핀 좌표) | 파싱돼 있다 | 부품 응답에 싣기(코너 볼·미실장은 작은 새 계산) |
| 부품 높이 | 평균 한 값만 낸다 | 최대·최소 그대로, 출처와 함께 |
| 부품 역할(AP·메모리·PMIC·센서·RF) | 규칙 내부에서만 쓴다 | 조회 + 실제 관리부품 목록(dev 는 샘플 목록이다) |
| 리비전 간 부품 변경(ΔX·ΔY·Δ회전) | 비교기가 만들고 요약 한 줄만 남긴다 | 변경 행 JSON |
| 보드 외곽 다각형·컷아웃·협폭부, 부품에서 외곽까지 거리 | 함수가 규칙 안에 있다 | 대상을 인자로 받는 조회(고정홀 목록과 거리는 원자료만 있어 식별 코드가 새로 필요하다) |
| 층별 동박률 | 계산하고 HTML 에만 남긴다 | 숫자 |
| 잡 식별·내용 해시 | 내부 메타에 있다 | 응답에 한 줄(스냅샷 해시의 원천) |

### 4.3 심사 계약 4도구는 실물과 어긋난다 → 계약을 고쳐야 한다

`odb_get_board`·`odb_get_stackup` 은 어디에도 없고, `odb_list_components`·`odb_list_nets` 는 이름만 같고 칸이 다르다. cae00 실물은 접두 없는 이름이고
`list_parts` 는 StepForge 의 `list_parts` 와 겹친다. 좌표가 부품당 1호출이라 1,500개 보드에서는 예산을 넘는다. 계약(`HWAXRisk/docs/odb-adapter-contract.md`)을
실물에 맞춰 고치는 일이 심사 쪽 선행이다.

계약이 **일부러 뺀 것**(패드·비아·트레이스 폭)을 깨야 답할 수 있는 P0 질문이 셋 있다.

| 질문 | 필요한 것 |
|---|---|
| 충전 경로의 최소 배선 폭과 비아 수는 | 넷 배선 기하 집계 |
| 열충격 SED 예측(`predict_sed`)의 필수 입력 `pad_size` | 핀별 랜드 패드 치수 |
| 마이크로비아 층 구간 | 드릴 층 구간 표 |

### 4.4 조용히 틀리는 자리 둘

- **"위반 0건" 이 미실행·대상 없음·샘플 참조와 구별되지 않는다.** dev 의 관리부품 참조 목록 6개는 전부 로더가 만든 내장 샘플이다. 좌석이 "규칙 통과" 를
  근거로 쓰면 틀린다 — 결과 상태 어휘(실행함·대상 없음·참조 없음)와 평가 대상 수가 응답에 있어야 한다.
- **부품 목록이 전부가 아닌데 전부처럼 보인다.** 안테나 접점·고정홀·테스트포인트·다이오드·서미스터가 Unknown 분류로 빠진다.

### 4.5 ECAD 가 줄 수 없는 것

넷 전압·전류 · 부품 소비전력 · 층 자재 물성 · 패키지 종류와 볼 사양 · 언더필 · 스텐실 두께 · 보드가 어셈블리 어디에 놓이는지 · 굽힘 주방향. 이것은 §5·§6 의 몫이다.

## 5. 둘을 잇는 것 — 지금 0건

| 뿌리 | 없으면 |
|---|---|
| **보드 → 어셈블리 좌표 변환**(레코드와 사람 확정 절차) | 보드 위 부품과 기구 사이의 거리·간극을 한 건도 못 낸다 |
| **refdes ↔ 기구 파트 ↔ 해석 PID 를 같은 것으로 묶는 키**(인스턴스 단위) | 부품·파트·해석 결과가 서로 남이다 |
| **과제 ↔ 보드 잡 결속**(메인·서브 여러 장, 보드 식별이 든 키) | 어느 보드의 U12 인지 모른다 |

이 셋이 서야 나오는 파생 사실이 전원·SoC·RF·센서 좌석의 핵심 질문이다.

- 부품 상면과 마주 보는 기구(실드캔·백플레이트) 사이 Z 간극.
- 발열원에서 배터리 셀·외장 표면까지, 자석에서 센서까지, 노이즈원에서 안테나 급전점까지의 3D 거리.
- 패키지 코너에서 고정홀·스크류 보스까지 거리(보드 굽힘이 솔더에 닿는 자리).
- 방사체 투영 영역 안의 동박·접지 겹침(안테나 클리어런스).
- 마이크 포트·USB·사이드 키와 하우징 개구의 정렬.

그리고 이 파생 사실을 **스냅샷의 엣지로 얼려 리비전 변화로 내야** 한다 — 지금 심사 diff 에는 ECAD 이벤트 코드가 없다.

## 6. CAD 밖 — 해석·요구·사양

- **해석 결과 잇기(데이터는 이미 온다).** 브리지 키(`parts`), 해석 조건(낙하 높이·케이스 수·항복 응력) 적재, 재료 카드 펴기, 최악 케이스 지정, 인자 이름
  (`top_n`) 맞추기. 다만 dev 에 해석 리포트가 0건이라 실데이터로 돈 적이 없다. 낙하 외 물리(열·전자기·모달)는 결과를 실을 층 자체가 없다.
- **요구 원장.** 한계값과 필수 시나리오를 등록해야 판정이 선다. 규격 좌석(std)은 이것이 유일한 근거다. 지금 요구 종류는 셋이고 여유는 치수 한계에서만 계산된다.
- **과제 사실 원장(표 입력 채널).** CAD 가 줄 수 없는 사실을 사람이 표로 넣는 길이 없다 — 부품별 소비전력, 패키지 사양, 실장 공정(언더필·솔더 합금),
  넷·레일 전기 조건, 안테나 ↔ 대역 매핑, BOM·공급처 변경.
- **좌석 통로와 세대 고정.** 좌석이 부르는 도구는 얼린 판이 아니라 소스의 지금 상태를 읽는다. 소스가 세대 토큰을 내고 조회가 그것을 받아야 "그때 그 판" 을 본다.

## 9. 조사 중에 드러난 심사 앱 결함 (2026-10-08 수정함)

소스 HEAD 를 사본에서 돌려 재현한 것이다. 여섯 가운데 앞의 다섯 줄(브리지와 해석 크기는 한 줄)과 게이트 요약을 2026-10-08 에 HWAXRisk 백엔드에서 고쳤다 — 좌석 계약의 `check_design_rules` 줄만 남아 있다.

- 브리프의 규칙 줄(E9)이 뒤집혀 있다 — **통과한 규칙을 싣고 실제로 발화한 규칙을 건너뛴다.**
- 브리프 요약(E1) 첫 줄이 ECAD 스텁만 있어도 `ecad=present` 라고 적는다(같은 요약의 결측 줄은 `ecad_absent`).
- 브리프 스코프(E0)가 906자인데 상한 500 에 잘려 결측·소스·잣대 4줄이 빠진다.
- CAD ↔ 해석 브리지가 응답 키 불일치(`parts` 대 `rows`)로 0건이다. 해석 파트 크기도 어댑터가 없는 칸(`size`)을 읽어 치수 대조가 불발한다 — 시험의 가짜 응답에는 그 칸이 있어 통과한다.
- 게이트 요약 신호가 판정 불가(null)를 실패로 적는다.
- 좌석 계약이 pcb 계열에 권하는 `check_design_rules` 는 복합재 적층 규칙 도구다(지금은 백엔드도 내려가 있다) — ODB 체크리스트 결과를 가리켜야 한다.
