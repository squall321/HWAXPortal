## D0 (2026-09-08) — 정찰에서 나온 사실

병렬 정찰 5축(프론트 챗 / AIDH 추천 / 심의 좌석 / 챗 스트림 / 포털 중계)을 돌렸다.
설계를 바꾼 사실만 적는다.

**① `low_confidence` 는 좌석별이 아니라 질의별이다.**
`recommend_svc.py:263-265` 가 `best_match = max(desc_match for r in ranked)` 하나를
top_k **전원에게 같은 값**으로 박는다. `app.py:2612` 의 `all(r.get("low_confidence"))`
는 방어처럼 보이지만 사실상 첫 원소와 동치다. → 좌석별 자격 판정에 이 값을 쓸 수 없다.
좌석별로는 `desc_match` 원값을 직접 봐야 한다.

**② `score` 는 코사인이 아니다.**
`score = record_mean + 1.0×sample_mean + 2.0×desc_match` (`recommend_svc.py:188-195`).
게다가 각 항의 유사도는 `(코사인+1)/2` 로 매핑돼 있어(`search_svc.py:306-307`)
무관 텍스트도 0.87~0.90 이 나온다. **절대 임계값으로 쓰면 안 되고 순위로만 쓴다.**
실측 대비 — '낙하 충격 패널 크랙' 3.11/desc 0.625/low=False vs
'OCA 산소 확산 계수' 2.13/desc 0.14/low=True. 갈리는 것은 `desc_match` 쪽이다.

**③ `agent_search` 가 자격 판정의 가장 직접적인 신호다.**
좌석의 **실제 바인딩 레코드** 위에서 그 좌석 자신의 설정으로 검색한다
(`mcp_runtime.py:598-605`). 다만 `score_threshold` 가 e5 스케일에서 사실상 작동하지
않아(무관 0.90 / 관련 0.94) `refused` 는 대부분 "hits 가 통째로 빔" 일 때만 켜진다.
→ `refused` 단독으로 자르지 않고 `hit_count` 와 `desc_match` 를 함께 본다.

**④ 심의 엔진에는 기권 채널이 아예 없다.**
스키마에 `abstain`/`pass` 없음, `_norm_stance` 판별 불가 → **`조건부 동의`**
(`deliberation.py:1348`), tally 3칸, 좌석 유실 라벨은 `(오류·시간초과)` 고정.
좌석이 산문으로 "제 도메인이 아닙니다" 라고 답하면 JSON 파싱 실패로
`"(구조화 실패 — 원문 강등)"` 이 붙어 **정당한 기권과 모델 고장이 구분되지 않는다.**
→ 심의 엔진 재사용 포기의 결정적 근거. 기권을 넣으려면 6~7곳 동시 수정이고
그 중 `_CHAIR_ITEMS` 는 JS 정본과 바이트 동일 검사를 받는다.

**⑤ 슬래시 접두사는 첫 발화에만 붙는다.**
`ChatContext.tsx:426` `applyPrefix`. → 매 턴 켜져 있어야 하는 모드를 트리거로 만들면
둘째 발화부터 조용히 꺼진다. 그래서 `thinking` 을 **top-level 필드**로 둔다.

**⑥ 새 이벤트 이름은 프론트 switch 에 없으면 조용히 사라진다.**
`chat.api.ts:52-77` 에 default 가 없다. 이미 `agents` 이벤트가 그 상태다
(서버는 보내고 프론트는 버린다). → 이벤트를 하나(`think`)로 접고 `kind` 로 나눈다.
그리고 **같은 내용을 `token`+`result` 로도 낸다** — 프론트가 몰라도 사용자는 답을 받고,
포털 저장 스니퍼가 `result.content` 만 보므로 대화 저장에도 그게 필요하다.

**⑦ 포털 중계는 손댈 곳이 없다.**
`routes.py:432-434` 가 `aiter_raw()` 로 바이트를 그대로 흘린다. nginx
`location /agent/` 도 이벤트 종류와 무관하다. 단 **`ChatRequest` 에 필드를 선언하지
않으면 `model_dump` 에서 빠져 조용히 유실된다** — 실제로 `chair_template`·`free_tools`
가 그렇게 사라진 적이 있다.

## D1 (2026-09-08) — `mode="hybrid"` 를 쓰지 않기로 한 이유

게이트웨이 경유 실측(`agent_search`, `sim-drop-impact`, 같은 질의).

| mode | 경과 | 결과 |
|---|---|---|
| semantic | **0.1초** | hits=3 |
| tag | 1.0초 | hits=0 |
| hybrid | **102.5초** | hits=3 |
| fts | **221.4초** | hits=0 |

`hybrid` 는 `fts` 를 포함해서 느리다. `fts_search`
(`AIDataHub/api_server/src/api/services/search_svc.py:83`)가
`to_tsvector('simple', content_text) @@ websearch_to_tsquery(...)` 를 쓰는데
**그 식에 GIN 인덱스가 없다** — 마이그레이션 전수 grep 0건. `record_sections` 862,910 행을
순차 스캔하며 행마다 `to_tsvector` 를 계산한다. 게다가 AND 매칭이 0건이면 OR 로
**한 번 더** 돌린다(`:135-136`).

띵킹 모드는 `semantic` 고정이다. 좌석마다 부르는 신호라 0.1초와 102초의 차이가
기능의 생사를 가른다.

⚠ **별건 파장** — 심의의 좌석별 지식카드 RAG(`deliberation.py:2426`)와 챗의
`_persona_knowledge`(`app.py:1673`)가 **둘 다 `mode="hybrid"`** 다. `_call` 이
타임아웃을 문자열로 삼키므로(`deliberation.py:880`) 조용히 "지식 0건" 으로 흐른다.
페르소나 설계 전체가 그 주입 위에 서 있다. 이 작업 범위 밖이라 보고만 한다.

## D2 (2026-09-08) — 예심 탈락을 AND 로 둔 이유

탈락 조건은 `hits == 0` **그리고** `desc_match < THINK_DESC_FLOOR` 다. OR 이 아니다.

두 신호는 서로 다른 실패를 잡는다.
- `hits > 0, desc_match ≈ 0` — 어휘는 안 겹치는데 내용이 걸린 좌석. 살려야 한다.
  질문이 현장 용어이고 문서가 표준 용어일 때 늘 이렇게 된다.
- `hits == 0, desc_match 높음` — 데이터는 아직 없는데 역할이 정확히 그것인 좌석.
  신규 도메인이 이렇다. 살려서 본심에 보내면 "내 담당은 맞는데 근거가 없다" 는
  **정확한 답**을 낸다. 그것이 이 모드가 주려는 값이다.

둘 다 없을 때만 자른다. 예심은 싸게 좁히는 단계이지 판정하는 단계가 아니다.
판정은 본심에서 좌석 자신이 근거를 보고 한다.

## D3 (2026-09-08) — 좌석에게 도구를 주지 않은 이유

심의 좌석은 자유 조회(ReAct 1턴, `_FREE_ALLOW` 화이트리스트)를 한다. 띵킹 v1 은 안 준다.

- **지연** — 좌석 수만큼 ReAct 왕복이 붙는다. 심의는 몇 분~몇 시간을 쓰는 모드라
  감당하지만, 띵킹은 챗 안에서 도는 모드다.
- **판정 오염** — 도구가 죽어서 못 답한 것과 도메인이 아니라서 못 답한 것이
  같은 `pass` 로 나온다. 자격 판정이 이 모드의 본체인데 그 신호를 흐린다.
- 근거는 좌석의 지식카드다. 없으면 없다고 말하는 것이 설계 의도다.

후속 과제로 남긴다 — 도구를 열 때는 `pass` 사유에 `tool_error` 를 별도 값으로
두어야 한다.

## D4 (2026-09-08) — 실주행에서 고친 것 넷

**① 전원 오류일 때 "전문성이 없다" 고 말하던 문구.**
vLLM 이 죽은 채로 돌렸더니 좌석 5명이 전부 `APIConnectionError` 였는데, 종합이
"답할 수 있다고 판정한 전문가가 없습니다" 를 냈다. **기권은 판정이고 오류는 장애다.**
섞어 말하면 풀에 전문성이 없다는 값진 신호가 LLM 불통에 묻힌다. 세 갈래로 나눴다 —
전원 기권 / 전원 실패 / 섞임.

**② 모델이 중국어로 새는 것.**
dev 모델(Qwen2.5-7B)이 `scope` 와 `refer` 를 중국어로 냈다. `refer` 가 오염되면
그 명사구로 재소집하므로 **위임 사슬이 통째로 망가진다**(실측: `材料科学` 로 소집해
`sw-model-safety`(생성형 AI 안전)가 불려왔다). 시스템 프롬프트에 한국어를 못 박았다.
prod(GLM)에서는 덜하겠지만 dev 에서 못 쓰면 개발이 안 된다.

⚠ 7B 는 지시를 박아도 가끔 문장 중간부터 샌다(실측 1건). 이걸 코드로 세척하는 것은
과한 방어라 넣지 않았다 — 모델 문제이지 설계 문제가 아니다.

**③ 기권 좌석이 자기 분야의 인접 주제를 넘김 대상으로 적던 것.**
`mech-lds-antenna` 가 OCA 접착제 질문에 'LDS 공정 체인 관리 · EM 해석 · 방사 성능 튜닝'
을 지목했다. 자기 분야를 나열한 것이지 질문을 넘긴 것이 아니다. 프롬프트에 반례를 넣고
"모르면 빈 배열" 을 강조했더니, 같은 질문에 세 좌석이 모두 '고분자 재료 물성' 으로
모였고 위임이 `material-twin-analyst`(물성 페르소나, 근거 17건)로 갔다.

**④ 답변 상한에 걸린 좌석이 조용히 사라지던 것.**
`THINK_MAX_ANSWERS`(5) 초과분을 그냥 잘랐더니, '예심 통과 10명' 이라고 해 놓고 5명만
물어본 사실이 어디에도 안 남았다. **묻지 않은 좌석이 기권한 것처럼 읽힌다.** 따로 담아
종합과 `summary.capped` 에 싣는다.

**⑤ 산문으로 온 답이 통째로 버려지던 것(테스트가 잡았다).**
JSON 을 못 낸 응답을 `error` 로 접었는데, 그러면 형식만 어긋난 **실제 답변**이 사라진다.
본문이 40자 이상이면 `(형식 미준수 — 원문 그대로)` 를 붙여 답으로 강등 보존한다.
심의 `_persona_round` 의 '구조화 실패 — 원문 강등' 과 같은 취급이다.

## D5 (2026-09-08) — 세션 토글로 둔 이유

`Conversation.thinking`(대화 단위)을 먼저 만들었다가 걷어내고 `searchSources` 와 같은
**세션 토글**로 바꿨다. 이유는 둘.
- 같은 성격이다. 둘 다 "지금 이 모드로 물어본다" 이지 대화의 속성이 아니다.
- 코드가 절반이다. 대화 단위로 하면 생성·복원·직렬화·draft 이관 네 곳이 늘어난다.

전송 시점 스테일을 막으려고 `thinkingRef` 를 둔다 — 상태만 쓰면 `sendMessage` 클로저가
옛 값을 실어 토글이 한 턴 늦게 반영된다(`delibOptsRef` 와 같은 패턴).

## D6 (2026-09-08) — 검증하지 못한 것

**브라우저 렌더는 실측하지 못했다.** 포털이 로그인을 요구하고 자격이 없다.
확인한 것은 여기까지다 — 타입 통과(`pnpm build` 성공), 포털 `ChatRequest.thinking` 파싱과
포워딩 분기(파이썬으로 직접 호출), agent-server SSE 프레임 전체(실주행 4회).
남은 위험은 `ThinkView` 의 시각 배치뿐이고, 데이터 경로는 전부 확인됐다.
