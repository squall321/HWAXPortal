# 띵킹 모드 — 답할 수 있는 전문가만 각자 답한다

## 무엇

챗에 켜고 끄는 모드 하나. 켜면 질문 하나가 전문가 풀(781명)에 돌아가고,
**답할 수 있는 좌석만 각자 답한다.** 못 하는 좌석은 억지로 답하지 않고
**넘길 곳을 지목한다.** 그 지목을 따라 한 홉 더 소집한다.

**심의가 아니다.** 라운드도 반박도 표결도 의장 결정문도 없다. 서로 읽지 않는다.
사용자는 각자의 답변을 그대로 듣는다.

## 왜 — 지금 없는 것

포털에는 전문가를 부르는 길이 셋 있는데 셋 다 이 일을 못 한다.

| 기존 | 하는 일 | 못 하는 일 |
|---|---|---|
| `pinned_agent` 챗 | 사용자가 **고른** 1명이 답한다 | 누가 적임인지 사용자가 이미 알아야 한다 |
| `/전문가` 검색 | 추천 목록을 **보여준다** | 답을 주지 않는다 |
| `/심의` | 5~8명이 **회의**해서 결정문 하나 | 오래 걸리고, 답 하나로 뭉개지고, 기권 채널이 없다 |

띵킹 모드는 그 사이를 메운다 — 사용자가 고르지 않아도, 회의하지 않아도,
답할 수 있는 사람들의 답을 각각 받는다.

## 핵심 요구 — "단순 벡터 유사도로 보지 않는다"

사용자 지시의 핵심이다. e5 임베딩은 **무관한 문장도 코사인 0.87~0.90** 을 낸다
(리포 정본 `docs/gotchas.md`, 메모리 `e5-embedder-baseline`). 실제 사고도 있었다 —
'OCA 의 산소 확산 계수' 질의에 백플레인 TFT·안테나 OTA 가 추천됐는데, 랭킹 버그가
아니라 **풀에 그 전문성이 아예 없었다**(`recommend_svc.py:255-262` 주석).

그래서 답변 자격을 **네 신호**로 본다. 벡터는 그 중 하나일 뿐이다.

| # | 신호 | 정체 | 벡터 독립 | 비용 |
|---|---|---|---|---|
| 1 | `desc_match` | 질의 토큰이 좌석 프로필에 포함된 **어휘 비율**(0~1) | **예** | 0 (추천에 딸려 온다) |
| 2 | `matched_sections` / `matched_records` | 의미검색 top-50 중 **그 좌석 소유** 근거 수 | 아니오(순위) | 0 |
| 3 | `agent_search(key, q)` 의 `hit_count` · `refused` | **그 좌석에 실제로 바인딩된 문서** 위에서 돌린 검색 | 아니오(순위) | 좌석당 1콜 (0.1초) |
| 4 | **좌석 자기판정** | 좌석이 자기 역할 + 자기 지식카드 발췌를 보고 스스로 "답할 수 있나" 를 판정 | **예** | 좌석당 LLM 1콜 |

1~3 은 **예심**이다. 후보를 싸게 좁힌다.
4 가 **본심**이고, 답변 가능 여부의 최종 판정은 좌석 자신이 자기 근거를 보고 내린다.
"이 어휘를 안다" 와 "답할 수 있다" 는 다르고, 그 차이는 근거를 봐야 갈린다.

## 파이프라인

```
질문
 │
 ├─(0) 소집    recommend_agents(q, top_k=THINK_CANDIDATES)
 │             → key · score · desc_match · matched_* · why
 │
 ├─(1) 예심    좌석마다 병렬 agent_search(key, q, mode="semantic")
 │             탈락 조건은 AND 다 — hits=0 **그리고** desc_match < 바닥값.
 │             한쪽만으로 자르지 않는다. 데이터는 없는데 어휘가 맞는 좌석
 │             (신규 도메인)과, 어휘는 안 맞는데 내용이 걸린 좌석을 둘 다 살린다.
 │
 ├─(2) 본심    통과 좌석마다 LLM 1콜(동시성 제한). 자기 지식카드를 보고 판정.
 │             {verdict:"answer"|"pass", scope, answer?, basis[], refer[]}
 │
 ├─(3) 위임    pass 좌석이 낸 refer(짧은 명사구)로 재소집.
 │             이미 나온 키·도메인 제외. 홉 THINK_HOPS 회(기본 1).
 │             새 좌석은 (1)(2) 를 다시 탄다.
 │
 └─(4) 종합    코드가 결정적으로 조립한다. LLM 합성 없음.
               답한 좌석 / 넘긴 좌석 / 넘긴 이유 / 넘긴 곳.
```

**아무도 답 못 하면 그렇게 말한다.** 그것이 이 모드의 가장 값진 출력이다 —
풀에 그 전문성이 없다는 사실을, 그럴듯한 오답 대신 받는다.

## 왜 심의 엔진을 재사용하지 않는가

재사용을 검토했고, **엔진 본체는 쓰지 않는다.** 이유 넷.

1. **회의가 아니다.** 라운드 루프·반박 계약·표결·의장은 전부 불필요하다.
2. **심의에는 기권 채널이 없다.** 스키마에 `abstain`/`pass` 가 없고, `stance`
   판별 불가는 **`조건부 동의` 로 떨어진다**(`deliberation.py:1348`) — 침묵이 동의로
   집계된다. 오히려 `rebut_quote` 가 켜지면 "인용 없는 반박 불인정" 으로 **재시도를
   걸어 할 말 없는 좌석을 재촉한다**(`:1144-1146`). 이 모드의 요구와 정반대다.
3. **`_CHAIR_ITEMS` 는 손댈 수 없다.** `scripts/check_chair_parity.py` 가 JS 정본
   `infra/pipeline/hwax-deliberate.js` 및 앱 자산과 **바이트 동일** 검사를 한다.
   새 유형을 파이썬에만 넣으면 파리티가 깨진다.
4. **`_DEFAULT_OPTS` 는 모듈 전역 SimpleNamespace 다.** mutate 하면 프로세스 전역이
   오염된다.

**재사용하는 것**은 순수 헬퍼뿐이다 — `_tools_by_name` · `_call` · `_llm_text` ·
`_parse_json` · `_first_dict` · `_restore_role` · `_sse` · `_dom_of`.
특히 `_call` 은 반드시 거친다. 직접 `MultiServerMCPClient` 를 쓰면 이미지 base64 가
근거로 새어 들어간다(실측 사고, `deliberation.py:868-870`).

## 계약

### 요청

`ChatRequest.thinking: bool = False` — **top-level 필드**다. `delib_opts` 가 아니다.
`delib_opts` 는 심의 경로에서만 소비되고, 슬래시 접두사는 **첫 발화에만** 붙어
(`ChatContext.tsx:426`) 둘째 턴부터 조용히 꺼진다. 매 턴 켜져 있어야 하는 모드는
필드로 실어야 한다.

편의용 슬래시 트리거 `/띵킹` · `/생각` · `/thinking` 도 둔다(MCP·단발용).

### SSE

공통 계약 `status` · `token` · `result` · `error` · `done` 을 그대로 지키고,
구조화 데이터는 **이벤트 하나(`think`) 안에 `kind` 로 접는다**. `delib` 의 선례를
따른다 — 종류마다 이벤트 이름을 늘리면 프론트 switch 를 매번 고쳐야 한다.

| kind | payload |
|---|---|
| `roster` | `{hop, seats:[{key, name, domain, score, desc_match, sections, records}]}` |
| `screen` | `{key, hits, top, passed, reason}` — 예심 결과 |
| `verdict` | `{key, verdict:"answer"\|"pass", scope, refer:[str]}` |
| `answer` | `{key, name, domain, text, basis:[str]}` |
| `handoff` | `{from_:[str], phrases:[str], seats:[str]}` |
| `summary` | `{answered:int, passed:int, screened_out:int, hops:int, no_answer:bool}` |

같은 내용을 `token` + `result` 텍스트로도 낸다. 프론트가 이벤트를 몰라도 사용자는
답을 받고, 포털 대화 저장소(`result.content` 만 본다)에도 남는다.

## 결정과 그 이유

- **v1 에서 좌석에게 도구를 주지 않는다.** 답변 근거는 역할 + 자기 지식카드다.
  도구를 열면 좌석 수만큼 ReAct 왕복이 붙어 지연이 배가되고, 자격 판정과 도구
  실패가 섞여 "못 답한 것" 과 "도구가 죽은 것" 이 구분되지 않는다. 후속 과제로 둔다.
- **의장 합성을 두지 않는다.** 사용자 요구가 "각자의 답변을 듣는 것" 이다.
  종합은 코드가 세는 숫자와 명단뿐이고 LLM 을 부르지 않는다.
- **`mode="semantic"` 고정.** `hybrid` 는 **102 초**, `fts` 는 **221 초** 다(실측).
  원인은 `record_sections.content_text` 의 `to_tsvector` 식에 GIN 인덱스가 없어
  862,910 행 순차 스캔이 나는 것이다. 별건이므로 따로 보고한다.
- **동시성 세마포어를 둔다.** 심의 엔진에는 없고(정찰 실측 0건) 좌석 수만큼 무제한
  팬아웃한다. 이 모듈은 자기 상한을 갖는다.

## 손잡이

| env | 기본 | 뜻 |
|---|---|---|
| `THINK_CANDIDATES` | 10 | 홉당 소집 후보 수 |

## 범위 밖

- MCP 진입점(`deliberate_*` 계열에 띵킹을 추가하는 것) — 사용자가 요구하지 않았다.
- 좌석 답변의 RA 보고서 저장 — 심의와 달리 결정문이 없으므로 저장 단위가 다르다.
- 답변 간 상호 참조·수렴 — 그것이 심의다.
