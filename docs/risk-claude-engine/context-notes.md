# 리스크 심사 Claude 길 — 결정과 까닭

**X-D1 사용자 결정(2026-10-15).** "일단 현행 계획대로 완료해주고 완전 클로드 버전으로도 할 수 있게끔만 해두고 그거는 테스트는 하지 말고 유저가 원하면 할 수 있게끔만 하자." — M3 는 GLM 으로 끝내고, Claude 길은 지어 두되 기본 꺼짐이다. '테스트는 하지 말고' 는 실제 Claude 로 심사를 돌리는 시험(사용량)을 하지 않는다는 뜻으로 읽었다 — 가짜 응답자로 배선이 깨지지 않았는지 보는 코드 시험은 넣는다(전역 지침 8 '테스트 후 완료').

**X-D2 사용량 어림(10-15, 실측 아님 — ±40%).** M3 전원 한 번은 호출 약 17,000(거르기 꺼짐)·10,000(켬), 입력 약 2.4억·1.5억 토큰, 출력 약 3,500만·2,200만 토큰이다. 바탕 — 카드 전부 평균 57,072자·카드당 약 1,900자·점검 카드 12.9장(8장씩 셀당 2번)·글자/토큰 2·단위 본문 3,000자(M0-c 미실측이 가장 큰 불확실). Claude Code 서브에이전트로 돌리면 호출마다 기본 문맥이 붙어 묶어 처리하지 않으면 두 배 가까이 된다. 그래서 전원 전부를 Claude 로 돌리는 것은 구독 한도로는 현실적이지 않다고 사용자에게 말했고, 나눠 쓰기(카드 대조 GLM · 쟁점 패널·종합만 Claude, 약 3,000만 토큰)와 대표 9명 비교 실행(600만~800만 토큰)을 권했다.

**X-D3 모양 — 앱이 아니라 엔진의 LLM 자리에 꽂는다.** 앱이 Claude 에게 직접 과제를 주면 엔진의 프롬프트·파서·보충 되묻기를 둘로 갈라 지녀야 한다(엔진과 앱의 정체성 규칙이 어긋나 D-44·D-46 의 결함이 났던 것과 같은 길). 엔진의 `delib_llm` 자리에 외부 응답자를 꽂으면 계약·검사·원장이 하나로 남는다. 쟁점 패널은 외부 응답자가 엔진의 도구를 실행할 수 없어 evidence_only 로 돈다.

**X-D4 X-1 을 지으며 정한 것(2026-10-15, 가지 `external-llm`).** 엔진에는 `tool_mode` 가 없다 — evidence_only 는 좌석의 자유 조회(`free_tools`)를 끄는 것이다. 외부 심의는 그 창(`EXTERNAL_LLM_CTX_TOKENS`)으로 근거 예산을 다시 잰다(1M 창 기준으로 지은 프롬프트가 Claude 로 가지 않게 — /health 의 `evid_budget`). 부재 판정은 '그 주인이 조용한 시간' 으로 잰다 — 주인이 과제를 집고 있는 동안은 대기 과제가 늙지 않는다(좌석 20개를 한 워커가 차례로 답하는 동안 '부재' 가 되지 않게). GLM 계약 디렉터리는 그대로 두고 외부 계약은 따로 둔다(리스크 앱이 GLM 계약을 바이트째 복사해 포털이 재생한다).

**X-D5 반대 검토 1라운드(2026-10-15, HIGH 1 · MEDIUM 2 · LOW 8 · 가설 2).** ① 요청이 다시 줄을 선 뒤 새로 집히면 앞 집기의 늦은 제출이 새 집기의 버퍼에 섞였다(두 답이 이어 붙은 '잘 생긴' 답) — 집기마다 `lease` 를 주고 읽기·제출이 그것을 요구한다. ② 퍼센트 풀기를 날 이메일에도 걸어 `ev%41l@…` 가 다른 사람의 과제를 받았다 — 게이트웨이 머리에서 온 신원만 푼다. ③ 사람 속도로 답하는 워커를 기다리는 외부 호출이 GLM 관문 자리를 쥐어 다른 사람의 GLM 카드 대조가 막혔다 — 외부 호출은 GLM 자리를 쓰지 않고 주인마다 상한(`EXTERNAL_LLM_MAX_INFLIGHT`)을 두되, 비우기 중에는 거절하고 비우기가 기다리는 활동 수에 든다(재기동은 메모리의 줄을 잃는다). ④ **반출 동의를 엔진도 본다** — 외부로 내용을 보내는 요청(카드 대조 run · 외부 심의 · MCP `advanced.llm`)은 `consent_external: true` 가 없으면 과제를 만들기 전에 `external_consent_required` 로 거절한다(앱이 동의를 받고 누가 했는지 적는다 — 엔진의 검사는 그 겹 위의 한 겹이다). ⑤ 이 박스의 GLM 챗·심의 에이전트는 과제 도구 셋을 묶지 않는다(지식카드에 숨은 지시로 챗이 사용자의 과제를 집거나 답하지 않게). ⑥ 작은 것 — 근거 예산 캐시를 창별 한 값으로, 부재 빠른 실패는 WAIT_S 뒤 풀림, 오프셋은 '유니코드 코드 포인트' 라고 적고 머리에 `max_chars`, 외부 길의 잘림 오류는 `EXTERNAL_LLM_MAX_TOKENS` 를 손잡이로, GLM 이어하기가 강제된 `free_tools:0` 을 물려받지 않게, 켠 박스에서 값이 틀리거나 시간 사슬이 깨지면 기능을 끈 채 기동 오류(더 큰 기본값으로 조용히 가지 않는다), 오래 쉰 주인 항목 정리.

**X-D6 반대 검토 2라운드(2026-10-15, MEDIUM 1 · LOW 3 · 가설 1).** 스위치를 끈 길은 main 과 바이트째 같다 — 도구 목록 · 기동 출력 · /health · /drain · limits · GLM 계약 · 심의 13 장면 · 챗 도구 묶기를 견줬다(운영 박스는 이 상태로 이 코드를 받는다). 켠 길에서 하나가 남았다 — 이 박스의 GLM 챗이 `deliberate_start` 를 `invoke_tool` 로 불러 `advanced.llm=external` 과 `consent_external:true` 를 **스스로** 달면 외부 심의가 서고 원장에 거짓 동의가 남는다(지식카드에 숨은 지시 한 줄로 X-D5 ④⑤ 를 비켜 간다). 자체 에이전트가 부르는 `deliberate_start`·`deliberate_continue` 에 외부 선택이나 동의 칸이 있으면 넘기지 않고 거절한다 — 사람의 동의는 사람의 클라이언트에서만 온다. 작은 것 — 아주 큰 수가 기동을 넘어뜨리던 것(설정 오류로 닫는다), 시험이 셸의 스위치를 물려받아 매달리던 것, 모르는 `delib_opts.llm` 값을 GLM 으로 조용히 돌리던 것(카드 대조처럼 거절), 사람 속도의 워커를 기다리는 외부 MCP 심의가 전역 심의 자리(`DELIB_JOB_MAX_RUNNING`)를 쥐던 것(주인마다 하나로 따로). X-3 워크플로는 자기가 맡은 잡(run_id·target_key)의 과제만 답한다(주인 줄은 선착순이라 겹으로 막는다).

**X-D7 X-2(리스크 앱) 반대 검토(2026-10-16, HIGH 1 · MEDIUM 3 · LOW 3).** GLM 길은 main(`d18e9d6`)과 같다 — main 의 시험을 새 코드에 돌리고(3,197 통과, 다른 것은 바뀐 표면 고정 둘뿐), 같은 장면의 잡 만들기 · 검토 루프 · 실패 처리 · 쟁점 패널 · 종합의 출력을 옛·새 나란히 떠 견줬다(의도한 칸 말고 차이 0). 결함은 모두 Claude 길을 켰을 때다. ① **동의가 번진다** — 쟁점·종합 잡이 대상마다 하나라, 남이 GLM 으로 낸 일(사슬 · 사람이 다시 줄 세운 쟁점 · 보고서 다시 내기)이 동의한 사람의 살아 있는 Claude 잡에 붙어 그 사람의 PAT 로 바깥에 나갔다. Claude 사슬 잡은 제 사슬이 고른 일만 하고, 다른 출처는 GLM 잡으로 간다(값이 다른 llm 끼리 잡을 다시 쓰지 않는다). ② MCP `risk_start_job` 의 동의 칸이 `"true"`·1 을 참으로 받았다 — StrictBool. ③ 멈췄다 재개한 종합 잡에 인프라 재시도 몫이 없었다. ④ 이 박스의 GLM 챗이 사용자 이름으로 `risk_start_job(llm=claude, consent_external=true)` 를 부를 수 있다(가설) — 엔진의 자체 에이전트 거절(X-D6)을 그 도구와 REST 다리까지 넓힌다. 작은 것 — Claude 패널의 모델 기록, 패널 모드에서 llm 선택을 말없이 버리던 것, 동의자 기록이 없을 때 대신 다른 PAT 로 가던 숨은 길(닫는다).


**X-D8 X-3b 워크플로 `hwax-risk-claude` 를 지으며 정한 것(2026-10-16, 가지 `x3b-workflow`).** 실제 Claude 로는 돌리지 않았다(X-D1) — 가짜 런타임과 엔진 Board 규칙을 따르는 가짜 과제 줄로만 본다(`backend/tests/test_risk_claude_workflow.py` 36건, 사본 변이 31/31).
① **프롬프트를 워크플로로 옮겨 오지 않는다.** 워크플로 스크립트는 MCP 를 직접 못 부르고 에이전트 출력으로만 값을 받는다. 훑기 과제의 프롬프트는 약 12만 자라 쪽을 옮겨 적게 하면 그만큼 출력 토큰이 들고(답 한도 `EXTERNAL_LLM_ANSWER_S` 1,200초 안에 끝나지 않는다) 옮겨 적기가 말없이 바꿔 적는다(`hwax-risk-review.js` 에코 예산의 실측 C37/C50). 그래서 에이전트를 셋으로 나눴다 — 집기(review_task_next 만, 한 에이전트가 긴 폴링 6번까지) · 답(review_task_read 로 직접 읽고 답만 돌려준다, 내지 않는다) · 내기(워크플로가 자른 조각 하나를 싣는다). 읽기가 끝까지 됐는지는 답 에이전트가 적어 온 쪽 사슬(보낸 offset · 받은 next_offset)로 본다 — 첫 쪽 0, 다음 쪽이 앞 쪽의 next_offset, 마지막이 null, 한 쪽 20,000자 이하, 끝이 머리의 chars. 자기 신고라 거짓말은 못 막지만 앞쪽만 읽고 쓴 답 · 건너뛴 쪽은 쪽 크기와 무관하게 드러난다. 빠졌으면 까닭을 붙여 한 번 다시 쓰게 하고, 또 빠지면 내지 않는다(read_incomplete — 잘 생긴 틀린 답보다 답 한도 뒤 다시 집히는 편이 낫다).
② **답은 워크플로가 코드 포인트로 잘라 내고, 받은 길이가 다 맞은 뒤에야 마친다.** 조각은 15,000 코드 포인트 안(도구 설명의 20,000 보다 좁게 — 옮겨 싣기 몫), 창의 뒤쪽 절반에 줄바꿈이 있으면 그 뒤에서 끊는다(줄 가운데서 끝난 조각을 '마저 잇는' 일을 줄인다). 조각마다 offset 을 명시하고 서버의 received_chars 가 조각 끝과 다르면 옮겨 싣기가 바꿔 적은 것이라 처음부터(offset 0) 다시 낸다 — 마치기 전이라 엔진에는 아무것도 가지 않았다. 마지막 조각의 에이전트는 받은 길이가 정확히 전체일 때만 빈 글 · final 로 마친다(에이전트 하나를 아낀다). 조건을 어기고 마쳤으면 엔진이 받은 길이(chars + cut_chars)로 견줘 delivered_mismatch 로 남긴다 — 성공으로 적지 않는다.
③ **offset_mismatch 는 받은 길이가 우리 조각의 경계이고 우리가 낸 범위 안일 때만 거기서 잇는다.** 보고를 잃은 조각이 이미 붙은 경우다. 경계가 아니면 서버의 버퍼는 우리 답의 앞부분이 아니므로 처음부터 낸다(그 자리에서 이으면 글이 겹치거나 빠진다). 마치는 호출의 보고를 잃은 뒤의 task_not_found 는 이미 엔진에 넘어갔을 수 있어 delivered_unconfirmed 로 남긴다. not_claimed 면 그 임대로 다시 내지 않는다 — 새 집기의 버퍼에 닿지 않는다(엔진 X-D5 ①).
④ **길이.** 답이 max_chars(엔진의 한국어 최악 어림 — 넘어도 꼭 잘리지는 않는다)를 넘으면 한 번 줄여 다시 쓰게 하고, 그래도 넘으면 그대로 낸다 — 엔진이 상한에서 잘라 받는 것(finish_reason=length, 끝 요약의 '잘린 답')이 집은 과제를 답 없이 두어 잡을 답 한도 동안 세우는 것보다 낫다. answer_too_large 는 min(max_chars, 서버 상한 − 1) 안으로 다시 써서 offset 0 부터 낸다 — 임대가 풀렸으면 첫 조각이 not_claimed 로 끝나 거기서 멈춘다.
⑤ **멈춤 · 동시 수.** 빈 집기(25초 긴 폴링)가 idlePolls 번(기본 6) 잇달면 멈추되, 그동안 어디서든 과제가 집히거나 끝났거나 누가 과제를 쥐고 있으면 세지 않는다 — 엔진은 답을 받은 뒤에 다음 라운드 · 다음 셀을 세우므로, 한 일꾼이 긴 과제를 쓰는 사이 다른 일꾼이 먼저 멈추면 그 뒤로는 일꾼 하나가 줄 전체를 받는다(시험이 본다). 일꾼은 기본 4 · 최대 8(엔진 `EXTERNAL_LLM_MAX_INFLIGHT` 기본값 — 더 많으면 빈 집기만 는다). maxTasks 는 집기 전에 자리를 잡아 동시에 도는 일꾼이 넘겨 집지 않는다. 런타임은 워크플로 하나에 에이전트 1,000 개까지라 800 개에서 새 과제를 집지 않고 쥔 과제만 끝낸다 — 과제 하나에 에이전트가 대개 셋(집기 · 답 · 내기)이라 한 번에 약 260건이다(전원을 Claude 로 돌리는 것은 X-D2 대로 현실적이지 않다 — 여러 번 돌린다). 집기 · 내기 에이전트는 effort low, 답 에이전트는 세션의 것을 쓴다.
⑥ **맡은 과제만.** 머리의 target_key 가 args 의 대상(targetKey · targetKeys)이 아니면 읽지도 답하지도 않는다(X-D6). 집은 과제를 놓는 도구가 없어 쥔 채 두고 다음 과제로 간다 — 엔진이 답 한도 뒤 되돌리고 두 번째도 답이 없으면 external_answer_timeout 이다. 그래서 같은 사람이 Claude 잡을 둘 돌리면 대상을 함께 줘야 한다(로그가 그렇게 말한다). 대상이 없는 과제도 같은 대우다 — 맡은 잡의 것인지 가릴 수 없다(run_id 는 심의 단마다 새로 지어 미리 알 수 없다).
⑦ **남은 틈(막힘) — 쟁점 패널 심의 과제에는 대상 표지가 없다.** 엔진은 카드 대조 과제의 대상을 요청의 target_key 에서, 심의 과제의 대상을 질문 머리 `[리스크심사 <과제> <대상>]`(`_RISK_Q_HEAD_RE`)에서만 읽는다. 리스크 앱의 쟁점 패널 질문(`issues.issue_question`)은 `[쟁점 <id> · <종류>] …` 로 열려 대상이 비고, ⑥ 대로 이 워크플로는 답하지 않는다 — 그대로면 Claude 잡의 쟁점 패널이 답 한도 뒤 external_worker 로 멈춘다(카드 대조 · 요약 과제는 대상이 실린다). 길은 셋이고 여기서 고르지 않았다 — (가) 엔진이 외부 심의 과제의 대상을 명시 칸(예 `delib_opts` 의 새 칸 — 포털 DelibOpts 는 선언 안 한 칸을 말없이 버리므로 중계도 함께)으로 받고 앱이 보낸다 (나) 앱이 쟁점 질문에도 `[리스크심사 <과제> <대상>]` 머리를 붙인다 — GLM 쟁점 패널의 앞 패널 보고서 거름이 '전부' 에서 '같은 과제' 로 바뀌므로 그 결정이 함께 든다 (다) 워크플로가 대상 없는 심의 과제를 켜는 칸으로 받는다 — 겹 하나가 약해진다. 가짜 시험은 대상 없는 과제를 답하지 않는 것과 그 까닭을 로그가 말하는 것을 본다.
⑧ **부르는 법.** 이름으로는 못 부른다(내장 워크플로만 이름 해석) — Workflow 의 scriptPath 에 `<리포루트>/infra/pipeline/hwax-risk-claude.js`, args `{targetKey: 'diff:…'}`(여럿이면 targetKeys). 자식 워크플로가 없어 사본(`.claude/workflows/`)에서 불러도 된다. 사본은 `sync-workflows.sh` 가 meta 있는 파일을 그대로 덮으므로 고칠 것이 없었다(사본 디렉터리에서 동기 뒤 `--check` 0 — 시험이 본다).
⑨ **X-4 에 넘길 것.** (가) 답 에이전트는 Claude Code 서브에이전트라 프롬프트 전문(엔진이 `EXTERNAL_LLM_CTX_TOKENS` 로 짠 크기) 위에 그 에이전트의 기본 문맥(시스템 · CLAUDE.md · 도구 목록)과 답(`EXTERNAL_LLM_MAX_TOKENS`)을 함께 담는다 — 그 손잡이는 사람들이 쓰는 Claude 창에서 그 몫을 뺀 값으로 잡는다(아니면 답 에이전트가 프롬프트를 다 담지 못한다). (나) 런타임의 에이전트 동시 수(min(16, CPU − 2))가 일꾼 수보다 작으면 긴 폴링 중인 집기 에이전트가 자리를 쥐어 답 에이전트가 한 폴링 창(최대 150초)만큼 늦게 뜬다 — 답 한도(1,200초) 안이지만 코어가 적은 PC 에서는 concurrency 를 그 수 아래로 준다. (다) 한 쪽(20,000자)이 드문 한자 · BMP 밖 글자로 Claude Code 의 MCP 결과 상한(`MAX_MCP_OUTPUT_TOKENS`, 기본 25,000토큰)을 넘으면 결과가 파일로 저장된다 — 답 프롬프트가 그 파일에서 꺼내 읽으라고 말한다(브리프의 GA-1 과 같은 길). 되풀이되면 그 셸의 상한을 올린다.

**X-D9 쟁점 패널 과제의 대상 열쇠는 (a) — 명시적으로 싣는다(2026-10-16).** X-3b 가 찾은 막힘 — 엔진은 과제 머리의 `target_key` 를 질문 머리 `[리스크심사 <code> <key>]` 에서만 읽는데 쟁점 패널 질문은 `[쟁점 …]` 로 시작하고 `run_id` 는 단계마다 새로 난다. 워크플로는 제 잡의 과제만 답하므로(X-D6) Claude 잡의 쟁점 패널이 시간을 넘겨 `external_worker` 로 선다. 길 셋 가운데 (a)를 골랐다 — 엔진이 외부 심의에 한해 `delib_opts.target_key` 를 받아 과제 머리에 싣고, 리스크 앱이 보내고, 포털이 중계한다. (b) 질문 머리에 `[리스크심사 …]` 를 붙이는 길은 GLM 쟁점 패널의 이전 보고서 거르기를 '전부' 에서 '같은 과제' 로 바꾼다 — GLM 길은 그대로 둔다는 원칙에 어긋난다. (c) 대상 없는 과제도 답하게 여는 길은 문지기를 약하게 한다. 포털 중계 칸은 엔진 변경이 main 에 든 뒤 함께 넣는다 — 계약 시험이 '포털이 내는 값을 엔진이 실제로 읽는가' 를 보므로 먼저 넣으면 깨진다.
