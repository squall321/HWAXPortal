# 심의 엔진 변경 — 결정 기록

## D-1. 요청서의 진단을 dev 에서 다시 재현하고 시작한다 (2026-10-07)
요청서는 cae00 소스를 읽고 쓴 것이다. dev 의 `deliberation.py` 는 4,189줄로 같고 인용된 자리가 1~4줄 안에서 전부 맞았다
(`:76` 좌석 상한 · `:89` 의장 상한 · `:781-786` 근거 정규화 · `:1836` 80자 절단 · `:3311-3339` 지식카드 · `delib_jobs.py:256-259`).
지적은 가설이라 재현한 것만 고친다 — 이번엔 전부 재현됐다.

## D-2. 도구 설명에 숫자를 다시 박지 않는다 (1-4)
`deliberate_start` 설명의 「항목당 12,000자」는 상수(150,000)를 복제해 두었다가 낡은 자리다. 숫자를 고쳐 적으면 같은 일이 또 난다.
설명 문자열을 **상수에서 읽어 만든다**(모듈 로드 때 f-string) — 상수가 바뀌면 설명이 따라 바뀐다. 시험은 설명에 실제 값이 들어 있는지 본다.

## D-3. 좌석 상한 — 엔진은 env 손잡이, 포털 셋은 20 그대로 (1-12·4-2)
실사용 팀은 MCP(`deliberate_start`)와 리스크 앱 경로로 부른다 — 둘 다 포털 스키마를 안 거치므로 엔진 env(`DELIB_MAX_SEATS`)만으로 21·22석
패널이 풀린다. 포털 웹 경로까지 env 를 따라가게 하려면 백엔드 설정 + 프론트가 값을 받아 오는 경로가 새로 필요한데, 요청된 것은 손잡이다.
포털은 더 좁은 쪽(20)으로 남아도 안전하다(초과는 422 로 **소리 내** 막힌다). 계약 시험은 포털 셋 == 엔진 **기본값** 으로 바꾼다.
⚠ 엔진은 지정 반대석을 상한 밖에서 얹는다 — 20석 요청은 21석으로 돈다(종전부터).

## D-4. 근거 키는 `[e:N|KEY]` 로 — 형식을 먼저 못박는다 (3-2)
엔진·JS 파이프라인·리스크 앱 셋이 같은 줄 모양을 알아야 해서 형식을 먼저 정했다.
- 입력: 근거 항목의 선택 필드 `key`(문자열, `^[A-Za-z0-9_.-]{1,24}$` — 아니면 무시).
- 표기: 키가 있으면 `· [e:N|KEY] [출처 …] 본문`, 없으면 종전 그대로 `· [e:N] …`.
- 인용: 좌석·의장은 종전대로 `[e:N]` 을 적는다. `[e:N|KEY]` 로 적어도 같은 항목으로 읽는다(인용을 해석하는 자리 전부).
리스크 앱은 `brief.py` 가 반환 직전에 떼던 `key` 를 다섯 번째 필드로 남기기만 한다 — `line_overhead`·`CAPS` 산술은 손대지 않는다.
⚠ 리스크 앱의 인용 문법에는 `e:` 가 엣지 참조로도 쓰인다 — 충돌 여부를 리스크 쪽에서 확인한다.

## D-5. 의장 전사 상한은 유도하되 env 가 이긴다 (1-7)
`DELIB_DECISION_CTX` 를 **명시하면 그 값**(0=무제한, 종전 의미 그대로)이고, 안 주면 모델 컨텍스트에서 유도한다. 좌석 프롬프트가 이미
감당하는 회계(`_SEAT_CTX`·`_pre_budget()`)를 넘지 않는 선에서 라운드 수로 나눈다 — 좁은 창(dev 16K)에서 종전(6,000)보다 나빠지지 않아야 한다.
실사용 팀이 §5 로 넣는 `DELIB_DECISION_CTX=24000` 은 이 유도를 덮는다 — 반영 뒤에는 빼도 된다고 알린다.

## D-6. 동시 실행 — 누출 수정 + 사용자별 손잡이까지, 큐는 안 한다 (1-9)
거절 메시지가 남의 job_id 를 보여 주던 것은 버그라 고친다. 사용자별 상한(`DELIB_JOB_MAX_RUNNING_PER_USER`)은 손잡이를 만들되 **기본값은
전역 상한과 같게** 둔다 — 전역 2 는 LLM 큐 보호선이고 용량은 여기서 잴 수 없어 기본 동작을 바꾸지 않는다. 운영은 전역을 올리고 사용자별을
낮춰 쓴다(예: 6 · 2). 대기 큐는 `deliberate_start` 의 반환 계약(즉시 running)을 바꿔 리스크 러너까지 건드리므로 요청서도 선택으로 둔 것을 뺐다.

## D-7. human_note — 조용히 자르지 않는다, 엔진 기본값은 포털 상한 이하 (1-11·4-4)
포털 `DelibOpts.human_note` 는 8,000자를 받는데 엔진은 2,000자에서 말없이 자른다 — 요청서가 찾은 것과 같은 모양의 결함이 하나 더 있었다.
상한을 env(`DELIB_HUMAN_NOTE_MAX`)로 빼고, 잘랐으면 화면에 남긴다. 엔진 기본값은 요청대로 2,000 이다 — 이 글은 매 라운드 전 좌석에
실리는데 컨텍스트 회계(`_pre_budget`)에 들어 있지 않아, 기본값을 포털에 맞춰 8,000 으로 올리면 좁은 창에서 넘칠 수 있다. 포털 8,000 은
바깥 경계로 그대로 두고, 계약 시험은 **엔진 기본값 ≤ 포털 상한** 을 본다(env 를 8,000 위로 올리려면 포털 상한도 같이 올린다).

## D-8. `as_of` 는 조사 먼저 (2-2)
소급 검증에 필요한 것은 **문서가 만들어진 날**이지 색인된 날이 아니다. records 를 최근에 일괄 적재했다면 `created_at` 필터는 전부 걸러
내거나(닫힌 쪽으로 틀림) 아무것도 못 거른다. 이번엔 날짜 컬럼의 실제 분포를 재고 구현 여부를 정한다 — 요청서도 분리 가능하다고 적었다.

## D-9. 반대석 에이전트 등록은 하지 않는다 (2-3)
운영 AIDataHub 에 에이전트·레코드를 만드는 일이고 요청서가 선택으로 두었다. 1-1 로 404 는 사라지고 반대석의 역할은 시스템 프롬프트로 실린다.

## D-10. 소속 자동 매핑은 꺼진 채로 넣는다 (4-3)
부서 Claim 이 아직 안 열렸다. 매핑 표(`config/…`)와 Claim 속성 이름 설정을 두고, **속성 이름이 비어 있으면 아무것도 하지 않는다.** 켜져도
소속이 **빈 사람만** 채우고 관리자가 준 값은 건드리지 않는다(`user_store` 의 종전 원칙 유지) — 소속이 곧 권한이라서다.

로컬 `main` 이 origin 보다 2커밋 앞서 있고(다른 세션의 UI 개편 `31fe42d`·`b197504`) 프론트 12파일이 미커밋이다(10-04 수정). push 는 HEAXHub 의

사용자 지시 둘. ① 전부 고친다 — 그래서 선택으로 빼 두었던 대기 큐(1-9 ③)와 `as_of`(2-2)를 되살린다. 다만 **지금 도는 구현 단위는
D-6·D-8 을 그대로 따른다**(같은 파일을 순서대로 고치는 중이라 도중에 범위를 바꾸면 엇갈린다) — 이 둘은 1차 구현·검토가 끝난 뒤 2차로 얹는다.
`as_of` 는 1차의 날짜 컬럼 조사 결과에 따라 구현 범위가 정해진다. 2-3(반대석 에이전트 등록)은 여전히 하지 않는다 — 묶을 레코드가 0건이고,

② HWAXRisk 는 지금 다른 세션이 UI 를 개발 중이다. 여기서는 백엔드만 커밋해 두고, 그 개발이 끝나면 프론트까지 한꺼번에 push 한다(D-11 의 보류를

## D-13. 합성 지정석 지식 조회는 env 로 되살릴 수 있게 — 2차 (2026-10-07, 사용자)

묻지 않아 코드를 다시 고쳐야 한다. 사용자 결정: **등록된 키를 env 로 지정하면 그 좌석은 조회한다**(기본은 빈 값 = 지금처럼 전부 건너뜀).
1차 구현 단위는 1-1 을 요청서대로 두고, 이 손잡이는 대기 큐·`as_of` 와 함께 2차에 넣는다.

## D-15. 1차 구현 뒤 검토를 8·9·10차와 합친다 — `as_of` 는 보류 (2026-10-08)
1차 구현(엔진 P1~P3 · AIDataHub · hwax-risk · 포털 계약)이 끝난 시점에 8·9·10차 총정리(`docs/change-request-8-10`)가 왔다. 그 #1 이 4-3(D-10)과
같은 문제를 더 정확히 요청해, 4-3 구현 단위는 돌리지 않고 #1 로 대체했다. 같은 포털 파일을 두 요청이 고치므로 1차의 반박 검토는 따로 돌리지 않고
8·9·10차 구현 뒤 **다섯 리포를 한꺼번에** 검토한다.
`as_of`(2-2)는 조사 결과로 보류한다 — `created_at` 은 적재일이고(상위 4일에 68%) 문서 고유 날짜는 유형별로 흩어져 31% 가 날짜 없음이다.
`doc_date` 컬럼 + 백필 + 적재 경로가 먼저이고(약 2일), **지식카드를 작성일로 볼지 시대 무관 지식으로 면제할지**가 사람 결정으로 남는다(카드는 전부
2026-07~08 에 쓰여, 닫힌 쪽으로 걸면 그 이전 제품의 소급 검증에서 전부 빠지고 141석이 0건이 된다). 봉인 Job 이 지식카드를 통째로 끄므로 소급
검증 자체는 `as_of` 없이 된다. 2차로 넣는 것은 대기 큐(1-9 ③)와 합성 지정석 지식 env(D-13)다.
1차가 요청 밖에서 더 고친 것 — MCP 호출자가 버려진 근거를 보게 잡 원장에 싣기, JS 의장 프롬프트의 쉼표 결함(출력 형식 지시가 한 번도 안 갔다),
포털이 `persona_knowledge`·`sealed` 요청 키를 말없이 버리던 것, hwax-risk 의 사용자 메모 유실·엉뚱한 잡 메모·품질 플래그 미적재.

## D-16. 2차·검토 결과 (2026-10-08)
- **대기 큐(1-9 ③)** — 상한에 걸리면 `queued` 로 줄을 세우고 자리가 나면 스스로 시작한다(`DELIB_JOB_QUEUE_MAX` 기본 20, 0 이면 종전처럼 거절).
  남의 잡에 가려 한 사람이 막히지 않게 사용자별 상한에 걸린 잡은 건너뛴다. 재기동은 줄을 못 넘긴다(호출자 토큰을 디스크에 두지 않는다) — 줄 섰던 잡은
  `interrupted` 로 닫히고 다시 시작하라고 알린다. 상태는 셋(queued · running · 끝)이고 도구 설명에 적었다.
- **반대석 지식 env(D-13)** — `DELIB_KNOWLEDGE_SYNTHETIC_SEATS`(쉼표 목록, 기본 빈 값). 적힌 합성 좌석만 지식카드를 묻는다. 봉인 실행은 이것도 닫는다.
- **잡 도구의 주인 확인** — 목록은 내 잡만 보이고, 남의 잡을 접는 것은 거절한다. **id 를 아는 사람이 남의 심의를 읽는 것**(상태·결과·전사·이어하기)은
  아직 열려 있다 — 운영자가 남의 심의를 들여다보던 쓰임이 있을 수 있어 사람이 정한다.
- **hwax-risk 후속** — 패널이 전부 HTTP 422 로 닫히고 있었다. 러너가 `timeout_s=2400` 을 보냈는데 그 값은 엔진에서 패널 벽시계가 아니라 **LLM 호출
  한 번**의 제한이고 상한이 1800 이다. 러너는 이제 그 값을 싣지 않고(호출당 제한은 박스 설정 몫), 벽시계 40분은 앱이 스트림에서 잰다. 이 제한들을
  넉넉하게 다시 잡는 일은 따로 한다(사용자 지시 10-08 — 시간 제한 전수 조사).
- **검토** — 8·9·10차와 한꺼번에 봤다(`docs/change-request-8-10` D-13). 엔진 쪽 major 는 여섯 — 이어하기가 이전 회차의 봉인을 풀던 것(둘), 시험·해석 설계가
  호출자의 사람 의견과 좌석을 말없이 버리던 것, 항목 상한에서 줄여 실은 근거가 흔적 없던 것, `key` 없는 좌석이 말없이 빠지던 것, 직렬화 값 700자 절단과
  지정 도구 결과 5,000자 절단이 표식 없던 것. 전부 고쳤다. 끝 시험 엔진 781건 통과.
- **요청 밖에서 더 고친 것** — 수치·웹 인용 대조를 보고서 저장 앞으로(저장된 보고서에 대조 결과가 실린다), 이어하기가 이전 결정문을 8,000자로 미리 자르던 것.

"타임아웃은 다 넉넉하게 — 실제 엄청나게 걸릴 수도 있으니까." 경로 전체(웹·MCP → nginx·게이트웨이 → 포털 → 엔진 → LLM, 엔진 → 게이트웨이 → 백엔드,
리스크 앱 러너)의 시간 제한 149건을 찾아 60건을 바꾸고 89건은 그대로 두었다. 값만 올리면 안 되는 사정이 넷이었다.
- **가장 빡빡한 것은 타이머가 아니라 자격이었다.** 포털이 찍는 심의용 토큰이 30~60분짜리라 그보다 긴 심의는 조회가 끊기고 마지막 RA 저장이 실패했다 → 24시간(`CHAT_PAT_TTL_S`).
- **살아 있다는 신호가 어디에도 없었다.** 의장 합성·좌석 발언 대기 동안 스트림이 0바이트라, LLM 제한만 올리면 침묵이 바깥 제한을 넘는다 → 엔진이 15초마다 ping(`DELIB_HEARTBEAT_S`).
- **LLM 제한이 박스마다 달랐다.** 설정 없는 박스는 무제한, 환경 키트 박스는 시도당 600초에 SDK 가 말없이 두 번 더 → 시도당 1800초·재시도 1회, 요청 상한 14400초(엔진·포털·프론트를 계약 시험으로 묶음).
- **끊긴 화면이 재시도를 권했다.** 엔진은 심의를 계속 돌리는데 화면은 네트워크 오류와 재시도 버튼만 보였다 → 끊겨도 돌고 있다고 알린다(회수·취소는 2단계).
정한 층(안쪽이 먼저 터진다) — LLM 연결 10초 < 시도 1800초 < 논리 호출 3608초 < 리스크 패널 벽시계 12시간 < 포털 릴레이 침묵 13시간 < nginx 14시간 < 리스크 앱 15시간 < 심의용 토큰 24시간.
도구 호출은 게이트웨이 600초(시간 초과는 재시도 안 함) < 엔진 900초, 지식카드 180초. 엔진에는 심의 전체 벽시계를 만들지 않는다(안쪽이 전부 유한하다).
패널 벽시계가 6시간이 아니라 12시간인 까닭 — 3라운드 패널은 LLM 단계가 직렬로 15번쯤 이어져, 단계마다 제한 안에 성공해도 7.5시간이다.
함께 들어간 것 — 의장이 끝내 실패해도 좌석별 마지막 입장과 회의록이 남는다(종전: 전 라운드 폐기) · 도는 심의가 있으면 에이전트서버 재기동과 update-all 의 포털·nginx
재기동이 멈춘다(강행 손잡이 있음) · 리스크 앱의 취소·일시정지가 도는 패널에 닿는다 · AIDataHub 워치독이 바쁜 API 를 죽은 것으로 보지 않는다.
