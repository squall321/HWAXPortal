# 소속·허가 기반 접근 — 결정 기록

## D-1. 전달은 합성 그룹(feat:·plat:) — 게이트웨이·에이전트서버를 새 개념 없이 태운다
끝까지 흐르는 인가 수단이 groups 하나다(PLAN 조사). 권한을 새 필드로 만들면 포털→에이전트서버→
게이트웨이 세 층을 모두 새로 배선해야 하지만, 합성 그룹으로 얹으면 게이트웨이의 기존 allowed_groups
겹침 판정이 그대로 먹는다(tools/list·call 둘 다). 에이전트서버에만 entitlements 필드를 따로 준다 —
트리거 판정(심의·Thinking)은 그쪽이 쥐고 있고, '권한 정보를 안 보낸 옛 호출'과 '권한이 없는 사람'을
구분해야 해서다.

## D-2. 권한은 요청마다 저장소에서 계산한다 — JWT·PAT 에 박힌 그룹을 믿지 않는다
세션 JWT 8시간·PAT 최대 100년에 그룹이 박혀 있어, 권한을 거둬도 그만큼 남는다. 포털은 요청마다
사용자 행(소속·개별 허가)과 정책 파일로 다시 계산한다. 게이트웨이도 PAT 호출자의 권한을 포털에서
짧은 캐시로 받아 쓴다. 관리자 여부(portal-admin)는 종전대로 로그인 때 값이다(거두려면 재로그인).

## D-3. 함의 — 전문가 기능은 AI 데이터 허브 위에서 돈다
심의·Thinking·전문가 챗은 좌석 발굴·역할·지식카드를 AI 데이터 허브 도구(recommend_agents·
get_agent_session·agent_search)로 한다. 이 기능만 주고 허브를 안 주면 기능이 조용히 부서진다.
기능 정의에 implies 를 두고, 내 권한 페이지는 '전문가 심의에 포함'처럼 이유를 적는다.

## D-4. 게이트웨이 정책은 포털에서 받아 온다 — 정본은 access.yaml 하나
게이트웨이 리포에 정책 파일을 따로 두면(tool_areas.json 선례) 포털 표와 두 곳이 된다. 게이트웨이는
어차피 PAT 호출자의 현재 권한을 포털에 물어야 하므로(D-2), 백엔드별 필요 권한도 같은 통로
(/internal/*, GATEWAY_SHARED_TOKEN)로 받는다. 받은 값은 디스크에 캐시해 포털이 잠깐 죽어도 직전
정책으로 돈다. gateway_config.json 의 allowed_groups 는 provision 이 다시 쓰며 날아가서 쓰지 않는다.
