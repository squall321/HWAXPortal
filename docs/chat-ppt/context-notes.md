# 포털 챗 PPT — 결정과 까닭

> 계획 [PLAN.md](PLAN.md) · 요청서 [request.md](request.md) · 체크리스트 [checklist.md](checklist.md).

**PP-D1 요청서를 사양으로 삼고 dev 의 지금 판에 넣는다 · 사용자 결정 둘(2026-10-22).** 요청서는 포털 `dba4c1e` · 에이전트 서버 `9d4c931` 기준으로
줄 번호를 적었다. dev 는 포털 `284e604` · 에이전트 서버 `bb307c6` 이고, 가리킨 자리의 내용은 같다(줄 번호만 밀렸다 — 읽어서 확인).
사용자 결정 — ① B 는 **만들고 켠 채로** 둔다(보안 정책 확인은 사용자가 받았다 — 요청서 B-2 의 2). ② 다시 저장한 PPTX 보내기(B6 선택)는
**이번에 넣지 않는다** — 글(`.hwax.md`)과 고르면 슬라이드 그림만 보낸다(요청서 B-2 의 1 — 다시 저장하면 DRM 이 다시 걸리는지 아무도 재지 않았다).

**PP-D2 A4 — RA 0블록은 포털이 가져오기 쪽을 저장 꼴 그대로 넘겨서다. AI 초안 꼴로 옮긴다(10-22).** ① RA `/api/imports/pptx` 의
`data.draft.pages[]` 는 `ReportPage.model_dump()` 다 — 위젯 정의 `extra_blocks: [{id, type, props}]` 와 내용 `content: {id: 내용}` 이 따로 있다.
`create_report_draft` → `/api/reports/ai-draft` → `_build_ai_page` → `normalize_extra_blocks(page["extra_blocks"])` 는 정의 항목 **안의** `content`
를 읽는다. 없으니 블록마다 '내용 없음/형식 불일치 — 건너뜀' 이고, 그래도 쪽은 만들어져 '29쪽 · 블록 0' 이 됐다. ② 확인은 RA 코드를 읽기 전용으로
돌려서 했다(RA venv · `PYTHONDONTWRITEBYTECODE=1` · 라우터 묶음을 건너뛰는 꾸밈 — RA 작업 트리는 그대로). python-pptx 로 만든 PPTX(제목 ·
글머리 둘 · 표 · 그림 둘 · 둘째 쪽)를 RA 파서 → RA 가져오기와 같은 조립 → 두 꼴로 정규화. 종전 꼴은 쪽마다 0블록, 정의에 내용을 넣은 꼴은
5 · 2 블록이 가져오기와 **내용 · 정의 모두 같다**(heading · rich_text · table · image — RA 파서가 내는 네 종 전부. RA 도 행을 고칠 때 같은
정규화를 다시 태운다 — `_renormalize_block`). ③ 배치만 다르다 — 가져오기는 전폭 세로 쌓기, AI 초안은 RA 자동 배치(그림이 반폭이라 둘씩 나란히,
나머지는 전폭). 일반 생성 API(`POST /api/reports`)는 저장 꼴을 그대로 받아 배치까지 같지만 `require_writer`(지금 보는 보드의 쓰기 권한)라
읽기 전용 보드를 보던 사람이 막힌다 — AI 초안 API 는 그래서 인증만 본다(RA 주석). AI 초안 길을 그대로 쓴다. ④ 0블록이면 보고서를 만들지
않는다(빈 초안을 RA 에 남기지 않는다) — 실패로 알리고 가져오기 경고를 보인다. ⑤ 응답의 `report_id` · `url` · `warnings` 를 돌려준다. 링크는
포털의 RA 경로(`/report-archive` + `url`)다. 블록 수는 보낸 수다(RA 응답에 블록 수가 없다 — RA 정규화가 더 버리면 그 경고가 `warnings` 에 온다).

**PP-D3 A2 — 보내기 결과는 대화의 어시스턴트 알림 한 건 + 활동 기록 하나로 남긴다(10-22).** ① 새 칸을 만들지 않고 이미 있는 길을 쓴다 —
활동 기록(`meta.activity`)은 서버 사본에 남고(`serverMessagesToLocal` 이 되살린다) 다음 턴 이력의 근거(`turnEvidence`)가 된다. 활동 항목에
`origin: 'upload'` 를 달고, 이력 근거 꼴에 `kind: 'upload'` 를 단다(포털 `ChatHistoryEvidence.kind` — `upload` 만 받는다). ② 에이전트 서버는
이 근거에 '어시스턴트가 이 물음에 답하려고 도구로 조회한 결과' 머리를 달면 안 된다 — 앞 물음과 상관없는 일이다. 따로 된 머리('사람이 챗 화면에서
파일을 올려 보낸 결과 — 포털이 사람 대신 도구를 불렀다 · 「방금 올린 것 · 변환한 것」 은 이것')를 달고, 앞 사람 발화에 붙이지 않고 알림 바로
앞에 사람 쪽 메시지로 **따로** 둔다(앞이 사람 메시지면 같은 메시지에 잇되 머리로 갈린다 — 같은 역할이 둘 잇달아 가지 않게). 압축본에는
'(올림: 도구)' 로 남는다. ③ AIDH 근거는 `convert_file` 결과 전부(초안 record JSON — 모델이 그 도구를 불렀을 때 받는 것과 같다)라 다시 부르지
않고 검토할 수 있다. RA 근거는 식별자(보고서 번호 · 제목 · 쪽 · 블록 · 주소 · 경고)뿐이다 — 내용은 `get_report_outline` · `get_report` 로 본다.
④ 대화가 없는 화면(첫 화면 · 새 챗)이면 새 대화를 만들어 거기 둔다. ⑤ **순서** — 포털은 답을 스트림이 끝날 때 서버 사본에 적는다. 답을 받는
중인 대화에 알림이 오면 화면에는 곧바로 붙이고(답 아래), 서버 사본에는 그 스트림이 끝나고 잠시 뒤 붙인다 — 먼저 적으면 다른 기기에서 알림이
답보다 앞에 선다. 서버 대화를 만드는 일과 붙이는 일은 대화마다 한 줄로 잇고, 다음 발화는 그 줄을 기다린다 — 알림이 만든 서버 대화를 다음
발화가 모르고 하나 더 만들지 않게.

**PP-D4 A1 — 지시문은 비어 있을 때만 저절로 채운다(10-22).** 사람이 쓰던 글을 지우지 않는다 — 비어 있지 않으면 단추('입력창에 넣기')만 둔다.
AIDH 「AI 데이터 허브 inbox 파일 `<이름>` 을 convert_file 로 변환한 초안을 검토하고, 모자란 항목은 import_record(dry_run=true)로 물어봐 줘」 ·
RA 「Report Archive 보고서 <번호>(「<제목>」)를 get_report_outline · get_report 로 읽고 검토해 줘」. 알림(A2)이 근거를 싣지만 이름을 글로 박는
까닭은 근거가 이력 예산에 밀려 '도구 이름만' 남는 경우에도 모델이 다시 부를 수 있게다.

**PP-D5 A3 — 다시 싣기 문구만 고친다(10-22).** ① `vision.history_images` 의 출처 설명에 상대 시점을 더한다 — '(N턴 전)' 은 그 항목 뒤의 사람
발화 수(답 · 근거의 그림은 그 턴의 물음까지 센다). 챗 · 띵킹 · 심의가 함께 쓰는 함수라 셋 다 같은 표기를 받는다. ② 챗의 다시 싣기 머리(그림 ·
판독문 둘 다)에 '이번 질문이 이 그림이 아니라 올리거나 변환한 파일 · 보고서를 가리키면 그림으로 대신 답하지 말고 이력의 업로드 근거를 보거나,
없으면 어느 파일인지 물어라' 를 더한다. ③ 시스템 프롬프트에 한 줄 — '방금 올린 것 · 변환한 것 · 보낸 것' 은 이력의 업로드 근거를 먼저 본다.
④ 다시 싣기를 빼거나 그림이 나온 턴 뒤로 옮기지 않는다 — 그림과 새 문서를 견주는 정상 질문, 이력 압축과 부딪친다(요청서 ⚠).

**PP-D6 A6 — 결함이 아니다. 낡은 주석만 고친다(10-22).** 붙인 문서는 처음 커밋(1901dbf, 09-12)부터 한 번도 비우지 않았다(`git log -G` 로 비우는
코드가 없었음을 확인) — 주석만 '보낸 뒤 비운다' 였다. 대화에는 문서 본문을 남기지 않으므로(쿼터) 칩을 떼기 전까지 매 턴 다시 가는 것이 뒤따르는
질문을 받는 길이고, 그림 커밋(2ff8dc0)도 '문서와 달리 보낸 뒤 비운다' 로 그 동작을 전제로 적었다. A2 는 이 길을 쓰지 않는다(PP-D3).

**PP-D7 A7 — AIDH 읽기 도구(`list_inbox`)는 하지 않는다(10-22).** ① AIDH 의 MCP 호출자는 게이트웨이의 서비스 키(api_key 로 정해지는 주체)라
최종 사용자를 모른다 — '호출자의 최근 inbox 파일' 을 가를 수 없고, 다 보여 주면 남의 파일 이름(사람 이름 · 과제명이 박힌다)이 샌다. ② 신원을
전하려면 게이트웨이 `IDENTITY_FWD_BACKENDS`(기본 hwax-deliberation 만)에 AIDH 를 넣어야 하는데, 그러면 AIDH 호출 전부가 신원 헤더 단발 세션으로
바뀐다(파급이 크다). ③ A1 · A2 로 파일 이름이 대화에 남는다 — 그날의 실패('도구는 찾았는데 넣을 이름이 맥락에 없었다')는 이것으로 닫힌다.
AIDH 리포 작업이라 필요해지면 따로 요청한다.

**PP-D8 B — 표(ticket)로 연다 · 받는 계정을 PC 에서 묻는다 · 서버는 대화에 쓰지 않는다(10-22).** ① 표 발급은 브라우저 세션 + CSRF 로만 —
PAT 로는 못 낸다(PC 에 포털 토큰을 새로 두지 않는다 — 요청서 B1). ② 표는 무작위 32바이트(base64url 43자), 디스크에는 SHA-256 만 남긴다(상태
파일을 읽어도 올릴 수 없다). 수명 10분 · 한 번(받음 · 취소 · 만료로 닫힌다) · 한 사람의 열린 표는 다섯까지(넘으면 가장 오래된 것을 닫는다).
③ **도우미는 URL 의 주소를 믿지 않는다** — 올릴 곳은 설치 때 설정 파일에 박은 포털 주소다. 가짜 링크가 남의 서버로 문서를 올리게 하지 못한다.
④ **도우미는 올리기 전에 받는 계정(이름 · 메일)과 포털 주소를 보여 주고 묻는다.** 남이 만든 링크(남의 표)를 누르면 내 문서가 남의 대화로 갈 수
있다 — 그것을 막는 문은 이 확인 하나다(표만으로는 누가 눌렀는지 모른다). ⑤ 받는 것은 `.hwax.md`(UTF-8 · 머리말 `schema: hwax-doc/1` 필수 ·
8MB)와 슬라이드 PNG(선택 · 12장 · 장당 8MB — 에이전트 서버 그림 상한과 같다 · PNG 첫 바이트)뿐이다. 원본은 받지 않는다(PP-D1 ②). ⑥ 받은 것은
그 사람 스테이징(지금 청소 규칙 6시간)에 두고, **서버가 대화에 직접 쓰지 않는다** — 화면이 받아 문서 칩 · 그림 칩으로 붙인다. 손으로 하던 길
(.hwax.md 를 붙이기)과 같은 끝이고, 사람이 칩을 보고 보낸다. 글은 스테이징의 한 상자(.md 하나 — AIDH 로 보낼 때 그 상자를 그대로 쓴다),
그림은 다른 상자. ⑦ 감사는 발급 · 도우미 열림 · 받음 · 실패 · 취소 다섯(주인 · 대화 · 파일 이름 · 크기 · 글자 수 · 그림 수 · IP). 본문은 남기지 않는다.

**PP-D9 B — 도우미는 같은 추출기의 `-Url` 모드다 · 설치는 따로 된 배치(10-22).** ① 새 파일을 만들지 않는다 — 추출 코드가 한 벌이어야 손으로
쓰는 길과 단추 길이 같은 글을 낸다. ② 설치 배치는 Claude 셋업 배치와 따로 둔다 — 웹 챗 사용자는 Claude 셋업을 돌리지 않는다. 생성기는
`setupBat.ts` 에(시험이 이미 있는 자리) `buildDocHelperBat(origin)`. HKCU 라 관리자 권한이 필요 없다. ③ 내려받은 추출기에 판 표식
(`HWAX_DOC_HELPER`)이 있는지 본다 — 없는 정적 경로는 SPA 가 `index.html` 을 200 으로 내 '받았다' 로 보인다. ④ 판 확인 — 도우미 판 상수가
서버 응답의 `helper_min` 보다 낮으면 '설치 배치를 다시 받으라' 로 멈춘다. ⑤ 연결 — 포털은 사내 주소라 직결을 먼저, 안 되면 시스템 프록시.
인증서는 Windows 저장소(브라우저와 같은 것)를 그대로 쓴다. TLS 1.2 를 켠다(PS 5.1 기본값이 낮은 PC 가 있다). ⑥ 올리기는 multipart 를
.NET `HttpClient` 로 만든다(PS 5.1 에는 `-Form` 이 없다). 파일 부분의 이름은 ASCII 로 두고 진짜 이름은 머리말 `source:` 에서 읽는다(.NET 의
비ASCII 파일 이름 인코딩을 서버 파서가 못 풀 수 있다). ⑦ **dev 에는 PowerShell 이 없어 이 모드는 Windows 에서 시험하지 못했다** — 사람 몫.

**PP-D10 평문 PPTX 에는 단추를 두지 않는다(10-22).** 평문은 서버가 그림 · 표까지 읽는다(RA 가져오기 · AIDH 변환). PC 길은 글(과 고르면 그림)만
간다. 요청서의 '평문이라도 원하면' 은 고르는 칸을 하나 더 늘리는 일이라 이번에는 암호 · 모름 판정 안내(`DocExtractHint`)에만 둔다.

**PP-D11 받은 글의 다음 단계는 AI 데이터 허브만이다(10-22).** 받은 `.hwax.md` 는 이미 스테이징 상자에 있으니 그 상자로 '어디로 보낼까요'
(UploadRouter)를 연다. `.md` 를 받는 목적지는 AIDH 하나다(RA 가져오기는 PPTX 만 — PP-D1 ②).

**PP-D12 알림만 있는 대화의 첫 발화도 '첫 발화' 다(10-23).** `sendMessage` 의 첫 발화 판정이 '메시지 0건' 이었다. 보내기 알림(어시스턴트)이
먼저 선 대화에서는 사람의 첫 질문이 첫 발화로 안 잡혀 심의 화면의 트리거(`/심의 `)가 빠졌을 것이다. '사람 발화가 없으면 첫 발화' 로 바꿨다 —
여태의 대화는 늘 사람 발화로 시작해 결과가 같다.

**PP-D13 확인은 실물로 — RA 정규화 · 헤드리스 브라우저 · 변이(10-23).** ① A4 는 RA 코드를 읽기 전용으로 돌렸다(PP-D2 ②) — 포털 변환 함수의
**실제 출력**을 RA 정규화에 다시 넣어 가져오기와 같은지까지 봤다. ② 보내기 알림의 순서(새 대화 · 답 받는 중 · 곧바로 보내기)와 입력창 흐름(파일 →
보내기 → 알림 · 지시문, 암호 파일 → PC 도우미 → 문서 칩 · 다음 단계 · 설치 안내)은 실제 `ChatProvider` · `Composer` 를 esbuild 로 묶어
playwright 가짜 fetch · 가짜 시계로 돌렸다(`test_chat_ppt_in_browser` — 심의 스트림 시험과 같은 길). ③ 변이 — 에이전트 서버 11/11 · 포털 백엔드
