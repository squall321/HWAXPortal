# AIDataHub 조각 스냅숏 — 결정 기록

계획은 [PLAN.md](PLAN.md), 할 일은 [checklist.md](checklist.md)다. 날짜는 KST.

**AP-1 분석 · 사용자 결정(11-04 · 11-05) — 조각 스냅숏.** 처음 권한 안(같으면 건너뛰고 바뀐 줄만 쓰기)은 바뀐 날의 ① 받기 ② 스테이징 적재(색인 재구축) ③ 전체
스냅숏을 그대로 둬 줄 하나에도 한 시간 넘게 든다 — 사용자가 짚었다. 그래서 받기 · 적재 · 백업까지 바뀐 크기에 비례하게 하는 조각 스냅숏을 골랐다. 버린 것 —
증분 덤프(절 표에 바뀐 시각이 없어 서명을 따로 지어야 하고, 빠진 증분 · 차례를 챙겨야 하며 빠지면 전체로 돌아간다), 지금 꼴 다듬기만(바뀐 날 30 ~ 40분).
조각 스냅숏은 목록이 매번 전체 모습이라 cae00 이 며칠을 건너뛰어도 마지막으로 병합한 목록과만 견주면 된다.

**AP-2 병합 규칙은 바꾸지 않고 스테이징에 든 것만 줄인다.** 지금 병합(`merge_table` · `merge_samples`)에는 운영에서 배운 규칙이 많다 — m3 슬롯은 비었을 때만 채움 ·
이 박스 조회 통계 지킴 · '운영이 더 새롭다' 셈 · agent 단위 표본 · dev 에만 있는 열이면 3 · 대리 id 는 운영 순번. 조각 길은 스테이징 DB 를 스키마로 비워 만들고 받은
조각만 실은 뒤 같은 함수를 부른다 — 안 실린 표는 0줄을 옮겨 아무것도 하지 않는다. 규칙을 두 벌로 갖지 않는다.

**AP-3 조각을 매일 바꾸는 열은 내지 않는다.** `records.read_count` · `last_accessed_at` 은 dev 의 조회마다 바뀌어 조각 해시를 매일 흔든다 — 병합은 그 둘을 이 박스
값으로 두고(덮지 않음) 새 행에만 dev 값을 넣었다. 내지 않으면 새 행은 이 박스의 기본값(0 · 비움)으로 들어간다 — 조회 통계는 그 박스의 것이라 그쪽이 맞다고 본다.
대리 id(record_sections · external_id_map · agent_sample_embeddings 의 id)는 병합이 이미 쓰지 않아 내지 않는다.

**AP-4 내기는 한 시점이다(pg_export_snapshot).** 조각마다 psql 을 따로 여니 따로 보면 표 사이 시점이 어긋난다 — 내는 도중 dev 에 든 레코드는 레코드
목록(처음에 읽는다)에는 없는데 한 조각인 표(external_id_map)에는 실려 cae00 에서 외래키에 걸리고, 레코드와 그 절이 서로 다른 판으로 실린다. 전체 덤프
(pg_dump)는 한 시점이라 이 일이 없었다. 쥔 세션 하나가 `BEGIN REPEATABLE READ; SELECT pg_export_snapshot()` 을 열어 두고 조각마다 `SET TRANSACTION
SNAPSHOT` 으로 빌린다(pg_dump 도 `--snapshot`). psql 은 질의 결과마다 표준출력을 비워(14 · 16 실측) 열린 트랜잭션에서 한 줄을 읽을 수 있다. 문장은
표준입력으로 준다 — 조각의 키 목록이 리눅스 인자 하나의 상한(128 KiB)에 레코드 수가 늘면 걸린다. 시험 `test_내기는_한_시점이다`(변이 M9 가 붉다).

**AP-5 조각 길이 전체 덤프 길과 다르게 하는 것 — 받아들인다.** ① 새 행의 조회 통계 · 상류 점검 칸은 이 박스 기본값(AP-3). ② 이 박스에서 지운
행은 dev 가 그 조각을 바꾸기 전엔 되살아나지 않는다(전체 길은 매번 덤프에 있는 행을 다시 넣었다 — 이 박스의 삭제를 되돌리던 셈이다). 그 행을
가리키는 자식이 바뀐 조각에 실리면 외래키로 그 표 병합이 실패하고 update-all 이 전체 덤프 길로 다시 해 되살린다(스스로 낫는다). ③ 절 · 첨부처럼
바뀐 시각 칸이 없는 표에서 이 박스가 고친 줄은 dev 가 그 조각을 바꿀 때만 dev 판으로 덮인다(전체 길은 매번 덮었다). 셋 다 전체 길보다 덜 덮는다.

**AP-6 목록 나열은 `--files-only` — 시험이 잡았다.** `rclone lsf <자리>/ --include 'manifest-*.json'` 은 조각 폴더 `files/` 도 낸다(그 아래에 맞는 파일이
있을 수 있다고 보고 폴더를 남긴다). 내기 쪽 정리는 목록이 KEEP 판보다 많으면 `files/` 를 '가장 옛 목록' 으로 지우려다 실패했고, 적으면
`rclone copyto <자리>/files/ …` 로 **조각 전부를 임시 폴더에 받았다** — 실제 Drive 면 내기마다 10 GB 다. 받기 쪽은 목록이 없고 폴더만 있으면 `files/`
를 최신 목록으로 읽는다. 시험이 rclone 호출을 적어 '받은 것은 목록 하나뿐' 을 본다(변이 M1 · M2).

**AP-7 update-all §3 — 조각 길 먼저, 넘어가는 규칙.** 받기 10 이면 끝(전체 길로 가지 않는다 — 덤프 이름은 매일 바뀌어 그쪽 표식으로는 늘
'바뀜' 이다). 받기 0 → 조각 병합 0 이면 `--commit`, 3 이면 표식 없이 끝(전체 길로 가도 같은 3이고 한 시간이 든다), 그 밖이면 전체 덤프 길로
다시. 받기 4(목록 없음) · 실패도 전체 길. 조각 길이 성공해도 전체 길 표식(`.last-merged`)은 그대로 둔다 — 그 덤프를 병합한 것은 아니다. 그래서
조각 길이 실패한 날 전체 길은 대개 돈다(표식이 옛 덤프). 운영자 미리보기(HE팀 페르소나)는 어느 길이든 병합이 돈 실행에만. 잠깐 끄기는
`AIDH_SYNC_MODE=full`(실행 때 환경변수 — `SF_RESTORE_DB` 와 같은 꼴, 박스 설정으로 두지 않는다).

**AP-8 앞 모습 폴더는 백업과 같은 보관 일수로 지운다.** 전체 길의 `pre-merge-*.sql.gz`(4.4 GB)는 포털 `backup-local.sh` 가 RETAIN_DAYS(7)로 지운다 —
`pre-parts-*` 폴더도 같은 줄에서. 앞 모습은 그 병합이 건드린 줄(덮일 수 있는 줄 = 받은 조각에 든 키의 운영 행)이라 바뀐 날엔 작고, 첫 조각 병합은
운영 행 거의 전부라 전체 스냅숏만큼 크다.

**AP-9 스키마 파일 이름은 내기마다 바뀐다 — 받을 조각을 고르는 데 쓰지 않는다.** pg_dump 16.10 · 17.6 부터 덤프마다 무작위 열쇠(`\restrict`)를 넣는다
(dev 16.14). 스키마 파일은 작고(수십 KB) 받을 조각이 있을 때만 받는다. 열쇠를 지우지 않았다 — 덤프 안의 psql 메타명령을 막는 장치다.

**AP-10 미룬 것 · 찾은 것.** 표본 병합은 표본 조각이 계획에 들 때만 돈다(전문가 조각이 바뀌어도 든다) — 이 박스 혼자 어긋난 색인은 바뀐 것이 없는
날엔 알리지 않는다(바뀐 것 없는 날은 아무것도 하지 않는다는 원칙). 찾은 것(고치지 않음, 전부터): 레코드는 '이 박스가 더 새로우면 이 박스 판' 인데
절은 '값이 다르면 dev 판' 이라, 이 박스에서 고친 카드의 절이 병합 때 dev 의 옛 절로 덮인다 — 조각 길은 그 조각이 바뀔 때만이라 덜하지만 같다.
사용자에게 알린다(고치면 병합 규칙이 바뀐다 — AP-2 밖).

**AP-11 목록 보관은 3판(처음 7판에서 줄임).** cae00 은 늘 최신 목록과 '병합함' 목록(그 박스에 사본이 있다)만 견주고 최신 목록이 가리키는 조각만 받는다 —
옛 목록은 받는 도중 새 내기가 든 때를 넘길 만큼만 있으면 된다. 다 바뀐 날(전체 다시 임베딩 등)이 이어지면 판마다 조각 전체(7 GB 남짓)라 7판이면 dev
디스크(쓰는 곳 88%) · Drive 에 50 GB 까지 쌓인다.

**AP-12 Drive 목록을 못 읽을 때.** 받기 — rclone 끝 코드 3(자리 없음)만 '목록 없음' 4, 그 밖(네트워크 · 인증)은 1(update-all 이 '받기 실패' 로 말하고 전체
길). 내기 쪽 정리 — 목록을 파일로 다 받고(끝 코드) 방금 올린 목록이 그 안에 있을 때만 지운다. 프로세스 치환은 rclone 의 실패를 놓쳐 일부만 읽힌 목록으로
'안 가리키는 조각' 을 셀 수 있었다. 시험이 대역 rclone 의 목록 읽기만 실패시켜 본다(변이 둘 붉음).

**AP-13 돌고 있는 내기 스크립트를 바꾸지 않는다.** dev 첫 내기(11-05 08:33 KST ~)가 main 체크아웃의 `parts-to-drive.sh` 를 실행하는 동안에는 AIDataHub
main 병합을 미뤘다 — bash 는 스크립트를 실행하며 읽어, 도중에 파일이 바뀌면 정리 구간(`rclone delete`)에서 엉뚱한 줄을 돌 수 있다. AP-11 · AP-12 는
내기가 끝난 뒤 병합한다.

**AP-14 낡은 목록이면 전체 덤프 길(5).** dev 의 하루 한 번 내기가 멈추면(cron 이 없거나 실패) Drive 목록이 그대로라 cae00 은 날마다 '바뀐 것 없음'
으로 끝나며 전체 덤프(매일 올라간다)의 새 데이터를 받지 않는다 — 조용히 낡는다. 받기가 목록을 가장 새 전체 덤프와 견줘 26시간 넘게 오래면 5 로
끝내고 update-all §3 은 ⚠ 로 말한 뒤 전체 덤프 길로 간다. 문턱 — 평소엔 내기가 덤프 1시간 남짓 뒤라 오늘 내기 전에도 덤프와 어제 목록의 차이는
22.5시간이다. 하루치를 빠뜨리면 46.5시간이라 26 이 그 사이를 가른다(`AIDH_PARTS_STALE_HOURS`). 덤프 자리를 모르거나 못 읽으면 한 줄 말하고 건너뛴다.
실 Drive 확인 — 덤프 11-04 04:45 · 목록 11-04 23:33 이라 낡지 않음.

**AP-15 dev cron 한 줄은 사용자 몫.** `15 6 * * *`(UTC — 전체 백업 04:45 · 45분 뒤 여유) 줄을 넣으려 했는데 자동 모드 분류기가 막았다(첫 시도는
`crontab <파일>` 의 파일 이름 100자 상한으로 잘려 실패 — 바뀐 것 없음을 확인했다). 우회하지 않았다 — 같은 효과를 백업 스크립트 끝에 붙여 내는 것도
막힌 뜻을 비켜 가는 셈이라 사용자 결정으로 넘긴다. 그동안 cae00 은 첫 목록(11-04 23:33 UTC)으로 조각 길을 쓰다가 그 목록이 하루 넘게 낡으면(AP-14)
전체 덤프 길로 돌아간다 — 데이터가 멈추지는 않는다.

**AP-16 사용자 결정(11-05) — 절 · 첨부 · 전문가 연결은 레코드를 이긴 쪽을 따른다.** 전부터 레코드는 '이 박스가 더 새로우면 이 박스 판' 인데 그 자식
(record_sections · record_attachments · agent_records)은 updated_at 이 없어 '값이 다르면 dev 판'(없으면 dev 줄을 넣음)이었다 — cae00 에서 고친 카드의
절이 병합 때 dev 의 옛 절로 덮이고, 이 박스가 지운 절이 되살아났다(AP-10). 이제 자식 병합은 dev 의 레코드 updated_at 과 운영의 것을 견줘 **운영이 더
새로운 레코드의 자식 줄은 dev 판으로 덮지도 넣지도 않는다.** 같은 판(시각이 같음) · dev 가 이긴 레코드 · 새 레코드의 자식은 예전 그대로다. 지우는 일은
여전히 없다(dev 가 지운 절이 운영에 남는 것은 전부터의 다른 빈틈 — 이번 범위 밖). 조각 길은 자식 조각을 실을 때 같은 k 의 레코드 조각도 싣는다 —
안 바뀐 레코드 조각이어도 그 시각이 있어야 가릴 수 있다(레코드 병합은 시각 조건이라 다시 쓰지 않는다). external_id_map 은 따르지 않는다(내용이 아니라
찾기 표다).

**AP-17 시점을 쥔 세션만 트랜잭션 안 유휴 상한을 끈다(2026-11-08 KST).** 업데이트 라운드에서 dev 조각 내기(`parts-to-drive.sh`)가 35분째 `records.8 COPY 실패: invalid snapshot identifier` 로 멈췄다. PG 로그가 까닭을 적었다 — 00:26:57 UTC `terminating connection due to idle-in-transaction timeout`. dev PG 의 `idle_in_transaction_session_timeout` 이 30min 이고, 시점을 쥔 세션(`_Snapshot` — `pg_export_snapshot` 뒤 트랜잭션을 연 채 기다린다)은 조각 세션들이 뜨는 동안 트랜잭션 안에서 논다. 11-05 첫 내기는 29분이라 비켜 갔고 이번에는 넘겼다. 고침 — 그 세션만 `SET idle_in_transaction_session_timeout = 0`(AIDataHub `a16716b` · 병합 `6e916cf`). 조각 세션은 바로 COPY 를 하니 놀지 않고, 서버 설정은 그대로 둔다(다른 클라이언트의 잊힌 트랜잭션은 계속 끊겨야 한다). 시험(폐기용 PG) — 1초 상한에서 2.5초 놀린 뒤 조각을 뜬다, 고치기 전 같은 오류로 붉고 고친 뒤 조각 동기화 13 · 병합 17 통과. dev 조각 목록이 11-04 판에서 멈춰 있던 것(매일 cron 이 없다 — 11-05 결정으로 사용자 몫)은 그대로다 — 이번 라운드에 한 번 다시 낸다.
