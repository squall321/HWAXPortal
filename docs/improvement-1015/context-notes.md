# 운영·관측·검색 개선 여섯 — 결정과 까닭

**IM-D1 받은 것(2026-10-16).** 사용자 — "하기 의견을 분석하고 반영할수 있는것도 해". 의견은 「HWAX 개선 아이디어 — 운영·관측·검색」(2026-10-15, @박용진) 여섯 제안이다. 문서가 든 근거(gotchas 번호 · `_search_tools`·`_SYN` · `to_tsvector('simple')` · 인자 설명 15/1,348 · `llm_ttft_probe.py` · `PORT-MAP.md` · G2)는 모두 지금 코드와 맞았다.

**IM-D2 결정이 필요 없는 것부터 한다.** 6(점수판)은 보고만 하는 게이트웨이 변경이라 바로 하고, 1(상태판)은 검사·화면까지 짓되 경보는 운영자·수신자·메일 길이 정해진 뒤 켠다. 3(용량 측정)은 도구와 절차서까지 짓고 측정은 사람이 심의 없는 때 cae00 에서 돌린다. 4·5 는 평가셋과 기준선을 먼저 만들고 바꿀지는 결과로 정한다. 2(추적)는 프롬프트 원문이 남는 데이터라 보존·열람을 먼저 정한다.

**IM-D3 상태판의 경보를 포털에 맡기지 않는다.** 포털 메일은 `console · smtp · graph` 가운데 하나다. 경보를 포털 엔드포인트로 보내면 포털이 죽은 순간(2026-10-16 아침 dev 의 실례) 경보도 같이 죽는다. SMTP 박스는 Gatus 가 직접, Graph 박스는 작은 독립 발신기로 보낸다 — 어느 쪽인지는 사람이 정한다.

**IM-D4 실례 하나(2026-10-16 09:17 KST, dev).** 메모리와 스왑이 바닥나 earlyoom 이 python 프로세스에 SIGTERM 을 보냈고 포털 백엔드 · 게이트웨이 · MX 백서 MCP 가 내려갔다. 포털 인스턴스는 남아 있어 `start.sh` 가 'already running' 으로 지나갔다(안의 백엔드만 죽었다) — 인스턴스를 내렸다 다시 띄워 살렸다. 상태판의 검사는 인스턴스가 아니라 **리스너의 응답**을 봐야 하는 까닭이다. 그때 메모리를 쓰던 큰 것은 다른 세션의 StepForge 시험 셋(각 1GB 남짓)이었다.

**IM-D5 PORT-MAP 에 서비스 포트 표를 더했다.** 제안의 공통 제약('포트는 PORT-MAP 에')을 보니 LLM 라우터 9130 을 거기 올리지 않았다 — 표가 DB 포트만 있었다. 포털 스택 리스너(8723 · 8088 · 9009 · 9110 · 9130)와 9120 을 피한 까닭을 적었다.

**IM-D6 사용자 결정 셋(2026-10-16).** ① 상태판 경보는 **팀 공용 주소**로 보낸다 — 주소는 `infra/.env` 에만 적고(추적 파일에 적지 않는다) 운영자도 그 팀이다. ② cae00 포털 메일은 **SMTP** 다 — Gatus 가 그 SMTP 로 직접 보낸다. 자격은 포털 `backend/.env` 의 메일 설정(`SMTP_*` · `MAIL_FROM`)을 그대로 읽어 gitignore 된 상태 디렉터리의 Gatus 설정(600)에만 쓴다 — 두 곳에 적지 않는다. ③ 호출 추적은 **원문 없이 시간·토큰만** 남긴다 — 프롬프트·답 본문은 트레이스에 싣지 않고(코드에서 가린다 — 환경값으로 끌 수 없게), 호출마다 서버 · 큐 대기 · 생성 시간 · 토큰 수 · 잡/라운드/좌석 id 만. 그래서 보존·열람 걱정 없이 지을 수 있다(2 를 뒤로 미루던 까닭이 풀렸다).


**IM-D7 상태판 포트는 8740 이다 — 9140 이 아니다(2026-10-16).** 제안받은 기본값은 9140 이었다(9110 게이트웨이 · 9130 라우터에 이어). 확인해 보니
9100~9999 가 HEAXHub 의 앱 포트 풀이다(`APP_PORT_RANGE_LOW`·`HIGH`, `port_allocator.py`) — 허브는 앱을 띄울 때마다 그 순간 비어 있는 포트를 골라 주고
풀어 준 포트를 먼저 다시 쓴다. dev 에는 그 범위에 허브 앱이 9132 · 9145 · 9213 … 으로 떠 있었다. 상태판이 내려간 틈(재기동 · 부팅 순서 — 허브는
tier 10, 상태판은 tier 30)에 허브가 그 포트를 앱에 주면 상태판은 포트를 못 잡고, services.py 는 그 앱의 `/health` 응답을 'already-up' 으로 읽어
**상태판이 없는데 초록**이 된다 — IM-D4 와 같은 꼴의 무음 결함이다. 그래서 그 범위 밖의 8740(이 박스 리스너 없음 · 리포 전체에 쓰는 곳 없음)으로
두고 PORT-MAP 에 그 범위를 적었다. 게이트웨이 9110 · 라우터 9130 은 같은 틈이 있으나 이번에는 옮기지 않는다(늘 떠 있어 허브가 비켜 간다 — 사람이 정할 일).

**IM-D8 update-all 의 자리는 5b(§5 뒤 · §6 앞)다.** 설정을 다시 만들고 곧바로 `update-sites status-board` 를 부른다 — 지문에 생성 설정이 들어
있어 생성이 먼저여야 바뀐 것을 본다('§4 앞에서 만든다' 는 요청의 까닭과 같다). §5 뒤로 둔 까닭은 둘이다. ① 게이트웨이 백엔드 이름을 재프로비저닝을
마친 게이트웨이에서 읽는다(§5 가 백엔드를 더한다). ② 지켜보는 서비스가 §2·§4·§5 에서 다시 뜬 뒤에 상태판이 다시 뜬다. 그리고 §4 의 챗 스택
update-sites 줄(`_us_rc` 를 LLM 라우터 내리기가 읽는다)과 다른 시험이 원문을 떼어 돌리는 구획(1e~2 · 3.5~4 · §4~1i 뒤처리) 어디에도 끼지 않는다.

**IM-D9 검사 조건.** ① 모든 검사의 첫 조건은 `[CONNECTED] == true` 다 — Gatus v5.37.0 은 호출 오류를 결과의 오류 칸에만 적고 성공 여부는 조건으로만
정한다. 스모크에서 죽은 포트가 `[STATUS] (0) < 500` ✓ 였다. ② `expect` 가 없는 리스너는 '5xx 가 아니다' 다(MCP 끝점은 GET 에 401·406 을 낸다 —
응답이 온 것이다). ③ 게이트웨이 백엔드는 이름마다 `!= false`(사라진 백엔드는 실패로 치지 않는다 — `== true` 면 허브 앱을 내린 날 거짓 경보가 난다)와
`[BODY].backends != pat(*:false*)` 한 줄(만든 뒤에 생긴 백엔드). ④ 수를 화면에 보이려고 성공한 조건도 값을 풀게 했다 — 그때 오른쪽이 0 이면 Gatus 가
길이(0s)로 읽어 '(0s)' 를 붙여서 `>= 1` · `> -1` 로 적었다. ⑤ 에이전트 서버는 `has([BODY].delib_active)` — 그 칸이 없으면 옛 판이라 재기동 미룸이 안 된다.

**IM-D10 경보.** 켜는 조건은 `STATUS_ALERT_TO` + `MAIL_BACKEND=smtp` · `SMTP_HOST` · `MAIL_FROM` 이다. `MAIL_FROM` 은 코드 기본값으로 메우지 않는다(추적
파일에 주소를 적지 않는다 — 박스의 backend/.env 에 적힌 값만 쓴다). backend/.env 는 포털과 같은 규칙(python-dotenv)으로 읽고 시험이 python-dotenv 를
오라클로 대조한다. Gatus 에는 STARTTLS 손잡이가 없다(서버가 내밀면 쓴다) — 포털이 `SMTP_STARTTLS=false` 면 검증을 끄고(`client.insecure`), 참이면
호스트 CA 묶음을 컨테이너에 덮어 사내 CA 서버도 검증되게 했다(이미지에는 공개 루트만 있어 조용히 못 보낸다). 문턱은 연속 5번 실패 · 2번 성공이다 —
update-all 의 재기동(대개 1~2분)으로는 메일이 나가지 않게. Gatus 는 설정 글 전체에서 `$이름` 을 환경변수로 풀어 `$` 가 든 비밀번호가 잘리므로 값의
`$` 는 전부 `$$` 로 적는다(Gatus 가 하나로 되돌린다). 받는 곳은 있는데 메일을 못 꾸리면 화면만 띄우고 ⚠ 다(생성기 종료코드 3).

**IM-D11 끄기와 손잡이.** `STATUS_BOARD` 줄을 지우면 다음 update-all 이 떠 있는 상태판을 내린다(켰다 끈 박스에서 메일이 계속 나가지 않게). if_env 는
값이 있으면 켜므로 `STATUS_BOARD=0` 은 켜짐이다 — update-all 이 ⚠ 로 알린다. env-sync 는 `STATUS_ALERT_TO` 를 '값을 정해야 한다' 로 재촉하지 않는다
(비우면 화면만 돈다 — `LLM_UPSTREAMS` 와 같다). `status-board.sh stop` 은 환경의 포트를 먼저 보므로 update-all · update-sites 머리가 물려받은
`STATUS_BOARD_PORT` 를 버린다(LP-D14 와 같다). 이미지 판은 v5.37.0(태그 + 다이제스트)이고 SIF 는 25MB 다.

**IM-D12 LLM 라우터 포트도 허브 풀 밖으로(2026-10-16).** 상태판이 9100~9999(HEAXHub 앱 포트 풀)을 피해 8740 을 고른 까닭(IM-D7)이 LLM 라우터 9130 에도 그대로 맞는다 — 아직 어디에도 배포하기 전이라 8730 으로 옮겼다(llm-pool LP-D16).

**IM-D13 3(용량 측정)은 도구·절차서까지(2026-10-16).** 길이 분포 추출기 · GuideLLM 측정 이미지 · 실행 스크립트 · 절차서(`docs/llm-pool/capacity.md`)를 지었고 dev vLLM 에 작은 스모크로 끝까지 돌려 봤다. 재는 것은 사람이 cae00 에서 심의 없는 때 한다(GPU 를 차지한다). 설계와 까닭은 `docs/llm-pool/context-notes.md` LP-D17 — 문서가 말한 '붙임 켬·끔' 의 끔은 문턱 0 이다(큰 값은 늘 붙임), 심의 보관소(`delib-runs`)는 Claude 워크플로 산출이라 부하에 쓰지 않고 카드 대조 원장의 서버 사용량으로 부하를 만든다.

**IM-D14 호출 추적 기록기의 자리(2026-10-16).** 기동 절차의 LLM(`_mk_llm`)과 외부 응답자 모델(`model_for`)에 LangChain 콜백을, 게이트웨이 도구 목록(`_get_tools_retry`)에 도구 코루틴 감싸기를 단다. 콜백은 `run_inline` 이고 스트리밍 콜백이 아니다 — 스트리밍 콜백이면 LangChain 이 비스트리밍 호출을 스트리밍으로 바꾼다(`_should_stream`). 켜도 요청 바이트가 같다는 것을 시험이 본다. 도구 감싸기는 `_cap_tool` 아래라 엔진의 문이 막은 호출은 스팬이 없다. 자리 id 는 contextvars(`tag`)다 — 좌석은 제 태스크라 그 좌석에만 붙고 부른 쪽으로 새지 않는다. 호출 하나가 트레이스 하나다 — 심의 잡은 몇 시간이고 재기동하면 부모 스팬이 영영 오지 않아 고아가 되므로 부모를 두지 않고 `session.id`(잡 id · 챗 턴 id)로 묶는다.

**IM-D15 보내기는 OTLP/HTTP protobuf 손 인코딩이다.** Phoenix 20.19.0 의 `/v1/traces` 는 `application/x-protobuf` 만 받는다(소스 · dev 에서 JSON 은 415). cae00 은 새 패키지를 들일 길이 없어 필요한 메시지만 직접 쓰고, 공식 `opentelemetry-proto`(requirements-dev 에만)로 읽어 맞대는 시험을 둔다. Phoenix 고유의 JSON 스팬 API 는 쓰지 않았다 — 표준 OTLP 라 받는 쪽을 바꿀 수 있다. 보내기는 `http.client` 다 — httpx 면 에이전트 서버의 로그 설정이 보낼 때마다 INFO 한 줄을 남겼다(dev 실주행). 스레드 하나 · 줄 2,000 · 한도 2초 · 실패 뒤 5초 쉼이고, 죽은 수집기에서 도구 호출 3,000번이 0.44초 · 알림 두 줄이었다.

**IM-D16 본문을 가리는 자리.** 콜백이 받는 메시지 · 토큰 조각은 열지 않는다. 끝난 결과에서는 사용량 · 모델 이름 칸만, 응답에서는 상태 코드와 라우터 머리만 읽는다. 예외는 이름과 HTTP 상태만 남긴다. id 자리는 공백 없는 160자 안의 표지만 받는다. 손잡이는 `CALL_TRACE_URL` 하나이고 본문을 켜는 값은 없다. 목록 밖이라 싣지 않은 것은 finish_reason 과 `invoke_tool` 의 안쪽 도구 이름이다. 스트리밍 챗의 토큰 수는 요청을 바꿔야 해서 두었다(사람이 정할 일 — cae00 은 GLM 이 스트리밍을 끈 박스라 비스트리밍 사용량이 남는다).

**IM-D17 Phoenix 는 20.19.0 이고 포트는 8750 하나다.** 판 · 다이제스트로 고정했다(2026-10-01 공개, 다음 판 20.20.0 은 10-08). gRPC 수신기는 `PHOENIX_HOST` 를 보지 않고 `[::]:4317` 에 열리고 끄는 환경값이 없다(읽기 전용 모드뿐이다) — 띄우는 셈(`phoenix_serve.py`)이 그 시작을 비우고, 자리가 없는 판이면 띄우지 않는다. 그래서 두 번째 포트가 필요 없었다. 공용 인터넷 자원 · 원격 측정 · 에이전트 도우미와 bash · /mcp · 샌드박스를 끄고 `--cleanenv --no-home` 으로 띄운다. 상태는 `infra/.state/call-trace` 다. 보존은 30일이고 Phoenix 는 DB 를 처음 만들 때만 이 값을 넣는다(그 뒤는 화면 Settings → Data Retention). 스팬 하나가 1~2KB 다(dev 2,000건에 DB 2.2MB).

**IM-D18 켜기는 두 줄 — 받는 쪽은 update-all 5c 가 맞추고, 보내는 쪽은 알리기만 한다.** 포털 `CALL_TRACE`(매니페스트 if_env)와 에이전트 서버 `CALL_TRACE_URL` 이다. env 킷은 없는 키만 더해 끄기 · 포트 바꾸기가 따라가지 않으므로(끈 박스가 죽은 주소로 계속 보낸다) 에이전트 서버 .env 는 고쳐 쓰지 않는다 — 고쳐 쓰려면 LLM 라우터 1i 만 한 구획이 든다. 처음 판(에이전트)은 update-all 을 건드리지 않아 Phoenix 를 손(`services.sh up`)과 부팅 유닛만 띄웠는데, 그러면 꺼진 박스에 ○ 줄이 없다 — '안 켠 기능도 로그에 켜려면과 함께' 라는 사용자 지시에 어긋나 합치기 전에 5c 를 더했다(상태판 5b 와 같은 꼴 — 켜면 update-sites 로 띄우고 지문이 바뀌었을 때만 다시, 줄을 지우면 떠 있는 것을 내리고 ○). 두 줄이 어긋나면 ⚠ 다(받는 쪽만 켜짐 · 끈 박스에 보내는 줄이 남음). update-all · update-sites 머리는 물려받은 `CALL_TRACE_PORT` 를 버린다(LP-D14 와 같다).

**IM-D19 라우터가 실제 서버를 머리로 알린다.** 라우터를 지나면 에이전트 서버는 어느 위 서버가 받았는지 모른다(설정 주소가 라우터다). 넘긴 응답에 `x-hwax-llm-upstream: <호스트:포트>` 를 단다 — 위 서버가 보낸 같은 이름은 버리고 라우터 자신의 502 · 503 에는 달지 않는다. 에이전트 서버는 LangChain 이 만든 httpx 클라이언트에 응답 고리만 달아 읽는다. `include_response_headers` 는 메시지의 response_metadata 를 바꿔서 쓰지 않았다.

**IM-D25 Gatus v5.37.0 실측(2026-10-17 dev — 실험용 Gatus · 가짜 SMTP · 켜고 끄는 HTTP).** ① 외부 끝점은 `POST /api/v1/endpoints/<그룹>_<이름>/external?success=&error=&duration=` + Bearer 토큰이고 토큰이 틀리면 401 이다. ② 메일 본문에 밀어 넣은 error 가 **없다** — `Alert description` 만 온다. 그래서 설명에 사유를 보는 곳(화면 · 로그 · `status-push.py once`)을 적었다. ③ heartbeat 가 돈다 — 밀어 넣기가 끊기면 `heartbeat: no update received within 20s` 실패가 기록된다(밀어 넣는 쪽이 죽은 것도 잡힌다). ④ maintenance 안에서는 일반 · 외부 끝점 모두 실패를 기록만 하고 메일을 보내지 않는다. ⑤ **메모리 저장소는 설정을 다시 읽을 때마다 기록을 비우고**(외부 끝점은 다음 밀어 넣기까지 화면에서 사라진다) **경보 상태도 잃는다** — 울린 경보의 풀림 메일이 오지 않는다. sqlite 면 다시 읽기 · 재기동을 넘어 기록과 경보 상태가 이어지고 풀림 메일이 온다(둘 다 실측). 그래서 '필요하면' 이던 기록 보존을 켠다. ⑥ maintenance 의 요일은 영어만 받는다 — ko_KR 박스의 `date +%A`('토요일')를 넣자 설정 거부, skip-invalid 가 없던 실험 Gatus 는 panic 으로 죽었다. ⑦ 경보마다 적은 failure-threshold 가 default-alert 를 덮는다(외부 끝점도). ⑧ 다시 읽을 때 검사마다 `Canceling current execution` WARN 한 줄이 남는다 — 정상이다.

**IM-D26 밀어 넣는 쪽(status-push.py)은 상태판과 한 몸이다.** `status-board.sh run` 이 Gatus 를 exec 하지 않고 부모로 남아 함께 띄우고, Gatus 가 끝나면(stop 이 그 리스너를 내리면) TERM 으로 내린다. 매니페스트 항목으로 따로 두지 않은 까닭 — 듣는 포트가 없어 health 가 없고, services.py 는 health 없는 항목을 up 마다 또 띄운다(`started (no health url)`). systemd 타이머는 박스마다 설치 · 환경이 달라 사람 몫이 하나 더 는다. 죽은 것은 heartbeat 가 잡는다. 셸이 먼저 죽어 부모가 바뀌면 스스로 끝난다(남아서 옛 토큰으로 밀지 않게). 검사 목록(push.json)은 돌 때마다 다시 읽어 update-all 이 설정을 다시 만들어도 다시 띄울 필요가 없다. 실 Gatus · 실 apptainer 로 생성 → 기동 → 밀어 넣기 → 멈춤 걸기 · 풀기(기록 20 → 55 → 74, 다시 읽기를 넘어 이어짐) → 정지(밀어 넣는 쪽까지 0개)를 dev 스크래치 배치에서 돌려 봤다.

**IM-D27 검사 둘의 꼴.** ① **MCP 실호출** — 30분마다 · 한 번 상한 10분 · heartbeat 45분 · 연속 2번(1시간)에 메일. `mcp-smoke.py --periodic` 은 읽기 낱말 허용 목록(`(^|_)(list|get|status|…)(_|$)` — 앱 접두가 붙은 `risk_list_projects` 도 잡는다)에 드는 무인자 도구만 백엔드당 하나, 호출마다 `X-HWAX-Corr: status-board:mcp-smoke` 를 실어 게이트웨이 감사에서 가려낼 수 있다(dev 1회 14줄 · 2.6초). 쓰기 낱말 규칙만으로는 샌 전례(ingest_now)가 있고 몇 분마다 부르면 샌 도구도 그만큼 자주 불려서 허용 목록이다. ② **Drive `latest/`** — 60분마다 · 상한 5분 · heartbeat 70분 · 연속 2번(2시간). 리모트마다 가장 새 `<접두>-<시각>/` 의 파일이 `latest/` 에 같은 MD5(없으면 크기)로 있는가 — gotchas 8(시각 폴더까지만 올라가고 `latest/` 가 낡으면 소비자가 옛 산출물을 오류 없이 받는다)을 그대로 잡는다. drive-drift(로컬 대 Drive — dev 에서만 뜻이 있다)와 달리 Drive 만 보므로 cae00 에서도 뜻이 있다. 리모트는 drive-drift 와 같은 셋(포털 `images-` · HEAXHub `dist-` · KooRemapper `dist-`, dev 실측 3곳 20초). 못 닿아도 실패다 — 그 박스의 update-all 도 못 받는다. '나이' 는 보지 않는다 — 올릴 것이 없어 며칠 안 올리는 것은 고장이 아니다. ③ 검사는 이 박스에서 돌 수 있을 때만 싣는다(게이트웨이가 대상 · 에이전트 서버 venv · rclone · 리모트) — 못 싣는 까닭은 생성기가 한 줄로 말한다.

**IM-D28 update-all 동안 경보 멈춤.** Gatus 에는 멈춤 API 가 없어 maintenance 칸을 쓴다. 1b2(1b 사전 백업 뒤 · 1c 앞 — 백업은 서비스를 멈추지 않고 오래 걸릴 수 있어 그 뒤에 건다)가 `--pause 60` 으로 생성 설정을 **읽어 그 칸만** 넣고, 5b 의 일반 생성이 푼다(손잡이가 틀려 못 만들어도 옛 설정의 창은 걷는다). § 머리 정지 경로와 완주 끝도 푼다. 전체를 다시 만들어 걸고 풀지 않는 까닭 — 손잡이가 틀린 박스에서 걸지도 풀지도 못하고 창이 남는다. 푼 글은 일반 생성과 글자까지 같다(지문이 그대로라 update-sites 가 다시 띄우지 않는다 — 시험이 글자로 본다). 5b 에서 푸는 까닭 — 걸린 채로 update-sites 가 지문을 적으면 다음 실행마다 창의 시작 시각이 달라 매번 다시 뜬다. 5b 뒤(5c · §6 · §7)의 재기동은 짧아 연속 5번 문턱이 막는다. Gatus 는 창을 요일마다 되풀이하므로 update-all 이 5b 전에 죽어 창이 남으면 다음 주 같은 시각에 또 멈춘다 — 시한을 `pause.json` 에 적고 밀어 넣는 쪽이 지난 것을 `--unpause-if-expired` 로 걷는다(시한 기록 없이 창만 남은 것도). 생성기 실행은 모두 `.gen.lock` 을 잡는다(걷어내기와 걸기가 겹치지 않게). 요일은 `time.gmtime` 의 순번으로 고른다(로캘을 타지 않는다 — IM-D25 ⑥). 처음엔 1h 뒤 · 1i 앞(1h2)에 두었다가 비우기 시험 35개가 깨졌다 — 그 구획(1h~1i)을 원문 그대로 떼어 돌리는 하네스에 `$SVC` 가 없다. 1d~§2 는 구획마다 그런 시험이 있어(1d~1h · 1e~2 · 1f~1h · 1h~1i · 1i~2) 그 앞으로 옮기고, 시험이 '떼어 돌리는 구획보다 앞' 을 본다(IM-D8 과 같은 규율).

**IM-D29 덤으로 찾은 기존 결함(2026-10-17).** ① **`status-board.sh stop` 이 진짜 Gatus 를 '상태판이 아니다' 로 거부했다.** 리스너의 명령줄이 `/gatus` 하나(첫 인자)라 판정 `* /gatus *` 의 앞 빈칸이 없다. IM-D21 ⑦ 에서 좁힐 때 call-trace.sh 는 `" $_cmd"` 로 견줬는데 이쪽만 빠졌고, 시험의 가짜가 `python -c … /gatus`(앞에 다른 인자)라 통과했다. 이대로면 update-all 5b 가 설정이 바뀐 상태판을 다시 띄우지 못하고(✗) 끈 박스에서 내리지도 못했다. 첫 인자가 `/gatus` 인 가짜(Popen `executable`)로 시험을 더했고 실 Gatus 로 정지를 확인했다. ② **mcp-smoke 가 사람 신원으로만 답하는 백엔드(ste)를 0성공으로 셌다.** 게이트웨이 토큰에는 신원이 없어 ste REST 가 401 이다(dev 실측 0/3, 감사 `note: no-identity`). 그래서 update-all §6 이 매번 '복구'(재프로비저닝 `--force` · 게이트웨이 재기동 — 도는 심의 보호 없이)를 돌리고 ✗ 로 끝났다. 정적 백엔드 가운데 `per_user_sso` 에 있고 `headers`(서비스 자격)가 없는 것은 부르지 않고 '검사 못 함' 으로 말한다 — ste 는 사람 신분 실호출이 따로 본다. 허브 앱(DynaForge)은 서비스 자격이 있어 토큰 만료가 그대로 0성공으로 잡힌다(이 스모크가 생긴 까닭). ③ **(고치지 않음)** smart-twin-mcp 직접 도구는 `args: dict` 하나로 노출돼, 잡을 내는 `fullangle_drop_simulation` 도 게이트웨이에서는 필수 인자가 없어 보인다 — update-all 스모크의 '무인자' 후보였다(감사 9월 2회). 서버가 실행 전에 jsonschema 로 막아 잡은 안 나갔고, 검증 오류가 정상 응답 모양이라 스모크는 성공으로 셌다. 주기 판은 허용 목록이라 부르지 않는다.
