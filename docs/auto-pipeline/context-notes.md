# 결정 기록 — 자동 파이프라인

> 계획은 [PLAN.md](PLAN.md), 체크리스트는 [checklist.md](checklist.md). 덧붙이기만 한다.

## 2026-11-27 — 개념과 사용자 결정

**AP-1 포털은 해석을 모르고 계약만 부른다.**
- 사용자가 「어떤 시뮬레이션을 할지는 모르니 여기서 셋업하는 것이 아니다」라고 했다. 그래서 해석 조건은 각 앱의 profile 에 두고, 포털은 계약 다섯
  (`auto_profiles` · `auto_check` · `auto_submit` · `auto_status` · `auto_result`)과 결과 봉투만 안다.
- 리스크 앱이 ODB 허브에 계약 4도구를 청한 선례와 같은 방식이다.

**AP-2 단계는 정해진 도구 · 정해진 인자로 돈다.**
- 자동은 같은 입력에 같은 행동이어야 한다. 분석 루틴처럼 LLM 이 도구를 고르면 과제마다 다른 일을 한다.
- 그래서 절차 쪽 보증(고정 인자 · 코드 판정 · 사람 자리)을 쓰고, LLM 은 보고서 서술과 선택적인 심의 단계에만 쓴다.

**AP-3 사용자 결정(11-27) — 다섯 다 권장안.**
- AP-D1 서비스 신원 · AP-D2 단계적(그림자 → 한 번 눌러 제출 → 자동) · AP-D3 자동 보고서 전용 게시판에 확인 없이 · AP-D4 모든 과제 + 제외 목록 ·
  AP-D5 도는 것만 끝까지.
- AP-D3 은 11-21 게시 관문(L21-4 B1)을 **자동 파이프라인의 RA 시스템 계정 길에만** 푸는 결정이다. 사람 · Claude 의 게이트웨이 길에서
  `create_report_from_format` 막기는 그대로다.

**AP-4 RA 쪽은 이미 있다 — v0.180 시스템 연계 3종.**
- RA `04a147e` 문서 `docs/[참고] 시스템이_올리는_보고서_형식등록.md` §6 을 읽었다.
- 시스템 계정(`svc.<시스템>@system.invalid`, `rat_` 토큰 — 만료를 비우면 무기한)은 「바깥 시스템이 스스로 올릴 때」 쓰는 것이라 RA 가 적었다. 사람
  토큰을 빌리면 12시간 만료 · 퇴사 때 조용히 죽음 · 작성자에 사람 이름이 찍히는 문제가 있다고도 적었다. AP-D1 과 같은 판단이다.
- 수신 게시판(시스템 양식 `format.destination.boards` · `/from-format`)과 `create_report_draft(publish=True)` 는 시스템 계정만 된다. 관리자가 게시판을
  미리 연결해 둔 것이 사전 승인이라는 RA 의 설계가 AP-D3 과 맞는다.
- 함정 둘을 운영 절차에 옮긴다 — 서비스 계정도 개인 워크스페이스가 있어야 한다 · 조직 grant 는 `edit` 이어야 게시된다(`view` 는 열람만).

**AP-5 감지는 묻기부터.**
- StepForge 웹훅(D-706)은 잡 끝 · 실패 · 취소 · 정체 알림뿐이고, 과제 등록 · 파싱 끝 알림은 없다. DynaForge 도 같은 창구가 없다.
- 그래서 v1 은 포털이 묻는다(앱 수정 0). 알림은 M4 에 더하고, 더한 뒤에도 묻기를 남겨 빠진 알림을 잡는다.

**AP-6 과제 열쇠는 project-insight-graph 와 같다.**
- (과제 = SP `plm_task` key, 차수 = 개발 단계 코드). 앱마다 과제 번호가 달라 A → Z 가 끊기는 문제(절차 PLAN 5-3)가 이 일의 가장 큰 위험이다.
- 계약 subject 에 SP key · 차수를 필수로 하고, 못 풀면 그 단계는 `blocked` 다. 과제 key 를 짐작하지 않는다.

## 2026-11-27 — 미리 짓기 전에 정한 것(사용자 지시 「미리 개발할 수 있는 것을 다」)

**AP-7 계산 클러스터 공유 저장소가 아직 깨져 있다 — 전각도 낙하의 실주행은 SH-01 뒤.**
- 운영 둘째 답 Q45 덧붙임 2(11-27): stcx 계산 노드 355대에 공유 볼륨이 없어, 업로드 입력이 있는 잡은 복사 단계에서 실패할 것으로 본다(request-1125 R25-25).
- 그래서 계약의 `auto_check` 에 `missing.kind = infra` 를 두었다. 앱이 박스 문제를 「입력 없음」과 갈라 말하게 한다. 포털은 그 단계를 `blocked` 로 세우고 제출하지 않는다.

**AP-8 서비스 토큰은 저장하지 않고 호출마다 찍는다.**
- PLAN §4.6 은 관리자가 발급한 1 ~ 365일 서비스 PAT 를 쓰고 만료를 표시한다고 적었다. 미리 지으며 바꿨다.
- 포털이 절차 PAT 와 같은 체계로 호출마다 15분짜리를 찍는다(청중 `mcp-gateway-service` · `sub` `system:auto-pipeline` · jti `ap-<run>-<step>`). 저장할 비밀 · 만료 관리 · 유출 표면이 없다.
- 무엇을 부를 수 있는지는 여전히 게이트웨이 박스 파일 `service_tools.local.json` 이 정한다.

**AP-9 권한은 grant_only 키 하나.**
- `feat:auto-pipeline` 은 전 과제 · 클러스터에 영향이 커서 「전부」 · 관리자 전권에 딸려 오지 않게 한다(`feat:chat-claude` 와 같은 꼴).
- 서비스 신원은 모든 과제를 보므로 현황판도 이 키를 가진 사람만 본다. 사람마다 과제 시야를 다시 거르는 일은 M5 로 미룬다.

**AP-10 RA 게시는 블록 초안 + 게시판 연결로 한다(HTML 양식 아님).**
- RA 시스템 양식의 `/api/imports/from-format` 은 HTML 뼈대 번들이 있어야 한다. 보고서 종류마다 HTML 뼈대를 지어야 해서 미루었다.
- 대신 지금 쓰는 블록 꼴 `POST /api/reports/ai-draft` 로 시스템 계정 개인 공간에 초안을 만들고 `POST /api/mounts` 로 게시판에 건다. 시스템 계정은 관리자가 게시판을 미리 연결한 것이 사전 승인이라 확인 토큰 없이 게시된다(RA 문서 §6.4).
- 시스템 공간 대시보드의 「양식별 수신」이 보려면 형식을 시스템 이름으로 등록한다(`ra-register-format.py`).
