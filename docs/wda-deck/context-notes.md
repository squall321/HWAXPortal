# 발표자료로(RA 보고서 → WebDesignAgents) — 결정과 까닭

> 계획 [PLAN.md](PLAN.md) · 체크리스트 [checklist.md](checklist.md) · WDA 요청서 [wda-request.md](wda-request.md).
> 사실의 파일 · 줄 근거는 PLAN §2 에 있다. 여기는 **왜 그렇게 정했나**를 적는다. 사람이 정할 것은 PLAN §13 — 뒤집히면 여기 덧붙인다.

**WD-D1 사용자 결정 1(2026-11-01) — 포털이 맡고 알린다.** 포털이 만든 RA 보고서 옆 '발표자료로' 단추. 포털이 그 보고서를 그 사람 명의로 읽어
본문을 WDA 에 넘기고(R2 (나)), 잡 기록(누가 맡겼나)을 남기고, 화면이 진행을 보이고, 끝나면 그 대화에 받기 링크 알림을 남긴다. DocForge 배달과 같은
꼴이다. 챗 LLM 은 잡을 폴링하지 않는다(HA-28).

**WD-D2 사용자 결정 2(2026-11-01) — 기본 출력은 PPT + PDF, `pptx_mode` hybrid.** 영상 · HTML · Word 는 단추에서 고를 수 있는 것이다. 내레이션은 끈다
(영상을 골라도 M1 은 끈 채 — 켜면 VoiceRecorder 를 부르고 길이가 크게 는다).

**WD-D3 부르는 길 — 허브 Caddy 를 거쳐 WDA 웹 REST 를, 그 사람 이름으로 찍은 짧은 포털 PAT(청중 `heax-hub`)로.** 견준 길 넷.
① 게이트웨이 MCP(DocForge 꼴) — 본문을 받는 도구가 없고(`report_ingest` 는 서버 경로), 게이트웨이는 WDA 에 신원을 싣지 않아(IDENTITY_FWD · per_user_sso 밖)
WDA 쪽 주인을 정할 수 없다. 바이트(PPT · PDF)를 MCP 로 나르면 base64 로 33% 불고 게이트웨이의 결과 가림(`_pii_mask`)과 상한을 지난다.
② 게이트웨이 REST 다리(`/api/<site>/`, SimFlow 꼴) — 사람 명의(per_user)는 WDA 에 위임 창구(`/auth/sso`)와 그 토큰 검증이 있어야 하고, 다리는
per_user 사이트에 허브 게이트용 Authorization 을 싣지 않아 Caddy 를 지나지 못한다(게이트웨이 손질까지 든다). 서비스 자격(inject)이면 사람 명의가 아니다.
③ WDA 루프백 포트 직결 — 포트가 허브 풀에서 바뀌고 허브의 앱 권한 검사(`can_view_app`)를 건너뛴다.
④ **허브 Caddy + 포털 PAT** — 허브 게이트가 이미 포털 PAT 를 받는다(followups-1017 결정 ⑦ — 허브 앱의 사람별 권한은 `can_view_app` 만, FU-D17).
게이트가 서명 · 청중 · 폐기 목록을 보고 허브 사용자로 잇고 앱 권한을 본 뒤, Caddy 가 클라이언트가 보낸 `X-Heax-User-Email` 을 지우고 확인한 값으로
다시 싣는다. WDA 는 머리 하나만 읽으면 되고, 본문은 이미 있는 `POST /api/runs {report_json}` 로 가고, 바이트는 HTTP 로 흐른다. 고른 까닭이 이것이다.
치르는 값 — 그 사람에게 허브 계정이 있어야 한다(허브 타일이 보이면 화면이 미리 로그인해 생긴다 — SsoPrimer). 이 청중의 첫 포털 쪽 쓰임이라
`config.py:243-245` 의 '소비처가 없다' 주석을 함께 고친다.

**WD-D4 WDA 의 신원 정본은 허브 Caddy 가 실은 `X-Heax-User-Email` 하나(REST 에서만).** WDA 세션은 'MCP 는 게이트웨이가 넣는 검증된 `x-hwax-user`
를 읽는다' 고 했다 — 코드는 그렇지만(`session.py:159-191`) 두 가지가 틀어진다. ① 게이트웨이는 WDA 에 그 머리를 싣지 않는다 — 신원을 싣는 길은
IDENTITY_FWD(기본 `hwax-deliberation` 하나 · 떠 있는 dev 게이트웨이 환경에도 따로 없다)와 per_user_sso(WDA 없음)뿐이고 나머지는 상주 세션이다.
② Caddy 는 `x-hwax-user` 를 지우지 않는다 — 자기 PAT 로 `/apps/web_design_agents/mcp` 에 직접 붙은 누구나 남의 이메일을 적어 보낼 수 있다(게이트웨이도
같은 까닭으로 소속에 서명을 붙였다, `gateway.py:259-262`). 그래서 `x-hwax-user` 는 주인 판정에 쓰지 않는다. `/mcp` 의 `X-Heax-User-Email` 은 허브
관리자(게이트웨이 서비스 토큰의 주인)로 접히므로(`gateway.py:273-278`, HWAXRisk 가 같은 까닭으로 위임 머리를 따로 둔다) MCP 는 주인을 정하지도, 주인 있는
run 을 열지도 않는다. MCP 쪽 주인은 2단계(WD-D19).

**WD-D5 WDA 의 주인 기능은 단추를 켜기 위한 전제다 — 사용자 결정 U-1 대기(권장 예).** 근거는 셋이다. WDA 원장에 주인 칸이 없다. `GET /api/runs` 가
전부를 준다. 허브 매니페스트가 company + stable 에 portal_auth 가 없어 게이트가 익명을 통과시킨다 — dev 실측(11-01)에서 포털 nginx 를 거친
`/apps/web_design_agents/api/runs` 가 로그인 없이 200 이었다. 사람의 RA 권한 안에 있던 보고서 본문을 그런 곳에 넘기면 RA 의 권한이 WDA 의 '누구나' 로
바뀐다. '이미 사내 공개인 보고서만 예외' 도 두지 않는다 — 포털은 RA 보고서의 독자가 WDA 의 독자(익명 포함)를 덮는지 알 수 없다.

**WD-D6 주인 규칙은 깨지 않는 꼴로.** 신원이 있는 REST 만들기는 주인을 갖고 주인만 본다(다른 사람 · 신원 없음은 없는 것과 같은 404). 신원 없이 만든
run(옛 것 · CLI · 신원 없는 MCP · 직결)은 지금 그대로다 — **주인 없는 run 은 비공개가 아니다**(WDA 세션이 이 문장을 요청서와 보안 절에 넣어 달라 했다).
포털은 늘 신원을 싣는다(허브 Caddy 경유). WDA 콘솔에서 새로 만든 run 도 신원이 있으니 그 사람 것만 된다 — 콘솔의 '모두의 목록' 이 '내 것 + 주인 없는 옛 것'
으로 바뀐다. 이 바뀜을 싫어하면 WDA 가 만들 때 고르는 칸(`private`)으로 좁힐 수 있지만, 콘솔에 붙여 넣는 보고서도 같은 값이라 권하지 않는다.

**WD-D7 포털이 모든 것을 중계한다 — 브라우저는 WDA 를 보지 않는다.** run_id · job_id · WDA 주소 · 서버 경로는 포털 응답 · 알림 · 링크 어디에도 없다.
내려받기는 포털 라우트가 잡 기록의 주인을 보고, **요청한 사람의** 이름으로 WDA 에서 받아 흘린다(WDA 가 주인을 다시 본다 — 두 겹). 서명 URL 은 쓰지
않는다 — 서버 쪽 가져오기가 이미 그 사람으로 인증되고, 들고 다니는 URL 은 로그 · 기록에 남는 열쇠라 지켜야 할 것이 하나 는다. 포털은 파일을 쌓지
않는다(받을 때마다 흘린다).

**WD-D8 상태 낱말은 하나 — `queued · preparing · rendering · done · failed`(+ step · 단계 기준 progress).** WDA 는 낱말이 둘이다 — 파이프라인
(run `queued/running/done/failed` · 단계 ingest · fragmentize · scenario · build 마다 `pending/running/done/failed`)과 렌더(웹 `queued/rendering/done/failed`,
MCP 잡은 `building` 이 더 있다). 화면에 둘을 그대로 보이면 '끝났는데 또 시작' 처럼 읽힌다. 다섯 낱말로 접고 단계 이름을 step 으로 보인다(표는 PLAN
§7.2). progress 는 시간이 아니라 단계로 센 값이라 그렇게 적는다.

**WD-D9 화면이 몬다 — 포털 뒤에서 기다리는 일감을 만들지 않는다(DF-D17 ③ 그대로).** 포털은 uvicorn 하나라 재기동하면 뒤의 일감이 사라지고, 사라진 것을
아무도 모른다. 화면이 3초마다 진행을 묻고, 끝을 보면 `advance` 를 부른다. 창을 닫은 잡은 입력창 위 '끝나지 않은 발표자료' 줄(DF-D23 꼴)이 다시 연다.
GET 은 부작용이 없다 — 렌더 맡기기 · 알림 남기기는 CSRF 를 거는 POST(`advance`)에서만 한다.

**WD-D10 끝난 잡의 알림은 저절로 남긴다.** DocForge 는 '저절로 넣지 않는다(사람이 고른다)'(DF-D23)였다 — 그쪽 배달은 RA 에 보고서를 만드는 쓰기라
남에게 보인다. 발표자료의 끝은 그 사람의 대화에 알림 한 건을 쓰는 일뿐이라 다시 묻지 않는다. 실패도 알림을 남긴다 — 다음 턴이 '왜 없나' 를 안다.

**WD-D11 알림은 서버가 단추를 누른 그 대화에 직접 남긴다.** DocForge · 보내기 알림은 화면이 **지금 대화**에 붙였다(`addUploadNotice` — 업로드 패널은
그 대화 안에서 열리고 그 자리에서 끝난다). 발표자료는 몇 분 걸리고 그 사이 사람이 다른 대화로 옮겨 간다 — 지금 대화에 붙이면 엉뚱한 대화에 남는다.
그래서 잡 기록에 대화 id 를 남기고(만들 때 그 대화가 그 사람 것인지 본다), `advance` 가 `conv_store.append`(주인 검사가 있다)로 그 대화에 쓴다.
화면은 응답의 알림을 그 대화의 **화면 사본에만** 붙인다(서버에 다시 쓰지 않는다). 그 대화가 답을 받는 중이면 끝날 때까지 기다렸다 `advance` 를 부른다 —
포털은 답을 스트림 끝에 쓰므로 먼저 쓰면 다른 기기에서 알림이 답보다 앞선다(PP-D3 ⑤). 알림의 꼴은 PP-D3 그대로다(어시스턴트 글 + 활동 하나
`origin: 'upload'` · meta `upload: true`) — 다음 턴 이력의 `kind: upload` 근거가 되고 포털 모델에 새 칸이 들지 않는다.

**WD-D12 단추 자리는 셋 — 심의 결과 카드 · `/보고서` 저장 답 · RA 보내기 알림(U-5 권장).** 셋 다 서버 사본에서 보고서 번호를 되살릴 수 있어야
새로고침 뒤에도 산다. ① 심의 — 중계가 outcome 을 버린다(`routes.py:2854-2895`). 답 meta `delib_outcome {report_id, title}` 로 남기고 화면이 되살린다
(이 고침은 '되살린 심의는 보고서 단계가 사라진다'(`DelibView.tsx:43,48`)도 바로잡는다). ② `/보고서` — 에이전트 서버가 글로만 낸다. 글을 파싱하지 않고
`result` 사건에 `ra_report {id, title}` 칸을 더하게 한다(에이전트 서버 한 칸 · 중계가 답 meta 로 남긴다) — 글은 바뀌고 파싱은 조용히 깨진다. ③ RA 보내기
알림은 활동 근거에 이미 `report_id` 가 있다. 분석 루틴 RA 초안은 M2.

**WD-D13 R1(`destApps` 한 줄)은 넣지 않는다 — 단추는 `DocActions` 가 아니다.** `DocActions` 는 붙인 문서를 '어디로 보낼지' 고르면 **LLM 에게 줄 지시문**을
입력창에 채우는 선택지다(`DocActions.tsx:27-38`) — 발표자료를 거기 두면 LLM 이 WDA 도구를 몰게 된다(서버 경로 `report_ingest` · `render_status` 되풀이 =
HA-28). `destApps.ts` 는 그 선택지와 업로드 목적지의 '지금 전문가' 순서표라(`destApps.ts:1-26`) 소비처 없는 `deck` 줄은 아무 일도 하지 않는다. 나중에 '붙인
문서 → 발표자료' 목적지를 만들면 그때 `deck: ['heax-web_design_agents']` 를 더한다.

**WD-D14 HTML 은 끼워 보지 않는다(M1) — 내려받기만.** 허브 앱은 포털과 같은 오리진(`/apps/`)이라 WDA 가 만든 HTML 을 포털 쪽에서 그대로 열면 그
스크립트가 포털 쿠키 · CSRF 값에 닿을 수 있다. 내려받기 응답은 `attachment` · `nosniff` · `no-store` 에 HTML 은 `Content-Security-Policy: sandbox` 를
더한다. 나중에 끼운다면 `sandbox="allow-scripts"`(allow-same-origin 없이) iframe 으로만 — 출처가 불투명해 포털에 닿지 못한다. WDA 의 장면 HTML
(`/api/runs/{id}/scenes/{name}/html`)도 같다.

**WD-D15 RA 그림은 M1 에서 싣지 않는다 — WDA 의 서비스 자격으로도 받지 않는다.** WDA 는 file_id 그림을 `WDA_RA_*` 서비스 자격이 있을 때 RA 에서 받는다
(`assets.py:92-121`) — 사람 명의 원칙과 어긋난다(서비스 계정이 사람 대신 RA 를 읽는 길은 2026-09-29 사고의 꼴이다). M1 은 그림 수를 세어 알림에 말하고, M2 에
포털이 그 사람 명의로 RA 파일을 받아 만들기 요청에 함께 넘긴다(WDA 가 파일을 받는 꼴이 먼저 — 요청 W-16). 심의 · `/보고서` 보고서는 글 블록이라 대개
그림이 없다.

**WD-D16 한도(시간 문턱 · 박스 상한은 WD-D30 이 고쳤다).** 본문 16MB — 심의 보고서는 회의록 400 · 결과 · 권고 각 200 항목 × 1,900자가 상한이라(HWAXAgentServer `deliberation.py:154-158`) 한글
3바이트로 어림하면 수 MB 다. 넘으면 WDA 를 부르지 않는다. 사람당 동시 2 · 같은 보고서 · 같은 옵션은 하나로 묶는다(두 번 눌러도 WDA run 하나).
시간은 '늦음' 표시만(준비 30분 · 렌더 60분 · 영상 180분) — WDA 의 실측이 오면 고친다. 24시간이 지나도 running 이면 포털이 실패로 닫는다(그물).

**WD-D17 'PDF' 의 뜻 — WDA 의 pdf 는 슬라이드 PDF 가 아니라 '읽는 문서' 다(U-4 대기 · 권장 정식 보고서).** WDA 는 같은 심의에서 나온 글(본문 = 내레이션,
삽화 = 장면 스틸)을 report · brief · memo 꼴로 조판해 HTML · PDF · Word 로 낸다. 사용자가 'PPT + PDF' 를 '슬라이드 + 그 PDF 판' 으로 생각했을 수 있어
묻는다. 기본은 report, 단추에서 요약 · 메모를 고르게 한다. 슬라이드 PDF 가 필요하면 WDA 에 새 출력을 청한다(W-19).

**WD-D18 배포 전제 — WDA push · 허브 SIF 재빌드(U-2 대기).** 허브는 GitHub 에서 SIF 를 짓는데 WDA main 이 68 커밋 앞서 있고 push 가 workflow 범위로
거절됐다. 지금 배치(08-19 판)는 렌더 출력이 video · pptx 뿐이라 사용자 결정 2 가 돌지 않는다. 역사를 다시 쓰는 길(CI 파일 커밋 빼기)은 권하지 않는다 —
68 커밋의 해시가 바뀌어 WDA 문서가 인용한 커밋이 사라진다. `git push --dry-run` 은 서버 쪽 검사에 닿지 않으니 통과해도 풀린 것으로 보지 않는다.

**WD-D19 MCP 쪽 주인(개인 Claude 로 내 발표자료 보기)은 2단계 — per_user_sso(HWAXRisk 꼴).** 게이트웨이가 WDA 의 `/auth/sso`(공유 비밀 + `X-Hwax-Delegate-Email`)
로 그 사람의 단기 단언을 받아 `token_header` 로 싣는 길이다. 단추에는 필요 없고 WDA · 게이트웨이 둘을 고쳐야 해 미룬다. 들어오면 로컬 포트 우회(WD-D21 ①)도
같이 닫힌다.

**WD-D20 운영자 페르소나 `he-doc-webdesign` 의 글을 고친다.** 지금 글은 챗 LLM 에게 `report_ingest`(서버 파일 경로) → … → `render_status` 로 산출물을 받으라고

## WDA 세션의 답 뒤(2026-11-01)

**WD-D29 템플릿 문 — `deliberation` 보고서는 WDA 의 `format:deliberation`(W-21)이 있어야 단추가 선다.** WDA 가 실제 꼴의 심의 보고서를 넣어 본 결과(Q2)
조각은 바르게 뽑히나 장면이 제품 소개 뼈대로 눌려 결정문 · 액션아이템이 사라졌다 — 넘기면 틀린 발표자료가 나간다. 그래서 RA 보고서의 템플릿(최상위와
페이지마다) 가운데 하나라도 `deliberation` 이면 `owner` 에 더해 `format:deliberation` 을 요구한다. 그 밖의 템플릿(RA 보내기 알림의 `__import_blank__`)은
`owner` 만. 화면은 자리마다 템플릿을 알고(심의 결과 카드 · `/보고서` 는 deliberation) `status.formats.deliberation` 으로 숨기며, 만들기는 RA 에서 읽은
실제 템플릿으로 다시 본다 — 화면이 아는 자리와 실제가 다르면(클라이언트가 번호를 바꿔 보내면) 실제가 이긴다. 사용자 결정(U-6, WD-D32) — 심의 형식이 설 때까지 숨긴다.

**WD-D30 시간 문턱과 박스 상한.** WDA 실측 5.5초(파이프라인 0.5 + 렌더 5.0, pptx 1.2 MB · pdf 1.9 MB)라 '늦음' 문턱을 준비 5분 · 렌더 15분 · 영상 60분으로
낮추고, 끝내 6시간이 지나면 실패로 닫는다 — WDA 는 재기동에 끊긴 실행을 running 으로 남겨(W-12 전) 24시간 그물로는 사람이 하루를 기다린다. WDA 에 동시
상한 · 보존이 없어(Q4) 포털이 사람당 2 에 더해 박스 전체 4 로 묶는다(`wda_deck_inflight_box_max`). WDA 콘솔 · MCP 로 들어오는 일은 포털이 막지 못하니
W-13 · W-14 를 '강하게 권함' 으로 올렸다.

**WD-D31 시험의 가짜 WDA 는 요청서의 계약 그대로 — 그리고 WDA 가 알려 준 블록 글자 규칙.** WDA 에는 W-1 ~ W-12 가 아직 없다(Q1). 포털 시험은 봉투
`{success, data, message, code}` · 상태 낱말 · 남과 신원 없음에 404 · 허브 게이트(포털 PAT 의 서명 · 청중을 보고 `X-Heax-User-Email` 을 싣는다)를 흉내 낸다.
만들기 본문은 WDA 의 규칙으로 센다 — `rich_text` 는 `content.markdown`, `heading` 은 `content.text`, `props.default_text` 는 대신 쓰지 않고, `content` 에
없는 블록은 글자 0, 모두 0 이면 거절. 포털은 RA ReportRead 를 바꾸지 않고 넘긴다(시험이 받은 본문과 RA 의 `data` 가 같은지 본다). 실물 `deliberation`
보고서는 블록 정의가 보고서에 없어(템플릿 블록은 `content` 키만) 지금 WDA ingest 로는 블록 0개가 될 것이다 — 요청서 4.6-2 에 적어 WDA 의 심의 꼴 일에 넘겼다.

**WD-D32 사용자 결정(11-01, U-6) — '심의 형식이 설 때까지 숨긴다'.** WD-D29 의 문을 확정했다. `deliberation` 템플릿 보고서는 WDA `/api/health` 의
features 에 `format:deliberation`(W-21)이 있을 때만 단추가 서고 만들기를 받는다. 그 밖의 템플릿은 `owner` 와 박스 스위치만 본다. 까닭은 WDA 자신의 Q2
실측이다 — 결정문이 한 장면에 묻히고 액션아이템 · 라운드 요지가 사라지며 '보고서 참조' 같은 채움 글이 영상에 나갔다. 코디네이터의 전언은 '`/보고서` ·
RA 보내기 알림은 owner 만' 이었지만, 문은 템플릿으로 가르고 `/보고서` 저장 답의 보고서도 `deliberation` 템플릿이다(에이전트 서버
`deliberation.py:7892` — 심의 결과는 `:7631`). 그래서 `/보고서` 도 같은 문에 걸리고, W-21 전에는 **RA 보내기 알림 자리에서만** 단추가 선다. 템플릿을 보는
곳은 둘이다 — 화면은 자리로(심의 결과 카드 · `/보고서` 는 deliberation) 숨기고, 서버는 RA 에서 읽은 실제 템플릿으로 다시 막는다(409).

## WDA 의 심의 꼴(2026-11-01 저녁)

**WD-D39 심의 꼴의 표지는 `format:delib-16x9` · 상태는 `formats` · 정책은 함수 하나(지금 active 만).** WDA 가 심의 꼴을 지었다(로컬 판 · 허브 SIF 전).
features 를 꼴 등록부에서 만들어 내므로 이름은 우리가 청한 `format:deliberation` 이 아니라 `format:delib-16x9` 다 — WDA 의 이름을 받았다(WD-D29 · D32 의
문은 그대로, 표지 이름만 바뀐다). `formats` 가 꼴마다 상태(draft · active …)를 주므로 '꼴이 있다' 와 '써도 된다' 를 가를 수 있다. 정책은 `format_ready`
하나다 — features 에 `format:delib-16x9` 가 있고 `formats["delib-16x9"] == "active"`. status 의 `formats.deliberation` 과 만들기의 문(409)이 이 함수를
같이 쓴다. draft 를 받을지는 코디네이터가 사용자에게 묻는 중이라(PLAN U-7) 답이 오기 전까지 active 만 — 바꿀 때는 그 한 줄이다. 준비됐으면 만들기에
`"format": "delib-16x9"` 를 싣고, 그 밖의 템플릿은 칸을 싣지 않는다(WDA 기본 wide-16x9 — 지금과 같다). 화면의 API(`formats.deliberation` 참거짓)는
바꾸지 않았다 — 템플릿에서 꼴로 잇는 것은 서버의 `TEMPLATE_FORMAT` 한 곳이다. WDA 는 모르는 꼴에 곧바로 400 을 준다(실행 없음 · 쓸 수 있는 꼴을
message 에). 포털은 그 까닭을 그대로 보이고(502 — WDA 가 받지 않았다) 잡을 남기지 않으며 **기본 꼴로 다시 보내지 않는다** — 탐침을 60초 붙잡으므로
그 사이 WDA 가 옛 판으로 되돌아가면 생길 수 있는 일이다. 붙잡은 탐침을 버리는 손은 두지 않았다(60초 뒤 저절로 다시 묻는다).

**WD-D40 `block_sections` 는 M1 에 포털이 만들어 싣지 않는다 — RA 블록 id 에서 단락이 하나로 정해지지 않는다.** WDA 는 머리글 추론을 덮어쓰는
`block_sections`(RA 단락 낱말 decision · action_item · alternatives · recommendation, 심의 전용 topic · round)를 받는다. 코디네이터의 조건은 'RA 블록에서
결정적으로 정해질 때만' 이었고, 정해지지 않는다. ① 같은 `deliberation` 템플릿을 세 곳이 다른 뜻으로 채운다 — 심의 결과(에이전트 서버
`deliberation.py:7589-7602` — `recommendation` 이 결정문 전체), `/보고서`(`:7859-7864` — `recommendation` 이 사람의 결론과 마지막 답), 분석 루틴 초안

**WD-D42 사용자 결정(11-01, U-7) — 심의 자리의 단추는 `delib-16x9` 가 active 일 때만 연다. draft 는 숨기고, draft 를 여는 손잡이는 두지 않는다.**

**WD-D43 WDA 판은 잡 기록에 남기고 막는 데 쓰지 않는다.** WDA 의 `/api/health` 가 맨 위에 `version`(패키지 판 — 허브 매니페스트 판과 같다, 11-01

**WD-D41 스스로 다시 읽고 고친 셋(11-01 저녁).** ① 입력창 위 줄이 잡을 잃었다. 목록 창구가 WDA 를 못 물은 잡을 목록에서 뺐고, 줄은 목록을 못

## 적대 검토 두 차례 뒤(2026-11-01 밤)

**WD-D44 `/\host` 도 다른 사이트다.** WD-D36 의 '프로토콜 상대는 여전히 글' 은 `//` 만 막았다. 브라우저는 특수 스킴 URL 의 경로에서 `\` 를 `/` 와
같게 읽어 `/\phish.example/login` 이 `https://phish.example/login` 이 된다(검토의 브라우저 탐침). 링크 고르기(`RE_INLINE`)와 검사(`lm`) 둘 다
`\/(?![/\\])` 로 바꾸고(문자 묶음 안의 `/` 는 이스케이프하지 않는다 — 린트) 주소 안의 `\` 는 받지 않는다(http(s) 링크도). 그림 규칙은 그대로 둔다 — 그림은 원래 http(s) 바깥 주소를 받으므로
`//` · `/\` 가 더 넓히는 것이 없다. 이력 · 시험 머리의 '여전히 글' 문구도 `/\` 를 더해 고쳤다. 두 겹이라 한 줄 변이(고르기만 · 검사만 옛 꼴로)는 다른
겹이 막아 시험이 붉지 않다 — 두 줄을 함께 되돌리면 붉다.

**WD-D45 보고서 번호는 ASCII 숫자만.** 중계의 `_report_id_of` 가 `str.isdigit()` 로 글 번호를 받았다 — '²' 는 isdigit 이 참인데 `int('²')` 가
터져 그 답의 meta 를 못 남기고, '٣' · '５８' 은 3 · 58 이 됐다. `[0-9]+` 로 좁혔다(`\d` 는 유니코드 숫자를 받아 변이 시험이 붉다).

**WD-D46 운영자 페르소나는 단추가 보일 때만 그 단추로 보낸다.** WD-D20 의 글('도구를 몰지 말고 단추를 안내')은 무조건이었다 — 단추는 박스 스위치 ·
WDA 주인 기능 · (심의 보고서는) 심의 꼴이 다 있어야 서므로 오늘은 모든 박스에서 숨어 있고, 그 글은 없는 단추로 사람을 보낸다. 단추가 보이면 쓰라 하고,
안 보이면 '이 박스에서는 아직 켜지지 않았다' 고 말하며, 어느 쪽이든 그 보고서의 렌더를 render_submit · render_status 로 대신 몰거나 되풀이해 묻지 않는다.

**WD-D47 허브가 포털 토큰을 WDA 까지 넘긴다 — 알려진 허브 쪽 위험으로 적고 허브는 고치지 않는다.** 검토가 찾았다 — forward_auth 는 신원 머리만 지우고
다시 실을 뿐 원 요청의 `Authorization` 은 WDA 까지 간다(HEAXHub `proxy_manager.py:59-61`). `heax-hub` 토큰은 그 사람이 볼 수 있는 모든 portal_auth
허브 앱에 통하므로 WDA 쪽에서 10분 동안 다른 허브 앱을 그 사람으로 부를 수 있고, 짧은 토큰의 jti 는 하나씩 거둘 수 없다. PLAN §8 에 허브 쪽 고침
제안(portal_auth 앱으로 넘길 때 authz 통과 뒤 `Authorization` 을 지운다)과 함께 적었다 — HEAXHub 는 이 가지가 손대지 않는다(코디네이터가 사용자에게).
같은 글에서 요청서 §6 의 옛 시간(준비 30분 · 렌더 60분 · 영상 180분 · 24시간)을 WD-D30 의 5 · 15 · 60분 · 6시간으로 고쳤다.

**WD-D48 가짜는 지금의 진짜보다 너그럽지 않게.** 검토가 가짜 허브 · WDA 가 진짜보다 친절한 곳을 짚었다. 가짜 WDA 의 4xx 는 이제 지금 WDA 처럼
`{"detail"}` 하나이고 code 가 없다(W-10 전) — 글은 `f"{type(exc).__name__}: {exc}"` 꼴이라 경로 · run_id 가 실린다. 모르는 꼴의 400 만 봉투
(11-01 저녁 판). 요청서 W-10 의 봉투 + code 는 `error_codes=True` 로 따로 본다. 허브 게이트는 HEAXHub 의 진짜 꼴이다 — 익명 401 은 몸이 비고,
거절된 포털 토큰 401 · 허브 계정 없음 403 · JWKS 를 못 읽음 503 은 `{"detail"}`, 앱을 볼 수 없음 403 은 몸이 비며(can_view_app), 읽기 전용 포털
토큰의 GET 밖은 403(`authz.py` · `portal_sso.py`).

**WD-D49 사람 · WDA 의 글은 알림 · LLM 근거에서 마크다운이 되지 않고, WDA 의 예외 글은 사람에게 가지 않는다.** 검토 R3 · R3b — RA 제목(사람이 쓴다)이
알림 글에 그대로 들어가 `\n\n> [!WARNING] … [포털 다시 로그인](https://evil…)` 이 콜아웃 · 링크 · 그림이 됐고, 다음 턴의 LLM 근거(`result_full`)에도
그대로 갔다. WDA 의 실패 글(`f"{type(exc).__name__}: {exc}"` — 경로 · run_id 가 실린다)이 브라우저 응답 · 알림에 그대로 갔다(WD-D7 위반). 고친 것 —
① `md_plain` 으로 줄바꿈 · 제어 · 방향 바꾸기 글자를 빈칸으로, 마크다운이 되는 글자(`` [ ] ( ) ! * _ \ ` # > | $ ~ < ``)를 같은 모양의 전각 글자로
바꿔 한 줄에 넣는다. 역슬래시 이스케이프가 아닌 까닭 — 포털 챗 글(md.ts)에는 이스케이프가 없어 `\[` 가 그대로 보이고, `\(..\)` 는 수식이 된다.
알림 머리의 제목 · 뺀 출력의 이름과 까닭 · LLM 근거의 제목에 쓴다(뺀 출력은 fold 와 알림 두 겹 — 한 겹만 되돌리는 변이는 다른 겹이 막는다). ② 허브 · WDA
· RA 의 거절은 code(있으면) · HTTP 상태로 고른 포털의 정해진 글로 말하고, 상대의 글은 서버 로그에만 남긴다. 단계 · 렌더 실패는 '어느 단계에서
실패' 만 말하고 WDA 의 예외 글은 `raw_error`(화면에 싣지 않는 칸)로 두었다가 끝을 적을 때 한 번 로그에 남긴다. ③ 렌더 맡기기의 409 는 code 가
없어도 '이미 맡겼다' 로 읽는다(지금 WDA 는 code 를 싣지 않는다 — WD-D48).

**WD-D50 권한 둘은 모든 창구에서 다시 본다.** 검토 R4 — 만들기만 `ensure` 해 권한을 거둔 뒤에도 목록 · 진행 · advance · 받기가 돌고 그 사람 이름의 허브
토큰이 찍혔다. 목록 · 진행 · advance · 받기 · 숨기기 모두 첫 줄에서 `plat:webdesign` · `plat:reportarchive` 를 다시 본다(403). 맡겨 둔 잡은 WDA 에서
계속 돌 수 있다 — 끝을 적는 것은 권한이 돌아오거나 다른 사람의 만들기가 그 잡을 정리할 때다(WD-D59).

**WD-D51 맡기기 · advance · 숨기기는 쓰기 — 세션이거나 write 범위의 PAT 만.** 검토 R7 — 읽기 전용 PAT(`['read']`)으로도 만들기가 돌아 포털이 허브에
쓰기(POST /api/runs)를 냈다(허브는 읽기 전용 포털 토큰에 GET · HEAD 만 연다 — 그 판정을 포털이 비켜 갔다). 세 창구의 본문 첫머리(인증을 마친 뒤)에서
PAT 의 scopes 를 읽어 write 가 없으면 403 이다. 코디네이터의 말대로 'write 가 있어야' 로 짰다 — 포털 루틴의 `_read_only_pat`(read 가 있고 write 가
없을 때만 막는다)보다 좁아 챗 PAT(`['chat']`)도 막는다. scopes 칸이 없는 옛 PAT 은 `/auth/pat` 의 기본값(read · write)으로 본다. 읽기(목록 · 진행 ·
받기)는 범위를 보지 않는다. 덮지 않은 진짜 인증 길 시험 둘을 더했다 — 세션은 CSRF 머리가 있어야 맡기고 advance 한다, PAT 은 범위 넷(read · chat ·
read+write · 칸 없음). 남긴 것 — 스위치가 꺼진 박스에서 깨진 본문은 404 가 아니라 422 다(본문 해석이 의존성보다 먼저다). 창구 이름은 공개
리포에 있어 드러날 것이 없다고 보고 그대로 둔다.

**WD-D52 WDA 가 준 run_id 의 '.' · '..' 를 받지 않는다.** 검토 R9 — 꼴 검사 `[A-Za-z0-9._-]{1,128}` 가 '..' 를 받아, 다음 부르기의
`{WDA}/api/runs/../download/pptx` 가 httpx 의 URL 정규화로 `/api/download/pptx` 가 된다(WDA 안의 다른 경로). '.' · '..' 만인 이름을 뺀다 — 만들기
응답이 그 꼴이면 '실행 번호를 주지 않았다' 로 실패하고 잡을 남기지 않는다(502). 변이는 고치기 전 꼴과 같다(시험이 붉다).

**WD-D53 받는 바이트에 상한 — RA 본문은 흘려 받고, 거절 응답의 몸은 앞만.** 검토 — RA 본문을 다 받은 뒤 재서 상한(16 MB)이 메모리를 지키지
못했고, WDA 받기가 실패하면 그 몸을 끝까지 읽었다(`aread`). RA 는 `stream` 으로 받으며 길이 머리가 상한을 넘거나 받은 바이트가 넘는 순간 멈춘다(413).
거절 응답은 앞 64 KB 만 읽어 까닭 로그에 쓴다. 다시 만든 응답에 원래 머리를 옮기지 않는다 — 풀어 읽은 바이트에 content-encoding 을 붙이면 다시
풀려다 깨진다. 진행 · 만들기 · 산출물 · 능력의 작은 JSON 응답은 그대로 받는다(검토가 짚은 두 곳만).

**WD-D54 알림은 잡마다 정해진 메시지 id 로 한 번만.** 검토 R6 — advance 가 알림을 덧붙인(conv_store.append) 뒤 잡 기록(finished) 저장이 실패하면
다음 advance 가 끝을 모른 채 알림을 한 번 더 썼다. 두 단계(먼저 '쓰는 중' 을 적기)로는 막을 수 없다 — 덧붙임과 기록 사이에서 끊기면 같은 물음이
남는다. 대신 덧붙임을 멱등으로 했다 — `conv_store.append(msg_id=...)` 를 더하고(그 id 의 메시지가 있으면 넣지 않고 True), 알림은 `deck-<잡 id>` 로
넣는다. 메시지 id 는 전역 PRIMARY KEY 라 잡 id(128비트 무작위)로 겹치지 않는다. 다른 덧붙임 자리는 그대로다(msg_id 없음 = 종전).

**WD-D55 6시간 그물은 WDA 에 묻지 못해도 건다.** 검토 — 그물이 `fold` 안에만 있어 WDA 의 답이 있어야 걸렸다. 허브가 그 사람을 막거나(허브 계정 ·
JWKS) WDA 가 답하지 않으면 목록은 '묻지 못했다' 로 잡을 영영 열어 두고(WD-D41 의 그 줄), 진행 · advance 는 오류만 냈다. `gave_up` 이 기록의 시각만
보고 그물을 넘었으면 fold 와 같은 '시간 초과' 실패(next=finish)를 준다 — 목록 · 진행에서 그 꼴로 보이고 advance 는 WDA 없이 끝을 적는다(알림 한 건).
그물 전이면 종전대로(목록은 '묻지 못했다', 진행 · advance 는 오류 — 화면이 다시 묻는다). 글은 fold 와 나눠 쓴다(`_give_up_error`).

**WD-D56 만들기의 박스 잠금은 기록만 — 네트워크는 잠금 밖에서 예약으로.** 검토 R2 — 박스 전체 잠금 `lock("create")` 이 RA 위임(15초) · RA 읽기(60초
\+ 다시) · WDA 만들기(60초)를 안고 있어 한 사람의 느린 RA 가 모두의 만들기를 세웠다(재현 — 이의 만들기가 김의 RA 읽기 3초를 기다렸다). 잠금 안에서는
기록만 본다 — 중복 · 사람당 · 박스 상한을 보고 자리를 잡는다(예약 = run_id 없는 잡 기록). RA 읽기 · 꼴 문 · WDA 만들기는 잠금 밖이고, 실패하면 예약을
지운다(WDA 에 간 것이 없다 — 상한 · 중복에서 빠진다). 성공하면 같은 기록에 run_id · 제목 · 꼴을 잇는다(잡 잠금 안). 예약은 상한 · 중복에 센다 —
같은 보고서 · 옵션을 두 번 누르면 둘째는 '맡기는 중' 인 첫째를 받는다. 예약은 WDA 에 묻지 않는다(목록 · 진행 · advance 는 '맡기는 중'). 그 길의 가장
긴 시간보다 긴 300초(RESERVE_TTL_S)가 지난 예약은 포털이 도중에 죽은 것으로 보고 세지 않으며 '맡기다 끊김' 으로 보인다(끝을 적을 것은 없다).
허브 토큰은 쓰기 바로 앞에서 새로 찍는다 — 탐침 때 찍은 것을 RA 읽기 너머로 들고 가지 않는다(WD-D47 의 노출을 줄인다).

**WD-D57 만들기는 탐침을 늘 새로 하고 202 의 주인을 본다.** 검토 R5 — 주인 기능 문(owner)이 60초 붙잡혀 옛 판(주인 없는 WDA)으로 되돌린 지 60초 안의
만들기는 본문을 그 WDA 에 넘겼고, 만들기 응답의 `owner` 를 보지 않았다(비거나 다른 사람이어도 따라갔다). ① 만들기는 `probe` 로 health 를 늘 새로 묻는다
— 코디네이터가 준 둘('다시 묻기' 또는 '몇 초로 붙잡기') 가운데 다시 묻기를 골랐다. 만들기는 드물고(사람이 누른다) 몇 초짜리 창이라도 주인 없는 WDA 에
본문이 간다. 화면(status)만 60초 붙잡는다. 탐침의 거절은 정해진 글로 말한다(허브 403 · 401 · JWKS 503 — WD-D49). ② 202 의 `data.owner` 가 맡긴 사람의
이메일과 같아야(대소문자 무시) 따라간다. 없거나 다르면 — WDA 에는 실행이 생겼으므로 — 잡을 '주인 확인 실패' 로 끝내고 run_id 와 본 주인을 기록에 남기며
(진단 · 지우기 W-17) 감사에 `owner_mismatch` 를 적고 502 로 말한다. 알림은 없다(맡긴 사람이 그 답을 지금 본다). 따라가지 않으므로 상한을 먹지 않는다.

**WD-D58 만들기의 답을 잃으면 '결과를 모른다' — 다시 누르면 같은 잡 id 로.** 검토 — 만들기를 보낸 뒤 읽기 시간 초과는 WDA 가 실행을 만들었을 수 있는데
'연결하지 못했습니다' 라 말했고, 다시 누르면 새 잡 id(새 Idempotency-Key)라 WDA 에 실행이 둘 생길 수 있었다. 연결 자체가 안 된 것(ConnectError ·
ConnectTimeout · PoolTimeout — 요청이 닿지 않았다)만 '연결하지 못했다' 로 말하고 예약을 놓는다. 그 밖(읽기 시간 초과 · 끊김)은 '만들어졌는지 모른다'(504)로
말하고 예약을 `create_unknown` 으로 남긴다 — WDA 에서 돌 수 있으니 자리를 계속 센다(300초까지). 같은 사람이 같은 보고서 · 출력을 다시 누르면 그 예약을
이어(새 자리를 잡지 않는다) 같은 잡 id 를 Idempotency-Key 로 다시 보낸다 — WDA 가 W-15 를 지으면 같은 실행을 돌려준다. 목록에는 '결과 모름' 실패로 보인다.
다시 누른 만들기가 다른 까닭(RA 읽기 등)으로 실패해도 그 예약은 지우지 않는다 — 앞선 실행이 WDA 에 있을 수 있어 잡 id 를 버리면 다음에 새 키로
보내 실행이 둘이 된다(적대 검토 뒤 스스로 다시 읽고 더했다).

**WD-D59 아무도 advance 하지 않는 잡이 자리를 먹지 않는다 — 만들기 앞의 정리 · 숨긴 잡도 한 걸음씩.** 검토 R1 — 상한은 '끝을 적지 않은 잡' 을 세는데
끝을 적는 것은 화면의 advance 뿐이라, 입력창 위 줄에서 숨긴 잡 · 창을 닫은 잡 · PAT 스크립트가 맡긴 잡은 WDA 가 몇 초 만에 끝내도 6시간 그물까지 자리를
먹었다(재현 — 사람당 2 를 숨기면 셋째가 429, 두 사람이 그러면 셋째 사람이 박스 상한 429). ① 만들기는 상한을 세기 전에 `settle_open` 으로 끝나지 않은
잡(숨긴 것 포함, 예약 제외)을 모두 한 걸음씩 간다 — advance 의 몸통을 `step` 으로 떼어 함께 쓴다. 남의 잡은 그 주인의 이름으로 묻는다(기록의
owner_sub · owner_email · owner_name — 허브는 이메일로 허브 사용자를 찾고 WDA 는 주인만 연다). 포털이 그 사람 이름의 짧은 토큰을 서버에서 찍는 것은
그 사람이 맡긴 잡을 그 사람 대신 마무리하는 일이다(그 사람의 대화에 그 잡의 알림을 남긴다 — 화면의 advance 와 같은 일). 한 잡의 실패는 만들기를 막지 않는다.
② '숨기기' 는 화면에서만 숨긴다 — 목록은 숨긴 잡도 끝나지 않았으면 `dismissed` 표지와 함께 싣고, 줄은 그 잡도 한 걸음씩(끝 알림을 남긴다) 가되
보이지 않는다. 숨긴 잡만 남아도 다시 묻기를 이어 간다(차례 수 `round`). 끝나서 숨긴 잡은 목록에서 빠진다. 끝난 잡의 알림을 숨겼다고 거두지 않는 것은
— 숨기기는 '진행을 그만 보겠다' 이지 '결과를 버린다' 가 아니고, 알림이 결과(받기 링크)를 남기는 유일한 자리이기 때문이다.

**WD-D60 잠금은 다 쓰면 지운다.** 검토 — 잡 id 마다 만든 `asyncio.Lock` 이 영영 남았다(WD-D41 ② 는 아무 id 로 만드는 길만 막았다). `lock()` 을 쥔 수 +
기다리는 수를 세는 비동기 문맥 관리자로 바꿔 0 이 되면 지운다. 한 이벤트 루프라 찾기 · 세기 · 지우기 사이에 다른 작업이 끼지 않는다. 쓰임새(`async with
lock(...)`)는 그대로다. 동시 advance 시험(알림 하나)이 그대로 지난다.

**WD-D61 목록은 바뀌지 않은 잡 기록을 다시 읽지 않는다.** 검토 — 줄이 10초마다 목록을 읽고, 만들기 · 정리도 박스의 모든 잡 기록(7일치)을 매번 다시 읽어
풀었다. `records()` 가 파일의 mtime_ns · 크기로 붙잡은 기록을 가린다(`save` 는 바꿔 끼우기라 시각 · 크기가 바뀐다). 붙잡은 기록은 읽기 전용이다 —
고쳐 쓰는 자리(결과 모름 예약 잇기)는 `load()` 로 새로 읽는다. 사라진 파일은 붙잡은 것에서도 지운다.

**WD-D62 다시 만들기 — 끝난 잡에도, 지워진 파일 대신, 다른 대화의 잡이면 그 대화를 말한다.** 검토 R8 — WDA 가 파일을 지우면(보존 기한 W-13 · 정리)
받기가 '다시 누르세요' 라 말했는데, 화면은 끝난 잡에 again 을 보내지 않아 같은 죽은 잡 · 같은 링크를 돌려받았다. ① 화면의 '다시 만들기' 를 끝난 잡에도
둔다(again — 새 잡). ② 받기가 WDA 의 404 · 410 을 받으면 그 잡의 파일을 지워진 것(`finished.expired`)으로 적는다 — 그 뒤 잡은 링크를 싣지 않고(`expired`
표지) 화면은 '지워졌다 — 다시 만들 수 있다' 와 '다시 만들기' 를 보이며, 같은 보고서 · 옵션을 again 없이 눌러도 그 잡을 돌려주지 않는다(새로 만든다).
대화의 알림에 남은 링크는 고칠 수 없다 — 누르면 '다시 만들기' 를 말하는 404 다. ③ 다른 대화에서 맡긴 같은 보고서 · 옵션의 잡이 돌면 그 잡을 받는다(중복
막기) — 칸은 '이 대화에' 가 아니라 「그 대화 제목」 에 알림이 남는다고 말한다.

**WD-D63 자리표시자 대화에는 화면 알림을 붙이지 않는다.** 검토(브라우저 재현) — 서버 목록에서 온 대화는 메시지 없는 자리표시자(`messages: []`)이고 열 때
서버 사본을 읽는다(`stale = messages.length === 0 || …`). 거기에 화면 알림을 붙이면 메시지가 하나 생기고 updatedAt 이 지금이 되어 열 때 서버를 읽지
않는다 — 다른 기기에서 쓴 이력이 알림 하나로 가려지고 브라우저 사본에도 그렇게 남는다. 서버가 이미 알림을 남겼으므로 자리표시자에는 붙이지 않는다 —
그대로 두면 열 때 서버에서 읽고, 지금 보는 대화면 곧바로 읽는다(`refreshFromServer`). 불러온 대화에는 종전대로 붙인다. 앞의 거르기(`convsRef`)와
`setConversations` 안의 거르기 두 겹이다(그 사이에 대화가 불려 올 수 있다) — 한 줄 변이는 다른 겹이 막고, 둘을 함께 빼면 붉다.

**WD-D64 두 챗 제공자 사이에 알림을 알린다.** 검토 — 앱 전체 제공자(일반 챗 · 독)와 '/deliberate' 페이지 안의 제공자가 따로라, 한쪽의 줄 · 단추가 받은
알림은 그쪽 화면 사본에만 붙고 다른 쪽에서 그 대화(이미 불러온)를 열면 알림이 없었다(목록을 다시 읽어 낡음을 알 때까지). 가장 작은 길을 골랐다 —
`addDeckNotice` 가 자기 화면 사본에 붙인 뒤 창 신호(`hwax:deck-notice`, 보낸 제공자 표지)를 내고, 다른 제공자는 그 신호로 같은 규칙(잡 id 로 한 번 ·
자리표시자에는 안 붙임)대로 붙인다. 자기 신호는 무시한다(되돌이 없음). 서버 사본은 이미 있다 — 이 신호는 화면 사본만 맞춘다.

**WD-D65 숨은 탭은 천천히 묻고, 창구가 404 면 묻기를 멈춘다.** 검토 — 단추 칸(3초)과 줄(10초)이 숨은 탭에서도 같은 박자로 물었고, 박스 스위치를 끄면
(창구 404) 멈추지 않고 계속 물었다(줄은 '못 읽음' 으로 다시 차례를 건다). ① 탭이 숨으면 박자를 열 배로 늦춘다(칸 30초 · 줄 100초) — 아주 멈추면 숨긴 채
둔 탭의 잡이 끝 알림을 남기지 못한다. 보이게 되면 그 효과가 다시 돌아 곧 박자로 돌아온다(`useTabVisible`). ② 창구가 404 를 주면(스위치가 꺼졌거나 그 잡이
없다) 붙잡은 상태 답을 버리고(`forgetDeckStatus` — 다음 화면이 다시 묻는다) 그 칸 · 줄은 다시 열 때까지 묻지 않는다. 칸은 까닭을 말한다. 오류에 상태를
싣는 `DeckHttpError` 를 더했다(종전엔 글만 있었다). 줄이 404 를 받은 뒤 다른 칸의 맡김 신호에도, 칸이 404 를 받은 뒤 탭을 숨겼다 보여도 다시 묻지 않는다.

**WD-D66 질문이 도는 대화에는 알림을 미룬다 — 중계가 도는 턴을 센다.** 검토 — 화면의 `afterStream` 은 그 탭의 스트림만 기다려, 다른 탭 · 기기에서 질문이
도는 대화에 알림이 오면 서버 사본에서 질문과 답 사이에 끼었다(다음 턴의 LLM 이력도 그 순서다). 중계(`/agent/chat`)가 사용자 발화를 남긴 순간부터 답을
남길 때까지 그 대화를 '도는 턴' 으로 센다(`routes._ACTIVE_TURNS` — 이 포털 프로세스, 잡 잠금과 같은 한 프로세스 가정). 빼는 자리는 셋 — 답을 남긴 뒤
(pump 의 저장 묶음 끝, 저장이 터져도), 생성기가 돌지 못하고 응답이 닫힐 때(머리를 보내다 끊김 — 퍼밋과 같은 on_close), 생성기를 만들기 전 예외(except).
`step` 은 끝을 적기 직전에 그 대화의 턴이 돌면 미룬다(`deferred` — 끝을 적지 않고 next 는 finish 그대로) — 칸 · 줄이 다음 차례에 다시 부른다. 끝 정리가
새더라도 알림을 영영 막지 않게 6시간이 지난 턴은 세지 않는다. 남은 틈 — 생성기를 만들기 전 예외 갈래는 시험으로 재현하지 않았다(그 줄의 변이는 붉지
않다). MCP 로 서버에서 도는 심의(대화를 따로 만든다)는 이 중계를 지나지 않아 세지 않는다 — 그 대화에는 '발표자료로' 단추가 서는 답이
그 심의가 끝난 뒤에만 생긴다.

**WD-D67 심의 결과 카드의 RA 링크는 그 보고서의 공간으로 — 포털이 읽어 옮긴다.** 검토 — `DelibView.tsx` 가 `/report-archive/w/dev/reports/<번호>` 를
박았다(관찰 ② 의 그것, 되살린 카드로 더 자주 보인다). RA 화면에는 공간 없는 보고서 주소가 없다(ReportArchive `frontend/src/App.jsx` 의 라우트 —
`/w/:workspace/reports/:reportId` 뿐, 코드 읽기만). 사람의 RA 연결에 묶인 공간만으로는 모자라다 — 위임(SSO) 길로 만든 보고서는 RA 가 그 사람 기준으로
공간을 정하고, 묶음은 나중에 바뀔 수 있다. 그래서 포털 길 `GET /agent/ra/reports/{번호}/open` 을 두었다 — 그 사람 명의로 RA 보고서를 읽어(RA
`GET /api/reports/{id}` 는 읽기 권한만 보고 머리의 공간을 보지 않는다) `workspace_slug` 로 302 한다. 못 읽으면 그 사람의 연결 공간, 그것도 없으면 RA 첫
화면(RA 가 기본 공간으로 보낸다) — 새 탭의 링크라 오류 JSON 대신 늘 옮긴다. 공간 이름은 `[A-Za-z0-9._-]{1,120}` 만 쓴다(주소를 바꿀 꼴은 버린다).
권한은 `plat:reportarchive`. 본문을 쓸 일은 없으나 공간 칸이 ReportRead 안에 있어 다 받는다(16 MB 상한).

**WD-D68 되살린 심의의 이어붙이기가 실패하면 결정문에서 보인다.** 검토 — 되살린 카드에 보고서 번호를 남긴 뒤(WD-D35) 이어하기가 그 번호로
`append_to_report_id` 를 싣는다. 그 보고서가 지워졌거나 볼 권한이 없으면? 도구의 거절(게이트웨이 · RA 오류)은 이미 결정문 끝에 '저장 실패 — 까닭' 으로
붙는다(에이전트 서버 `_ra_save_outcome` — 이어붙였다고 말하지 않고 번호도 비운다). 남은 틈은 도구 밖의 예외(블록 조립 · 일지 쓰기 등)였다 — 로그뿐이라

**WD-D75 질문이 도는 대화에서도 끝은 곧바로 적고 대화 알림만 미룬다 — WD-D66 을 고친다.** 2차 검토 D — WD-D66 은 끝을 적는 일 전체를 미뤘다. 심의 ·

**WD-D77 받기는 WDA 가 낸 답만 믿는다 — 지워짐은 WDA 봉투로, 흘리는 것은 꼴과 앞 바이트로.** 2차 검토 E · R6 — ① 받기의 404 · 410 이면 무엇이든
'지워졌다' 로 적었다(WD-D62). 허브 쪽 404 도 그렇게 적혀 링크가 사라지고, 다시 누르면 새로 만들었다. 이제 WDA 오류 봉투(W-10 — `success: false` ·
`message`)나 WDA 오류 어휘 `code: NOT_FOUND` 가 실린 404 · 410 만 지워짐으로 적는다. 그 밖의 404 · 410 은 502 '허브에서 닿지 못했다 — 파일은 남아 있을 수
있다' 로 말하고 기록은 그대로 둔다. W-10 이전의 WDA(detail 하나)는 지워짐을 알아채지 못하고 받기만 실패한다 — WDA main 은 W-10 을 갖췄다(코드 읽기).
허브 게이트(authz)는 401 · 403 과 `detail` 만 내므로 봉투와 겹치지 않는다(HEAXHub `authz.py` 읽기). ② 허브 Caddy 는 앱 경로가 없으면 SPA 첫 화면을 200
으로 준다(HEAXHub `caddy_bootstrap.json` 의 `try_files`). 포털은 그것을 `deck.pptx` 로 흘렸다. 이제 흘리기 전에 머리의 꼴과 앞 8바이트를 본다. 꼴은 WDA 가
꼴마다 다는 media type(`_DOWNLOAD_META`)이고 `application/octet-stream` 도 받는다. 앞 바이트는 pptx · docx 가 zip 의 `PK\x03\x04`, pdf 가 `%PDF`, mp4 가
4번째 바이트부터 `ftyp` 이다. html 은 바이트로는 허브의 index.html 과 가를 수 없어 WDA 가 늘 다는 `content-disposition: attachment`(FileResponse 의
filename)를 함께 본다 — 허브의 정적 파일에는 없다. 맞지 않으면 502 로 말하고 흘리지 않으며 지워짐으로도 적지 않는다(허브가 돌아오면 받는다). 본 바이트는
흘리는 몸의 앞에 그대로 붙인다. 가짜 WDA 의 받기 머리를 진짜 꼴(꼴마다 media type)로 고쳤다.

**WD-D78 심의 결과 카드는 RA 가 준 주소로 바로 연다 — 포털 길은 주소 없는 옛 카드만, 화면이 물어서.** 2차 검토 ① — WD-D67 의 포털 길(`/open` 302)은

않고 RA 가 자기 로그인을 한다. 주소가 없는 옛 카드는 `href` 를 RA 첫 화면으로 둔다(가운데 단추 · 주소 복사는 그리로 간다). 누르면 `openRaReport` 가
누른 순간 빈 탭을 열어(물은 뒤에 열면 팝업 막기에 걸린다) 오프너를 끊고, `apiFetch` 로 `/open` 에 묻는다 — 세션이 지났으면 되살려 다시 묻는다. 그 답으로

작다. '/보고서' 답(ra_report)에는 RA 링크가 없어 주소를 싣지 않았다.

**WD-D79 상류가 끝난 직후 브라우저가 떠나도 답을 남긴다 — 있던 결함, 사용자 결정(11-01)으로 고친다.** 2차 검토 — pump 가 상류를 다 읽고 finally 에서
상류를 닫고 저장하는 사이에 브라우저가 떠나면(done 프레임을 받은 직후), 생성기 쪽 취소가 pump 로 번졌다. 길은 둘이다. 생성기가 끝 표지 뒤의 `await task`
에 서 있으면 그 await 를 끊는 취소가 기다리던 작업(pump)으로 그대로 간다(asyncio 는 기다리던 Task 도 취소한다). 생성기가 yield 에 서 있으면(2.4 —
보내다 끊김) 응답이 생성기를 닫고 finally 가 `task.cancel()` 을 부른다. 어느 쪽이든 취소가 pump 의 finally 안의 await(상류 닫기 ·
`anyio.to_thread.run_sync(_save)`)에 떨어진다. anyio 의 CancelScope(shield) 는 asyncio 의 취소를 막지 못해(앞서 실측) 저장이 돌지 않았고, 서버
사본에는 사용자 발화만 남았다(검토 재현 — roles `['user']`). 두 길을 견줬다. ① 'finishing' 표지 — pump 의 finally 첫 줄에서 세우고, 그 뒤로는 생성기가
취소하지 않고 기다린다. 끝 표지 뒤의 생성기 await 는 가린다. ② 저장만 따로 가린다(저장을 shield 한 작업으로 띄운다) — 저장 앞의 상류 닫기 · 퍼밋 반납 ·
턴 빼기도 같은 취소에 끊기므로 가릴 자리가 여럿이 된다. 취소가 이미 든 작업에서 새 작업을 띄우는 꼴이라 끝맺음의 차례도 흐려진다. ①을 골랐다 — 표지 하나와
두 줄이다. 도중에 떠나면(표지 전) 종전처럼 취소해 상류를 끊는다 — ■ 멈춤 · 탭 닫기 · 루틴 떼어 내기 · 이어하기는 바뀌지 않는다. 끝 표지 뒤의 생성기
await 는 루틴 턴만 가리던 것을 모든 턴에 가린다 — 그때는 상류가 이미 끝나 끊을 것이 없고, pump 의 예외는 가려도 그대로 다시 난다(응답을 끊는다).

**WD-D80 같은 오리진의 세션 쿠키가 WDA 까지 가는 것 — 기록만 한다(사용자 결정 11-01).** 2차 검토 — 허브 앱은 포털과 같은 오리진(`/apps/…`)이라 사람이
WDA 화면을 열면 허브 세션 쿠키(`heax_access_token`)와 포털 세션 쿠키가 허브 Caddy 를 지나 WDA 까지 간다. 모든 허브 앱에 해당하고 새로 생긴 길이 아니다
(포털의 서버 쪽 부르기는 쿠키를 싣지 않는다). 허브가 앱으로 넘길 때 `Cookie` 를 지우는 선택(앱마다 켜기)이 닫는 길이지만, 쿠키로 로그인을 잇는 앱
화면을 깰 수 있어 따로 설계가 필요하다. PLAN §8 의 알려진 위험에 적고 고치지 않는다.

## 3차 적대 검토 뒤(2026-11-01 밤 — main 에 들어간 판에 대한 검토, 낮음 넷)

**WD-D81 끝맺는 pump 를 기다리는 데 상한을 둔다 — 120초, 넘기면 저장은 뒤에서 끝까지.** 3차 검토 — WD-D79 뒤로 생성기는 끝맺는 pump(상류 닫기 ·
저장)를 끊지 않고 기다린다. 저장이 막히면(잠금을 놓지 않는 쓰기 뒤에 선 저장) 그 기다림에 끝이 없어 ASGI 호출이 저장이 풀릴 때까지 붙잡혔다. 브라우저가
떠났든(finally) 연결을 둔 채 끝을 기다리든(끝 표지 뒤) 같다. 두 자리의 기다림을 `_wait_pump` 하나로 모아 상한(`_RELAY_FINISH_WAIT_S` 120초)까지만
기다린다. 120초는 저장소 잠금 대기(`CONV_STORE_BUSY_TIMEOUT_S`, 기본 30초)의 네 배다. 저장은 첫 실패에서 멈추므로 정상이면 닿지 않는다. 넘기면
`logger.error` 로 크게 남기고 응답을 닫는다. 저장은 끊지 않는다 — pump 를 `_LATE_PUMPS` 에 쥐어 두고(루프는 작업을 약하게만 쥔다) 끝나면 늦게 끝난
초와 결과를 다시 남긴다. 기다림은 `asyncio.wait` 로 한다 — 기다리는 쪽이 끊겨도 pump 를 취소하지 않는다(`gather` 는 취소한다 — 종전 finally 의
`gather` 는 그래서 위험했다). `anyio.fail_after` 대신 이것을 고른 까닭이다 — 마감을 넘긴 취소가 기다리던 작업으로 번질 길이 아예 없다. 끝 표지 뒤에서
상한을 넘겼으면 finally 는 다시 기다리지 않는다. 남긴 것 — 연결을 둔 채 끝 표지 뒤에서 기다리다 브라우저가 떠나면 finally 가 새 상한으로 한 번 더
기다린다(최악 240초 — 끝은 있다).

**WD-D82 남의 대화는 주인부터 본 뒤 — 도는 턴으로 세지 않는다.** 3차 검토 — WD-D76 은 턴을 먼저 세고 발화를 남기며(`append` 가 주인을 본다) 남의 대화면
곧바로 뺐다. 발화 저장은 저장소 잠금을 기다릴 수 있어(다른 쓰기가 쥐고 있다) 그 동안 남의 대화가 '도는 턴' 으로 보였고, 그 주인의 발표자료 알림이
밀렸다(검토 재현 — 잠금을 0.5초 쥔 동안 `turn_active` 가 참). 이제 스레드에서 `owner_state` 로 주인부터 보고, 내 대화일 때만 턴을 센 뒤 발화를 남긴다.
앞쪽 틈(발화를 남긴 뒤에 세면 그 사이 알림이 낀다 — WD-D76)은 닫힌 채다. 주인을 본 뒤 남기기 전에 그 대화가 지워지면(남기기가 False) 곧바로 뺀다.
남은 틈 — 알림이 '턴 없음' 을 본 뒤 저장 스레드로 가는 사이에 질문이 시작되면 둘이 저장소 잠금에서 줄을 선다(검토의 거울 재현 — 고치라는 항목이
아니라 남겨 둔다. 닫으려면 알림 저장과 턴 세기를 한 잠금 아래 두어야 한다).

**WD-D83 루틴 턴의 상한 로그는 끊을 때만.** 3차 검토 — 떼어 낸 중계가 상한에 닿은 루틴 턴은 브라우저가 떠나면 '…상류를 끊는다' 를 남겼다. 그런데
pump 가 이미 끝맺는 중이면(WD-D79) 끊지 않고 기다린다 — 로그가 한 일과 달랐다. 로그를 취소하는 갈래 안으로 옮겨 실제로 끊을 때만 남긴다. 루틴이
아닌 턴에는 이 로그가 없다는 것도 시험이 본다(변이로 드러난 빈 곳).

**WD-D84 팝업이 막히면 옛 카드는 링크대로 RA 첫 화면으로.** 3차 검토 — 옛 카드(주소 없음)를 누르면 기본 이동을 늘 막고 빈 탭을 열었다. 팝업이
