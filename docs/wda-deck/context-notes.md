# 발표자료로(RA 보고서 → WebDesignAgents) — 결정과 까닭

> 계획 [PLAN.md](PLAN.md) · 체크리스트 [checklist.md](checklist.md) · WDA 요청서 [wda-request.md](wda-request.md).
> 사실의 파일 · 줄 근거는 PLAN §2 에 있다. 여기는 **왜 그렇게 정했나**를 적는다. 사람이 정할 것은 PLAN §13 — 뒤집히면 여기 덧붙인다.

**WD-D1 사용자 결정 1(2026-11-01) — 포털이 맡고 알린다.** 포털이 만든 RA 보고서 옆 '발표자료로' 단추. 포털이 그 보고서를 그 사람 명의로 읽어
본문을 WDA 에 넘기고(R2 (나)), 잡 기록(누가 맡겼나)을 남기고, 화면이 진행을 보이고, 끝나면 그 대화에 받기 링크 알림을 남긴다. DocForge 배달과 같은
꼴이다. 챗 LLM 은 잡을 폴링하지 않는다(HA-28).

**WD-D2 사용자 결정 2(2026-11-01) — 기본 출력은 PPT + PDF, `pptx_mode` hybrid.** 영상 · HTML · Word 는 단추에서 고를 수 있는 것이다. 내레이션은 끈다
(영상을 골라도 M1 은 끈 채 — 켜면 VoiceRecorder 를 부르고 길이가 크게 는다).

**WD-D3 부르는 길 — 허브 Caddy 를 거쳐 WDA 웹 REST 를, 그 사람 이름으로 찍은 짧은 포털 PAT(청중 `heax-hub`)로.** 견준 길 넷.
① 게이트웨이 MCP(DocForge 꼴) — 본문을 받는 도구가 없고(`report_ingest` 는 서버 경로), 게이트웨이는 WDA 에 신원을 싣지 않아(IDENTITY_FWD · per_user_sso 밖)
WDA 쪽 주인을 정할 수 없다. 바이트(PPT · PDF)를 MCP 로 나르면 base64 로 33% 불고 게이트웨이의 결과 가림(`_pii_mask`)과 상한을 지난다.
② 게이트웨이 REST 다리(`/api/<site>/`, SimFlow 꼴) — 사람 명의(per_user)는 WDA 에 위임 창구(`/auth/sso`)와 그 토큰 검증이 있어야 하고, 다리는
per_user 사이트에 허브 게이트용 Authorization 을 싣지 않아 Caddy 를 지나지 못한다(게이트웨이 손질까지 든다). 서비스 자격(inject)이면 사람 명의가 아니다.
③ WDA 루프백 포트 직결 — 포트가 허브 풀에서 바뀌고 허브의 앱 권한 검사(`can_view_app`)를 건너뛴다.
④ **허브 Caddy + 포털 PAT** — 허브 게이트가 이미 포털 PAT 를 받는다(followups-1017 결정 ⑦ — 허브 앱의 사람별 권한은 `can_view_app` 만, FU-D17).
게이트가 서명 · 청중 · 폐기 목록을 보고 허브 사용자로 잇고 앱 권한을 본 뒤, Caddy 가 클라이언트가 보낸 `X-Heax-User-Email` 을 지우고 확인한 값으로
다시 싣는다. WDA 는 머리 하나만 읽으면 되고, 본문은 이미 있는 `POST /api/runs {report_json}` 로 가고, 바이트는 HTTP 로 흐른다. 고른 까닭이 이것이다.
치르는 값 — 그 사람에게 허브 계정이 있어야 한다(허브 타일이 보이면 화면이 미리 로그인해 생긴다 — SsoPrimer). 이 청중의 첫 포털 쪽 쓰임이라
`config.py:243-245` 의 '소비처가 없다' 주석을 함께 고친다.

**WD-D4 WDA 의 신원 정본은 허브 Caddy 가 실은 `X-Heax-User-Email` 하나(REST 에서만).** WDA 세션은 'MCP 는 게이트웨이가 넣는 검증된 `x-hwax-user`
를 읽는다' 고 했다 — 코드는 그렇지만(`session.py:159-191`) 두 가지가 틀어진다. ① 게이트웨이는 WDA 에 그 머리를 싣지 않는다 — 신원을 싣는 길은
IDENTITY_FWD(기본 `hwax-deliberation` 하나 · 떠 있는 dev 게이트웨이 환경에도 따로 없다)와 per_user_sso(WDA 없음)뿐이고 나머지는 상주 세션이다.
② Caddy 는 `x-hwax-user` 를 지우지 않는다 — 자기 PAT 로 `/apps/web_design_agents/mcp` 에 직접 붙은 누구나 남의 이메일을 적어 보낼 수 있다(게이트웨이도
같은 까닭으로 소속에 서명을 붙였다, `gateway.py:259-262`). 그래서 `x-hwax-user` 는 주인 판정에 쓰지 않는다. `/mcp` 의 `X-Heax-User-Email` 은 허브
관리자(게이트웨이 서비스 토큰의 주인)로 접히므로(`gateway.py:273-278`, HWAXRisk 가 같은 까닭으로 위임 머리를 따로 둔다) MCP 는 주인을 정하지도, 주인 있는
run 을 열지도 않는다. MCP 쪽 주인은 2단계(WD-D19).

**WD-D5 WDA 의 주인 기능은 단추를 켜기 위한 전제다 — 사용자 결정 U-1 대기(권장 예).** 근거는 셋이다. WDA 원장에 주인 칸이 없다. `GET /api/runs` 가
전부를 준다. 허브 매니페스트가 company + stable 에 portal_auth 가 없어 게이트가 익명을 통과시킨다 — dev 실측(11-01)에서 포털 nginx 를 거친
`/apps/web_design_agents/api/runs` 가 로그인 없이 200 이었다. 사람의 RA 권한 안에 있던 보고서 본문을 그런 곳에 넘기면 RA 의 권한이 WDA 의 '누구나' 로
바뀐다. '이미 사내 공개인 보고서만 예외' 도 두지 않는다 — 포털은 RA 보고서의 독자가 WDA 의 독자(익명 포함)를 덮는지 알 수 없다.

**WD-D6 주인 규칙은 깨지 않는 꼴로.** 신원이 있는 REST 만들기는 주인을 갖고 주인만 본다(다른 사람 · 신원 없음은 없는 것과 같은 404). 신원 없이 만든
run(옛 것 · CLI · 신원 없는 MCP · 직결)은 지금 그대로다 — **주인 없는 run 은 비공개가 아니다**(WDA 세션이 이 문장을 요청서와 보안 절에 넣어 달라 했다).
포털은 늘 신원을 싣는다(허브 Caddy 경유). WDA 콘솔에서 새로 만든 run 도 신원이 있으니 그 사람 것만 된다 — 콘솔의 '모두의 목록' 이 '내 것 + 주인 없는 옛 것'
으로 바뀐다. 이 바뀜을 싫어하면 WDA 가 만들 때 고르는 칸(`private`)으로 좁힐 수 있지만, 콘솔에 붙여 넣는 보고서도 같은 값이라 권하지 않는다.

**WD-D7 포털이 모든 것을 중계한다 — 브라우저는 WDA 를 보지 않는다.** run_id · job_id · WDA 주소 · 서버 경로는 포털 응답 · 알림 · 링크 어디에도 없다.
내려받기는 포털 라우트가 잡 기록의 주인을 보고, **요청한 사람의** 이름으로 WDA 에서 받아 흘린다(WDA 가 주인을 다시 본다 — 두 겹). 서명 URL 은 쓰지
않는다 — 서버 쪽 가져오기가 이미 그 사람으로 인증되고, 들고 다니는 URL 은 로그 · 기록에 남는 열쇠라 지켜야 할 것이 하나 는다. 포털은 파일을 쌓지
않는다(받을 때마다 흘린다).

**WD-D8 상태 낱말은 하나 — `queued · preparing · rendering · done · failed`(+ step · 단계 기준 progress).** WDA 는 낱말이 둘이다 — 파이프라인
(run `queued/running/done/failed` · 단계 ingest · fragmentize · scenario · build 마다 `pending/running/done/failed`)과 렌더(웹 `queued/rendering/done/failed`,
MCP 잡은 `building` 이 더 있다). 화면에 둘을 그대로 보이면 '끝났는데 또 시작' 처럼 읽힌다. 다섯 낱말로 접고 단계 이름을 step 으로 보인다(표는 PLAN
§7.2). progress 는 시간이 아니라 단계로 센 값이라 그렇게 적는다.

**WD-D9 화면이 몬다 — 포털 뒤에서 기다리는 일감을 만들지 않는다(DF-D17 ③ 그대로).** 포털은 uvicorn 하나라 재기동하면 뒤의 일감이 사라지고, 사라진 것을
아무도 모른다. 화면이 3초마다 진행을 묻고, 끝을 보면 `advance` 를 부른다. 창을 닫은 잡은 입력창 위 '끝나지 않은 발표자료' 줄(DF-D23 꼴)이 다시 연다.
GET 은 부작용이 없다 — 렌더 맡기기 · 알림 남기기는 CSRF 를 거는 POST(`advance`)에서만 한다.

**WD-D10 끝난 잡의 알림은 저절로 남긴다.** DocForge 는 '저절로 넣지 않는다(사람이 고른다)'(DF-D23)였다 — 그쪽 배달은 RA 에 보고서를 만드는 쓰기라
남에게 보인다. 발표자료의 끝은 그 사람의 대화에 알림 한 건을 쓰는 일뿐이라 다시 묻지 않는다. 실패도 알림을 남긴다 — 다음 턴이 '왜 없나' 를 안다.

**WD-D11 알림은 서버가 단추를 누른 그 대화에 직접 남긴다.** DocForge · 보내기 알림은 화면이 **지금 대화**에 붙였다(`addUploadNotice` — 업로드 패널은
그 대화 안에서 열리고 그 자리에서 끝난다). 발표자료는 몇 분 걸리고 그 사이 사람이 다른 대화로 옮겨 간다 — 지금 대화에 붙이면 엉뚱한 대화에 남는다.
그래서 잡 기록에 대화 id 를 남기고(만들 때 그 대화가 그 사람 것인지 본다), `advance` 가 `conv_store.append`(주인 검사가 있다)로 그 대화에 쓴다.
화면은 응답의 알림을 그 대화의 **화면 사본에만** 붙인다(서버에 다시 쓰지 않는다). 그 대화가 답을 받는 중이면 끝날 때까지 기다렸다 `advance` 를 부른다 —
포털은 답을 스트림 끝에 쓰므로 먼저 쓰면 다른 기기에서 알림이 답보다 앞선다(PP-D3 ⑤). 알림의 꼴은 PP-D3 그대로다(어시스턴트 글 + 활동 하나
`origin: 'upload'` · meta `upload: true`) — 다음 턴 이력의 `kind: upload` 근거가 되고 포털 모델에 새 칸이 들지 않는다.

**WD-D12 단추 자리는 셋 — 심의 결과 카드 · `/보고서` 저장 답 · RA 보내기 알림(U-5 권장).** 셋 다 서버 사본에서 보고서 번호를 되살릴 수 있어야
새로고침 뒤에도 산다. ① 심의 — 중계가 outcome 을 버린다(`routes.py:2854-2895`). 답 meta `delib_outcome {report_id, title}` 로 남기고 화면이 되살린다
(이 고침은 '되살린 심의는 보고서 단계가 사라진다'(`DelibView.tsx:43,48`)도 바로잡는다). ② `/보고서` — 에이전트 서버가 글로만 낸다. 글을 파싱하지 않고
`result` 사건에 `ra_report {id, title}` 칸을 더하게 한다(에이전트 서버 한 칸 · 중계가 답 meta 로 남긴다) — 글은 바뀌고 파싱은 조용히 깨진다. ③ RA 보내기
알림은 활동 근거에 이미 `report_id` 가 있다. 분석 루틴 RA 초안은 M2.

**WD-D13 R1(`destApps` 한 줄)은 넣지 않는다 — 단추는 `DocActions` 가 아니다.** `DocActions` 는 붙인 문서를 '어디로 보낼지' 고르면 **LLM 에게 줄 지시문**을
입력창에 채우는 선택지다(`DocActions.tsx:27-38`) — 발표자료를 거기 두면 LLM 이 WDA 도구를 몰게 된다(서버 경로 `report_ingest` · `render_status` 되풀이 =
HA-28). `destApps.ts` 는 그 선택지와 업로드 목적지의 '지금 전문가' 순서표라(`destApps.ts:1-26`) 소비처 없는 `deck` 줄은 아무 일도 하지 않는다. 나중에 '붙인
문서 → 발표자료' 목적지를 만들면 그때 `deck: ['heax-web_design_agents']` 를 더한다.

**WD-D14 HTML 은 끼워 보지 않는다(M1) — 내려받기만.** 허브 앱은 포털과 같은 오리진(`/apps/`)이라 WDA 가 만든 HTML 을 포털 쪽에서 그대로 열면 그
스크립트가 포털 쿠키 · CSRF 값에 닿을 수 있다. 내려받기 응답은 `attachment` · `nosniff` · `no-store` 에 HTML 은 `Content-Security-Policy: sandbox` 를
더한다. 나중에 끼운다면 `sandbox="allow-scripts"`(allow-same-origin 없이) iframe 으로만 — 출처가 불투명해 포털에 닿지 못한다. WDA 의 장면 HTML
(`/api/runs/{id}/scenes/{name}/html`)도 같다.

**WD-D15 RA 그림은 M1 에서 싣지 않는다 — WDA 의 서비스 자격으로도 받지 않는다.** WDA 는 file_id 그림을 `WDA_RA_*` 서비스 자격이 있을 때 RA 에서 받는다
(`assets.py:92-121`) — 사람 명의 원칙과 어긋난다(서비스 계정이 사람 대신 RA 를 읽는 길은 2026-09-29 사고의 꼴이다). M1 은 그림 수를 세어 알림에 말하고, M2 에
포털이 그 사람 명의로 RA 파일을 받아 만들기 요청에 함께 넘긴다(WDA 가 파일을 받는 꼴이 먼저 — 요청 W-16). 심의 · `/보고서` 보고서는 글 블록이라 대개
그림이 없다.

**WD-D16 한도(시간 문턱 · 박스 상한은 WD-D30 이 고쳤다).** 본문 16MB — 심의 보고서는 회의록 400 · 결과 · 권고 각 200 항목 × 1,900자가 상한이라(HWAXAgentServer `deliberation.py:154-158`) 한글
3바이트로 어림하면 수 MB 다. 넘으면 WDA 를 부르지 않는다. 사람당 동시 2 · 같은 보고서 · 같은 옵션은 하나로 묶는다(두 번 눌러도 WDA run 하나).
시간은 '늦음' 표시만(준비 30분 · 렌더 60분 · 영상 180분) — WDA 의 실측이 오면 고친다. 24시간이 지나도 running 이면 포털이 실패로 닫는다(그물).

**WD-D17 'PDF' 의 뜻 — WDA 의 pdf 는 슬라이드 PDF 가 아니라 '읽는 문서' 다(U-4 대기 · 권장 정식 보고서).** WDA 는 같은 심의에서 나온 글(본문 = 내레이션,
삽화 = 장면 스틸)을 report · brief · memo 꼴로 조판해 HTML · PDF · Word 로 낸다. 사용자가 'PPT + PDF' 를 '슬라이드 + 그 PDF 판' 으로 생각했을 수 있어
묻는다. 기본은 report, 단추에서 요약 · 메모를 고르게 한다. 슬라이드 PDF 가 필요하면 WDA 에 새 출력을 청한다(W-19).

**WD-D18 배포 전제 — WDA push · 허브 SIF 재빌드(U-2 대기).** 허브는 GitHub 에서 SIF 를 짓는데 WDA main 이 68 커밋 앞서 있고 push 가 workflow 범위로
거절됐다. 지금 배치(08-19 판)는 렌더 출력이 video · pptx 뿐이라 사용자 결정 2 가 돌지 않는다. 역사를 다시 쓰는 길(CI 파일 커밋 빼기)은 권하지 않는다 —
68 커밋의 해시가 바뀌어 WDA 문서가 인용한 커밋이 사라진다. `git push --dry-run` 은 서버 쪽 검사에 닿지 않으니 통과해도 풀린 것으로 보지 않는다.

**WD-D19 MCP 쪽 주인(개인 Claude 로 내 발표자료 보기)은 2단계 — per_user_sso(HWAXRisk 꼴).** 게이트웨이가 WDA 의 `/auth/sso`(공유 비밀 + `X-Hwax-Delegate-Email`)
로 그 사람의 단기 단언을 받아 `token_header` 로 싣는 길이다. 단추에는 필요 없고 WDA · 게이트웨이 둘을 고쳐야 해 미룬다. 들어오면 로컬 포트 우회(WD-D21 ①)도
같이 닫힌다.

**WD-D20 운영자 페르소나 `he-doc-webdesign` 의 글을 고친다.** 지금 글은 챗 LLM 에게 `report_ingest`(서버 파일 경로) → … → `render_status` 로 산출물을 받으라고

## WDA 세션의 답 뒤(2026-11-01)

**WD-D29 템플릿 문 — `deliberation` 보고서는 WDA 의 `format:deliberation`(W-21)이 있어야 단추가 선다.** WDA 가 실제 꼴의 심의 보고서를 넣어 본 결과(Q2)
조각은 바르게 뽑히나 장면이 제품 소개 뼈대로 눌려 결정문 · 액션아이템이 사라졌다 — 넘기면 틀린 발표자료가 나간다. 그래서 RA 보고서의 템플릿(최상위와
페이지마다) 가운데 하나라도 `deliberation` 이면 `owner` 에 더해 `format:deliberation` 을 요구한다. 그 밖의 템플릿(RA 보내기 알림의 `__import_blank__`)은
`owner` 만. 화면은 자리마다 템플릿을 알고(심의 결과 카드 · `/보고서` 는 deliberation) `status.formats.deliberation` 으로 숨기며, 만들기는 RA 에서 읽은
실제 템플릿으로 다시 본다 — 화면이 아는 자리와 실제가 다르면(클라이언트가 번호를 바꿔 보내면) 실제가 이긴다. 사용자 결정(U-6, WD-D32) — 심의 형식이 설 때까지 숨긴다.

**WD-D30 시간 문턱과 박스 상한.** WDA 실측 5.5초(파이프라인 0.5 + 렌더 5.0, pptx 1.2 MB · pdf 1.9 MB)라 '늦음' 문턱을 준비 5분 · 렌더 15분 · 영상 60분으로
낮추고, 끝내 6시간이 지나면 실패로 닫는다 — WDA 는 재기동에 끊긴 실행을 running 으로 남겨(W-12 전) 24시간 그물로는 사람이 하루를 기다린다. WDA 에 동시
상한 · 보존이 없어(Q4) 포털이 사람당 2 에 더해 박스 전체 4 로 묶는다(`wda_deck_inflight_box_max`). WDA 콘솔 · MCP 로 들어오는 일은 포털이 막지 못하니
W-13 · W-14 를 '강하게 권함' 으로 올렸다.

**WD-D31 시험의 가짜 WDA 는 요청서의 계약 그대로 — 그리고 WDA 가 알려 준 블록 글자 규칙.** WDA 에는 W-1 ~ W-12 가 아직 없다(Q1). 포털 시험은 봉투
`{success, data, message, code}` · 상태 낱말 · 남과 신원 없음에 404 · 허브 게이트(포털 PAT 의 서명 · 청중을 보고 `X-Heax-User-Email` 을 싣는다)를 흉내 낸다.
만들기 본문은 WDA 의 규칙으로 센다 — `rich_text` 는 `content.markdown`, `heading` 은 `content.text`, `props.default_text` 는 대신 쓰지 않고, `content` 에
없는 블록은 글자 0, 모두 0 이면 거절. 포털은 RA ReportRead 를 바꾸지 않고 넘긴다(시험이 받은 본문과 RA 의 `data` 가 같은지 본다). 실물 `deliberation`
보고서는 블록 정의가 보고서에 없어(템플릿 블록은 `content` 키만) 지금 WDA ingest 로는 블록 0개가 될 것이다 — 요청서 4.6-2 에 적어 WDA 의 심의 꼴 일에 넘겼다.

**WD-D32 사용자 결정(11-01, U-6) — '심의 형식이 설 때까지 숨긴다'.** WD-D29 의 문을 확정했다. `deliberation` 템플릿 보고서는 WDA `/api/health` 의
features 에 `format:deliberation`(W-21)이 있을 때만 단추가 서고 만들기를 받는다. 그 밖의 템플릿은 `owner` 와 박스 스위치만 본다. 까닭은 WDA 자신의 Q2
실측이다 — 결정문이 한 장면에 묻히고 액션아이템 · 라운드 요지가 사라지며 '보고서 참조' 같은 채움 글이 영상에 나갔다. 코디네이터의 전언은 '`/보고서` ·
RA 보내기 알림은 owner 만' 이었지만, 문은 템플릿으로 가르고 `/보고서` 저장 답의 보고서도 `deliberation` 템플릿이다(에이전트 서버
`deliberation.py:7892` — 심의 결과는 `:7631`). 그래서 `/보고서` 도 같은 문에 걸리고, W-21 전에는 **RA 보내기 알림 자리에서만** 단추가 선다. 템플릿을 보는
곳은 둘이다 — 화면은 자리로(심의 결과 카드 · `/보고서` 는 deliberation) 숨기고, 서버는 RA 에서 읽은 실제 템플릿으로 다시 막는다(409).

**WD-D35 되살리기 — 집계는 넷이 다 있을 때만 · 브라우저 사본도 잇는다.** 서버 사본의 `delib_outcome` 을 `delib.outcome` 으로 되살릴 때 집계는

## WDA 의 심의 꼴(2026-11-01 저녁)

**WD-D39 심의 꼴의 표지는 `format:delib-16x9` · 상태는 `formats` · 정책은 함수 하나(지금 active 만).** WDA 가 심의 꼴을 지었다(로컬 판 · 허브 SIF 전).
features 를 꼴 등록부에서 만들어 내므로 이름은 우리가 청한 `format:deliberation` 이 아니라 `format:delib-16x9` 다 — WDA 의 이름을 받았다(WD-D29 · D32 의
문은 그대로, 표지 이름만 바뀐다). `formats` 가 꼴마다 상태(draft · active …)를 주므로 '꼴이 있다' 와 '써도 된다' 를 가를 수 있다. 정책은 `format_ready`
하나다 — features 에 `format:delib-16x9` 가 있고 `formats["delib-16x9"] == "active"`. status 의 `formats.deliberation` 과 만들기의 문(409)이 이 함수를
같이 쓴다. draft 를 받을지는 코디네이터가 사용자에게 묻는 중이라(PLAN U-7) 답이 오기 전까지 active 만 — 바꿀 때는 그 한 줄이다. 준비됐으면 만들기에
`"format": "delib-16x9"` 를 싣고, 그 밖의 템플릿은 칸을 싣지 않는다(WDA 기본 wide-16x9 — 지금과 같다). 화면의 API(`formats.deliberation` 참거짓)는
바꾸지 않았다 — 템플릿에서 꼴로 잇는 것은 서버의 `TEMPLATE_FORMAT` 한 곳이다. WDA 는 모르는 꼴에 곧바로 400 을 준다(실행 없음 · 쓸 수 있는 꼴을
message 에). 포털은 그 까닭을 그대로 보이고(502 — WDA 가 받지 않았다) 잡을 남기지 않으며 **기본 꼴로 다시 보내지 않는다** — 탐침을 60초 붙잡으므로
그 사이 WDA 가 옛 판으로 되돌아가면 생길 수 있는 일이다. 붙잡은 탐침을 버리는 손은 두지 않았다(60초 뒤 저절로 다시 묻는다).

**WD-D40 `block_sections` 는 M1 에 포털이 만들어 싣지 않는다 — RA 블록 id 에서 단락이 하나로 정해지지 않는다.** WDA 는 머리글 추론을 덮어쓰는

결정적으로 정해질 때만' 이었고, 정해지지 않는다. ① 같은 `deliberation` 템플릿을 세 곳이 다른 뜻으로 채운다 — 심의 결과(에이전트 서버
