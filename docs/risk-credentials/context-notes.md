# 결정 기록 — 리스크 심사 앱 사람 자격

## 2026-10-14 — 조사와 결정

**C-1 요청서의 전제와 다른 사실(dev main, 리스크 앱 `af4d9ee`·포털 `7b6aaaf`·게이트웨이 `9dc6c01`).** 요청서는 cae00 의 리스크 앱 `c3f46ba`(스키마 3)를 기준으로 썼다. 지금 main 에서 다시 찾은 근거다.

- RA 쓰기 키 `HWAXRISK_PORTAL_PAT_RW` 로 클라이언트를 만드는 `ra_client_from_settings` 는 시험 밖에서 부르는 곳이 없다. `main.py` 는 `external_sync_send` 를 넘기지 않아 `nightly.retry_external_sync` 가 `{"skipped":"sender 미배선"}` 이다. RA·ADH 일은 `rr_targets.external_sync_json` 에 쌓이기만 한다.
- `HWAXRISK_AIDH_API_KEY` 로 `AdhClient` 를 만드는 곳이 없고, 브리프는 `adh=None` 이다.
- `main.py` 의 `secrets_valid = box_match and all(k in secrets for k in SECRET_KEYS)` 는 파일 `secrets.env` 만 본다. 다섯 키 가운데 둘은 운영에서 쓰지 않는다.
- StepForge 에는 인증이 없다(StepForge `mcp_server.py` — 401 은 허브 forward_auth 가 낸다). 게이트웨이 `provision-config.sh` 의 `rest["step-forge"]` 는 허브 관리자 토큰을 주입하는 GET 전용 사이트다. 포털 PAT 로 `/api/step-forge/…` 를 읽을 수 있다.
- AIDataHub 의 사람별 길은 브라우저 포털 SSO(`sso:<email>` 키)뿐이다. 게이트웨이의 `ai-data-hub` 백엔드는 신원 없이 붙는다.
- 포털 `/auth/pat` 는 세션 쿠키와 CSRF 만 받고, Bearer PAT 로는 발급하지 않는다. `/internal/*` 넷은 전부 GET 이고 토큰을 발급하지 않는다. 챗 PAT(`chat-<sub>-<창>`)·절차 PAT 는 `token_store` 에 기록되지 않는다.
- 게이트웨이의 위임 단언 발급(`_mint_user_pat`)은 도구 호출 요청 안에서 돈다. 그 요청의 `Authorization` 이 호출자 본인의 포털 PAT 다(GW_TOKEN 호출이면 GW_TOKEN).
- RA 사람별 SSO 는 dev 에서 꺼져 있다(`RA_SSO_SECRET` 비어 있음). 게이트웨이를 거친 RA 호출은 그래도 사람 자격이다 — RA SSO → 그 사람이 등록한 RA 토큰 → 거부 순이다(09-29 결정).

**C-2 Claude 경로는 토큰 교환이다(U-1).** 요청서의 (가)·(나)와 견줬다.

- (가) '게이트웨이 비밀이면 아무 이메일의 PAT 를 발급' 은 가장 단순하다. 그러나 GW_TOKEN 을 쥔 쪽(게이트웨이·에이전트 서버)의 힘이 게이트웨이를 넘어 포털 중계까지 넓어진다. 그 사람의 챗 대화 목록(`/agent/conversations`)을 읽는 것이 한 예다. 지금 GW_TOKEN 으로는 포털 중계에서 남이 될 수 없다.
- (나) '저장하지 않고 매번 받기' 는 백그라운드 러너가 사람 없이 몇 시간씩 돌기 때문에, 리스크 앱이 아무 때나 아무나의 자격을 받을 힘을 가져야 한다. (가)보다 넓다.
- 교환은 이미 있는 증거만 쓴다. Claude 로 온 호출에는 호출자가 직접 낸 포털 PAT 가 있다. 그것으로 같은 사람의 더 좁은 PAT 를 받는 일은 누구에게도 새 사칭 힘을 주지 않는다. 훔친 PAT 를 가진 사람은 이미 그 사람이다. 막을 것은 둘이다.
  - 수명 늘리기 — 만료를 원 PAT 이하로 묶고, 기록되지 않은 챗·절차 PAT 를 원으로 받지 않는다.
  - 폐기를 피해 살아남는 자식 — 원을 폐기하면 자식도 폐기한다.
- 리스크 앱은 호출자의 원 PAT 를 보지 않는다. 게이트웨이가 포털에만 보내고, 리스크 앱은 좁힌 PAT 만 받는다.

**C-3 웹은 화면이 한다(U-2).** 앱 서버에도 같은 출처라 포털 세션 쿠키가 온다. 서버가 그것으로 대신 발급하면 화면을 안 고쳐도 되지만, 앱 서버가 포털 세션을 다루는 길이 새로 생긴다. 지금 버튼이 하는 일(브라우저가 직접 `/auth/pat`)을 자동으로 하는 편이 신뢰 경계를 바꾸지 않는다. 화면은 다른 세션 몫이라 백엔드는 `portal_pat.auto` 칸과 끄기만 만들고 요청서를 넘긴다.

**C-4 사람이 시작한 잡은 서비스로 내려가지 않는다(U-3).** 카드 대조의 D-26 과 같은 규칙을 패널에도 둔다. 서비스 시야(조직 공개 과제만)로 돈 패널은 결과가 그 사람의 기대와 다르면서 겉으로는 정상이다(무음 결함의 꼴). 짧은 호출 셋(로스터·현장 VOC·캡처 MCP 폴백)은 사람의 비공개 자료를 열지 않으므로 서비스 PAT 를 남기되, 쓰였다는 표시를 남긴다.

**C-5 RA 쓰기는 M4 에 둔다(U-4).** 요청서는 「자격이 없어 조용히 pending」이라고 봤으나, 실제로는 보내는 코드가 없다. 쓰기를 당기면 무엇을 어느 워크스페이스에 쓰는지·한도·과제 비공개 기본값(PLAN M4 의 열린 물음)을 같이 정해야 한다. 이번에는 '반영 안 됨 — 보내는 쪽이 아직 없다' 를 보이게만 한다.

**C-6 필수 키는 `CRED_KEY` 하나다(R5).** 나머지는 없으면 특정 길이 닫힐 뿐 앱은 돈다. 필수로 세면 운영자는 늘 켜진 경고를 보고 진짜 문제를 놓친다. `cred.key` 폴백은 동작은 하지만 운영자가 그 파일의 존재를 모르면 백업·이관에서 빠져 등록된 PAT 가 전부 안 풀린다. 그래서 '틀렸다' 가 아니라 '옮기라' 는 경고다. 옮길 때는 값을 그대로 옮겨야 한다(Fernet 키가 바뀌면 `portal_pat_enc` 가 안 풀린다 — `test_me.py` 의 키 교체 시험).

## 2026-10-14 — P1 포털 토큰 교환 구현

**C-7 교환으로 받은 PAT 은 원이 될 수 없다.** 계획은 '기록된 PAT·`purpose` 없음' 만 적었다. 자식이 다시 원이 되면 폐기 연쇄가 한 단만 내려가므로, 손자가 원 PAT 의 폐기를 피해 살아남는다. 같은 이름 대체가 원 자신을 폐기하는 꼴도 생긴다. 쓰임도 없다 — 게이트웨이는 사람이 Claude 에 넣은 PAT(토큰 화면에서 낸 것)로만 바꾼다. 그래서 원은 `parent_jti` 가 빈 PAT 만이고, 연쇄는 한 단으로 충분하다.

**C-8 거절 code 는 일곱이다.** 계획의 넷(`source_not_exchangeable`·`widen_audience`·`widen_scopes`·`bad_ttl`)에 셋을 더했다.

- `invalid_source`(401) — Bearer 없음, 또는 `verify_pat` 실패(서명·청중 `mcp-gateway`·`scope=api`·만료·폐기).
- `account_disabled`(403) — 계정 정지(`entitled`).
- `permission_denied`(403) — `feat:api-token` 없음(`ensure`).

게이트웨이가 감사 note 를 code 로 쓰므로 이 끝점의 거절은 전부 `{detail:{code, message}}` 한 꼴이다. `AuthError` 에 선택 칸 `code` 를 더해 이 꼴을 낸다(안 주면 종전 꼴 `{detail:"…"}` 이라 다른 끝점은 그대로다). 본문 꼴이 틀린 것(칸 빠짐·이름 길이)만 FastAPI 기본 422 이고 `detail` 이 목록이다. 빈 `audiences` 는 `widen_audience` 다 — `/auth/pat` 에서 빈 청중은 '기본 전체' 라 좁히기로 읽으면 안 된다. 본문 네 칸은 전부 필수다(기본값이 원보다 넓을 수 있다).

**C-9 기록할 때 원의 폐기를 다시 본다.** 검사와 기록 사이에 원이 폐기되면 연쇄는 아직 없는 자식을 못 보고 자식이 살아남는다. 기록(`record_exchanged_pat`)이 폐기와 같은 잠금 안에서 원이 폐기됐는지 다시 보고, 폐기됐으면 기록도 반환도 하지 않는다(403 `source_not_exchangeable`). 이 재확인은 '그사이 폐기' 하나만 본다 — 원이 될 수 있는지까지 다시 보면 앞의 원장 대조와 겹쳐, 한쪽을 빼도 시험이 안 깨진다(변이로 확인). 같은 이름 대체도 같은 트랜잭션이다 — 동시 교환 둘이 서로를 못 보고 둘 다 사는 일을 막는다.

## 2026-10-14 — P2·P3 맞대기

**C-10 자동 등록이 바라는 PAT 의 청중은 `mcp-gateway`·`step-forge` 둘이고, 게이트웨이가 호출자 PAT 의 청중과 겹치는 것으로 좁혀 교환에 싣는다.** 세 갈래를 맞대 보니 R2(위임 캡처의 REST 다리)가 열리지 않았다. 게이트웨이 REST 프록시(`rest_proxy._verify`)는 PAT 의 aud 에 사이트 이름(`step-forge`)이 있어야 받는데, 계획의 교환 명세는 `mcp-gateway` 하나였다.
- 앱이 `step-forge` 를 그냥 더하면, 그 청중이 없는 옛 PAT(09-23 원-토큰 D-1 전에 청중을 골라 낸 것)의 교환이 `widen_audience` 로 통째 실패한다. 그러면 MCP 길(패널·카드 대조)까지 막히고 앱은 6시간 쉼에 든다.
- 그래서 게이트웨이가 이미 검증한 호출자 PAT 의 aud 를 읽어 바란 청중과 겹치는 것만 싣는다(게이트웨이 `5ab2e5c`, 리스크 앱 `9ee4776`). 포털은 그대로 넓히기를 거절하므로 이 줄은 좁히기만 한다. 겹치는 것이 없으면 `skipped-no-audience` 다(게이트웨이에 들어온 PAT 는 `mcp-gateway` 를 가지므로 실제로는 생기지 않는다).
- 옛 PAT 의 사람은 `mcp-gateway` 만 받는다. 위임 캡처의 REST 다리는 닫힌 채이고, 앱의 `capture_rest_note` 가 까닭(토큰 화면에서 새로 발급)을 말한다.
- 화면 자동 등록도 같은 두 청중을 바라게 요청서에 더했다(웹은 브라우저가 `/auth/pat` 로 새로 내므로 좁힐 원이 없다).
