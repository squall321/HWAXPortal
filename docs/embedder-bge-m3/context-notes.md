# 임베더 BGE-M3 전환 — 결정과 까닭

**EM-D1 받은 것(2026-10-16).** 사용자 — "BGE-M3로 바꿔서 정합성을 향상시키는걸 해줬으면 좋겠어", "모든 데이터를 검색하는게 빠른것도
중요한데 시멘틱이 잘 되어야 하거든", "원래 하던 작업도 하고 이것도 다 진행해줘". 근거는 한국어 검색 기준선(포털 `docs/improvement-1015`
IM-D22) — 한국어 카드는 0.98~1.00 인데 한국어 질의로 영어 카드를 찾는 것이 0.39~0.57(전역 의미검색 0.10)이다.

**EM-D2 무중단 — 슬롯 둘.** 예전 384→768 이행(AIDataHub alembic 0013)은 임베딩을 전부 비우고 열 형을 바꾼 뒤 백필했다 — 그동안 의미검색이
빈다. 절 1,090,531개를 다시 임베딩하는 동안 그럴 수 없어 새 열을 나란히 두고 채운 뒤 설정 한 줄로 읽기를 옮긴다. 되돌리기는 그 줄이다.

**EM-D3 새 열은 `halfvec(1024)` 다.** pgvector 0.8(dev — `hnsw.iterative_scan` 이 있다)과 pgvector-python 0.4.2(HALFVEC)가 받는다. 벡터
하나 2KB 로 지금 `vector(768)`(3KB)보다 작고, 반정밀도의 순위 손실은 검색에서 무시할 만하다(견주기가 본다).

**EM-D4 백필을 새로 짓는다.** 지금 `embed_handler` 는 빈 절 전부를 ORM 객체로 메모리에 올리고 끝에 한 번 커밋한다 — dev 에서 21만 절에
8~9GB · 몇 시간 열린 트랜잭션이었고, 스케줄러가 30분마다 새 잡을 겹쳐 띄운다(한국어 검색 측정 중 관찰). 110만 절에는 쓸 수 없다 —
키셋 페이지로 읽고 청크마다 커밋하고 advisory lock 으로 한 번에 하나만 돌게 한다.

**EM-D5 cae00 은 dev 가 계산한 벡터를 merge 로 받는다.** `merge-from-drive.sh` 는 운영 DB 의 열 목록으로 dev 덤프의 값을 덮는다(절은
자연키 `record_id, section_id`, id 는 운영 시퀀스). 그래서 dev GPU 로 채운 v2 벡터가 cae00 에 그대로 간다. cae00 이 CPU 로 110만 절을
다시 임베딩하지 않는다. cae00 에서만 생기는 행은 그 박스의 백필이 채운다.

**EM-D6 dev 모델 파일.** dev 는 `~/.cache/huggingface/hub` 에 `BAAI/bge-m3` · `bge-reranker-v2-m3` 가 이미 있다(`/opt/models` 없음).
cae00 은 폐쇄망이라 `model-to-drive.sh` · `model-from-drive.sh` 에 bge_m3 를 더해 나른다.

**EM-D7 절대 점수 문턱을 전수로 본다.** e5 는 무관한 글끼리도 코사인 0.7~0.9 라 그 분포로 잰 문턱은 BGE-M3 에서 뜻이 바뀐다. 셈한 것 —
AIDataHub 의 에이전트별 `retrieval_config.score_threshold` 는 dev 796개 가운데 774개가 0.3 · 1개가 0.5 인데 검색 점수가 (1+코사인)/2 라
코사인 −0.4 · 0 에 해당해 어느 모델에서도 거의 걸러지지 않는다(B1 에이전트가 나머지 — 미리보기 · 추천 · 군집 0.4 · 거절 · 유사도 — 를
본다). 확실히 깨지는 곳은 **포털 대화 검색**이다 — 날 코사인 0.84(긴 질의) · 0.75(짧은 질의)가 e5 분포로 잰 값이라 그대로면 BGE-M3 결과를
거의 다 버린다. 그래서 표지마다 하한을 두고(`_FLOORS`), 재지 않은 표지는 점수로 거르지 않고 응답 note 로 알린다. BGE-M3 하한은 전환 뒤 dev
대화로 같은 방법(정답 발췌의 최소 점수 대 무관 질의 1위의 최대)으로 잰다. 에이전트 서버의 0.5(`_rank_tools`)는 어휘 겹침 점수라 상관없다.

**EM-D8 소비처는 응답의 모델을 따른다.** 포털 대화 검색은 저장 표지를 상수(`aidh-768`)로 박았고, 에이전트 서버 도구 벡터 캐시는 도구 이름만
봤다 — 임베더가 바뀌면 새 벡터를 옛 표지로 저장하거나, 새 질의를 옛 공간 벡터와 견준다(zip 이 차원을 말없이 잘라 엉뚱한 순서가 오류 없이
나온다). 둘 다 `/api/embed` 응답의 model · dim 을 공간으로 보고, 다르면 다시 색인 · 다시 짓는다. 응답에 model 이 없거나 e5-base(768)면 옛
표지를 그대로 써 지금 박스는 다시 색인하지 않는다.

**EM-D9 dev 실관찰 — 백필과 검색이 한 토크나이저를 다툰다(2026-10-16 08:0x UTC).** vLLM 을 내리고 AIDataHub 를 다시 띄우자 임베더가 GPU 로
돌아왔고(e5-base, 프로세스 GPU 1.4GB), 첫 주기에 옛 백필이 21만 절을 ORM 객체로 한꺼번에 올렸다 — 프로세스 RSS 16GB(EM-D4 그대로). 그 백필이
스레드에서 `encode_many` 를 도는 동안 검색 요청이 같은 임베더로 질의를 인코딩해 묶음이 `Already borrowed` 로 실패했다 — HF 빠른 토크나이저는
여러 스레드가 함께 쓰면 안 된다. 새 백필은 검색과 나란히 돌아야 하므로 임베더 안에서 인코딩을 한 번에 하나로 묶는다(B1).

**EM-D10 B1 합침 · B2 시작(2026-10-16 09:27 UTC).** 가지 `embed-m3`(커밋 12)를 검토해 AIDataHub main 에 합치고 올렸다(`e036812`). 슬롯 설정을
안 적은 박스는 지금과 같다(활성 · 채움 모두 v1 — `embed_slots.active_name` · `fill_names` 기본값). 옛 API(옛 스윕이 몇 시간 열린 트랜잭션 ·
RSS 29GB)를 `restart.sh --api` 로 내리고 띄우자 0031→0032 가 올라갔고 v1 의미검색 · `/api/embed`(model · dim · slot)가 그대로 돌았다. m3
백필은 CLI(`embed-slot.sh fill --slot m3`)로 뒤에서 돈다 — 시그니처 59,032 · 표본 7,670 · 도구 4 는 9분에 끝났고 절 1,090,531 이 남았다.
인앱 v1 스윕은 새 청크 백필로 v1 백로그 214,837 을 함께 채운다(GPU 를 나눠 쓴다). 시험 — 본 venv 엔 `aiosqlite` 가 없어 SQLite 시험이
건너뛰므로 따로 깐 곳을 붙여 돌렸다. 합친 main 629 통과 · 35 실패, 35건은 합치기 전 main 도 같다(적재 · 시드 — 임베딩과 무관).

**EM-D11 dev 의 백필은 HDD 의 색인 갱신에 묶였다 — 캐시를 데워 풀었다.** 새 열 UPDATE 는 대부분 HOT 이 아니어서(절 7% · 레코드 30%만
HOT) 표의 모든 색인을 갱신한다 — v1 HNSW 는 같은 벡터를 이미 있는 원소의 힙 TID 목록에 덧붙이지만 그 원소를 찾는 그래프 탐색이 필요하고,
레코드의 content GIN 은 content 를 풀어 읽는다. dev PG 데이터는 HDD(`/data/pg/aidh`)이고 `shared_buffers` 는 기본값 128MB 라 첫 청크가
무작위 읽기에 묶였다(레코드 4.8행/초 · 디스크 100%). 두 표의 표 · TOAST · 색인 파일(약 11GB)을 한 번 순차로 읽어 OS 캐시에 올리자 레코드
120~280행/초 · 절 155~160행/초가 됐다. PG 설정(shared_buffers · max_wal_size)은 바꾸지 않았다 — 재시작이 dev 의 모든 소비처를 끊고, 캐시
데우기만으로 읽기가 0 이 됐다. 명령은 AIDataHub `docs/embedder-bge-m3.md` dev 절차 1)에 그대로 적었다(`29c9c38`).

**EM-D12 v1 도 다시 잰다(B3).** 한국어 검색 기준선과 정확 범위 수정 뒤 측정(IM-D22 · IM-D23)은 절 214,837개(약 20%)에 v1 임베딩이 없던 DB
에서 쟀다 — 그 절들은 의미검색에 보이지 않았다. 인앱 v1 스윕이 그것을 채우고 있으므로 견주기는 v1 · m3 백필이 둘 다 끝난 같은 DB 에서
v1(본 API) · m3(견주기 API)를 함께 잰다. 옛 수치와 바로 견주지 않는다.

**EM-D13 cae00 갱신 순서.** HWAXPortal update-all → deploy-all → `boot.sh --force` → `start_api.sh` 는 이행을 옛 API 를 내리기 **전에**
돌린다. 0032 는 잠금을 10초만 기다리므로 그때 cae00 의 옛 스윕이 긴 트랜잭션을 쥐고 있으면 'aidh failed' 가 보이고 옛 API 가 옛 코드로 돈다
— 조용한 고장은 아니고 다음 update-all 이 다시 올린다. 절차서(B6)에 적는다.
