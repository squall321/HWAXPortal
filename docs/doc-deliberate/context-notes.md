# 문서 심의 — 결정 기록

작업하면서 내린 판단과 **왜 그렇게 했는지**. 다음 세션이 같은 판단을 다시 하지 않도록.

---

## D-1. 추출은 클라이언트에서 — 이게 전부를 정한다

사용자 요구: "업로드하는 PC 의 오피스 COM 을 이용해서 한번 읽고 출력하는게 되었으면 해
그걸 전제로 해야 DRM 이 안 걸리거든."

DRM 문서는 **그 PC, 그 사용자 세션**에서만 복호화된다. 서버가 원본을 받아 파싱하면 암호화된
바이트만 본다. 그래서 서버로 가는 것은 원본이 아니라 **추출된 글**이다.

**사용자가 2026-09-12 에 COM 동작을 실측 확인했다** — 가장 큰 미지수였고, 풀렸다.

## D-2. 이미 있던 두 경로가 왜 못 쓰이나 (코드로 확인)

사용자가 "ReportArchive 에서 올릴 수 있었던 것 같은데" 라고 해서 코드를 봤다. 둘 다 있다.

| 경로 | 무엇을 하나 | 왜 DRM 에서 막히나 |
|---|---|---|
| RA `POST /imports/pptx` | PPTX → 보고서 draft(슬라이드 1장=페이지 1장) | `routes.py` 가 `parse_pptx(data)` 를 **서버에서 python-pptx 로** 돈다. DRM PPTX 는 zip 이 아니라 암호화된 OLE 컨테이너라 여기서 400 |
| AIDataHub `convert_file` | docx/xlsx/pdf/pptx 정밀 변환 | 설명 그대로 "서버 inbox 에 파일을 두면 서버가 변환" |
| RA `prepare_upload` | 티켓+URL 발급 → PC 에서 curl 로 바이트 POST | **업로드는 된다.** 다만 첨부 저장(file_id)이고 내용 추출이 아니다 |

즉 **취입 기능은 이미 있었고, DRM 문서에서만 못 쓴다.** 이 작업은 새 기능이 아니라
변환 지점을 서버에서 PC 로 옮기는 것이다.

## D-3. 왜 마크다운을 먼저 만들었나 (RA 세그먼트가 더 좋은데)

RA 파서의 출력(heading/rich_text/table/image)은 `create_report_draft(extra_blocks=…)` 가
받는 모양과 같다. 추출기가 그 모양으로 뱉으면 DRM 문서도 보고서로 그대로 들어간다 —
**RA 리포를 건드리지 않고**(커밋 금지 대상) 기존 MCP API 만으로.

그런데 원래 요청은 "내용을 읽고 **심의**" 다. 심의 근거는 글이면 되고, 페이지·슬라이드
번호만 있으면 인용이 된다. 그래서 1차는 마크다운, 2차가 세그먼트다. 순서를 뒤집으면
쓰지도 않을 위젯 변환을 먼저 만들게 된다.

## D-4. Word·PowerPoint 를 함부로 Quit 하면 사용자 문서가 닫힌다

둘 다 **단일 인스턴스 자동화 서버**다. 사용자가 문서를 편집 중이면 `New-Object` 는 그
인스턴스에 붙고, 거기서 `Quit()` 을 부르면 **작업 중인 창이 닫힌다.**

→ 실행 전 프로세스(WINWORD/POWERPNT) 존재 여부로 `Owned` 를 판정하고, 우리가 띄운 것만
우리가 끈다. PowerPoint 는 다른 발표자료가 남아 있으면 아예 안 끈다.

`Marshal::GetActiveObject` 를 쓰려다 버렸다 — **.NET Core 에서 삭제돼 PowerShell 7 에서
터진다.** 프로세스 유무 판정은 5.1·7 양쪽에서 똑같이 된다.

## D-5. PowerShell 5.1 은 BOM 없는 UTF-8 .ps1 을 ANSI 로 읽는다

한글 출력 문자열이 전부 깨진다. `.ps1` 은 **BOM + CRLF** 로 배치한다.
`.bat` 은 반대로 **ASCII 만** 쓴다 — cmd 코드페이지(cp949/65001)에 따라 한글이 깨지므로,
안내 문구는 전부 `.ps1` 이 낸다.

## D-6. 페이지 단위로 읽는다(문단 단위 아님)

`$doc.Paragraphs` 를 돌면 COM 왕복이 문단 수만큼이라 100쪽짜리에서 몇 분 걸린다.
`GoTo(wdGoToPage, …)` 로 페이지 경계만 잡아 `Range(start,end).Text` 로 한 번에 읽으면
호출이 페이지 수에 비례한다. 대신 heading 구조는 포기했다 — `[p.N]` 표지만으로 인용이 된다.

표는 예외다. 본문 `Range.Text` 에선 셀 구분자(CR+BEL)로만 남아 읽을 수 없으므로
`$doc.Tables` 에서 따로 뽑아 마크다운으로 복원한다(표당 COM 1회).

## D-7. PowerPoint 는 `Visible=$false` 를 거부한다

버전에 따라 예외가 난다. 대신 `Presentations.Open(file, ReadOnly, Untitled, WithWindow=msoFalse)`
의 네 번째 인자로 창 없이 연다 — 이게 정석이다.

## D-8. 심의 사전 근거 예산이 **문서 한 건도 못 담고 있었다**

종전: 12항목 · 항목당 2,000자 · 합계 11,000자. 발표자료를 추출하면 보통 30,000~80,000자다.
**첫 항목에서 잘렸다.** 그런데 심의는 정상적으로 돌고 결론도 나온다 — 좌석이 표지만 보고
논의한 것을 아무도 모른다. 이 기능을 만들기 전에 이걸 먼저 고쳐야 했다.

새 값(전부 env 손잡이): `_EVID_ITEMS` 40 · `_EVID_ITEM_MAX` 12,000 · `_EVID_BUDGET` 60,000.

**같이 올려야 하는 것이 하나 더 있었다** — `HANDOFF_RESULT_CHARS`(1,200→4,000).
예산만 올리고 발췌 길이를 그대로 두면 예산은 크고 실제로 실리는 건 그대로다.
`test_doc_attach.py::test_핸드오프_발췌가_심의_예산에_맞다` 가 이 짝을 본다.

## D-9. 상한은 세 계층에 있고, 어긋나도 아무 신호가 없다

프론트 `handoff.ts` → 포털 `DelibOpts` → 엔진 `_EVID_*`. **가장 작은 곳에서 잘린다.**
좌석 상한과 달리 여기는 422 도 안 나고 심의도 멀쩡히 돈다.
→ `backend/tests/test_evidence_budget_contract.py` 가 세 값이 같은지 본다.

## D-10. 문서는 sys_prompt 에 싣는다(user 메시지 아님)

챗 경로는 세 갈래다 — 첫 호출 · 오류 재시도 · 강제 도구호출. **셋 다 `sys_prompt` 를
공유하고 `req.message` 를 따로 쓴다.** user 메시지에 붙이면 재시도 경로에서 조용히 빠진다.

## D-11. 예산은 문서 **건수로 균등 분배**한다

앞 문서가 예산을 다 먹으면 사용자는 두 건을 붙였는데 답이 한 건만 본 채로 나온다. 그 실패는
화면에 아무 흔적도 안 남는다. → `_doc_block` 이 몫을 나누고, 자른 문서마다 원문 길이와
"앞 N자만 실림" 을 적는다. 모델이 못 본 구간을 알아야 지어내지 않고 되묻는다.

## D-12. 본문은 대화에 저장하지 않는다

`Message.docs` 에는 **이름·길이·종류만** 남긴다. 수만 자 본문까지 localStorage 에 넣으면
쿼터를 바로 먹는다(`agentCatalog` 를 안 남기는 것과 같은 이유). 본문은 전송 1회성이고,
`attachedDocs` 는 보낸 뒤 비운다 — 안 비우면 매 턴 수만 자가 다시 실린다.

## D-13. 정독에서 나온 것들 — PowerShell 을 못 돌리는 박스에서 만들었다

이 박스에는 PowerShell 도 Office 도 없다. **문법 검사조차 못 한다.** 그래서 전체를 한 번
정독했고, 아래 넷이 나왔다. 셋은 실행해 보기 전엔 안 보이는 종류다.

1. **`Get-OfficeApp` 에 인자를 추가하고 호출부 4곳을 안 고쳤다.** `$ProcName` 이 비면
   `wasRunning` 이 늘 false 가 되어 **사용자가 편집 중인 Word 를 Quit 한다** — 막으려고 만든
   장치가 정확히 반대로 동작하는 상태였다. 인자를 `Mandatory` 로 못박았다.
2. **무한 루프.** Word 표에서 `$cols` 가 0 이면 `for (… $i += $cols)` 가 영원히 제자리다.
   오류도 안 나고 그냥 안 끝난다. 열 수를 못 읽는 표는 건너뛰고 경고에 남긴다.
3. **배열 슬라이스 `$cells[0..($cells.Count - 2)]`** — Count 가 1이면 `0..-1` 이 되어 첫 칸과
   **마지막 칸이 중복**으로 잡힌다. 2개 이상일 때만 자른다.
4. **RCW 누수** — 도형 루프 안에서 `$slide.Shapes.Title` 을 매번 다시 가져와 COM 객체가 도형
   수만큼 쌓였다. 루프 밖에서 한 번만 집는다.

## D-14. Office 앱 수명은 '파일당' 이 아니라 '실행당' 이다

파일마다 열고 닫으면 두 가지가 깨진다.

- **경합** — `Quit()` 은 비동기다. 다음 파일에서 `Get-Process WINWORD` 를 보면 아직 살아
  있어 "남의 Word" 로 오판하고, 그러면 **영영 안 끈다**(누수). 자가 시험의 누수 검사도
  이것 때문에 거짓 경고를 냈다.
- **속도** — 50개 폴더에서 Word 를 50번 띄운다.

→ `$script:OFFICE` 에 ProgId 로 캐시하고, 실행이 끝날 때 `Close-OfficeApps` 가 한 번에
정리한다. 본 실행 루프를 `try/finally` 로 감싸 **Ctrl+C 로 끊겨도** Office 를 안 남긴다.
PowerPoint 는 우리가 띄웠더라도 그 사이 사람이 발표자료를 열었으면 안 끈다.

## D-16. 긴 발표자료 — 숫자를 올리는 걸로는 안 됐다

"PPT 가 길 수도 있으니 큰 것도 받아라"(사용자). 여기서 셋이 드러났다.

**① 계층 역전 — 내가 만든 버그.** 프론트 `DOC_CHARS_MAX` 400,000 vs 포털 `ChatDocument.text`
200,000. 사용자는 붙일 수 있는데 **전송이 422 로 죽는다.** 근거 예산의 역전(D-9)은 조용하지만
이쪽은 대놓고 실패한다 — 대신 원인이 "긴 문서" 라는 걸 아무도 모른다.
→ `test_문서_상한은_뒤로_갈수록_작아지면_안_된다` 가 추출기→프론트→포털 순서를 본다.

**② 앞에서 자르면 결론이 날아간다.** 발표자료·보고서는 결론이 **뒤**에 있다. 실측 180슬라이드
326,341자에서 앞 예산만큼 남기면 결론 슬라이드가 통째로 사라지는데, 답변은 겉보기에 멀쩡하다.
→ `evidence.fit_document` 가 **낱장 경계**(`## [s.N]`·`## [p.N]`)에서 앞뒤를 남기고 가운데를
덜어낸다. 빠진 구간을 `s.4~s.177` 처럼 번호로 밝혀 모델이 "못 봤다" 고 말할 수 있게 한다.
챗과 심의가 같은 함수를 쓴다 — 한쪽만 고치면 같은 문서가 화면마다 다르게 잘린다.

**③ 진짜 천장은 고정 숫자가 아니라 모델 컨텍스트다.** `DOC_TOTAL_CHARS=400000` 으로 올렸더니
dev(16,384 토큰)에서 그대로 400 이 났다 — 사용자에게는 **'응답 생성 실패'** 로만 보인다.
같은 일이 운영 GLM(128K)에서도 30만 자 문서면 똑같이 난다.
→ 시작 시 `/v1/models` 의 `max_model_len` 을 한 번 읽어 예산을 유도한다
(`컨텍스트 × 1.2자/토큰 × 0.45`). env 로 박으면 박스마다 한쪽이 반드시 틀린다.
`DOC_TOTAL_CHARS` 를 명시하면 그 값이 이긴다.

**실측(dev 16,384 토큰)** — 180슬라이드 326,341자를 붙였을 때.

```
붙인 문서 1건을 읽습니다 — 길어서 가운데 일부는 건너뜁니다
→ 답변: 결론(s.180) 정확히 인용 + "s.4~s.177 은 실리지 않았습니다" 스스로 밝힘
```

새 상한 — 추출기 2,000,000 ≤ 프론트 2,000,000 ≤ 포털 2,000,000 (전송은 통째로),
모델에 넣을 때만 컨텍스트에 맞춰 줄인다. 심의 `_EVID_ITEM_MAX` 40,000 · `_EVID_BUDGET` 160,000.

## D-17. 예산은 컨텍스트의 **비율**이 아니라 '컨텍스트 − 예비분 − 이력'

사용자: "GLM 이나 클로드 오푸스 이상을 생각하고 컨텍스트를 고려해야 해."

비율 배분(`ctx × 0.45`)이 왜 틀렸나 — **고정 오버헤드는 창 크기에 비례하지 않는다.**
시스템 프롬프트·도구 스키마·출력은 창이 1M 이든 16K 든 비슷하게 든다. 비율로 떼면 큰 창에서
수십만 토큰을 그냥 놀린다.

```
                     비율(0.45)      현재(ctx − 예비 − 이력)
  dev      16K        8,847자            5,675자   (한국어)
  GLM     128K       69,120자          150,181자   ← 2.2배
  Opus    200K      108,000자          243,397자
  Opus      1M      540,000자        1,279,129자
```

**글자↔토큰은 글자 구성으로 환산한다.** 한글은 토큰당 1자 남짓, 라틴 문자는 3.6자다(실측).
한 값으로 뭉뚱그리면 한국어에서 400 이 나거나(과대평가) 영문 문서에서 창의 3분의 1만 쓴다.
같은 128K 창에서 한국어 150,181자 / 영문 417,641자 — 2.8배 차이다.

**이력을 빼야 한다.** `HIST_BUDGET` 이 200,000자라 이력만으로 128K 창을 넘길 수 있다. 고정값을
빼면 긴 대화 중에 문서를 붙이는 순간 400 이 난다. 그래서 그 턴의 **실제** 이력을 뺀다.
이력이 창을 이미 먹었으면 자리를 있다고 하지 않고 최소치만 준다 — 바닥값(`ctx × 0.15`)을
두었다가 없는 자리를 있다고 계산하는 버그를 만들었고, 바로 지웠다.

원인이 다르면 안내도 달라야 한다. 대화가 길어 자리가 없는 것이면 **"새 대화에서 붙이면 더
읽습니다"** 가 답이고, 문서 자체가 긴 것이면 그 구간을 따로 붙이는 게 답이다.

## D-18. 심의는 400 이 나면 **좌석 전원이 같이 죽는다**

챗은 400 이 나면 그 발화 하나가 실패한다. 심의는 좌석이 동시에 도니까 라운드가 통째로 죽는다.
그래서 근거 예산을 챗보다 더 보수적으로 잡는다.

좌석 프롬프트 하나 = 시스템 + 페르소나 + 직전 라운드(`_SEAT_CTX` 48,000자) + 근거 + 도구 스키마.
근거 천장을 160,000자로 올렸더니 **근거만으로 152,000토큰**, `_SEAT_CTX` 까지 더하면 198,000토큰
— GLM 128K 를 넘는다. 올린 그 커밋이 심의를 죽일 뻔했다.

→ `_EVID_BUDGET` 은 **천장**으로 두고, 실제 예산은 `min(천장, ctx − _SEAT_CTX − 예비분)`.

```
  GLM  128K → 근거  69,600자 · 좌석 프롬프트 최악 112,000토큰  OK
  Opus 200K → 근거 145,200자 ·                  184,000토큰  OK
  Opus   1M → 근거 160,000자(천장) ·            198,000토큰  OK
```

dev 16K 는 `_SEAT_CTX`(48,000자 ≈ 45,700토큰)만으로 이미 창을 넘는다 — **이건 종전부터 그랬고**
이번 변경과 무관하다. dev vLLM 은 배포 타깃이 아니라 건드리지 않았다.

`DELIB_EVID_BUDGET` 을 env 로 못박으면 그 값이 이긴다(컨텍스트 조회가 틀릴 때의 손잡이).

## D-19. 이력은 버리지 않고 압축한다

종전 `_history_messages` 는 예산을 넘긴 오래된 턴을 **그냥 버렸다.** 그러면 모델은 그런 대화가
있었다는 것조차 모르고, 사용자는 "아까 말했잖아" 가 왜 안 통하는지 알 수 없다 — 화면에도
아무 흔적이 없다. 문서까지 같은 창을 다투게 되면서 이 드롭이 훨씬 자주 일어난다.

→ 최근 턴은 원문으로, 밀려난 오래된 턴은 **발췌 압축본 한 덩어리**로 맨 앞에 넣는다.

**LLM 요약을 안 쓴 이유** — 이력은 매 턴 클라이언트에서 다시 온다. 요약도 매 턴 다시 해야
하므로 발화마다 요약 호출이 하나씩 더 붙는다(지연·비용). 서버 대화 저장소에 요약을 캐시하면
LLM 요약이 가능해지지만 그건 별건이다. 지금은 결정적·무비용 발췌로 간다.

**몫을 균등하게 주지 않는다.** 요구·결정은 사용자 턴에 있고 어시스턴트 턴은 그것을 풀어 쓴
것이라, 같은 글자를 쓸 거면 사용자 쪽을 남기는 편이 복원력이 높다(사용자 2 : 어시스턴트 1).
첫 턴은 대개 과제 자체를 규정하므로 한 몫 더 준다.

실측(dev 16K 창, 이력 71,623자 30턴 + 문서 48,937자):
```
이전 대화 29턴은 길이 때문에 발췌로 압축해 넣었습니다(최근 1턴은 원문)
붙인 문서 1건을 읽습니다 — 대화가 길어 문서에 줄 자리가 적습니다(새 대화에서 붙이면 더 읽습니다)
→ 답변: 과제(20만회)를 기억하고, 문서 결론([s.60] 12um)도 정확히 인용
```

## D-20. env 는 **낮추기만** 한다

`HIST_BUDGET=16000` 한 줄이 dev 의 16,384 토큰 창을 넘겨 400 을 냈다. 낡은 .env 한 줄이
컨텍스트를 조용히 무시하면 안 된다 — 그 결과는 '응답 생성 실패' 로만 보인다.

→ `HIST_BUDGET` · `DOC_TOTAL_CHARS` · `DELIB_EVID_BUDGET` 은 전부 `min(env, 컨텍스트 유도값)`.
탐지가 틀려 창을 **크게** 잡아야 하면 그건 `LLM_CONTEXT_TOKENS` 로 고칠 일이다. 손잡이의
역할을 나눠 두지 않으면 어느 것을 만져야 하는지 아무도 모른다.

이력·문서 예산이 각각은 맞는데 **합치면 넘는** 경우도 있었다(128,000 창에서 142토큰 초과 —
토큰↔글자 왕복 변환 오차). `DOC_SAFETY`(0.97)로 덮고 테스트로 고정했다.

| | 이력 최대 | 문서 예산 | 합계/컨텍스트 |
|---|---|---|---|
| GLM 128K | 61,866자 | 58,281자 | 126,425 / 128,000 |
| Opus 200K | 100,266자 | 94,455자 | 197,448 / 200,000 |
| Opus 1M | 526,933자 | 496,394자 | 986,596 / 1,000,000 |

## D-21. cae00 은 1M 창이다 — 그에 맞춰 다시 잡았다

사용자 확인(2026-09-12): **cae00 운영 GLM-5-2 는 컨텍스트 1M.** 리포 어디에도 안 적혀 있던
값이라 추측하지 않고 물었다(모델명·엔드포인트만 `infra/env-kits/agent-server.env` 에 있다).
코드는 `/v1/models` 의 `max_model_len` 을 읽으므로 숫자를 박을 필요는 없지만, **상한들이
1M 을 전제로 잡혀 있지 않았다.**

**가장 큰 것 — 프론트가 먼저 버리고 있었다.** `HISTORY_MAX_TOTAL_CHARS = 180,000`. 서버가
88만 자를 쓸 수 있어도 그만큼이 **아예 도착하지 않는다.** 게다가 이제 서버는 오래된 턴을
압축해 남기는데(D-19), 프론트가 미리 떨어뜨리면 **압축할 것조차 없다.**

| | 종전 | 현재(1M) |
|---|---|---|
| 이력(대화만) | 180,000자 | **881,790자** |
| 이력(문서 붙인 턴) | 180,000자 | 414,960자 |
| 문서 합계 | 69,120자 | **733,691자**(한국어) · 2,000,000자 상한(영문) |
| 심의 사전근거 | 11,000자 | **500,000자** |
| 이력 항목 | 60 | 160 |
| 문서 건수 | 5 | 10 |

**문서가 없는 턴에 이력이 창을 더 쓴다.** 종전엔 문서 유무와 무관하게 40% 만 써서 1M 창의
절반 넘게 놀렸다. 문서를 붙인 턴에만 이력이 양보한다(그 턴의 본론은 문서다).

### 이 과정에서 잡은 버그 둘 (둘 다 조용한 종류)

**① 문서 예산이 압축 *전* 이력을 빼고 있었다.** `_doc_block(documents, req.history)` 이 원본
이력을 셌다. 긴 대화에서 문서가 자리를 통째로 잃는다 — 실측 128K 창에서 문서 몫이
**1,502자**까지 떨어졌다. 이력을 먼저 확정하고 **압축 뒤 실제 크기**를 빼도록 순서를 뒤집었다.

**② 짧은 표본의 정수 절사가 예산을 27% 부풀렸다.** `_chars_for_tokens` 가 토큰 수를 int 로
거쳐 나눴는데, `"가나다라"`(4자·3.81토큰 → **3**)로 재면 예산이 부푼다. 1M 창에서
**1,066,412토큰짜리 이력 예산**이 나왔다 — 즉 컨텍스트를 넘는 예산이다. 밀도(실수)로 바로
나누도록 고치고, 왕복 검증 테스트를 붙였다.

### 확정 예산 (1M, 한국어 최악 기준)

```
대화만       이력 839,800tok                        + 예비 12,000 = 851,800 / 1,000,000
문서 붙이면  이력 395,200tok + 문서 575,015tok      + 예비 12,000 = 982,215 / 1,000,000
심의 좌석    근거 500,000자 + _SEAT_CTX 48,000자    ≈ 521,904tok / 1,000,000
```

영문 문서는 같은 토큰 예산이 2,070,057자에 해당해 **전송 상한(2,000,000자)이 먼저 걸린다** —
차이가 4% 라 실질 손실은 없다. 더 키우려면 전송 상한을 올려야 하는데, 그건 브라우저가 4MB
문자열을 읽어 JSON 으로 싣는 비용이라 지금은 두었다.

## D-22. 남겨 뒀던 것들 — 셋은 했고 하나는 막혔다

**① 띵킹 모드 문서 주입 — 했다.** 두 가지를 지켰다. 문서를 질문(q)에 붙이면 `recommend_agents`
검색어가 수십만 자가 되어 **전문가 발굴이 통째로 망가진다** → 좌석 프롬프트에만 싣는다.
그리고 띵킹은 선별 좌석 **전원이 동시에** 도니 챗과 같은 몫을 주면 한 발화에 수백만 토큰이
나간다 → `THINK_DOC_SHARE`(0.5)로 줄인다.

**② 목적지 선택 — 했다. 다만 전용 라우트를 파지 않았다.**
등록·발행은 되돌리기 어렵다. 전용 라우트를 만들면 확인 절차를 거기 다시 지어야 하는데
챗 경로엔 이미 있다 — `import_record` 는 `dry_run` 으로 모자란 항목을 되묻고,
`create_report_draft` 는 템플릿을 먼저 보게 한다. 그래서 칩이 **지시문을 입력창에 채우고,
보내는 건 사람이 한다.** 코드가 줄고 확인 절차가 한 곳에 남는다.

**③ 로컬 MCP 서버 — 했다.** `hwax-doc-mcp.mjs`(Node, 무의존 stdio JSON-RPC). 포털 경로는
추출한 *글*을 서버로 보내지만 이 경로는 그것조차 안 보낸다. 읽기 폴더를 화이트리스트로
좁혔다(`HWAX_DOC_ROOTS`, 기본 내문서·바탕화면·다운로드) — MCP 는 **모델이 인자를 정하므로**
경로를 열어 두면 모델이 아무 파일이나 읽어 달라고 할 수 있다.
실측 검증: initialize·tools/list·tools/call 정상, `notifications/*` 는 무응답(규약),
`/etc/passwd` 거절, 없는 파일 거절, PowerShell 부재 시 깨끗한 오류.

**④ RA 세그먼트(문서 → 보고서) — 막혔다고 했다가 정정. 된다.**

> **정정(사용자 지적).** "옵션으로 뜨면 되는 거 아니냐, 선택적으로 버릴 수 있으면 되잖아."
> 맞다. 아래는 *자유형식 템플릿이 없다* 는 사실이고, 그건 **기능 차단이 아니라 분류 문제**다.
> 어느 템플릿에 담을지는 **사용자 결정**인데 내가 대신 막고 있었다.
>
> **dry_run 으로 실제 확인했다 — 된다.** 기존 `deliberation` 템플릿 + `extra_blocks` 로
> heading·table·rich_text 를 넣어 호출하니 `warnings: []` 로 통과했다.
>
> ```
> create_report_draft(template_id="deliberation", extra_blocks=[heading, table, rich_text],
>                     dry_run=true)  →  page_count 1, blocks 4개, warnings []
> ```
>
> 그래서 칩 `📄 Report Archive 에 올리기` 를 붙였다. 지시문이 ⑴ 템플릿 목록을 보여 주고
> ⑵ 딱 맞는 게 없으면 **없다고 말한 뒤** 가장 가까운 것을 근거와 함께 제안하게 하고
> ⑶ 고르는 건 사람이 하게 한다. 긴 문서는 `update_report_draft(page=N)` 으로 쪽을 이어
> 붙이게 안내한다 — 한 번의 도구 호출에 다 담으려 하면 출력 토큰 상한에서 끊긴다.
>
> 아래 사실은 그대로 유효하다. 자유형식 템플릿이 생기면 결과가 더 깔끔해지므로 UI 에
> 그 방법을 적어 뒀다(칩 옆 접힘 안내).

`create_report_draft` 로 넣으려면 자유형식 템플릿이 필요한데 **게이트웨이에 없다.**

```
list_templates       → "심의 보고서", "DOE 분석 보고서" 둘뿐
describe_template("__import_blank__") → Template not found: __import_blank__@1
```

RA 웹의 `/imports/pptx` 가 쓰는 `__import_blank__` 는 그 라우트가 **처음 쓰일 때 만든다**
(`ensure_import_template`, get-or-create). 아직 아무도 안 써서 존재하지 않는다.

분류가 어긋나는 것은 사실이다. 다만 그건 **사람이 감수할지 정할 일**이지 코드가 막을 일이
아니었다 — 이 판단을 내가 대신 한 것이 이번 건의 교훈이다.

더 깔끔하게 하려면 둘 중 하나다.
  (a) RA 웹에서 아무 PPTX 나 한 번 '가져오기' 하면 템플릿이 생긴다(그 뒤엔 MCP 로 보인다).
  (b) RA 소유자에게 자유형식 템플릿 게시를 요청한다.
둘 중 하나가 되면 변환기(마크다운 → heading/rich_text/table 위젯)를 붙인다.
**PowerShell 은 안 건드린다** — 마크다운에 이미 `[s.N]`·표가 있으므로 서버에서 변환하면
시험 못 하는 코드를 늘리지 않는다.

## D-23. 행선지 전수 조사 — 처음 셋은 전부가 아니었다

사용자: "특정 플랫폼에 올리기는 상당히 여러 개가 할 만한 게 있을 것 같은데 저게 전부인 거 맞지?"

아니었다. 17개 앱을 **'본문을 문자열로 받는가'** 기준으로 다시 훑었다 — 그게 DRM 에서
갈리는 유일한 기준이다(서버 경로를 받는 도구는 전부 막힌다).

### 쓸 수 있는 것 (추출문이 그대로 들어간다)

| 행선지 | 도구 | 권한 | 언제 |
|---|---|---|---|
| 심의 | `deliberate_start` | `feat:deliberation` | 판단이 갈리는 것을 좌석으로 수렴 |
| 지식카드 | `import_record` | `plat:aidatahub` | 나중에 검색·심의 근거로 재사용할 것 |
| Report Archive | `create_report_draft` | `plat:reportarchive` | 보고서로 남길 것 |
| **MX 백서** | `create_document`+`insert_block` | `plat:mxwhitepaper` | 노하우·가이드 (← 빠뜨렸던 것) |
| **논문 코퍼스** | `submit_paper`(markdown) | `plat:paperingest` | 외부 논문·특허 (← 빠뜨렸던 것) |
| **DynaForge 세션** | `ingest_report`(html_content) | `plat:dynaforge` | 낙하·충격 리포트 HTML |
| StepForge 물성표 | `register_materials_csv`(text) | `plat:stepforge` | CSV 물성표 — 문서 경로 아님(기존 업로드) |

### 막히는 것 (서버가 파일을 읽는다 = DRM 차단)

`convert_file`(AIDataHub) · `import_file`(MX 백서) · `mxwhitepaper_extract_pptx_images` ·
`report_ingest`(WebDesignAgents) · `intake`/`upload_step`(StepForge) · RA `/imports/pptx`.

**패턴이 같다** — 어느 앱이든 "파일을 주면 우리가 파싱한다" 는 도구는 전부 DRM 에서 죽는다.
COM 추출은 그 도구들 **각각의** DRM 대체재다. 하나 만들어 여섯 곳에 쓴다.

### 형식이 행선지를 가른다

```
ppt   delib · read · report · wiki · card · paper     검토·보고 자료
word  read · card · wiki · delib · report · paper     표준·절차서는 재사용 자산
pdf   read · paper · card · wiki · delib · report     논문일 확률이 높다
html  dyna · read · delib · …                         낙하 리포트가 정확히 이 형식
```

없애지 않고 **순서만** 바꾼다. 교육자료·회의록은 PPT 로 오고, 논문을 PPT 로 받는 일도 있다 —
판단은 사람이 한다(지식카드 건에서 배운 것).

## D-24. 행선지는 레지스트리다 — 하나뿐이어도 자동으로 보내지 않는다

사용자: "여러 플랫폼에 계속 추가될 테니까 **한 개만 있더라도 바로 보내지지 말고 선택지를 줘.**"

두 가지를 박았다.

**① 늘어나는 것을 전제로 만든다.** `DESTINATIONS` 배열에 항목 하나 = 행선지 하나다
(`{key, label, title, need, onlyKinds, text}`). 플랫폼이 늘면 **여기 한 줄 더 쓰면 된다** —
조건문을 늘리지 않는다. 지금 7개(심의·요약·지식카드·RA·MX백서·논문·DynaForge).

**② 하나뿐이어도 자동 실행하지 않는다.** 권한이 하나만 있어도 선택지로 띄운다.
하나뿐이라고 자동으로 보내면, 둘이 되는 순간 습관이 어긋난다 — 그때 사람은 이미
"붙이면 알아서 간다" 로 학습돼 있다. 되돌리기 어려운 일에서 그건 위험하다.

그리고 이 판 자체가 **보내지 않는다.** 입력창에 지시문을 채울 뿐이고 읽고 고쳐서 보내는 건
사람이다. 등록·발행 앞의 확인은 UI 가 아니라 이 습관이 지킨다.

### 사고 하나 — 커밋 메시지가 코드보다 앞서 있었다

D-23 커밋(`bcdb82c`)은 "MX 백서·논문 코퍼스·**DynaForge** 를 빠뜨렸다" 고 적었는데, 편집
스크립트가 상대경로 오류로 실패해 **DynaForge 는 코드에 안 들어갔다.** 문서만 커밋됐다.
`git show --stat` 과 `grep -c dyna` 로 확인해 다음 커밋에서 채웠다.
교훈은 편집 스크립트의 실패를 **커밋 전에** 확인하라는 것이다 — 여러 파일을 한 번에 바꾸는
스크립트는 앞쪽이 죽어도 뒤쪽이 성공하면 전체가 성공한 것처럼 보인다.

## D-25. K파일·형식별 행선지·전문가 기반 미리선택

사용자: "K파일은 DynaForge 로 가고, PPT 는 여러 곳 중 고르게 하고, **그 툴 에이전트가 현재
전문가로 선택돼 있으면 그쪽이 미리 선택돼 있고 진행만 하면 되게 — 확인 한 번만.**"

**① K파일은 문서 경로가 아니라 업로드 경로다.** LS-DYNA 덱은 수십 MB 가 흔하다. 브라우저가
읽어 프롬프트에 실으면 컨텍스트를 통째로 먹고, `upload_kfile(content=문자열)` 로도 못 싣는다.
→ `upload.py DESTINATIONS` 에 `dynaforge`(k·key·dyn·inc) 를 더하고, dispatch 가
`create_session` → `upload_local_path(호스트 경로)` 로 보낸다. StepForge 와 같은 방식이다
(apptainer 가 $HOME 을 공유해 다른 컨테이너가 같은 절대경로로 읽는다).

**② 하나뿐이어도 묻는다 — 종전 동작을 뒤집었다.** `UploadRouter` 는 목적지가 하나면 묻지 않고
바로 들어갔다("버튼 하나짜리 질문은 방해"). 목적지가 둘로 늘어난 지금 그건 위험하다 —
사람이 이미 "올리면 알아서 간다" 로 학습돼 있으면, 선택지가 생긴 걸 모른 채 잘못 보낸다.

**③ 전문가가 행선지를 미리 고른다.** 전문가를 고르면 그 사람의 앱이 `pinnedApps` 로 묶인다
(`he-team.json` 의 `apps`). 그 사실만으로 어디로 갈지 짐작할 수 있다 —
`destApps.ts` 가 행선지↔앱을 잇고, 맞으면 **앞에 놓고 입력창에 미리 채운다.**
사람은 읽고 보내기만 하면 된다(확인 한 번). **자동 전송은 여전히 안 한다** — 짐작이기 때문이다.

미리 채우기는 사람이 이미 쓰던 글을 덮지 않는다(`input.trim()` 이 비었을 때만),
그리고 붙인 문서·추천이 바뀔 때 **한 번만** 채운다(`filledFor` ref).

매핑이 빠지면 **아무 오류 없이 추천만 사라진다** — 그래서
`test_업로드_목적지가_전부_앱_매핑에_있다` 가 목적지마다 매핑 존재를 본다.

## D-26. 두 가지를 빠뜨렸다 — 포털 재기동과 RA 게시판

사용자: "dev 도 다시 띄운 거 맞아? Report Archive 조직도 등록하는 게 추가가 안 된 것 같은데."

둘 다 맞았다.

**① 포털을 재기동 안 했다.** `routes.py`·`upload.py` 를 고쳐 놓고 `hwax_portal` 인스턴스를
그대로 뒀다. 코드는 바인드 마운트지만 **uvicorn 은 다시 읽지 않는다** — dynaforge 목적지도
documents 릴레이도 안 붙은 채로 떠 있었다. 프론트만 `pnpm build` 하면 되는 것과 다르다.

> 규칙 — **프론트를 고쳤으면 `pnpm build`, 백엔드 파이썬을 고쳤으면 인스턴스 재기동.**
> 둘은 반영 경로가 다르다(agent-server 는 `./start.sh -d`, 포털은 인스턴스 stop → start.sh).

**② RA 는 초안을 만들면 개인함에 생긴다.** 조직 게시판에 올리려면 별도 단계가 필요한데
지시문에 없었다. 그대로 두면 문서가 **아무도 못 보는 개인함에 쌓인다.**

RA 지시문에 두 단계를 더했다.
- 축 태그 — `suggest_report_tags` → `add_report_tags`. 안 붙으면 `list_reports(entity=…)`·
  `aggregate_reports` 로 **안 찾힌다**(도구 설명이 직접 경고한다).
- 게시 — `list_boards` 로 후보를 보이고 **사람이 고른 뒤** `preview_publish` → `publish_report`.
  확인 토큰은 10분이고 (보고서, 게시판 집합)에 묶여 있어 미리 본 것과 다른 대상으론 안 나간다.
  폴더까지는 `list_folders` → `set_report_folders`. "개인함에만" 이면 게시하지 않는다.

## D-27. RA 워크스페이스(소속)와 게시판은 다른 축이다 — 지시문이 틀렸었다

사용자: "RA 소속은 제대로 등록되게 되어 있음? 토큰 등록할 때 조직 관련된 것도 해야 하는 거 아니던가?"

**등록 자체는 이미 잘 돼 있다**(코드 확인, `backend/app/auth/routes/connections.py`).

- RA PAT 를 붙여넣으면 포털이 `/api/me` 로 검증하고 **memberships** 를 받는다.
- 기본값을 **조직 우선**으로 고른다(`_pick_default_workspace`) — 예전엔 `home_workspace_slug`
  를 그대로 썼는데 그게 `personal-N` 이면 보고서가 계속 개인함에 쌓였다.
- 오타 슬러그는 `_validate_workspace` 가 막는다 — 저장은 성공한 것처럼 끝나는데 보고서는
  어디에도 안 보이는 부류의 실패라서.
- 바꾸면 게이트웨이 캐시를 깬다(`/conn-invalidate`) — 안 깨면 최대 5분간 옛 워크스페이스로 간다.
- 호출 시 게이트웨이가 `X-Workspace-Slug` 를 실어 보낸다(`gateway.py:1894`). 비어 있으면
  헤더를 **지운다** — 서비스 계정 값이 남으면 남의 부서 명의로 기록된다.

**그래서 내 지시문이 틀렸었다.** "초안은 내 개인함에 생깁니다" 라고 적었는데, 실제로는
**토큰 등록 때 지정한 워크스페이스**(기본 = 소속 조직)에 생긴다. 고쳤다.

두 축을 구분해 적었다.

| | 무엇 | 어디서 정하나 |
|---|---|---|
| 워크스페이스 | 보고서가 **어디에 쌓이나**(조직/개인) | 포털 “내 연결” 의 RA 토큰 등록 |
| 게시판(board) | 그 보고서를 **어디에 거나** | `list_boards` → `preview_publish` → `publish_report` |

지시문이 만든 뒤 워크스페이스를 확인해 알리고, `personal-…` 이면 포털에서 조직을 다시
고르라고 일러 주게 했다. 칩 옆 안내에도 같은 말을 적었다.

## D-28. 챗→심의 핸드오프가 대화를 6,000자만 넘기고 있었다

사용자: "심의로 넘기기가 그동안 했던 챗을 기반으로 넘기는 거 맞아? **그냥 문장 하나만
넘기는 것처럼 보여.**"

경로는 다 이어져 있었다. `startHandoff` → `sendMessage('/심의 '+topic, extra)` → history 가
그대로 실려 `run_deliberation(…, req.history)` → `_chat_context_note(history)` 로 좌석에 간다.

**문제는 예산이었다.** `CHAT_CONTEXT_BUDGET = 6000` 자 — 1M 창의 **0.6%** 다. 발화당 상한도
사람 1,200자·챗 900자라, 조금만 긴 대화면 앞 몇 턴에서 `(이하 생략 — 예산)` 으로 끊겼다.
"문장 하나만 넘어간 것처럼" 보이는 게 당연하다.

그리고 **더 나쁜 구조 문제**가 있었다 — 근거 예산(`_evid_budget`)과 챗 맥락 예산이 **따로**
계산됐다. 둘은 같은 좌석 프롬프트에 함께 실리므로, 각각은 컨텍스트에 맞아도 **합치면 넘는다.**

→ 한 통(`_pre_budget`)으로 묶고 나눈다. 근거 70% · 챗 맥락 30%.

```
             통        근거      챗맥락    좌석 최악
GLM  128K  69,600 →  48,720 +  20,880 →  112,000tok  OK
Opus 200K 145,200 → 101,640 +  43,560 →  184,000tok  OK
Opus   1M 985,200 → 500,000 + 150,000 →  664,761tok  OK
                                          (종전 챗맥락 6,000자)
```

발화당 상한도 올렸다 — 사람 4,000자 · 챗 2,500자. 사람 쪽을 더 주는 이유는 종전과 같다:
요구·제약은 사람 발화에 있고, 어시스턴트의 잠정 해석은 없어도 심의가 다시 만든다.

**남는 사실 하나** — `conversationEvidence` 는 **도구 호출 결과만** 긁는다(핸드오프 헌법 P1
"원천만, 결론 금지"). 도구를 한 번도 안 쓴 순수 대화는 `evidence` 가 비고, 대화 내용은
`_chat_context_note` 로만 간다. 이건 설계대로지만, 사용자에게는 "근거가 하나도 안 넘어갔다"
로 보일 수 있다.

## D-29. 예비분이 도구 스키마의 3분의 1이었다 — TOOL_MAX=0 덕에 찾았다

사용자가 cae00 `.env` 를 확인하다 `TOOL_MAX=0` 을 보고 알려 줬다. 그 값 자체는 **맞다**
(0 = 무제한, prod 기본). 그런데 그 덕에 내 계산 전제가 틀린 걸 찾았다.

`DOC_RESERVE_TOKENS = 12000` 으로 박아 두고 주석에 "시스템 + 도구 스키마 + 출력" 이라고
적었는데, **`TOOL_SCHEMA_BUDGET` 기본이 40,000 토큰**이다. 도구 스키마 하나만으로 3배 초과다.
128K 창에서 문서·이력에 **43,000 토큰을 과대 배정**하고 있었다 — 넘치면 400 이고 사용자에겐
'응답 생성 실패' 로만 보인다.

→ 고정값을 버리고 **거기서 유도**한다. `TOOL_SCHEMA_BUDGET + 16000`(= 56,000).
심의도 같다(`_EVID_RESERVE`) — 좌석은 자유 조회가 기본 켜짐(`DELIB_FREE_TOOLS=1`)이라 도구가
바인딩된다. 고정값으로 두면 도구 예산을 올릴 때마다 조용히 어긋난다.

### 그러고 나니 좌석 프롬프트가 **정확히 128,000/128,000** 이었다

우연이 아니라 구조다 — `_pre_budget = ctx − SEAT_CTX − reserve` 로 잡고 다시 더하니 당연히
`ctx` 다. 여유 0 이면 토큰 추정 오차 한 번에 넘친다. `_PRE_SAFETY`(0.93)를 넣었다.

작은 창에서 여유가 얇은 것은 **정상**이다 — 128K 에서는 고정비(직전 라운드 48,000자 +
도구 스키마 40,000토큰)만으로 이미 80% 를 쓴다. 사전 컨텍스트에 줄 수 있는 게 원래 적다.

```
GLM 128K   좌석 최악 126,159 / 128,000   여유  1%   ← 고정비가 79%
1M         좌석 최악 720,761 / 1,000,000 여유 28%
```

테스트도 이 사실에 맞춰 고쳤다. `<= ctx` 만 보면 **딱 맞는 것도 통과**하므로 `<= ctx*0.99` 로
'구조상 딱 맞게 떨어지지 않는다' 를 본다. 3% 를 요구했다가 실패했는데, 그건 코드가 아니라
**테스트가 현실을 몰랐던 것**이다(쌓인 상한들의 동시 최악은 실제로 잘 안 난다).
