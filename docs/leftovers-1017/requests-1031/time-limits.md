## 0. 층 규칙 — 안쪽이 먼저 걸린다

10-08 에 경로 전체의 시간 제한을 '넉넉하게, 그러나 안쪽이 먼저 걸리게' 맞췄다(D-17 · 8·9·10차 server-setup §4-8 의 층 표). 심의 · 리스크 심사의
줄은 LLM 연결 10초 < LLM 호출 한 번 1800초 < 재시도까지 3608초 < … < 챗 PAT 86400초다. 도구 호출의 줄은 게이트웨이가 백엔드를 기다리는
600초(`GATEWAY_CALL_TIMEOUT` — `gateway.py:188`) < 엔진이 게이트웨이를 기다리는 900초(`MCP_CALL_TIMEOUT_S`)다.

까닭 둘. ① 안쪽이 먼저 걸려야 '어느 손잡이가 몇 초에 걸렸는지' 가 든 문구가 나온다. 바깥이 먼저 끊으면 '600초 안에 답하지 않았다' 만 남고 안쪽
일은 계속 돈다. ② 바깥이 끊은 쓰기는 다시 나갈 수 있다. 그래서 새 한도는 기본값을 넉넉하게 두되 바깥 층보다 짧게 두고, 걸리면 값과 손잡이 이름을
문구에 싣는다. 게이트웨이 주석도 같은 말이다 — 더 긴 일은 잡 도구(제출 + 상태 조회)로 간다(`gateway.py:179-187`).

## 1. KooRemapper(DynaForge)

### 1-1. MCP 서버가 제 REST 를 기다리는 한도 — 60초가 일곱 곳

**지금** — MCP 서버(`platform/mcp_server/server.py`)가 백엔드 REST 를 부를 때마다 httpx 한도를 글자로 박았다. 60초가 일곱 곳이다.

| 줄 | 함수 | 쓰는 도구 |
|---|---|---|
| :70 | `_get` | 읽기 도구 거의 전부(`report_*` · `find_reports` · `get_session` · `get_job` …) |
| :87 | `_delete` | 지우기 도구 |
| :253 | `get_job` | `include_logs=true` 일 때 로그 붙이기 |
| :273 | `update_session` | 같은 이름 |
| :377 | `_job_log_tail` | 그림 잡이 실패했을 때 문구에 붙이는 로그 꼬리 |
| :840 | `update_report_meta` | 같은 이름 |
| :914 | `attach_report_scenario` | 같은 이름 |

다른 값도 박혀 있다(열한 곳) — 120초(`_post` :75 · `_put` :80 · `upload_kfile` :157 · `download_result` :303 · `mesh_section_figure` :500 ·
`_download_bytes` :1070) · 180초(`ingest_report` :814) · 300초(`upload_local_path` :179 · `save_result_to_path` :193 · `attach_render` :871 ·
`attach_cad` :903).

**왜 문제인가**
- 게이트웨이는 600초를 기다린다. 60초를 넘는 정당한 읽기(큰 전각도 리포트의 `report_query` · 수천 건 `find_reports` · 코퍼스 집계)는 게이트웨이
  한도보다 훨씬 먼저 MCP 층에서 httpx 시간 초과로 끊기고, 그 문구에는 손잡이 이름이 없다.
- 거꾸로 한 도구가 REST 를 여러 번 부르면 한도의 합이 600초를 넘는다. `compare_reports`(:1427-1453)는 리포트마다 GET 둘(각 60초)이라 리포트
  다섯이면 최악 600초를 채운다. 그림 도구의 기다림(`_run_figure_job` :338-369)은 잠 1초만 세고 그사이 GET 의 시간은 세지 않으며(:354-359),
  `timeout_s`(기본 180 · 300 · 180 — :444 · :569 · :628)에 상한이 없다. 그래서 게이트웨이가 먼저 끊을 수 있다.
- dev 게이트웨이 감사(08-07 ~ 10-17, DynaForge 호출 913건)에서 60초 근처에서 끊긴 호출은 0건이다. 실측 사고가 아니라 cae00 의 큰 리포트에서 생길
  일을 층 규칙으로 미리 막는 것이다.

**바라는 것**
1. MCP → REST 한도를 손잡이 하나로 — 이름은 그쪽이 정한다(예 `KOORM_MCP_API_TIMEOUT_S`). 기본값은 넉넉하되 게이트웨이 600초 안쪽(예 540 —
   게이트웨이 한도와 60초 틈)으로 두고, 글자로 박힌 60 · 120 · 180 · 300 을 그 값 아래로 모은다. 업로드처럼 일부러 다른 값을 둘 곳은 그쪽이 판단한다.
2. 한 도구 호출 안에서 REST 를 여러 번 부르는 도구(`compare_reports` · 그림 도구의 기다림)는 요청마다가 아니라 **호출 하나의 벽시계 기한**
   (`time.monotonic()` 기준)을 건다 — 남은 시간만큼만 다음 요청을 기다린다. 그림 도구의 `timeout_s` 는 그 기한 안으로 죈다.
3. 걸리면 문구에 값과 손잡이 이름을 싣는다 — 예 'DynaForge 백엔드가 540초 안에 답하지 않았다(<손잡이>)'. 지금은 httpx 예외가 그대로 오른다.

### 1-2. 전처리 잡 벽시계 1800초 — 이미 손잡이다, 남은 것은 문구

**바로잡음** — 10-08 표와 triage B38 은 '설정 손잡이로' 라고 적었지만 이미 손잡이다. `KOORM_JOB_TIMEOUT_SEC`(06-17 `4310a7f` 부터) —
`platform/.env.example:19` · `platform/ENVIRONMENT.md:25` · 기동 `platform/infra/scripts/start.sh:203` · `restart-api-only.sh:43` →
`platform/backend/app/config.py:76` `job_timeout_sec` → `worker/runner_loop.py:246` · `runner/binary.py:41`. 잡은 `run_operation` 이 곧바로 job_id 를
돌려주는 비동기라 게이트웨이 600초와 겹치지 않는다 — 층 순서는 문제가 아니다.

**남은 것** — 걸렸을 때 잡의 오류가 값과 손잡이를 말하지 않는다. 지금은 stderr 에 `[timeout exceeded]` 한 줄과 종료코드 124
(`runner_loop.py:262-263` · `binary.py:44-51`)이고, 잡 요약은 `exit 124: … [timeout exceeded]`(`runner_loop.py:780`)다.

**바라는 것**
1. 시간 초과로 끝난 잡의 `error_summary` 에 '전처리 잡이 1800초 벽시계에 걸렸다(KOORM_JOB_TIMEOUT_SEC)' 꼴로 값과 손잡이를 싣는다.
2. (확인 부탁) cae00 잡 원장에서 종료코드 124 로 끝난 잡이 있었는지 — 있으면 기본값을 넉넉하게 올릴지 그쪽이 정한다(D-17 '넉넉하게'). 없으면 값은 그대로 둔다.

### 1-3. 받아들임

- 60초를 넘는 DynaForge 읽기(늦게 답하는 가짜 백엔드로 보는 시험)가 게이트웨이 한도 안에서 끝난다 — 손잡이 값 안이면 결과, 넘으면 손잡이 이름이 든 문구.
- `compare_reports` 와 그림 도구가 호출 하나의 기한을 넘기지 않는다(느린 가짜 백엔드로 리포트 여섯 비교 · 끝나지 않는 그림 잡).
- 손잡이 기본값이 게이트웨이 600초보다 작다는 시험이 그 리포에 있다.
- 시간 초과로 끝난 잡의 `error_summary` 에 값과 `KOORM_JOB_TIMEOUT_SEC` 이 있다.

### 1-4. 하지 않을 것

- 한도를 게이트웨이 600초 이상으로 두지 않는다 — 게이트웨이가 먼저 끊어 손잡이 없는 문구가 남고 REST 일은 계속 돈다.
- 끊긴 요청을 스스로 다시 보내지 않는다 — 쓰기가 두 번 나갈 수 있다(게이트웨이도 시간 초과는 다시 보내지 않는다).
- 게이트웨이 값을 올려 맞추지 않는다 — 그 값은 엔진 900 · 포털 절차 워밍업 690 · nginx `/mcp-gw/` 3600 이 감싼다(`gateway.py:184-187`).
- 오래 걸리는 일을 도구 한 번에 붙잡지 않는다 — 잡(제출 + 상태 조회)으로 간다.

## 2. HEAXHub — 인가 요청(forward_auth) 한도 · 생사 탐침

**넘기는 때** — HEAXHub 10-31 운영 전환(`docs/2026-10-31-prod-cutover/` — HH-14 ~ HH-16) 판이 cae00 에 들어간 뒤. 아래 줄 번호는 main
`beebec5` 이고, 전환 가지(`cutover/prod-1031` · `wt1031/override`)는 여기 인용한 세 파일을 바꾸지 않는다(10-31 대조).

### 2-1. forward_auth 에 짧은 연결 · 응답 한도

**지금** — 모든 `/apps/<앱>/` 요청 앞에서 Caddy 가 허브 인가(`GET /api/v1/authz` — 허브 백엔드 `127.0.0.1:4040`)를 묻는다. 그 처리기
(`backend/app/services/proxy_manager.py:48-119` `_forward_auth_handler`, 돌려주는 JSON :95-119)는 `reverse_proxy` 에 `transport` 를 주지 않아 연결 ·
응답 머리 한도가 Caddy 기본값이다(Caddy 문서상 응답 머리 기다림은 기본으로 끝이 없다 — 그쪽 Caddy 판에서 확인 부탁). 허브 백엔드가 멎으면(DB
잠금 · 스레드 고갈) 모든 앱 요청이 그 자리에서 서고, 게이트웨이를 거친 도구 호출은 600초를 다 채운 뒤 '답하지 않았다' 로만 끝난다 — 원인이 인가
단계라는 말이 없다. 같은 파일에 `transport` 를 쓰는 꼴이 이미 있다(바깥 TLS 프록시 :393-397).

**바라는 것**
1. 인가 서브요청에 연결 한도와 응답 머리 한도를 둔다 — 연결은 짧게(수 초), 응답은 넉넉하되 유한하게(예 30초 — 인가 안에서 포털 JWKS · 폐기 목록을
   받는 5초 · 3초(`backend/app/api/v1/portal_sso.py:53` · :168)보다 길고 게이트웨이 600초보다 훨씬 짧게). 값은 손잡이로.
2. 걸리면 502 · 504 와 함께 '허브 인가가 N초 안에 답하지 않았다(<손잡이>)' 가 Caddy 로그나 응답에 남는다.

### 2-2. 생사 탐침 — 한 번 놓쳤다고 앱 서버를 하나 더 띄우지 않는다

**지금** — reconcile 이 45초마다(`backend/app/workers/celery_app.py:70-72`) 앱마다 `integration_launcher.launch` 를 부른다
(`backend/app/workers/integration_tasks.py:172-175`). SIF 앱의 '이미 떠 있음' 판정(`backend/app/services/integration_launcher.py:654-662`)은 상태
파일 · 인스턴스 · pid 와 함께 **탐침 한 번**(`_is_healthy` :1751 — 주소 넷 × 2초, `_HEALTH_TIMEOUT` :92)을 요구한다. 바쁜 앱이 2초 안에 못 답하면
'이미 떠 있음' 이 아니게 되고, 인스턴스는 떠 있으니 새 인스턴스는 건너뛰지만(:758) 같은 인스턴스 안에 서버 프로세스를 하나 더 실행한다
(`apt_runner.instance_exec` :795-805). 둘째 프로세스는 포트를 못 잡고 죽더라도 그 전에 기동 코드(복구 · 이행 · 스케줄러)를 같은 데이터 디렉터리에서
돈다 — 리스크 앱은 도는 패널이 `restart` 로 닫혀 프로세스 잠금을 따로 넣었다(HWAXRisk `4a6e00b`). 코드도 이 오판을 안다(:689-692 주석 '헬스 프로브
일시 오판 → 콜드스타트 재진입').

**바라는 것**
1. 앱마다 잇단 실패 수를 센다 — 정한 수(예 3번 — reconcile 45초 × 3)를 잇달아 놓쳤을 때만 다시 띄운다. 한 번이라도 답하면 0 으로 돌린다.
2. 다시 띄울 때도 서버를 둘 두지 않는다 — 옛 프로세스(또는 인스턴스)를 먼저 내리고 띄운다. pid 가 살아 있고 포트를 쥔 동안에는 새 프로세스를
   실행하지 않는다.
3. 탐침 한도(2초)를 바쁜 앱에 맞게 넉넉하게 — 손잡이로. 본보기는 게이트웨이다 — 탐침 10초(`GATEWAY_LIVENESS_TIMEOUT`) × 잇단 2번
   (`GATEWAY_LIVENESS_STRIKES`)이 지나야 세션을 간다(`gateway.py:218-223`).

### 2-3. 받아들임

- 탐침을 한 번 놓쳐도 앱 서버가 둘이 되지 않는다 — 가짜 앱이 한 번 늦게 답하면 `instance_exec` 0회, 잇달아 정한 수만큼 놓치면 내림 1회 뒤 실행 1회
  (프로세스 하나).
- 진짜로 죽은 앱(pid 없음 · 인스턴스 없음)은 지금처럼 한 번에 다시 뜬다 — reconcile 의 회복은 그대로다.
- 인가 백엔드가 멎은 시험에서 `/apps/<앱>/` 요청이 한도 안에 502 · 504 로 끝나고 손잡이 이름이 남는다.

### 2-4. 하지 않을 것

- 운영 전환 창에 넣지 않는다(위 '넘기는 때').
- 탐침 실패 한 번으로 내리거나 새로 띄우지 않는다.
- 한도에 걸린 인가를 통과시키지 않는다 — 걸리면 막는다(닫힌 쪽).
- 게이트웨이 · 포털은 고치지 않는다.
