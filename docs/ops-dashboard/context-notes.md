# 운영 현황 — 결정 기록

**OD-1 조사(2026-11-02 KST, 읽기만) — 이용 통계는 지금 있는 원장만으로 관리자 첫 화면을 지을 수 있고, 날마다 접는 표가 있어야 기록이 남는다.**
원천은 포털 안 원장(접속 · 챗 감사 · 사용자 · 대화 · 절차/루틴 · PAT) · 게이트웨이 `audit.jsonl` · 에이전트 서버 MCP 심의 원장 · 리스크 앱 호출 원장이다.
오래 남지 않는 것 넷(챗 · 심의 토큰 · 턴 종류 · 엔진 호출의 사람 · 허브 앱 열기)과 사라지는 원천(만료 PAT 삭제 · 대화 삭제 · nginx 14일 · 검색 기록 · 호출 추적
30일) 때문에 M2 의 접기 표가 필요하다. 포털 컨테이너는 다른 서비스의 파일을 열지 못하므로 게이트웨이 · 에이전트 서버에 공유 비밀 창구를 둔다
(`/search-log` 와 같은 꼴). 사람별 줄은 관리자 그룹으로 막는다 — CAEG 가 `"*"` 를 쥐어 `feat:` 키는 사실상 모두에게 열린다.

**OD-2 조사(같은 날) — LLM 서버 상태는 지금 읽히고, GPU 잡 · 하드웨어는 접근 확인 · 다른 팀 승인이 먼저다.** vLLM 0.23.0 의 `/metrics` · `/health` · `/version` 은
API 키가 지키지 않는다(키는 `/v1` 아래만). cae00 의 묶음 nginx(Qwen 18700 · GLM 18800)는 아무 한 대로 보내므로 서버 · 복제본마다 직접 묻는다. Slurm 잡 표는
사람 없는 `ssh stcx` 가 되는지가 먼저고(미확인 — 받은 편지함 Q8), SmartTwinMCP 의 Slurm ssh 별칭은 문서끼리 가리키는 곳이 어긋나 재사용하지 않는다.
GPU 사용률 · 온도 · 전력은 어느 리포도 읽지 않는다 — stcx 는 노드 관리자, GLM 은 운영 팀의 승인을 사용자를 거쳐 받는다. 수집기는 포털 백엔드가 아니라 호스트
쪽 작은 서비스다(`portal.sif` 에 ssh 가 없고, 에이전트 서버는 심의 중 재기동이 미뤄진다).

**OD-3 근거 없는 수치는 계획에 옮기지 않는다.** 토큰 절감 설계안 v1.0 의 'GLM 서버당 동시 34건에 1건당 201 tok/s' · '학습과 겹치면 6 tok/s' 는 리포 어디에도 근거가
없었다. 근거가 있는 값은 GLM 요청당 약 116 tok/s(`docs/chat-depth-context/request.md:100`) · Qwen 복제본 하나가 동시 8 에 779 · 32 에 1,212 tok/s
(`docs/chat-llm-stcx/server-setup.md:264-265`)다. GLM 의 지금 모델 · 창도 문서끼리 다르다(10-20 '20만' · 10-22 두 서버가 300K · 1M) — 화면은 늘 살아 있는 값을 읽는다.

**OD-4 사용자 결정(2026-11-02 KST) — 합계도 관리자만 · LLM/GPU 는 호스트 수집기.** 이용 통계는 사람별 줄과 합계 모두 관리자 화면에만 둔다(나중에 넓힐 수 있다).

나머지 기본값(사람별 집계 400일 · k = 5 · 사람별 LLM 토큰은 M3 에서 다시 묻는다 · 허브 앱 열기는 HEAXHub 세션 몫)은 계획서 권장 그대로 두고, 바꿀 일이 생기면 묻는다.

**OD-13 라우터 해석기는 고치지 않고 넓힌 해석기를 따로 둔다(2026-11-02 KST, M1).** 라우터의 `parse_metrics` 는 지문(services.yaml `fp: infra/llm-router`)에

**OD-15 켜는 줄은 하나(`LLM_STATUS`) — 수집기와 화면이 함께 켜진다.** update-all 5d 가 매니페스트 `if_env: LLM_STATUS` 로 수집기를 띄우고, start.sh 가
같은 줄을 보고 포털에 `LLM_STATUS_URL=http://127.0.0.1:<LLM_STATUS_PORT>` 를 넘긴다(포털 설정 `llm_status_url`, 기본 빈 값). backend/.env 에 주소를
따로 적게 하면 두 줄이 어긋난다 — 포트를 바꾸면 화면만 502 가 되고, 끈 박스의 화면이 '안 닿는다' 로 잘못 말한다. 그래서 포털 창구는 둘을 가른다 —
주소가 없으면 503 '수집기가 꺼져 있다'(무엇을 켜면 되는지), 주소가 있는데 닿지 않거나 답이 수집기 꼴이 아니면 502 '수집기가 답하지 않는다'.
infra/.env 가 바뀌면 포털 지문이 바뀌어 같은 update-all 의 §2 가 포털을 다시 띄운다(그때 주소가 든다).

**OD-16 지문은 수집기 파일 · 띄우는 스크립트뿐이다(`fp_git: false` + `fp: [infra/llm-status, infra/scripts/llm-status.sh]`).** 포털 HEAD 를 넣으면 문서
커밋 하나에도 수집기가 다시 떠서 창(60초 · 5분)이 비고 몇 분 빈칸이 생긴다. infra/.env 도 넣지 않는다 — 수집기가 주기마다 파일의 mtime · 크기 · inode 를
견주어 바뀌었으면 다시 읽는다(대상 · 키를 바꿔도 다시 띄우지 않는다 — 라우터와 같다). 바이트코드는 지문이 보지 않고(`_fp_noise`), 띄우는 스크립트는
`python3 -B` 로 남기지도 않는다.

**OD-17 대상마다 스레드 하나 — 앞 읽기가 끝나지 않으면 그 주기는 건너뛴다.** 15초마다 `/health` · `/version` · `/metrics`, 60초마다 `/v1/models`. 연결 3초 ·
읽기 5초(머리부터 몸까지의 기한 — http.client 는 서버가 닫는 답이면 `conn.sock` 을 비우므로 소켓을 따로 쥐고, 몸을 다 읽으면 소켓이 닫혀 그 뒤
settimeout 이 EBADF 라 `isclosed()` 로 멈춘다 — 손 점검에서 둘 다 실제로 터졌다). `/health` 가 닿지 않거나(거부 · 연결 시간 초과 · 이름 · TLS) 매달리면
나머지를 묻지 않는다 — 걸린 서버 하나가 제 스레드에서 몇십 초를 쓰지 않게. 걸린 대상은 주기를 쌓지 않고 건너뛰고(`skipped`), 스냅숏은 잠금 없이 곧바로
답한다(읽기 동안 잠금을 쥐지 않는다). 주기 · 기한은 코드 값이다 — GLM 운영 팀(받은 편지함 Q12 1번)이 더 길게를 요구하면 그때 손잡이를 더한다.

**OD-18 키 — `/v1/models` 에만, 주소로 고른다.** `CHAT_LLM_BASE_URL` 과 같은 호스트:포트와 복제본은 `CHAT_LLM_API_KEY`, 나머지는 `LLM_API_KEY`. 401 이어도
다른 키로 다시 해 보지 않는다 — 한 서버의 키를 다른 서버에 보내지 않는다. 키는 명령줄 · 환경으로 받지 않고(수집기는 `env -i` + `python3 -I` — 띄운
셸의 비밀 · 프록시가 딸려 들어가지 않고, M3 의 ssh 자식도 물려받을 것이 없다) 두 겹으로 가린다 — 원격에서 받은 글은 받는 자리(`scrub` — 주소는 호스트:포트로,
Bearer · 키는 `<가림>`)에서, 답 · 로그는 내기 직전(`dumps` · `log`)에. 주소는 늘 호스트:포트만 낸다 — 설정이 틀린 칸의 까닭에도 원문 대신 호스트만.

**OD-19 저장 — 대상 종류마다 쌓는 지표를 고른다.** (series, raw, rollup) 세 표 · `WITHOUT ROWID` · 지우기는 대상 · 지표마다 기본 키 앞부분으로(ts 색인을
두지 않는다). 주 서버 14 · 복제본 6 · 에이전트 7 · 라우터 2 지표 — cae00 의 대상 13 개(GLM 둘 · Qwen 묶음 · 복제본 열)면 약 110 계열, 표본 48시간 ·
5분 칸 35일로 수십 MB 다. 5분 칸은 끝나고 60초 뒤에 접는다(늦게 끝난 읽기가 들어올 틈). 24시간 그래프의 끝(아직 안 접은 칸)은 표본을 같은 폭으로 묶어
잇는다. 값이 없던 때는 줄이 없다(채워 넣지 않는다 — 화면이 선을 끊는다).

**OD-20 속도 · 분위수의 창.** 카운터는 이웃한 표본 쌍의 차로 잰다 — 줄어든 쌍(서버 재기동)은 빈칸이고, 리셋 뒤 값을 0 부터의 증가로 치지도 않는다(음수 ·
부풀림 없음). 사이가 주기 넷(60초)보다 벌어진 쌍도 평균으로 치지 않는다. 그래프에 쌓는 토큰 속도는 마지막 쌍 하나로(리셋이면 그 표본은 빈칸), 카드의 지금
값은 60초 창의 쓸 수 있는 쌍으로 잰다. p50 · p95 · 오류 · 끊김 · 선점 · 앞부분 캐시 적중은 5분 창의 증가로 잰다(서버가 뜬 뒤의 누적으로 재면 몇 시간 전의
느린 요청이 지금 값을 끌어올린다) — 분위수는 칸 안 선형 보간 어림이라 `approx` 표지를 달고 화면이 ≈ 를 붙인다. 라벨 카운터(끝난 까닭 · HTTP 5xx)는
패밀리가 있는데 그 라벨 줄이 아직 없으면 0(한 번도 없었다)이고 패밀리가 없으면 '모름' 이다. 오류는 HTTP 5xx 와 끝난 까닭 error 를 더한 것이다.

**OD-21 값은 모두 `{value, at, source, error, stale, age_s}` — 설정된 대상은 숨기지 않는다.** at 은 마지막으로 제대로 읽은 때, error 는 마지막 시도가
실패한 까닭(또는 값이 없는 까닭 — '요청 없음(5분)' 등). 주기 셋을 놓치면 stale(지표 45초 · 모델 목록 180초) — 마지막 값은 남기고 표지만 단다. 설정이 틀린
칸(꼴 · 이름 · 주소 · 겹침 · 32개 상한)도 대상으로 남아 모든 값이 `모름 — <까닭>` 이다. 같은 모델의 창이 서버마다 다르면(섞인 풀 · rolling 중의 복제본)
`context_mismatch` 와 위 `context` 칸이 그 짝을 낸다. 대상 이름은 영숫자 · . _ - 40자 — 그래프 주소(`?target=`)에 쓴다.

**OD-22 Slurm · GPU 는 자리만 둔다(M3 · M4).** 스냅숏의 `slurm` · `gpu` 칸은 `모름 — <무엇이 필요한가>` 와 `milestone` 이다(Q8 — 사람 없는 `ssh stcx` ·
Q11 · Q12 — 승인). 원천이 생기면 같은 꼴(주기 · 보기)로 갈아 끼운다. 복제본의 포트 → 노드 짝 파일은 Q7 답 전까지 가정한 꼴(줄 · JSON)로 읽고, 다르면
`read_replica_map` 하나만 고친다 — 못 읽으면 복제본은 포트로만 돌고 머리에 까닭이 뜬다.

**OD-23 화면 — 관리자만 · 인라인 SVG.** `GET /auth/admin/llm-status` · `/series` 는 `require_role(ADMIN_GROUP)` 이다 — CAEG 는 `"*"` 로 모든 `feat:` 키를
쥐므로 기능 키로는 막히지 않는다(OD-1 · OD-4). 포털은 수집기 답을 그대로 넘기고(꼴 확인만) 저장하지 않는다. 그래프는 차트 라이브러리 없이 인라인 SVG ·
토큰 CSS(관리 화면은 인라인 style 이 린트 오류다 · hex 래칫 그대로 90) — 카드(복제본 · 설정 문제 대상 빼고)마다 도는/기다리는 요청의 1시간(1분마다) ·
24시간(5분마다), 화면이 보이는 동안만 받는다. 모름 · 내려감의 까닭은 풍선 도움말이 아니라 글로 보인다.

**OD-24 시험 격리 · 띄우는 길 둘.** conftest 가 `LLM_STATUS_STATE_DIR` · `LLM_STATUS_ENV_FILE` 을 임시 자리로, `LLM_STATUS_URL` 을 빈 값으로 둔다 —
수집기 시험이 이 박스의 `infra/.state/llm-status` 에 쌓거나 실제 infra/.env 의 키로 실 LLM 서버를 부르거나, 포털 시험이 떠 있는 수집기를 부르지 않게.
test_suite_isolation 은 수집기의 기본 자리를 **열기 전에** 보고 연 파일을 sqlite 에 묻는다. 띄우는 길은 둘이다 — services.py · update-sites 는
`llm-status.sh run`(앞에서 · services.py 가 떼어 띄운다), 사람 손은 `start`(nohup + disown — `( … & )` 서브셸이면 호출자가 자식 수명만큼 매달린다 — 시험이
걸린 시간을 단언한다). 정지는 그 포트를 LISTEN 하는 pid 의 명령줄이 `…/infra/llm-status/collector.py serve` 일 때만(docs/gotchas.md §1).

**OD-25 update-all 5d 가 5c 뒤에 끼면서 호출 추적 시험의 구획 끝을 옮겼다.** `test_call_trace.py` 는 update-all 을 '5c 머리 ~ §6 머리' 로 잘라 돌렸는데,
그 사이에 5d 가 들어 5c 시험이 5d 의 `services.sh enabled llm-status` 까지 부르게 됐다. 구획 끝을 5d 머리로 옮겼다(그 시험의 뜻은 그대로다).

**OD-26 속도 · 분위수는 같은 서버 프로세스의 표본끼리만 잰다(반대 검토 11-02 — MEDIUM, 묶음 주소에서 서로 다른 서버의 누적 차가 속도로 잡혔다).**
OD-2 의 묶음 nginx(18700 · 18800)는 요청마다 아무 한 대로 보내고 수집기는 요청마다 연결을 닫으므로 이웃한 두 표본이 다른 서버의 것일 수 있다 —
한 대 초당 100 토큰이 96,766 · 128,989 로 찍히고 그 값이 저장됐다(재현 `lb_rates.py`). `/metrics` 표본마다 `process_start_time_seconds` 를 서버
프로세스의 표지로 단다 — prometheus_client 기본 레지스트리의 ProcessCollector 줄이고(같은 프로세스는 늘 같은 값 · 다시 뜨면 바뀐다), vLLM 0.23.0 은
API 서버가 하나면 그 레지스트리를 쓴다(`get_prometheus_registry`). 마지막 표본과 표지가 같은 표본만으로 잰다 — 이어지지 않아도 된다(그 사이에 다른
서버가 답했으면 건너 이웃으로 친다). 재기동은 표지가 바뀌어 저절로 끊긴다 — OD-20 의 '줄어든 쌍만 빼고 앞의 쌍으로 잰다' 대신 새 프로세스의 표본이
둘 쌓일 때까지 빈칸이다(카드가 앞 프로세스의 숫자를 보이지 않는다). 표지가 없는 서버(api_server_count > 1 — 다중 프로세스 레지스트리에는 그 줄이
없다)는 종전대로 이웃한 표본으로 재되, 창 안에서 카운터 · 라벨 카운터 · 히스토그램이 하나라도 줄면 그 창(카드 60초 · 5분)의 값을 모두 비우고 그동안
저장도 하지 않는다 — 줄어든 쌍만 빼면 작은 누적에서 큰 누적으로 넘어간 쌍이 속도로 남는다. 늘기만 한 첫 넘어감은 표지 없이 가려낼 수 없다(그 한
표본은 남는다 — 시험이 그 한계를 적어 둔다). 어느 길로 쟀는지는 창 셈 값의 `source`(`metrics/process_start_time_seconds` · `metrics/counters_only`)
와 비운 까닭(`… process_start_time_seconds 가 없어 …`)이 말한다. 주기 넷(60초)보다 벌어진 쌍을 치지 않는 OD-20 규칙은 그대로라, 뒤에 서버가 많은
묶음 주소는 대개 '모름' 이다 — 서버마다 보려면 `LLM_STATUS_TARGETS`(server-setup.md 1절). 가짜 vLLM 은 그 줄을 prometheus_client 0.25.0 이 가짜 /proc
로 낸 글과 같은 꼴(`floatToGoString`)로 내고, 시험이 그 실제 글을 담아 대조한다. 버린 것 — 묶음 대상의 속도를 아예 내지 않기(둘 묶음이면 한 대의 값이
쓸모 있고 대상 종류를 따로 적게 해야 한다), `*_created` 를 표지로(라벨 묶음마다 따로 있고 처음 쓰일 때 생겨 표지 하나로 쓰기 어렵다), 사이가 벌어진
같은 표지 쌍을 받아 주기(카드의 '지난 60초' 가 몇 분의 평균이 된다).

**OD-27 계열 번호 캐시는 COMMIT 된 줄만 남긴다(반대 검토 11-02 — LOW-MED).** `_sid()` 가 새 계열의 번호를 COMMIT 전에 캐시에 넣어, 그 쓰기가
되돌려지면(디스크 가득 · I/O 오류) series 줄은 사라지고 번호만 남았다 — 다음 새 계열이 같은 번호를 받아 두 계열이 한 번호를 나눠 쓰고, raw 의 기본
키가 (번호, 초)라 같은 초의 값을 서로 덮었다(재현 `store_rollback.py` — glm-1/running 과 chat/kv 가 같은 점). 이번 쓰기가 만든 계열을 따로 적어
두고(`_fresh`) COMMIT 하면 비우고, 되돌리면 그 열쇠만 캐시에서 지운다 — 다음 쓰기가 다시 INSERT · SELECT 로 제 번호를 받는다. 버린 것 — 되돌릴 때
캐시 전체를 비우거나 DB 에서 다시 읽기(비우면 다음 쓰기 전까지 그래프 · 접기가 계열을 못 보고, 다시 읽기는 I/O 오류가 난 그 DB 를 또 읽는다).

**OD-28 꺼진 5d 는 /health 의 몸으로 수집기를 알아본다(반대 검토 11-02 — LOW).** 꺼진 박스의 5d 는 그 포트가 200 을 내면 `llm-status.sh stop` 을
불렀다 — 그 포트에서 남의 앱이 200 을 내면 stop 이 명령줄을 보고 건드리지 않는 것은 맞지만, update-all 마다 5d 머리 · '✗ … 수집기가 아니다' ·
'⚠ 내리지 못했다'(WARN_ITEMS)가 남아 §0 의 '○ 한 줄' 약속이 깨졌다. 수집기 `/health` 에 `"service":"hwax-llm-status"` 를 싣고, 새 `llm-status.sh probe`
가 그 몸을 글자 그대로 찾을 때만 0 을 낸다(curl `--noproxy '*'` · 3초, 상태 코드는 보지 않는다 — 멈춘 수집기는 503 이어도 내린다). 5d 는 probe 가 0 일
때만 머리를 찍고 stop 을 부른다 — 남의 앱이면 ○ 한 줄뿐이다(시험은 진짜 llm-status.sh 와 진짜 http_code 로 — 고치기 전 판에서 머리 · ✗ · ⚠ 가 나는 것을
본다). PORT-MAP 의 8760 확인은 dev 와 형제 리포뿐이었다 — cae00 은 켜기 전에 사람이 `ss -ltnpH 'sport = :8760'` 로 본다(server-setup.md 2절).
버린 것 — 5d 안에서 curl 로 몸을 받아 보기(포트 · 표지를 아는 곳이 llm-status.sh 다 · 5d 시험 대역이 http_code 하나만 갈아 끼운다).

**OD-29 재기동 생략 · start 의 '이미 떠 있다' 는 명령줄로 수집기인지 본 뒤에만(반대 검토 11-02 — LOW).** services.py `health_ok` 는 상태 코드만 보고
(몸을 보는 손잡이가 없다) update-sites 는 `services.sh status` 의 '✓ up' 을 믿는다. 켰다 끈 뒤 지문 기록(`infra/.state/restart-fp/sites/llm-status`)이
남은 박스에서 남의 앱이 그 포트를 쥐고 200 을 내면 다시 켤 때 '재기동 생략 · ✓ up' 과 5d 의 'OK' 로 끝났다(기록이 없으면 이미 크게 실패했다).
`llm-status.sh start` 도 듣는 것이 있기만 하면 '이미 듣는 프로세스가 있다' 로 0 을 냈다. stop 의 명령줄 판정(인자 하나가 `…/infra/llm-status/collector.py`
로 끝나고 바로 뒤가 serve)을 함수 하나(`_owned` — 0 수집기 · 1 남 · 2 ss 로 모름 · 3 아무도 없음)로 떼어 stop · start · 새 `check` 가 함께 쓴다 —
start 는 남이면 띄우지 않고 1, ss 를 못 쓰면 종전대로 띄운다. update-sites 의 생략 조건에 llm-status 만 `llm-status.sh check` 를 더했다 — 아니면 생략하지
않고 재기동 길로 가서 stop 이 남을 건드리지 않고(✗) 같은 리스너가 답해 '✗ 재기동이 되지 않았다' 로 실패한다. 다른 서비스의 조건은 글자 그대로다
(시험이 llm-router 로 본다). stop 의 문구 · 종료코드는 그대로다. 버린 것 — services.py 에 몸 검사 손잡이(`expect_body` 같은 것)를 더하기(모든 서비스의
판정 길을 건드린다 — 지시가 몸 검사가 없으면 명령줄로 하라고 정했다), 매니페스트에 `verify:` 같은 일반 고리(쓰는 곳이 하나다 — update-sites 에는 이미
서비스 이름으로 가르는 자리가 여럿이다).

**OD-30 오류는 둘로 따로 낸다 — HTTP 5xx 답 · 오류로 끝난 요청(반대 검토 11-02 — LOW).** `errors_per_min` 은 `http_requests_total{status="5xx"}` 와
`vllm:request_success_total{finished_reason="error"}` 를 더했다(OD-20). vLLM 0.23.0 의 `FinishReason.ERROR` 는 '언제나 500 으로 바뀐다' 가 약속이다
(`vllm/v1/engine/__init__.py` — 이미지 소스에서 확인, 살아 있는 서버로는 재현하지 않았다) — 스트리밍이 아닌 요청 하나가 둘에 함께 들어 두 번 세졌다.
스트리밍은 200 을 보낸 뒤 스트림 안에서 끝나 5xx 에 들지 않는다. 그래서 더한 값은 무엇을 세는지 말할 수 없다 — `http_5xx_per_min` · `finished_error_per_min`
으로 나눠 둘 다 쌓고(주 서버 지표 14 → 15) 카드에 'HTTP 5xx 답' · '오류로 끝난 요청' 으로 따로 보인다. 겹칠 수 있다는 것은 server-setup.md 5절에 적었다.
버린 것 — 한쪽만 내기(5xx 는 라우터 · nginx 쪽 실패와 맞대 보는 수이고, 오류로 끝남은 스트리밍 오류를 세는 유일한 칸이다), 겹친 몫을 빼기(지표만으로는 한
요청이 둘 다인지 알 수 없다).

**OD-31 읽기 기한은 머리부터 몸까지 하나다 — 지나면 타이머가 소켓을 닫는다(반대 검토 11-02 — LOW).** `fetch` 는 기한을 `resp.read(65536)` 사이에서만
쟀다 — `read` 하나와 `getresponse()` 의 머리 읽기는 1바이트 recv 를 이어 붙이므로, 바이트를 조금씩 흘리는 서버(recv 마다는 소켓 시간 초과 안)는 끝없이
붙들었다(재현 `drip.py` — 몸 · 머리 둘 다 20초에도 그대로). 그 대상 스레드만 붙들리지만(바쁨 → 낡음) docstring 의 '읽기 5초 — 머리부터 몸까지' 와 어긋났다.
연결 뒤 `_Deadline`(threading.Timer)을 걸어 기한이 지나면 `sock.shutdown(SHUT_RDWR)` 로 막힌 recv 를 깨우고, 기한 뒤에 http.client 가 낸 것(잘린 머리
· 몸 · 끊김 · 잘린 몸을 '다 읽음' 으로 끝낸 것까지)은 모두 읽기 시간 초과다 — 마지막 경우를 위해 예외가 없어도 `fired` 를 본다. with 를 나오면 잠금으로
더는 손대지 않는다(끝난 연결의 소켓을 닫지 않는다). recv 하나의 상한(`settimeout(read_s)`)은 뒷받침으로 둔다. 시험은 0.2초마다 한 바이트를 흘리는 서버로
몸 · 머리 둘 다 기한 1초에 2.5초 안에 읽기 시간 초과인지 본다(붙들려도 시험은 6초 뒤 실패로 끝난다). 버린 것 — 덩이 크기를 줄여 사이마다 재기(머리
읽기는 여전히 막힌다), select 로 직접 읽기(http.client 의 머리 · 덩이 해석을 다시 써야 한다).

**OD-32 읽기 스레드를 못 띄우면 그 대상만 까닭을 남기고 주기는 이어진다(반대 검토 11-02 — LOW).** `_kick` 이 바쁨을 세운 뒤 `Thread.start()` 를
불러, 한 번의 `RuntimeError("can't start new thread")` 로 그 대상이 영영 바쁨으로 남고(0 회 · 건너뜀만 쌓인다 — `/health` 는 200 그대로) 예외가 그 주기의
뒤 대상 · 정리까지 끊었다(재현 `thread_fail.py`). 띄우기를 잡아 바쁨을 풀고 그 대상의 원천에 '수집기 오류 — 읽기 스레드를 띄우지 못했다(…)' 를 남기고
로그 한 줄 — 나머지 대상과 정리는 그대로 돈다, 다음 주기가 다시 띄워 본다. 원천에 까닭을 다는 몫은 `_run` 의 예외 길과 같은 함수(`_fail_sources`)다.
`once`(손 점검)의 스레드는 그대로 둔다 — 한 번 돌고 끝나는 길이라 예외가 그대로 보이는 편이 낫다.

**OD-33 키는 그 키의 주소에만 — 루프백 별칭은 같은 주소다(반대 검토 11-02 — LOW, OD-18 을 좁힌다).** 키를 주소 글자 그대로(`a == chat`) 골라
`CHAT_LLM_BASE_URL=http://127.0.0.1:P` 인 챗 LLM 을 `LLM_STATUS_TARGETS` 에 `localhost:P` 로 적으면 `LLM_API_KEY` 가 그 서버로 갔고(재현 `key_alias.py` —
401), 보기만 하려고 더한 GLM 아닌 vLLM 에도 `LLM_API_KEY` 가 갔다 — server-setup.md 의 '키를 다른 서버에 보내지 않는다' 와 어긋났다. 이제
`LLM_API_KEY` 는 `LLM_BASE_URL` · `LLM_UPSTREAMS` 의 서버에만, `CHAT_LLM_API_KEY` 는 `CHAT_LLM_BASE_URL` 과 복제본에만 싣고 그 밖의 주소에는 아무 키도
싣지 않는다 — 그 서버가 키를 물으면 까닭이 '이 주소에는 키를 싣지 않는다' 다. 같은 주소는 스킴 · 포트가 같고 호스트가 같거나 둘 다 루프백 별칭
(`localhost` · `127.0.0.1` · `::1`)일 때다(`same_server`). 대가 — 서버별 GLM 주소를 `LLM_STATUS_TARGETS` 에만 적고 `LLM_UPSTREAMS` 에 없는 박스는 그
서버의 모델 목록 · 창을 못 읽는다(상태 · 지표는 키 없이 읽힌다 — server-setup.md 2 · 3절). 버린 것 — 대상마다 키 이름을 적는 손잡이(쓸 곳이 생기면
더한다), 이름 풀이로 같은 서버를 알아보기(DNS 를 묻게 되고 루프백 밖의 별칭은 지시 범위 밖이다).

**OD-34 벽시계가 뛰어도 그래프 · 모델 목록 주기가 서지 않는다(반대 검토 11-02 — LOW).** 셋이 벽시계에 기대어 섰다(재현 `clock_jump.py`). ① 접은 끝
표지(`rolled_until`) — 시계가 앞으로 뛰었다 바로잡히면 표지가 앞날에 남아 지금이 따라잡을 때까지 5분 칸을 접지 않았다(24시간 · 7일 · 35일 그래프에
바로잡힌 뒤의 칸이 없다). 표지가 지금보다 앞이면 지금 앞의 마지막 접은 칸(계열마다 기본 키 앞부분으로 찾는다)부터 다시 접는다 — 그 칸은 표본으로
다시 셈해 같은 값이고(INSERT OR REPLACE), 지금 앞에 접은 칸이 없으면(뒤로 간 경우) 처음처럼 가장 이른 표본부터다. ② 정리 간격(`_last_maint`) — 시계가
뒤로 가면 지난 정리 시각이 앞날이라 300초 간격 검사가 그때까지 막았다 — 시계가 거꾸로 갔으면 곧바로 돈다. ③ 모델 목록 주기 — '마지막으로 물은 때'
를 벽시계로 재서 시계가 뒤로 가면 `/v1/models` 를 그만큼 묻지 않았다 — monotonic(`Collector(mono=…)` — 시험이 끼운다)으로 잰다. 시험은 저장소에서
앞으로 뛰었다 돌아온 경우 · 뒤로 간 경우(힘주지 않은 maintain 으로) 둘 다, 수집기에서 벽시계가 뒤 · 앞으로 뛸 때 모델 목록 주기를 본다.
남는 것 — 뛴 동안 앞날 시각으로 적힌 표본 · 칸은 지우지 않는다(지금 시계가 틀린 쪽일 수 있다 — 그 시각이 48시간 · 35일을 지나면 지워진다). 그동안
1시간 그래프 끝 너머와 24시간 그래프의 마지막 점이 그 앞날 칸일 수 있다(화면의 그래프 밖으로 잘린다).

**OD-35 시험의 빈 포트는 다른 주소의 리스너도 피한다(시험만).** 고치는 도중 `test_start_는_뒤에서_띄우고_곧바로_돌아온다` 가 한 번 '리스너가 있는데 pid 가
안 보인다' 로 끝났다 — `_free_port()` 는 127.0.0.1 에 비어 있는 번호를 주는데, dev 에 다른 계정의 `[::]:38643`(IPv6 만 — 127.0.0.1 바인드와 겹치지 않는다)
리스너가 있었고 띄우는 스크립트의 `ss -ltnpH "sport = :P"` 는 주소와 상관없이 그 번호를 본다. 고치기 전 start 도 같은 번호면 '이미 듣는 프로세스가 있다'
로 실패했다(전부터 있던 흔들림 — 이번에 처음 걸렸다). 두 시험 파일의 `_free_port` 가 고른 번호를 `ss -ltnH` 로 한 번 더 보고, 어느 주소에든 리스너가
있으면 다시 고른다. 스크립트의 판정은 그대로 둔다 — stop 과 같은 판정이어야 하고(OD-29), cae00 은 켜기 전에 같은 식(`ss -ltnpH 'sport = :8760'`)으로 그
번호를 비워 두기 때문이다(server-setup.md 2절). 그 번호를 다른 주소에서 남이 쥐면 stop · start · check 가 '남이다' 로 크게 실패한다 — 조용히 넘어가지 않는다.

**OD-36 에이전트 서버는 제 읽기 기한(12초)으로 읽고, 늦으면 내려감이 아니라 모름이다(반대 검토 11-02 — LOW).** 에이전트 서버 `/health` 는 창을 아직 못
물었으면 그 자리에서 LLM 의 `/models` 를 묻는다 — LLM 이 안 닿으면 `_ask_context` 의 httpx `timeout=5.0` 만큼(연결 · 읽기 각각) 걸리고 60초마다
되풀이한다(`../HWAXAgentServer/app.py` `_model_context_tokens` · `_ask_context` — 소스로 확인, 살아 있는 서버로는 재현하지 않았다). 수집기 기한이 같은
5초라 LLM 이 죽은 바로 그때 '지금 쓰는 일' 이 내려감(0 저장)으로 찍혔다(기한을 줄인 시험으로 재현). 에이전트 서버만 `AGENT_READ_S = 12.0`(5초 둘에 여유)
으로 읽고, 늦으면 `up` 이 모름(None — '늦음 — /health 가 12초 안에 답하지 않았다(…)')이며 저장하지 않는다. 내려감(False · 0 저장)은 연결 거부 · 오류
상태(200 이 아닌 답)일 때만이다 — 그 밖의 실패(연결 시간 초과 · 끊김 · JSON 이 아닌 200 등)도 모름이다. 주기(15초)보다 짧아 앞 읽기가 다음 주기를 막지
않는다(막으면 건너뛴다 — OD-17). 라우터는 그대로 5초다(제 `/health` 가 LLM 을 묻지 않는다).

**OD-37 대상 이름 agent · router 는 받지 않는다(반대 검토 11-02 — LOW).** 둘은 에이전트 서버 · 라우터의 대상 id 다 — `LLM_STATUS_TARGETS` 에 그 이름의 vLLM
을 받으면 저장의 계열 열쇠(예 `("agent", "up")`)가 에이전트 서버의 것과 겹쳐 서로 덮고, `/series` 의 대상 표가 그 대상의 종류를 에이전트로 덮어썼다.
이름 꼴이 틀린 칸과 같은 길로 받지 않는다 — `item-<칸>` 대상으로 남기고 모든 값이 '모름 — … 수집기가 쓰는 이름이다(agent · router)' 다(설정된 대상은
숨기지 않는다 — OD-21). 글자 그대로만 막는다 — 대상 id 는 대소문자를 가리므로 `Agent` 는 겹치지 않는다.

**OD-38 켠 박스의 죽은 수집기는 감시가 다시 띄운다(`watch: true` — 반대 검토 11-02 INFO).** 감시 크론(`services.sh heal` — `HWAX_WATCHDOG=1` 인 박스만)은
`watch: true` 항목만 보는데 llm-status 에 없어, 죽은 수집기는 다음 update-all 까지 내려가 있었다(상태판을 켰을 때만 알린다). `cmd_heal` 은 항목마다
`enabled_here` 를 먼저 보고 그것이 `if_env` 를 따른다 — 그래서 `watch: true` 를 더해도 끈 박스(`LLM_STATUS` 없음)에서는 그 포트가 죽어 있어도 띄우지
않는다(꺼진 것은 꺼진 채로). 시험이 진짜 매니페스트 항목 · 진짜 `enabled_here` 로 끈 박스는 손대지 않고 켠 박스는 down · up 하는지 본다. 감시 대상
목록 시험에 llm-status 를 더했다. 켠 박스에서 손으로 내려 두면(`llm-status.sh stop`) 감시가 1분 안팎에 다시 띄운다 — 다른 감시 대상과 같다(오래 내려
두려면 `LLM_STATUS` 줄을 지운다).
