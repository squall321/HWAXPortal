## 2. 문제와 원인

### P1. 챗 답이 가볍다 — 생각을 끄고 보낸다

- 에이전트 서버는 챗 요청마다 `chat_template_kwargs: {"enable_thinking": false}`를 붙인다(`CHAT_LLM_ENABLE_THINKING` 기본 0).
- 모델 자체는 아무것도 지정하지 않으면 **생각을 켜고 강도는 최고(`xhigh`)**로 돈다. 모델 채팅 템플릿에 `reasoning_effort|default('xhigh')`라고 되어 있다. 고를 수 있는 값은 `xhigh` · `medium` · `low`다.
- 그래서 서버(vLLM) 쪽은 바꿀 것이 없다. **포털이 끄라고 보내는 값을 거두면 된다.**

### P2. 챗이 앞에서 조회한 내용을 잊는다 — 이력에 조회 결과가 없다

이력은 세 군데를 거치는데, 세 군데 모두 "역할 + 글" 두 칸만 다룬다.

1. 화면 `frontend/src/components/chat/history.ts` `buildHistory()`: 메시지마다 **표시 글(`m.text`)만** 보낸다. 도구 단계(`steps`)에는 조회 결과 전문(`result_full`)이 남아 있는데 버린다.
2. 포털 백엔드 `backend/app/agent/routes.py` `ChatHistoryMessage`: `role` · `content` 두 칸뿐이다.
3. 에이전트 서버 `app.py` `_history_messages()`: user · assistant 글만 싣는다. 예산을 넘는 오래된 턴은 앞부분 발췌로 압축한다(`_compact_turns`).

결과적으로 다음 턴의 모델은 앞 턴에서 **무엇을 조회했고 어떤 값이 나왔는지 모른다.** 앞 답이 생각 없이 짧게 요약한 글이면(P1), 남는 맥락이 더 얇다. 사용자가 "아까 그 값"을 물으면 다시 조회하거나 지어낸다.

### P3. 띵킹이 앞 대화를 싣지 않는다 — 설계상 의도

`thinking.py` `run_thinking()`의 주석이다.

> 앞선 대화는 좌석에 싣지 않는다(좌석은 질문 하나로 자기판정한다).

화면에는 "띵킹은 질문만 좌석에 준다 — 앞선 대화 N건은 싣지 않는다"는 한 줄만 나온다. 사용자가 기대하는 흐름은 다르다. 챗에서 플랫폼들을 파헤친 뒤 띵킹을 켜면, **그 조회 내용이 좌석(전문가)에게 주입되고 전문가가 그 위에서 의견을 내는 것**이다. 지금은 전문가가 질문 한 줄만 보고 각자 처음부터 검색한다.

### P4. 생각을 켜면 생기는 일 — 오래 걸리고, 가끔 끝없이 길어진다 (실측)

같은 질문(낙하 해석 시나리오 선택, 한국어 약 150자)을 Qwen 1벌에 보냈다. 2026-10-18, 다른 요청은 거의 없었다(30분 22건).

| 생각 설정 | 걸린 시간 | 생각 토큰 | 답 길이 |
|---|---|---|---|
| 끔 (포털 현재값) | 10.9초 | 0 | 4,285자 |
| `medium` | 16.6초 | 691 | 4,789자 |
| `xhigh` (모델 기본) | **102.2초** | **13,052** | **23,183자** |
| `xhigh` 같은 질문 다른 회차 | **12분 넘게 안 끝남**(중단) | — | — |

- `xhigh`는 답이 5배 넘게 길고 깊다. 대신 한 번 호출이 1~2분이다. 챗은 ReAct라서 도구를 부를 때마다 한 번씩 더 생각한다. 그래서 도구 3~4번이면 한 턴이 수 분이다.
- **생각이 끝없이 길어지는 회차가 있다.** 포털은 출력 상한(`max_tokens`)을 보내지 않는다(app.py 주석: "운영은 max_tokens 를 안 보내"). → **10-18에 stcx 서버 쪽 상한 131,072토큰으로 막았다(0장).** 폭주한 회차는 약 11~13분에 상한에서 끊기고, 포털이 `output_cut` 경고를 낸다.
- 챗 서버는 스트리밍으로 돈다(`/health` `streaming: true`). 그런데 챗 루프는 `chunk.content`만 화면에 내보내고, 생각 토큰(`reasoning_content`)은 내보내지 않는다. 그래서 생각 1~2분 동안 화면에는 글이 안 나오고 도구 단계 표시만 움직인다.

### P6. 심의가 오래 걸린다 — GLM이 호출마다 길게 생각한다 (실측, 챗 설정과 무관)

심의는 `delib_llm`(GLM-5.2, 호출 1회 1800초 · 재시도 1회 · effort 미전달)으로 돈다. 챗의 Qwen 설정과는 경로가 다르다. GLM 서버의 `/metrics` 누적값을 봤다. 10-05 기동 이후 요청 21,236건이고, 포털이 GLM에 보낸 요청 전체다(심의만이 아니다).

| 항목 | 요청당 평균 |
|---|---|
| 전체 시간 | **114초** |
| 대기열 대기 | 1.4초 |
| 생성(디코드) | 111.7초 |
| 생성 토큰 | **13,008** (대부분 생각) |
| 입력 토큰 | 56,598 |

- 120초를 넘는 호출이 30%이고, 가장 긴 것은 약 16분이다. 선점(preemption)은 0건이고, 거의 다 정상 종료(`stop`)다.
- **붐벼서 느린 게 아니다**(대기 1.4초). GLM이 호출마다 1.3만 토큰을 생각하며 쓰는 데 시간이 든다(요청당 약 116 tok/s).
- 심의는 라운드가 순차다. 그래서 라운드마다 **가장 느린 좌석 하나**가 그 라운드 시간을 정한다. 좌석이 20석을 넘으면 꼬리(10분대) 좌석을 만날 확률이 높아진다.
- 줄이는 손잡이(선택, 품질과 맞바꿈): `DELIB_REASONING_EFFORT`(GLM 생각 강도, 지금 미전달 = 모델 기본), 좌석 수 상한, 라운드 수(`rounds`). 또는 좌석 본심을 Qwen 10벌에 나눠 돌린다(M3). 어느 쪽이든 같은 화두로 품질을 비교한 뒤 정한다.

### P5. 포털 경로 `/stcx-llm/`의 60초 제한 (별건, 이미 보고)

`gen-nginx-conf.sh` `loc_extras()`에 `stcx-llm` 갈래가 없어서, 포털 밖에서 이 경로로 비스트리밍 요청을 보내면 60초에 504가 난다(실측 60.1초). 생각을 켠 요청은 거의 다 60초를 넘는다. 에이전트 서버는 `127.0.0.1:18700`을 직접 부르므로 이 제한을 받지 않는다. 고칠 내용(패치)은 「stcx GPU LLM 사용 가이드 v1.2」 6장에 있다.

### 맥락 유지 — 기능 수정 (포털 + 에이전트 서버)

**M1. 챗 이력에 "조회 근거"를 싣는다 (P2)**

- 화면 `buildHistory()`: 어시스턴트 메시지의 도구 단계(`steps`)에서 `tool` · `call` · `result_full`(없으면 `result_preview`)을 모아 **별도 칸** `evidence`로 보낸다. 글(`content`)에 섞지 않는다.
- 포털 `ChatHistoryMessage`: `evidence: str | None` 칸을 더한다. 기존 화면과 호환되고, 합계 상한(`_history_total`)에 함께 센다.
- 에이전트 서버 `_history_messages()`: 근거에 **따로 몫**(예: `HIST_EVIDENCE_SHARE`)을 주고, 그 턴의 답 바로 앞에 `[이 턴에서 조회한 근거 — 도구 · 인자 · 결과 발췌]` 블록으로 싣는다. 예산이 모자라면 **오래된 근거부터** 줄인다. 결론 글보다 원자료를 먼저 버린다. 압축(`_compact_turns`)에는 도구 이름과 record_id만 남긴다.
- 효과: "아까 조회한 그 값"에 다시 조회하지 않고 답한다. Qwen 창은 262,144토큰이라 조회 결과 수십 건을 싣고도 여유가 있다(CL-D5가 두 서버 중 작은 창을 쓴다 — GLM으로 넘길 때도 안전).

**M2. 띵킹에 세션 맥락을 주입한다 (P3)**

- `run_thinking()`이 이미 `history`를 받는다. 지금은 세기만 하고 버린다. 이것을 쓴다.
  1. **세션 맥락 블록**: 앞 대화 요지(`_compact_turns` 방식)에 M1의 조회 근거를 더한다. 예산은 좌석 지식카드 몫과 따로 잡는다(예: `THINK_SESSION_SHARE`).
  2. **본심(좌석 답변) 프롬프트에만** 싣는다. **예심(`recommend_agents` · `agent_search`) 검색어에는 싣지 않는다.** 검색어가 길어지면 전문가 발굴이 망가진다 — 붙인 문서를 질문에 섞지 않는 현재 규칙과 같은 이유다.
  3. 소집 검색어는 질문에 **대화 화두**(`_derive_topic(history)`, 심의가 이미 쓰는 함수)를 더한다. 그러면 "그럼 이건 어때?" 같은 짧은 후속 질문에도 맞는 전문가가 소집된다.
  4. 좌석 프롬프트에 규칙을 한 줄 넣는다: "세션 근거는 앞 대화에서 조회된 사실이다. 그 위에서 판단하되, 자기 근거와 다르면 다르다고 말하라."
  5. 손잡이 `THINK_WITH_HISTORY`(기본 1). 화면 상태 줄도 바꾼다: "앞선 대화 N건 · 조회 근거 M건을 좌석에 실었다".
- 효과: 챗에서 파헤친 플랫폼 내용 위에서 전문가가 의견을 낸다. 사용자가 기대하는 흐름이다.

**M3. (선택) 띵킹 모델 손잡이**

- `THINK_LLM=base|chat`(기본 `base` = GLM, 10-17 결정 ①을 유지한다). `chat`으로 두면 좌석 본심을 Qwen 10벌에 `xhigh`로 돌린다. 심의가 GLM을 차지해 띵킹 좌석이 600초에 빠지는 문제(thinking.py `SEAT_TIMEOUT_S` 주석)도 피한다.
- 품질은 GLM 쪽이 낫다고 보고 ①을 정했다. 그래서 바꿀 때는 같은 질문으로 비교한 뒤에 정한다.

## 4. 적용 순서와 확인

1. **S1**(적용 완료) — 다음은 **C1**: 강도 손잡이를 넣고 재시작한다. 기동 줄과 `/health`로 생각 켬 · effort를 확인한다.
2. 같은 대화로 전후를 비교한다. 1턴에서 플랫폼 2~3곳을 조회하고, 2턴에서 1턴의 수치를 되묻는 질문을 한다. 확인할 것은 셋이다.
   - 2턴 답이 1턴 수치를 다시 조회 없이 인용하는가 (M1 후)
   - 한 턴이 몇 분 걸리는가
   - GLM 넘김 횟수(`/health` `chat_llm.fallback.count`)
3. **C2**: 생각 진행 표시를 넣는다.
4. **M1 → M2** 순서로 넣는다. M2는 M1의 근거 칸을 그대로 쓴다.
5. P5(포털 경로 60초)는 별도 커밋으로 넣는다.
