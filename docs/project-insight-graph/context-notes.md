# 과제 인사이트 그래프 — 결정 기록

**PG-1 조사(2026-11-02 KST, 읽기만) — 제안은 맞고 리스크 심사 몫은 반쯤 있다. 빠진 것은 심의 쪽이다.** 저장소 여덟(리스크 앱 · RA 지식층 · MX 백서 위키 ·
AIDataHub · StepForge · DynaForge · SP 허브 · ODB 허브)을 견줬다. 리스크 앱 원장의 등록부 클러스터가 이미 '과제 · 설계 판 · 부품에 묶인 인사이트' 이고
(`../HWAXRisk/backend/app/risk_store.py:365-383`), 선례 · 비슷한 과제 · 주장 역색인이 다른 과제의 앞선 판정을 시야 교집합으로 다시 쓴다. 일반 심의는 주제를
구조로 적지 않는다 — `deliberate_start` · 포털 심의 시작 · 잡 원장 · RA 보고서 · 위키 원천 어디에도 과제 · 설계 자료 칸이 없다. 근거 줄은 PLAN 머리의 판이다.
에이전트 서버 줄은 조사 때의 `9f08507` 이 아니라 `aadd591`(11-02 토큰 절감 병합 뒤)로 다시 맞췄다.

**PG-2 입력 조사에서 바로잡은 것 둘과 대조해 맞은 것.** 서브에이전트 조사(스크래치 패드의 kg-*.md)는 모델 출력이라 쓰기 전에 줄을 대조했다.

- MX 백서 `subject_hints` 는 원천 봉투의 **맨 위 칸**이다(`../MXWhitePaper/apps/api/app/wiki/envelope.py:314-325`) — 'DeliberationBody 에 칸이 없어 심의
  원천은 주제를 못 싣는다' 가 아니다. 문서 고르기도 종류와 무관하게 힌트를 읽는다(`…/wiki/resolve.py:264-284`). 그래서 엔진이 봉투에 힌트를 더하면 MX 백서를
  고치지 않고 과제 문서가 고쳐질 수 있다 — 그래도 들이기 LLM 이 문서를 고치는 일이라 그 세션에 먼저 묻는다(PLAN §10).
- MCP 심의 잡 원장은 11-02(`aadd591`)부터 표결(tally · unanimous · votes) · 보고서 주소 · 숫자 대조를 남긴다(`../HWAXAgentServer/delib_jobs.py:1220-1233`) —
  '원장이 표결을 버린다' 는 그 앞 판의 사실이다. 여전히 버리는 것은 진행 일지(도구 · 인자)다(`:422-431` · `:1352`).
- 그 밖의 핵심 주장(RA 엔티티 시야 없음 · 근거 보고서 제목 · `create_object` 가 고치지 않고 돌려줌 · AIDataHub 인증 꺼짐과 `tags` 를 받지 않는 검색 ·
  DynaForge 개정 보기 · 루틴 키 규칙 · D-18 의 엔진 집행 · RK-01 의 보내는 꼴)은 줄을 대조해 맞았다.

**PG-3 그래프는 보는 꼴이고 저장은 열쇠 달린 원장이다.** 묻는 말이 '이 과제 주변' 이라 그래프로 보이는 것이 맞지만, 첫 값어치에 그래프 DB 가 필요하지 않다 —
주제(SP 키 · 설계 자료 열쇠) → 인사이트 → 근거 참조의 칸이 있으면 읽을 때 합쳐 그래프 꼴로 보인다. 다중 관계 탐색은 RA 가 이미 설계한 자리이고(M5), 그
전에 짓는 것은 원장 하나와 읽기다. 인사이트 한 줄은 '출처 하나가 한 주제에 대해 낸 주장 하나 + 근거 참조' 이고, 생산자마다 꼴이 다르다 — 리스크는 등록부
클러스터(이미 있다), 일반 심의는 결정 카드(새로), 루틴은 단계 발견(나중). 근거 참조는 리스크 설계의 문법(`docs/design-risk-review/plan.md:184-212`)을 그대로
쓰고 새 접두는 둘만 더한다(`delib:` · `call:`).

**PG-4 주제는 시작에 사람이 고르고, 끝의 짐작은 후보만이며, SP 키는 서버가 스스로 부른 풀이의 결과 행에서만 받는다.** 시작에 고른 주제가 정본이다 — 후보는
그 사람의 도구 결과(StepForge 과제 · ODB `find_job` · DynaForge 리포트 · SP 과제 찾기)에서 오고, 리스크 앱의 보드 붙이기와 같이 후보에 실제로 있을 때만
적는다(`../HWAXRisk/backend/app/routes.py:2200-2213`). 끝에 코드가 성공한 호출에서 찾은 열쇠는 사람이 확인하기 전에는 과제에 잇지 않는다 — 좌석이 고른
인자에 든 id 는 '그 심의가 닿았다' 의 증거일 뿐 '그 심의의 주제다' 의 증거가 아니다. SP 키는 루틴 키 규칙의 **원칙**(모델 글 · 받은 인자에서 온 값은 근거가
아니다 — `backend/app/procedures/routine_routes.py:584` · `:599`)만 가져오고 그 **글자 대조**는 쓰지 않는다(반대 검토 5 · 6 — PG-13). 웹은 포털이 풀이를 부르고
사람이 고른 행의 `key` 칸, MCP 는 엔진이 시작 때 같은 풀이로 다시 찾아 key 가 글자 그대로 같은 행이 하나일 때만 확인(아니면 '주장' 으로 두고 잇지 않는다),
기구 CAD 는 StepForge `get_project_meta` 의 `plm_task`(받는 앱의 한 판정 `match_task` — `../StepForge/core/sp_core.py:1159-1182`)다. 허브 key 의 꼴은 가정하지
않는다(`docs/procedures/app-project-keys.md:44-46`). A13 (A) 가 '(C) 포털 새 레지스트리' 를 고르지 않았으므로 포털은 과제 목록을 쥐지 않고 SP 키를 칸으로만
든다(`docs/leftovers-1017/triage-1031.md:113`).

**PG-5 자리 — 생산자 원장이 정본이고 일반 심의 인사이트만 포털 원장 하나에 둔다(권장, 사용자 결정 기다림 — PLAN §11-2).** 리스크 행은 베끼지 않는다 — 리스크
설계의 원칙 'ID 권위는 앱 DB 다'(`docs/design-risk-review/plan.md:2271`)이고, 베끼면 시야 · 낡음 · 거두기가 두 벌이 된다. 과제별 보기는 읽을 때 그 사람
신원으로 리스크 앱에 묻는다. 리스크 러너 패널도 포털 중계를 지나는 웹 심의이므로(`../HWAXRisk/backend/app/engine_client.py:33-38` · `runner.py:847-869`) 들이기는
리스크 심사가 낳은 심의(의장 risk-review · risk-review-sealed, `started_by=app`)를 뺀다 — 빼지 않으면 리스크 판정이 포털 원장에 베껴지고(버린 (마) 안) 그
원장을 거쳐 같은 과제 좌석에 돌아간다. 심의 몫을 포털에 두는 까닭 — 사람 · 소속 원장과 권한 정책(요청마다 다시 센다 — `backend/app/access/policy.py:5-6`),
웹 심의가 끝나는 중계 저장, 포털이 원장을 쥐고 게이트웨이가 사람 PAT 만 넘기는 루틴 도구 꼴(`../HWAXMcpGateway/gateway.py:4819-4825` · `:4939-4948`)이 다
포털에 있다. 에이전트 서버에 두면 웹 심의(메모리에만 있다)와 사람 확인 화면이 따로 놀고, RA 에 두면 시야가 없어 조직 공개분만 쌓이며, SP 허브 · 위키는
cae00 에서 지금 쓸 수 없거나 다른 팀이 먼저다. 새 저장소 파일보다 이미 등록 · 백업되는 포털 저장소 안의 표를 먼저 본다 — 새 경로를 더하면 시험 격리도 함께다.

**PG-6 시야 — MX 백서의 범위 꼴 · 최소 범위 규칙을 그대로 쓰고 읽을 때 원장을 쥔 쪽이 거른다(기본값은 사용자 결정 기다림 — PLAN §11-1).** 토큰 넷
(`user:` · `aff:` · `plat:` · `org`)의 그리고, 범위는 근거들의 토큰을 다 담는다, 서로 다른 `aff:` · `user:` 가 섞이면 넓히지 못한다, 넓히기는 사람만 ·
`plat:` 빼기는 관리자만(`../MXWhitePaper/docs/llm-wiki/CONTRACTS.md:184-185` · `:189-190`). 새로 짓지 않고 가져온 까닭 — 같은 사람들이 같은 소속 원장으로 두
곳을 보게 되므로 규칙이 다르면 한쪽이 샌다. **한 칸 다르게 둔 자리** — 범위를 모르는 근거(남의 RA 보고서 · 남의 리포트)가 있으면 MX 백서 그대로라면 넓히지
못하지만, 여기서는 주인이 자기 소속까지는 넓힐 수 있게 했다. 같은 심의의 결정문이 MCP 잡 원장에서 이미 같은 소속에 보이는 선(FU-D17 —
`../HWAXAgentServer/delib_jobs.py:959-974`)이라 새 노출이 아니기 때문이다. `org` 는 근거 범위가 다 알려졌을 때만이다. 게이트웨이 도구는 사람 PAT 로만
돈다 — 심의 잡 원장은 신원 없는 호출에 다 보이는데(`delib_jobs.py:965-966`) 새 원장은 그 길을 따르지 않는다. 수 · 잇기 · 표지는 거른 뒤에 센다(넓은 쪽은
좁은 쪽이 있다는 것도 말하지 않는다 — `CONTRACTS.md:193-195`). 권장 기본값 '초안은 주인만 · 확인하면 같은 소속' 의 까닭은 둘이다 — 사람 손 없이 넓히지
않는다, 그리고 에이전트 서버가 머리로 온 신원을 믿어(`../HWAXAgentServer/start.sh:36-40`) MCP 에서 들인 주인 · 소속은 주장일 뿐이다.

**PG-7 D-18 은 범위 그대로 두고 새 길을 열지 않는다 — 지금 닿는 길은 솔직히 적는다(사용자 결정 기다림 — PLAN §11-3).** D-18 은 '좌석은 같은 과제의
등록부(앞 패널의 판정)를 도구로 보지 못한다' 이고 까닭은 '앞 판정을 읽고 따라 말하면 지지 수가 독립 근거 없이 오른다' 다
(`docs/risk-review-redesign/context-notes.md:117-118`). 처음 초안은 '리스크 좌석은 같은 과제의 앞선 인사이트를 보지 않는다' 고 적었는데 지금도 사실이 아니다
— 같은 과제의 일반 심의 결론은 보고서 검색(엔진은 리스크 러너 머리가 든 제목만 가린다 — `deliberation.py:1100-1105`) · 호출자 근거(의장과 무관하게 실린다 —
`:6491-6498`) · 리스크 심사로 바꾼 이어하기(앞 결정문이 요약으로 — `../HWAXAgentServer/mcp_server.py:926`)로 닿는다. D-18 의 글에는 어긋나지 않으므로 고치지
않고 적어 두고, 넓힐지 · 뒤집을지를 사용자에게 묻는다. 이 계획이 새로 여는 길은 막는다 — 도구 이름 `insight_`(좌석 자유 조회의 접두 `list_` · `get_` ·
`search_` · `find_` 에 안 걸린다 — `deliberation.py:3872`) · 거절 목록(`_RISK_PRIOR_TOOLS` — `:987`)에도 넣기 · 리스크 심사에는 깔지 않기 · 엔진 받침(의장이
risk-review 면 `insight_*` 근거를 뺀다) · M1 은 주제를 RA 보고서에 적지 않기. Claude 워크플로 좌석은 막지 못한다(PLAN §12-4).

**PG-8 엔진은 포털을 사람 대신 읽지 않는다 — 웹은 포털이 깔고 MCP 는 호출자가 넘긴다.** 심의 시작에 앞선 인사이트를 깔 때 엔진이 포털 원장을 읽으려면 잡
주인의 신원을 엔진이 포털에 주장하는 새 신뢰 길이 필요하다. MCP 잡의 엔진은 사람 PAT 가 없고 게이트웨이 비밀 + 사람 머리로 부르며(토큰 절감 TS-1), 루틴
도구는 그 길을 막는다(`gateway.py:4945-4947`). 웹은 포털이 그 사람을 알아 `delib_opts.evidence` 에 넣으면 되고, MCP 는 개인 Claude 가 `insight_find` 로
받아 `deliberate_start(evidence=…)` 로 넘기면 된다 — 지금 챗 → 심의 넘기기와 같은 길이다. 깔기는 새 심의의 산출물(잡 원장 · RA 보고서 · 위키 원천)을 읽을
사람이 모두 볼 수 있는 인사이트만이다(반대 검토 4 — PG-13). 새 신뢰 길은 쓸모가 보인 뒤 따로 검토한다.

**PG-9 MCP 잡은 포털이 에이전트 서버의 공유 비밀 창구로 읽어 들인다(엔진이 밀지 않는다).** MCP 심의는 포털을 지나지 않으므로 들일 길이 따로 있어야 한다.
읽어 오는 꼴을 고른 까닭 — 어느 쪽이 내려가 있어도 다음 읽기에 따라잡고(포털은 갱신마다 다시 뜨고, 에이전트 서버는 심의가 돌면 재기동이 미뤄진다), 같은
꼴의 창구가 이미 있다 — `/seat-questions` 는 게이트웨이 공유 비밀을 요구하고 '질문 원문을 내므로 루프백만 믿지 않는다'(`../HWAXAgentServer/app.py:9271-9282`).
에이전트 서버는 루프백에 뜨고 앞에 인증이 없어(`start.sh:36-40`) `/drain` 같은 창구는 그 경계에만 기댄다(`app.py:9118-9126`). **남는 믿음** — 잡의 주인 ·
소속은 엔진이 머리로 받은 값이고 루프백에 닿는 프로세스는 그 머리를 지어낼 수 있다(박스 안 프로세스를 믿는 지금의 경계 그대로다). 그래서 MCP 에서 들인 카드는
주인이 포털에 로그인해 확인하기 전까지 그 주인만 보는 초안이다. 주인이 빈 잡은 들이지 않는다.

**PG-10 심의 인사이트는 결정 카드를 단마다 코드로 짓는다(권장, 사용자 결정 기다림 — PLAN §11-4).** 주장은 결정문의 '■ 핵심 요약' 불릿(엔진이 이미 짓는
3 ~ 5줄 — 결론 · 핵심 근거 · 소수 의견, `../HWAXAgentServer/deliberation.py:7436-7449`)에서 자르고, 없으면 쉬운 설명의 결론 줄, 둘 다 없으면 비운다. 결정문
머리를 자르지 않는 까닭 — 코드가 찍는 표지(외부 응답자 · 봉인 · 기준일)가 맨 위에 오고(`:7450-7459`), 요약이 실패하면 머리는 제목 · 근거 프로파일 줄이다(반대
검토 14). 카드는 엔진이 단마다 짓는다 — 위키 원천을 짓는 자리가 단마다 돌고(원천 열쇠 `delib:<잡>:<틀>` — `:3638`), 잡 원장 · 중계는 단마다 `decision` 을
덮어쓴다(`delib_jobs.py:1211-1212` · `backend/app/agent/routes.py:3058-3059`). 이어하기는 새 잡 id 를 내므로(`mcp_server.py:971-975`) 앞 카드를 `continues`
로 잇는다. 새 LLM 호출이 없다. 의장에게 기계판독 인사이트 목록을 더 내게 하면(risk_spec 꼴) 모든 심의의 의장 지시문 · 출력이 바뀌고 품질을 따로 재야 한다.

**PG-11 M1 은 주제 달기 하나다 — 그것만으로 값어치가 서는 가장 작은 걸음이다.** 주제 칸 하나가 뒤 단계 전부(원장 · 다시 쓰기 · 낡음 · 투영)의 열쇠이고,

⑤ 화면의 깔기 미리보기 · 끄기 단추는 짓지 않았다 — 깔기는 저절로 돈다(끄는 길은 주제를 달지 않는 것뿐이다).

**PG-43 시험 · 변이(11-21 ~ 22).** 시험을 먼저 세웠다(엔진 받침 · 워크플로 받침 · 범위 이어받기 · 읽기 창구는 붉음 → 초록, 깔기의 단위 규칙은 코드와
함께 쓰고 변이로 붉어지는 것을 봤다). 고친 곳을 되돌리는 변이 서른여덟(에이전트 서버 다섯 · 포털 깔기와 이어받기 열일곱 · 읽을 때 셈 열넷 ·
워크플로 둘)을 시험이 모두 잡는다 — 처음엔 다섯이 살아남아 시험을 더했다(초안을 깐다 · 거둔 근거의 범위를 이어받는다 · 범위 밖 공유 카드를 같은
결론에 센다 · 보이지 않는 key 로 이력을 부른다 · 찾기 도구에 적힌 id 를 읽은 카드로 친다 — 앞의 넷은 다른 겹(SQL 의 창 · 범위 토큰)이 가려 주던
것이라, 그 겹 없이도 지는 시험을 세웠다). '종전과 바이트까지' 는 깔기를 통째로 뺀 중계가 보내는 요청과 견준다(주제 없음 · 챗 · 과제 없는 주제 ·
주장 · 다른 key 로 확인 · 확인 창구 불통 · 볼 수 있는 카드 없음 · 리스크 심사 계열 · 권한 없음 · 다른 소속 · 깔기 실패 · 기한 넘김).

## 11-22 — 사용자 결정 하나와 반대 검토(높음 0 · 중간 5 · 낮음 9)의 고침(PG-44 ~ PG-52)

본 세션이 통합 가지에 한 번 합친 뒤 반대 검토를 돌렸다. 지적은 가설로 받아 코드에서 다시 확인했다 — 중간 다섯 · 낮음 여덟(L1 ~ L8 과 낮음 4)이 모두
맞았다. L9(일반 잡을 risk-review 로 잇는 `deliberate_continue` 의 `continue_summary` · 웹 리스크 심사의 챗 맥락)는 이 가지 밖이고 D-18 은 사용자
결정으로 지금 그대로라 건드리지 않았다. 고친 판 — 에이전트 서버 `c05104c` · 게이트웨이 `5c13082` · `2ea4eff` · 포털 `29a11d8e` · `fbb78b5a` ·
`b31bdef7` · `4b20ea0f` · `6cf535d2`. 꼴은 [contracts.md](contracts.md) §10 이 정본이다.

**PG-44 사용자 결정(2026-11-22 · `docs/leftovers-1121` L21-17 ③) — 부서 작업 공간은 소속 안으로 본다.** PG-36 의 '부서 · 조직 작업 공간은 조직으로
친다' 와 PG-42 ① 을 **사용자 결정으로 뒤집었다**. 깔기의 독자 판정(`reuse.output_audience`)에서 새 보고서가 갈 RA 작업 공간이 부서인 경우와 RA
위임(SSO) 박스의 기본 부서를 「같은 소속」 독자로 보고 소속 범위 카드도 깐다. 조직 · 시스템 작업 공간은 종전대로 조직이고, 개인 작업 공간 · 보고서
저장 안 함도 종전대로다. `plat:` 토큰이 붙은 카드의 규칙은 바꾸지 않았다(그 플랫폼 권한이 독자에게 있는지 모르면 깔지 않는다). **감수한 것 — RA
부서 구성이 포털 소속과 어긋난 사람은 소속 범위 인사이트의 요약을 보고서에서 볼 수 있다.**
- **내가 읽은 것(구현 판단 — 틀렸으면 고친다).** RA 의 작업 공간 종류(`WorkspaceKind`)는 `org`(조직도의 본부 · 팀 — 이름이 org 지만 이것이 부서다) ·
  `personal` · `tf` · `system` · `virtual` 이다. 결정의 '부서' 는 `org`, '조직 · 시스템 작업 공간' 은 `tf`(부서를 가로질러 뽑은 사람들) · `system`(조직
  단위 게시판) · `virtual`(모아 보기)로 읽었다. 종류를 모르는 공간(옛 RA · 멤버십에 없는 슬러그) · RA 에 못 물은 때도 조직이다.
- **있는 보고서에 덧붙이기(`append_to_report_id`)는 조직 그대로 뒀다.** 그 보고서가 어느 공간에 있는지는 RA 를 한 번 더 읽어야 안다 — 결정의 범위
  (새 보고서가 저장될 공간) 밖이라 짓지 않았다. 웹 이어하기는 같은 대화의 카드를 어차피 깔지 않는다.
- **어느 공간인가.** 등록한 토큰으로 부르는 박스는 그 사람이 '외부 연결' 에 저장한 공간(게이트웨이가 `X-Workspace-Slug` 로 싣는다), 비었으면 RA 가
  고르는 기본 공간이다. 위임 박스(`RA_SSO_SECRET`)는 게이트웨이가 부서 머리를 떼고 불러(`strip_headers`) 엔진의 보고서가 RA 의 기본 공간(홈 부서 →
  첫 조직 멤버십 → 개인 공간 — RA `shared/auth.py` `_default_workspace_for_token`)으로 간다. 그런데 포털이 직접 부르는 저장(PPT 가져오기 등)은 위임
  박스에서도 남아 있는 저장 공간을 싣는다(일부러 둔 것 — `docs/change-request-8-10` D-7). 그래서 위임 박스는 **둘 다** 보고 하나라도 부서 · 개인이
  아니면 조직으로 친다. 위임 여부는 그 요청이 위임 토큰을 받았는지가 아니라 박스 설정(`RA_SSO_SECRET`)으로 본다 — 포털의 위임만 잠깐 실패해도
  게이트웨이는 기본 공간으로 쓴다.
- **RA 의 기본 공간은 `/api/me` 만으로 다 알 수 없다.** 그 답에는 멤버십의 차례 · 보관 여부가 없다. 홈 부서가 멤버십에 있으면 그 종류, 홈이 없으면
  개인 · 가상 밖의 멤버십이 하나도 없을 때 개인, 전부 부서일 때 부서로 읽고, 부서와 TF 가 섞였거나 홈이 멤버십에 없으면 모른다(조직).
- **가짜를 진짜 꼴로 고쳤다.** 처음 세운 RA 대역은 `/api/me` 가 `workspace_slug` 로 기본 공간을 준다고 꾸몄다. 진짜 RA 는 그 칸에 **받은 부서 머리**를
  되돌릴 뿐이라 머리 없이 물으면 비어 온다 — 그대로였으면 위임 박스에서는 늘 '모름 → 조직' 으로 떨어져 결정이 먹지 않고, 시험은 초록이었다. 대역을
  RA `get_me` 의 꼴로 바꾸고, 기본 공간의 차례와 답의 칸을 RA 소스(이 박스의 사본 v0.186.3 `b552f09`)와 견주는 시험을 뒀다(형제 리포가 없으면 건너뛴다).
- **남는 것.** 깔기에 RA 호출 하나(`/api/me` · 8초)가 더해진다 — 보고서를 새로 저장하는 심의이고 확인된 주제에 볼 수 있는 카드가 있을 때만이다.
  포털과 게이트웨이의 위임 설정이 어긋난 박스(한쪽만 재기동)는 따로 보지 않았다(둘 다 같은 `infra/.env` 줄에서 온다). cae00 에서 볼 것 — 부서
  공간인 사람에게 소속 범위 카드가 깔리는가, 위임 박스의 `/api/me` 가 `home_workspace_slug` 를 주는가.

**PG-45 M1 — 퍼지는 자리에는 판정 낱말만.** 맞았다. 판 표지의 `say` 는 '(뒤 판 A2)' 를, `items[].next` 는 뒤 판의 CAD 과제 id 를, `risk_diffs` 는 리스크
과제 코드 · 이름 · 변경 줄을 싣는다 — 읽는 사람의 StepForge · 리스크 앱 권한으로 읽은 것이다. 그것이 ① 깐 근거의 '판' 줄(→ 새 심의의 산출물 · 다음
카드의 근거)과 ② 사람 PAT 의 읽기(게이트웨이 `insight_get` · `insight_find` 의 답 → 호출자가 근거로 넘긴다)로 나갔고, 그 답을 근거로 쓴 카드의 범위는
`insight_get` 의 앱(`_gateway`)만 보아 그 플랫폼 토큰이 없다. 두 자리에는 `lineage.public` — `{state, say}`(뒤 판이 있다 · 내용이 바뀌었다 · 모름 —
이름 · id · 변경 줄 없이) — 만 낸다. PAT 의 읽기는 리스크 변경 심사를 부르지도 않는다. 자세한 것은 포털 화면(세션)의 그 사람에게만이다. 가르는
기준은 `Authorization: Bearer` 머리다(`principal_pat_or_session` 과 같은 순서 — 머리가 있으면 쿠키가 있어도 PAT 로 본다). 게이트웨이 `insight_get` 의
설명이 `risk_diffs` 를 약속하던 것도 고쳤다(`2ea4eff`). 통합 판에서 절차 실행의 단계 기록이 `insight_get` 단계를 같은 표지 꼴로 근거 앞에 싣는다는
것은 알고만 둔다(이어받기 셈은 넓히지 않았다) — 이 고침으로 그 길로 퍼지는 양도 준다.

**PG-46 M2 — 봉인 · 기준일.** 맞았다(`subject_key` 가 `sealed` · `as_of` 를 보지 않았다). 봉인 심의는 호출자가 준 자료만으로 도는 심의라 깔기의 대상이
아니다 — 확인도 부르지 않고 요청이 바이트까지 같다. 기준일이 있으면 생긴 때(`created_at`)나 주장을 고친 때(`claim_edited_at`)가 그 날의 끝(KST)보다
뒤인 카드를 빼고 수(`after_as_of`)를 알린다. 못 읽는 기준일이면 전부 뺀다(닫힌 쪽 — 포털의 `DelibOpts` 가 꼴을 먼저 거르므로 오지 않는 값이다). 확인한
때(`confirmed_at`)는 보지 않는다 — 주장이 그 날에 있었으면 그 날의 지식이다. 그 날 뒤에 달린 반박 메모는 싣지 않는다(상태 줄은 오늘의 상태다).

**PG-47 M3 · 낮음 4 — 인사이트 근거 판정을 한 규칙으로.** 맞았다. 엔진 받침의 옛 규칙(`(?:^|__|[.:/])insight_`)은 `hwax-insight_get` · `hwax insight_get` ·
`hwax_insight_get` · `(insight_get)` 을 놓쳤고, 범용 실행기(`invoke_tool` — `args.name` 이 `insight_get`)는 도구 이름이 인사이트가 아니라 지나갔다. 또
엔진은 `strip` · `lower`(유니코드 공백 · 접기), 워크플로는 `trim` · `toLowerCase` 라 머리에 BOM · `\x1c` 가 붙은 이름에서 답이 갈렸다. 한 규칙으로
바꿨다 — `insight_` 앞이 영숫자가 아니면 인사이트다(ASCII 로만 대소문자를 접고, 다듬거나 소문자로 바꾸지 않는다). 껍데기면 인자 글의 `"name"` 값
전부에 같은 규칙을 건다(어느 깊이든 — `arguments` 안의 `name` 칸에 그런 값이 있어도 인사이트로 친다. 닫힌 쪽이다). 넓힌 값 — `get_insight_summary`
같은 이름도 인사이트로 친다: 리스크 심사에서는 빠지고, 일반 심의에서는 그 카드의 확인이 주인만으로 떨어진다. 지금 게이트웨이 목록에 그런 이름의 다른
도구가 있는지는 확인하지 않았다(cae00 `tools/list` 로 본다). 엔진의 근거 표지는 껍데기를 벗겨 안쪽 도구 · 인자로 적는다 — 벗겨야 확인이 읽은 카드를
안다. 같은 입력표를 엔진(소스에서 그 함수만 떼어) · 포털 · 워크플로(스텁 런타임)에 돌려 같은 답인지 포털 시험이 맞댄다.

**PG-48 M4 · M5 — 워크플로 대화.** 둘 다 맞았다. (M4) 깔기가 '이 대화의 앞 카드' 를 웹 길(`path=web`)에서만 뺐다 — 워크플로 대화를 웹에서 이어가면
그 대화의 카드(`ins:wf:<대화 id>`)가 깔렸다. `mcp-workflow` 도 `source_id` 가 그 대화면 뺀다(MCP 잡의 `source_id` 는 잡 id 라 견주지 않는다).
(M5) 워크플로 카드는 `calls` · `tools` 가 비어 앞선 인사이트를 근거로 썼어도 확인하면 제 범위로 열렸다. 대화 저장에 읽은 카드 id 를 싣는 쪽을
골랐다 — **주제 안의 `insights`** 로(카드 id 목록 60개까지 또는 `"unknown"`). 주제 안에 둔 까닭 — 따로 칸이면 옛 게이트웨이 · 옛 포털이 그 칸만
버리고 주제는 넘겨, 카드는 서는데 이어받기가 없는 열린 쪽이 된다. 주제 안이면 모르는 쪽이 주제를 통째로 버려 카드가 없다(닫힌 쪽). 포털은 그 칸을
떼어 표지 꼴로 적고(주제 확인에는 넘기지 않는다) 그 뒤는 다른 카드와 같은 길이다.
- **사용자가 정할 것 — 옛 워크플로 사본.** 그 칸을 싣지 않는 옛 사본(PC 에 받아 둔 것)으로 인사이트 근거를 넘긴 심의의 카드는 종전대로 소속에
  열린다(포털은 근거에 인사이트가 있었는지 알 길이 없다). (가) 그대로 — 사본은 `update-all` 의 `sync-workflows` · 리포 받기로 따라온다(지금).
  (나) 칸이 없는 워크플로 카드는 확인해도 주인만 — 새 사본은 늘 `insights: []` 를 싣게 한다. 옛 사본의 워크플로 카드가 전부 공유되지 않고, 새
  사본이 옛 게이트웨이를 만나면 모든 주제가 버려진다.
- 좌석이 워크플로 안에서 스스로 부른 도구(인사이트 포함)는 종전대로 모른다 — 워크플로 좌석은 도구 목록 없이 도는 에이전트다. 그래서 워크플로
  카드는 조직 공개가 닫혀 있다(PG-28 의 `apps_unknown = ["(workflow)"]`).

**PG-49 L1 · L2 — 읽은 카드를 '다 안다' 는 것.** 맞았다. (L1) 도구 이름(`tools`)에 표지 없는 `insight_find` 가 있어도 `insight_get` 표지만 보고 다
안다고 했다 — 이름에 든 인사이트 도구가 다 표지로 덮일 때만 안다. (L2-가) 실패한 표지(`ok` 가 참이 아님)도 읽은 카드로 셌다 — 읽었다는 증거가
아니라 모름이다. 엔진의 `ok` 는 결과 글의 성패(`_delib_tool_result_ok`)이고 포털이 깐 항목의 글은 통과한다. (L2-나) 확인이 읽은 카드를 시야 없이
(`st.get`) 읽어, 표지에 남의 카드 id 를 적으면 그 카드의 범위 토큰(내게 없는 `plat:` 포함)이 내 카드에 찍혔다 — 있는지 · 범위가 무엇인지의
오라클이다. 읽은 카드를 확인하는 사람의 시야로(관리자 표지 없이) 보고, 안 보이는 것이 하나라도 있으면 주인만이다. 검토는 '까닭 글 없이' 를 권했는데
**경우를 가르지 않는 한 글**을 달았다 — 글이 아예 없으면 주인이 왜 주인만인지 알 수 없다. 없는 id · 남의 초안 · 거둔 카드 · 범위 밖이 같은 글이라
오라클이 아니다(읽은 카드를 모르는 때의 글은 따로지만 제 카드의 표지 꼴에서만 나오는 말이다).

**PG-50 L3 — 관리자가 카드 하나를 볼 때의 같은 결론.** 맞았다(`same.ids` 에 범위 밖 읽기로 본 남의 초안 id 가 실리고 감사에 없었다). 시야로 거르는
쪽을 골랐다 — 관리자 표지 없이 센다. 감사를 남기는 쪽은 카드를 열 때마다 같은 칸의 남의 초안이 전부 감사에 쌓인다. 연 카드 자신이 범위 밖이면
종전대로 감사에 남는다.

**PG-51 L5 · L6 — 기한.** 맞았다. (L5) `asyncio.wait_for` 는 취소한 일이 끝나기를 기다린다 — 게이트웨이 호출(`mcp_call`)은 취소 뒤에도 세션 닫기를
보내 호출 기한만큼 더 걸려, 깔기의 60초 상한이 그만큼 늘었다. `lineage.bounded` 는 취소만 걸고 놓는다(끝난 뒤의 예외는 읽어 둔다). 개정 줄 · 리스크
변경 심사 · key 이력도 저마다 이것으로 건다. (L6) 호출 하나 15초를 차례로 불러 안쪽 합(개정 줄 + 리스크 변경 심사)이 게이트웨이 `insight_get` 의
30초보다 길 수 있었다. 호출 하나 8초 < 갈래 하나 10초로 줄이고, PAT 의 읽기는 리스크 앱을 부르지 않으며(PG-45), 과제 보기의 갈래 둘(key 이력 +
개정 줄)도 20초라 30초 안이다 — 시험이 게이트웨이 소스의 기본값과 견준다. 갈래가 기한을 넘기면 답한 것만 쓰고 나머지는 '모름' 이다. **남는 것** —
읽기 창구 앞의 MCP 잡 당기기(`intake.sync_jobs` — 쪽마다 15초 · 60초에 한 번)는 M2 의 것 그대로다. 당기는 차례에 걸린 읽기는 그만큼 더 걸린다.

**PG-52 L7 · L8 · 시험 · 변이.** (L7) 사람이 '심의로 넘기기' 로 이미 근거에 넣은 카드(`insight_get` + 카드 id — 껍데기 포함)는 다시 깔지 않고 수
(`already`)를 알린다. 깐 항목의 `key` 는 호출자가 쓴 `key` 를 피한다. (L8) 변이가 살아남던 배선 여섯 — 깔기의 위임 토큰 · 덧붙이기 · 반박 메모의
끝(`to_id`)과 종류(`disputes`) · 낡음 셈 · 빈 범위 — 에 시험을 세웠다. 고침을 되돌리는 변이 마흔여덟(포털 마흔 · 에이전트 서버 다섯 · 게이트웨이 셋)을
시험이 모두 잡는다. 처음엔 둘이 살아남았다 —
위임 박스 표지(`sso`)와 확인의 관리자 표지: 다른 겹(고른 공간의 종류 · 소속이 둘이 되는 것)이 가려 주던 것이라 그 겹 없이도 지는 시험을 더했다.

## 11-22 — M5 RA 투영을 스위치 뒤에(PG-53 ~ PG-60)

사용자 결정 2026-11-21(`docs/leftovers-1121` L21-6 ③) — 「과제 인사이트의 RA 투영을 RA 최신판 기준(객체를 id 로 다는 길 — SP 에서 받은 객체는 code = SP 키)
으로 지어 스위치 뒤에 둔다. 관리자 토큰 사용 자체는 승인하지 않았다」. 가지 `wt1122/insight-m5`(포털만 — 에이전트 서버 · 게이트웨이는 고치지 않았다).
RA 는 이 박스의 사본 v0.186.3(`b552f09`)을 읽기만 했다. 꼴은 [contracts.md](contracts.md) §11, 켜는 절차는 [server-setup.md](server-setup.md) 1절.

**PG-53 투영은 '보고서에 객체 태그 하나' 다 — 객체 쪽 투영(RK-01 꼴)은 관리자 몫이라 짓지 않았다.** RA 에서 사람 권한으로 되는 쓰기는 보고서에 이미 있는
객체를 id 로 다는 것(`POST /api/reports/{id}/entities/add` — 더하기만 · 보고서 주인 · 편집자)뿐이다. 객체 만들기 · 고치기 · 별칭 · 관계(REST 의
`PATCH /api/entities/{id}` · `POST /{id}/relations` · `/object-links` 는 `_require_admin`, MCP 의 `create_object` · `update_object` · `link_objects` ·
`add_object_alias` 는 '[시스템 관리자 전용]' — `/api/ai/ontology/write`)와 축 · 관계 종류 정의는 모두 관리자다. PLAN §6.5 가 그린 투영(인사이트를 RA
객체로 만들어 과제 객체에 잇고, 거두면 값을 '비공개@…' 로 바꾸는 RK-01 꼴)은 그 셋이 다 필요해 관리자 토큰 없이는 설 수 없다 — 짓지 않았다. 그래서
카드 하나는 그 카드의 RA 보고서(`card.report_id` — 그 심의의 결정문이 든 보고서)에 SP 과제 객체 태그 하나다. RA 의 과제 객체 화면(관련 보고서)과
`search_reports(entity_ids=…)` 로 '이 과제를 다룬 심의' 가 찾아진다. 주장 글을 RA 에 따로 싣지 않는다(보고서에 결정문이 있고, 사람이 고친 주장은 포털
원장에만 있다 — 남는 것).

**PG-54 과제 객체는 code 가 key 와 글자 그대로 같은 살아 있는 객체 하나일 때만.** RA 의 SP 받기는 새로 만드는 객체의 code 에 SP key 를 적고(64자까지 —
넘으면 비운다), code 가 빈 기존 객체에만 채운다(`connectors/sp_pull.py`). RA 에 code 로 거르는 창구가 없어 `POST /api/entities/search {q: key}`(값 · code ·
설명의 부분 일치 · 소문자)로 받아 code 를 글자 그대로 견준다. 닫힌 쪽 셋 — 같은 code 가 둘 이상(사람이 만든 사본 · 다른 축)이면 고르지 않는다 ·
`total` 이 받은 수보다 크거나 없으면(200개 상한) 하나뿐인지 몰라 달지 않는다 · 지워진(deprecated) 객체는 검색이 빼고 우리도 뺀다. 이름이 key 와 같아도
code 가 다르면 SP 객체가 아니다. 축(받을 타입)은 RA 관리자가 고르는 것이라 보지 않는다 — 축을 하나로 좁히는 손잡이는 짓지 않았다(겹침이 실제로
나오면 cae00 에서 본다). **남는 것** — SP 에서 과제 key 가 바뀌면 RA 객체의 code 는 처음 key 그대로다(이미 채워진 code 는 받기가 고치지 않는다) — 옛
key 의 카드는 맞고 새 key 의 카드는 '객체가 없다' 가 된다. 옛 key(`previous_keys` — lineage.old_keys)로 한 번 더 찾는 일은 짓지 않았다.

**PG-55 거두면 RA 는 건드리지 않고 원장 표지만 바꾼다.** RA 에는 사람 권한으로 태그 하나만 떼는 길이 없다 — 태그를 바꾸는 쓰기는 보고서
`PATCH`(·`ai-draft`)의 `entity_ids` 통째 교체뿐이라, 읽고 빼고 쓰는 사이에 남이 단 태그를 지울 수 있고(RA 의 `add_report_tags` 설명이 그 경고다) 편집
잠금(409)에 걸린다. 지우기 · 끊기가 없다는 PLAN §6.5 의 자세와 같다. 태그는 '이 보고서가 그 과제의 것이다' 라는 사실이라 카드를 거둔 뒤에도 참이고,
거둔 카드가 가리키던 결정문은 원래 RA 보고서에 남는다(PLAN §6.5 '이미 읽힌 것은 못 거둔다'). 원장 줄은 `withdrawn` 으로 바꾸고(스위치와 상관없이 —
원장만이다), 스위치가 켜져 있으면 거두기 답이 '태그는 RA 에 남는다 — 보고서 편집 화면에서 손으로 뗀다' 고 알린다.

  지울 수 있고 누가 편집 화면을 열어 두면 실패한다. (다) RA 에 '태그 하나 떼기' 창구를 청한다(RA 는 우리 몫이 아니라 사용자를 거쳐서다).

**PG-56 사람이 누른다 — 조직 공개에 딸려 저절로 달지 않는다.** 태그는 남의 RA 검색 결과를 바꾸고(RA 의 `add_report_tags` 설명 — '혼자 정하지 마라 …
보여주고 확인받아라'), 포털 관문도 `add_report_tags` 를 확인이 필요한 쓰기로 둔다(`procedures/models.py` MUST_GATE · `agent/panel.py`). '조직에 열기'
