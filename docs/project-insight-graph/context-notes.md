# 과제 인사이트 그래프 — 결정 기록

**PG-1 조사(2026-11-02 KST, 읽기만) — 제안은 맞고 리스크 심사 몫은 반쯤 있다. 빠진 것은 심의 쪽이다.** 저장소 여덟(리스크 앱 · RA 지식층 · MX 백서 위키 ·
AIDataHub · StepForge · DynaForge · SP 허브 · ODB 허브)을 견줬다. 리스크 앱 원장의 등록부 클러스터가 이미 '과제 · 설계 판 · 부품에 묶인 인사이트' 이고
(`../HWAXRisk/backend/app/risk_store.py:365-383`), 선례 · 비슷한 과제 · 주장 역색인이 다른 과제의 앞선 판정을 시야 교집합으로 다시 쓴다. 일반 심의는 주제를
구조로 적지 않는다 — `deliberate_start` · 포털 심의 시작 · 잡 원장 · RA 보고서 · 위키 원천 어디에도 과제 · 설계 자료 칸이 없다. 근거 줄은 PLAN 머리의 판이다.
에이전트 서버 줄은 조사 때의 `9f08507` 이 아니라 `aadd591`(11-02 토큰 절감 병합 뒤)로 다시 맞췄다.

**PG-2 입력 조사에서 바로잡은 것 둘과 대조해 맞은 것.** 서브에이전트 조사(스크래치 패드의 kg-*.md)는 모델 출력이라 쓰기 전에 줄을 대조했다.

- MX 백서 `subject_hints` 는 원천 봉투의 **맨 위 칸**이다(`../MXWhitePaper/apps/api/app/wiki/envelope.py:314-325`) — 'DeliberationBody 에 칸이 없어 심의
  원천은 주제를 못 싣는다' 가 아니다. 문서 고르기도 종류와 무관하게 힌트를 읽는다(`…/wiki/resolve.py:264-284`). 그래서 엔진이 봉투에 힌트를 더하면 MX 백서를
  고치지 않고 과제 문서가 고쳐질 수 있다 — 그래도 들이기 LLM 이 문서를 고치는 일이라 그 세션에 먼저 묻는다(PLAN §10).
- MCP 심의 잡 원장은 11-02(`aadd591`)부터 표결(tally · unanimous · votes) · 보고서 주소 · 숫자 대조를 남긴다(`../HWAXAgentServer/delib_jobs.py:1220-1233`) —
  '원장이 표결을 버린다' 는 그 앞 판의 사실이다. 여전히 버리는 것은 진행 일지(도구 · 인자)다(`:422-431` · `:1352`).
- 그 밖의 핵심 주장(RA 엔티티 시야 없음 · 근거 보고서 제목 · `create_object` 가 고치지 않고 돌려줌 · AIDataHub 인증 꺼짐과 `tags` 를 받지 않는 검색 ·
  DynaForge 개정 보기 · 루틴 키 규칙 · D-18 의 엔진 집행 · RK-01 의 보내는 꼴)은 줄을 대조해 맞았다.

**PG-3 그래프는 보는 꼴이고 저장은 열쇠 달린 원장이다.** 묻는 말이 '이 과제 주변' 이라 그래프로 보이는 것이 맞지만, 첫 값어치에 그래프 DB 가 필요하지 않다 —
주제(SP 키 · 설계 자료 열쇠) → 인사이트 → 근거 참조의 칸이 있으면 읽을 때 합쳐 그래프 꼴로 보인다. 다중 관계 탐색은 RA 가 이미 설계한 자리이고(M5), 그
전에 짓는 것은 원장 하나와 읽기다. 인사이트 한 줄은 '출처 하나가 한 주제에 대해 낸 주장 하나 + 근거 참조' 이고, 생산자마다 꼴이 다르다 — 리스크는 등록부
클러스터(이미 있다), 일반 심의는 결정 카드(새로), 루틴은 단계 발견(나중). 근거 참조는 리스크 설계의 문법(`docs/design-risk-review/plan.md:184-212`)을 그대로
쓰고 새 접두는 둘만 더한다(`delib:` · `call:`).

**PG-4 주제는 시작에 사람이 고르고, 끝의 짐작은 후보만이며, SP 키는 서버가 스스로 부른 풀이의 결과 행에서만 받는다.** 시작에 고른 주제가 정본이다 — 후보는
그 사람의 도구 결과(StepForge 과제 · ODB `find_job` · DynaForge 리포트 · SP 과제 찾기)에서 오고, 리스크 앱의 보드 붙이기와 같이 후보에 실제로 있을 때만
적는다(`../HWAXRisk/backend/app/routes.py:2200-2213`). 끝에 코드가 성공한 호출에서 찾은 열쇠는 사람이 확인하기 전에는 과제에 잇지 않는다 — 좌석이 고른
인자에 든 id 는 '그 심의가 닿았다' 의 증거일 뿐 '그 심의의 주제다' 의 증거가 아니다. SP 키는 루틴 키 규칙의 **원칙**(모델 글 · 받은 인자에서 온 값은 근거가
아니다 — `backend/app/procedures/routine_routes.py:584` · `:599`)만 가져오고 그 **글자 대조**는 쓰지 않는다(반대 검토 5 · 6 — PG-13). 웹은 포털이 풀이를 부르고
사람이 고른 행의 `key` 칸, MCP 는 엔진이 시작 때 같은 풀이로 다시 찾아 key 가 글자 그대로 같은 행이 하나일 때만 확인(아니면 '주장' 으로 두고 잇지 않는다),
기구 CAD 는 StepForge `get_project_meta` 의 `plm_task`(받는 앱의 한 판정 `match_task` — `../StepForge/core/sp_core.py:1159-1182`)다. 허브 key 의 꼴은 가정하지
않는다(`docs/procedures/app-project-keys.md:44-46`). A13 (A) 가 '(C) 포털 새 레지스트리' 를 고르지 않았으므로 포털은 과제 목록을 쥐지 않고 SP 키를 칸으로만
든다(`docs/leftovers-1017/triage-1031.md:113`).

**PG-5 자리 — 생산자 원장이 정본이고 일반 심의 인사이트만 포털 원장 하나에 둔다(권장, 사용자 결정 기다림 — PLAN §11-2).** 리스크 행은 베끼지 않는다 — 리스크
설계의 원칙 'ID 권위는 앱 DB 다'(`docs/design-risk-review/plan.md:2271`)이고, 베끼면 시야 · 낡음 · 거두기가 두 벌이 된다. 과제별 보기는 읽을 때 그 사람
신원으로 리스크 앱에 묻는다. 리스크 러너 패널도 포털 중계를 지나는 웹 심의이므로(`../HWAXRisk/backend/app/engine_client.py:33-38` · `runner.py:847-869`) 들이기는
리스크 심사가 낳은 심의(의장 risk-review · risk-review-sealed, `started_by=app`)를 뺀다 — 빼지 않으면 리스크 판정이 포털 원장에 베껴지고(버린 (마) 안) 그
원장을 거쳐 같은 과제 좌석에 돌아간다. 심의 몫을 포털에 두는 까닭 — 사람 · 소속 원장과 권한 정책(요청마다 다시 센다 — `backend/app/access/policy.py:5-6`),
웹 심의가 끝나는 중계 저장, 포털이 원장을 쥐고 게이트웨이가 사람 PAT 만 넘기는 루틴 도구 꼴(`../HWAXMcpGateway/gateway.py:4819-4825` · `:4939-4948`)이 다
포털에 있다. 에이전트 서버에 두면 웹 심의(메모리에만 있다)와 사람 확인 화면이 따로 놀고, RA 에 두면 시야가 없어 조직 공개분만 쌓이며, SP 허브 · 위키는
cae00 에서 지금 쓸 수 없거나 다른 팀이 먼저다. 새 저장소 파일보다 이미 등록 · 백업되는 포털 저장소 안의 표를 먼저 본다 — 새 경로를 더하면 시험 격리도 함께다.

**PG-6 시야 — MX 백서의 범위 꼴 · 최소 범위 규칙을 그대로 쓰고 읽을 때 원장을 쥔 쪽이 거른다(기본값은 사용자 결정 기다림 — PLAN §11-1).** 토큰 넷
(`user:` · `aff:` · `plat:` · `org`)의 그리고, 범위는 근거들의 토큰을 다 담는다, 서로 다른 `aff:` · `user:` 가 섞이면 넓히지 못한다, 넓히기는 사람만 ·
`plat:` 빼기는 관리자만(`../MXWhitePaper/docs/llm-wiki/CONTRACTS.md:184-185` · `:189-190`). 새로 짓지 않고 가져온 까닭 — 같은 사람들이 같은 소속 원장으로 두
곳을 보게 되므로 규칙이 다르면 한쪽이 샌다. **한 칸 다르게 둔 자리** — 범위를 모르는 근거(남의 RA 보고서 · 남의 리포트)가 있으면 MX 백서 그대로라면 넓히지
못하지만, 여기서는 주인이 자기 소속까지는 넓힐 수 있게 했다. 같은 심의의 결정문이 MCP 잡 원장에서 이미 같은 소속에 보이는 선(FU-D17 —
`../HWAXAgentServer/delib_jobs.py:959-974`)이라 새 노출이 아니기 때문이다. `org` 는 근거 범위가 다 알려졌을 때만이다. 게이트웨이 도구는 사람 PAT 로만
돈다 — 심의 잡 원장은 신원 없는 호출에 다 보이는데(`delib_jobs.py:965-966`) 새 원장은 그 길을 따르지 않는다. 수 · 잇기 · 표지는 거른 뒤에 센다(넓은 쪽은
좁은 쪽이 있다는 것도 말하지 않는다 — `CONTRACTS.md:193-195`). 권장 기본값 '초안은 주인만 · 확인하면 같은 소속' 의 까닭은 둘이다 — 사람 손 없이 넓히지
않는다, 그리고 에이전트 서버가 머리로 온 신원을 믿어(`../HWAXAgentServer/start.sh:36-40`) MCP 에서 들인 주인 · 소속은 주장일 뿐이다.

**PG-7 D-18 은 범위 그대로 두고 새 길을 열지 않는다 — 지금 닿는 길은 솔직히 적는다(사용자 결정 기다림 — PLAN §11-3).** D-18 은 '좌석은 같은 과제의
등록부(앞 패널의 판정)를 도구로 보지 못한다' 이고 까닭은 '앞 판정을 읽고 따라 말하면 지지 수가 독립 근거 없이 오른다' 다
(`docs/risk-review-redesign/context-notes.md:117-118`). 처음 초안은 '리스크 좌석은 같은 과제의 앞선 인사이트를 보지 않는다' 고 적었는데 지금도 사실이 아니다
— 같은 과제의 일반 심의 결론은 보고서 검색(엔진은 리스크 러너 머리가 든 제목만 가린다 — `deliberation.py:1100-1105`) · 호출자 근거(의장과 무관하게 실린다 —
`:6491-6498`) · 리스크 심사로 바꾼 이어하기(앞 결정문이 요약으로 — `../HWAXAgentServer/mcp_server.py:926`)로 닿는다. D-18 의 글에는 어긋나지 않으므로 고치지
않고 적어 두고, 넓힐지 · 뒤집을지를 사용자에게 묻는다. 이 계획이 새로 여는 길은 막는다 — 도구 이름 `insight_`(좌석 자유 조회의 접두 `list_` · `get_` ·
`search_` · `find_` 에 안 걸린다 — `deliberation.py:3872`) · 거절 목록(`_RISK_PRIOR_TOOLS` — `:987`)에도 넣기 · 리스크 심사에는 깔지 않기 · 엔진 받침(의장이
risk-review 면 `insight_*` 근거를 뺀다) · M1 은 주제를 RA 보고서에 적지 않기. Claude 워크플로 좌석은 막지 못한다(PLAN §12-4).

**PG-8 엔진은 포털을 사람 대신 읽지 않는다 — 웹은 포털이 깔고 MCP 는 호출자가 넘긴다.** 심의 시작에 앞선 인사이트를 깔 때 엔진이 포털 원장을 읽으려면 잡
주인의 신원을 엔진이 포털에 주장하는 새 신뢰 길이 필요하다. MCP 잡의 엔진은 사람 PAT 가 없고 게이트웨이 비밀 + 사람 머리로 부르며(토큰 절감 TS-1), 루틴
도구는 그 길을 막는다(`gateway.py:4945-4947`). 웹은 포털이 그 사람을 알아 `delib_opts.evidence` 에 넣으면 되고, MCP 는 개인 Claude 가 `insight_find` 로
받아 `deliberate_start(evidence=…)` 로 넘기면 된다 — 지금 챗 → 심의 넘기기와 같은 길이다. 깔기는 새 심의의 산출물(잡 원장 · RA 보고서 · 위키 원천)을 읽을
사람이 모두 볼 수 있는 인사이트만이다(반대 검토 4 — PG-13). 새 신뢰 길은 쓸모가 보인 뒤 따로 검토한다.

**PG-9 MCP 잡은 포털이 에이전트 서버의 공유 비밀 창구로 읽어 들인다(엔진이 밀지 않는다).** MCP 심의는 포털을 지나지 않으므로 들일 길이 따로 있어야 한다.
읽어 오는 꼴을 고른 까닭 — 어느 쪽이 내려가 있어도 다음 읽기에 따라잡고(포털은 갱신마다 다시 뜨고, 에이전트 서버는 심의가 돌면 재기동이 미뤄진다), 같은
꼴의 창구가 이미 있다 — `/seat-questions` 는 게이트웨이 공유 비밀을 요구하고 '질문 원문을 내므로 루프백만 믿지 않는다'(`../HWAXAgentServer/app.py:9271-9282`).
에이전트 서버는 루프백에 뜨고 앞에 인증이 없어(`start.sh:36-40`) `/drain` 같은 창구는 그 경계에만 기댄다(`app.py:9118-9126`). **남는 믿음** — 잡의 주인 ·
소속은 엔진이 머리로 받은 값이고 루프백에 닿는 프로세스는 그 머리를 지어낼 수 있다(박스 안 프로세스를 믿는 지금의 경계 그대로다). 그래서 MCP 에서 들인 카드는
주인이 포털에 로그인해 확인하기 전까지 그 주인만 보는 초안이다. 주인이 빈 잡은 들이지 않는다.

**PG-10 심의 인사이트는 결정 카드를 단마다 코드로 짓는다(권장, 사용자 결정 기다림 — PLAN §11-4).** 주장은 결정문의 '■ 핵심 요약' 불릿(엔진이 이미 짓는
3 ~ 5줄 — 결론 · 핵심 근거 · 소수 의견, `../HWAXAgentServer/deliberation.py:7436-7449`)에서 자르고, 없으면 쉬운 설명의 결론 줄, 둘 다 없으면 비운다. 결정문
머리를 자르지 않는 까닭 — 코드가 찍는 표지(외부 응답자 · 봉인 · 기준일)가 맨 위에 오고(`:7450-7459`), 요약이 실패하면 머리는 제목 · 근거 프로파일 줄이다(반대
검토 14). 카드는 엔진이 단마다 짓는다 — 위키 원천을 짓는 자리가 단마다 돌고(원천 열쇠 `delib:<잡>:<틀>` — `:3638`), 잡 원장 · 중계는 단마다 `decision` 을
덮어쓴다(`delib_jobs.py:1211-1212` · `backend/app/agent/routes.py:3058-3059`). 이어하기는 새 잡 id 를 내므로(`mcp_server.py:971-975`) 앞 카드를 `continues`
로 잇는다. 새 LLM 호출이 없다. 의장에게 기계판독 인사이트 목록을 더 내게 하면(risk_spec 꼴) 모든 심의의 의장 지시문 · 출력이 바뀌고 품질을 따로 재야 한다.

**PG-11 M1 은 주제 달기 하나다 — 그것만으로 값어치가 서는 가장 작은 걸음이다.** 주제 칸 하나가 뒤 단계 전부(원장 · 다시 쓰기 · 낡음 · 투영)의 열쇠이고,
