# 챗·심의 액션 바 — 결정 기록

## A-1. 킬 스위치는 새 환경변수가 아니라 타일 목적지다

사용자 조건 "환경변수에 Knox 연결 부분이 없으면 비활성화". 포털에는 이미 목적지 규약이 있다 —
routes(.local).env 의 `<id>=URL` 한 줄 또는 `SYS_<ID>_URL` 환경변수(`catalog/registry.py`).
목적지 없는 proxy 타일은 `coming_soon` 으로 강등된다(2026-09-03 ste 실사고로 생긴 규칙).
그래서 `knox-bridge` 가 `available` 이라는 것 = Knox 연결 설정이 있다는 것이다. `KNOX_ENABLED` 같은
두 번째 스위치를 만들면 둘이 어긋나는 상태(스위치는 켰는데 목적지가 없다)가 생긴다.

선례의 범위 — `AppHeader.tsx` 의 '리스크 심사' 메뉴도 env 플래그 없이 타일 가시성으로 입구를 숨긴다. 다만
그것은 권한(타일이 보이느냐)만 보고 status 는 안 본다(hwax-risk 는 url 있는 jwt-handoff 라 늘 available).
**available 판정을 기능 스위치로 쓰는 것은 이번이 처음이다.**

주의 — `SYS_KNOX_BRIDGE_URL` 환경변수는 타일만 켜고 nginx 라우트는 안 만든다(`gen-nginx-conf.sh` 는
routes 파일만 읽는다). 그 상태에서 `/knox-bridge/ui/actions.json` 은 포털 SPA catch-all 이 `200 text/html`
로 받으므로 content-type 검사에서 버려진다 → 버튼 0(dev 8723 실측). 홈 카드는 '열기' 로 뜨는데 `/knox-bridge/`
는 SPA 로 떨어진다 — ste 실사고와 같은 모양이다. **사내 실배선은 routes.local.env 한 줄이다.**
끄는 법은 줄·변수를 지우는 것이다. 값이 비어 있지 않으면 `off` 도 켠다(registry 의 기존 동작).

## A-2. 1차 요청서의 데이터(타일·플랫폼)가 이 리포에 없어서 같이 넣었다

2차 요청서는 `knox-bridge` 타일과 `plat:knoxbridge` 가 이미 있다고 전제한다(1차, 데이터 2건).
이 리포에는 둘 다 없었다(`git log -S knox` 0건). 없으면 `/systems` 에 타일이 안 내려와 게이트가
영영 닫힌다 — 버튼이 절대 안 뜬다. 1차 원문 문구를 모르므로 타일 문구는 요청서의 주문
("타일 문구가 '메일' 을 약속하지 않게")만 따랐다. 게이트웨이 백엔드 키는 A-8.

## A-3. 매니페스트는 knox-bridge 하나만 읽는다 — 요청서 §2 코드와 다르다

요청서 §2 코드는 `available` 인 **모든** proxy 타일에 `/<id>/ui/actions.json` 을 찔러 본다. 같은 요청서
§1-1 은 "매니페스트를 부르기 전에 knox-bridge 타일로 먼저 게이트한다, 요청 자체를 만들지 않는 것이
핵심" 이라고 한다 — 요청서 안에서 둘이 어긋난다. 전부 찌르면 페이지를 열 때마다 관계없는 앱(STE, dev 에서는
routes 항목으로 proxy 가 된 RA)에 404·401 요청이 한 번씩 간다. 사용자가 요구한 것은 Knox 메일이다.
출처는 `ACTION_SOURCES = ['knox-bridge']` 한 줄이고, 다른 앱을 더하는 것은 그 배열 한 칸이다(빌드 1회).
출처끼리 id 가 겹치면 `mergeActions` 가 앞의 것만 남긴다.

## A-4. 매니페스트가 없을 때 포털에 내장된 기본 버튼을 띄우지 않는다

'메일 기능이 포함돼야 한다' 를 보장하려고 내장 기본값을 둘 수도 있었다. 하지 않은 이유 — 사이드카가
죽었거나 게이트웨이에 bridge 도구가 안 붙었을 때 버튼이 "bridge_draft_mail 로 초안을 만들어 줘" 를
LLM 에게 보내면, 도구가 없는데도 "초안을 만들었습니다" 로 답할 수 있다. 이 허브에서 가장 위험한
실패("실패가 정상 응답과 똑같이 생겼다")다. 매니페스트를 사이드카가 내주는 것 자체가 "지금 이 기능이
살아 있다" 는 신호다.

## A-6. 매니페스트 fetch 는 `apiFetch` 가 아니라 `fetch(credentials: 'same-origin')`

실익은 둘뿐이다 — `apiBase` 접두사가 필요 없고, 사이드카의 401 에 포털 `/auth/refresh` 재시도를 걸 이유가 없다.
**포털 세션 쿠키(`hwax_session`, httpOnly, path=/)는 어느 쪽으로 불러도 사이드카에 간다** — 같은 오리진
path-proxy 이기 때문이다(`apiFetch` 는 Authorization 헤더를 싣지 않는다). 사이드카는 그 쿠키로 포털
`/auth/me` 에 되물어 신원을 본다. 즉 사이드카는 포털 세션과 같은 신뢰 경계 안에 있다.

## A-7. 캐시

모듈 수준 캐시 하나 — 대화 전환마다(`.cx-thread key={activeId}` 로 다시 마운트된다) 다시 받지 않는다.

- **사용자·권한에 묶는다**(키 = subject + entitlements). SSO 로그인은 페이지를 새로 읽지만 로컬 계정 로그인·
  로그아웃은 새로고침이 없다 — 전역 하나로 두면 앞 사람의 버튼이 뒷사람에게 남는다(1라운드 검토가 jsdom 으로 재현).
  entitlements 가 키에 있으므로 포커스 refresh 가 권한 회수를 감지하면 다시 받는다.
- **일시 실패는 캐시하지 않는다** — `/systems` 실패, 매니페스트 타임아웃·네트워크·본문 파싱 실패·5xx·408·429. 사이드카
  콜드 스타트 한 번에 SPA 수명 내내 버튼이 사라지지 않게. 확정 결과는 캐시한다 — 404·401·403(사이드카가 이 사용자를
  거절, 되풀이되는 거절을 대화 전환마다 다시 찌르지 않는다)·SPA html·schema 불일치. 깨진 JSON 은 배포 도중 한 번
  읽힐 수 있어 일시 실패로 둔다.
- 킬 스위치를 닫아도(routes 줄 삭제 + reload) 키가 안 바뀌므로 **열린 탭은 새로고침해야** 버튼이 사라진다.

같은 모양의 전역 캐시가 `AppHeader.tsx` `catalogOnce` 에도 있다(리스크 심사 메뉴, 이번 변경 전부터) — 범위 밖, A-11.
`/systems` 를 AppHeader 와 따로 받아 SPA 로드마다 1건 더 부른다(일시 실패가 이어지는 동안은 마운트마다) — 공용화는
AppHeader 를 고치는 일이라 두었다. 요청 폭주는 없다 — 리렌더 50회에 추가 요청 0(2라운드 실측).

## A-8. 게이트웨이 키 — 버튼은 가리지만 도구는 막지 않는다

게이트웨이 `_backend_allowed` 는 `access.yaml` 에 필요 권한이 없는 백엔드를 **누구에게나** 연다(목록·호출 둘 다).
`knoxbridge.gateway` 가 비어 있는 동안 사내에서 bridge MCP 가 게이트웨이에 붙으면, `plat:knoxbridge` 가 없는
사용자도 챗에서 말로·PAT 로 bridge 도구를 부를 수 있다 — 툴바 버튼만 권한으로 숨는 비대칭이다.

키를 짐작으로 넣지 않았다. heax registry 로 흡수되면 `heax-<id>` 꼴이 되어 짐작이 틀리기 쉽고, 틀린 키는
아무것도 막지 못하면서 막은 것처럼 보인다. **사이드카를 게이트웨이에 붙이기 전(또는 같은 변경)에 확정 키를
넣는다** — checklist '반영' 의 순서 항목. 게이트웨이 백엔드 목록이 박스 설정에만 있어 리포 테스트로는 강제할 수 없다.

## A-9. 반박 검토 1라운드(2026-09-16)

네 관점(킬 스위치·보안·화면 회귀·요청서/권한) 검토자 넷이 39건을 내고, 건마다 검증자가 재현을 시도했다.

  확인 화면), link 가 외부 https 를 연다(설계대로, 제안된 제한은 위험을 못 막는다), 라벨·id 모양 제한 없음(막히는
  위험이 없다), 툴바 이름 '대화 내보내기' 오인, 요청서 날짜, CLAUDE.md 문서 표.
- **남긴 것** — 사내 개통 박스에서 라우트는 있는데 사이드카가 404·502 면 콘솔 네트워크 에러(PLAN), 미개통
  박스의 '곧 공개' 카드·권한 행(사용자 결정 대기).

## A-9-2. 반박 검토 2라운드(2026-09-16) — 1라운드 **수정 자체**를 대상으로

두 관점(로직·화면/문서) 검토자 둘이 13건, 검증자가 전부 재현했다. 1라운드 수정이 만든 결함이 둘이었다.

  바이트가 다시 박혔다(→ 말로 바꿨다).
- **1라운드 수정이 못 채운 것** — send 의 '대답 있음' 이 실패한 심의를 거르지 못했다(→ 결정문 기준). 408·429 가 확정으로
  캐시됐다(→ 일시 실패). 콘솔 에러 건수·요청 수 문장이 캐시 정책과 어긋났다.
- **확인만 한 것(문제 없음)** — StrictMode 이중 effect 1건, 같은 키 동시 마운트 1건, 키 A→B→A 경합에서 늦은 결과 숨김·새 항목
  보존, user null 로 로드 없음, `res.json()` 도중 타임아웃은 일시 실패로 회복, safeUrl 코드값 판정이 1라운드 정규식과
  BMP 전체 65,536 코드 단위에서 같은 집합, 포커스 선택자가 두 화면에서 입력창 하나에만 걸림.
- **범위 밖으로 넘긴 것** — A-11.

## A-10. 대조한 것과 다시 돌리는 법

프론트에 테스트 러너가 없다. 순수 규칙은 esbuild 로 `chatActions.ts` 를 ESM 으로 떼어 node assert 로,
컴포넌트는 esbuild 번들 + jsdom + react-dom `act` 로(목: listSystems·useAuth·useCan·useChat·useLocation) 돌렸다.
esbuild 는 `frontend/node_modules/.pnpm/esbuild@*/node_modules/esbuild/bin/esbuild`.

## A-12. Knox 가 없는 박스에서는 숨긴다 — '곧 공개' 로도 보이지 않게(사용자 결정 2026-09-17)

1라운드에서 남긴 가시 변화(미개통 박스의 'Knox Bridge — 곧 공개' 카드·'Knox 연계' 권한 행)를 사용자가 숨기기로 정했다.
사내 전용 연계는 사외·dev 에서 **영영 열릴 일이 없어** '곧 공개' 가 거짓 약속이 된다.

- **타일** — `systems.yaml` 의 `hide_unless_routed: true`. registry 가 목적지 없는 proxy 타일을 coming_soon 으로 내리면서
  `enabled=False` 로도 둔다 → `visible_for` 가 거른다. proxy 가 아닌 타일에 쓰면 로드 때 거절한다(다른 타일은 목적지와
  무관하게 열리므로 뜻이 없다). ste 처럼 표식이 없는 타일은 종전대로 '곧 공개' 로 남는다.
- **플랫폼** — `access.yaml` 의 `hide_unless_routed: true`. 그 플랫폼의 타일이 이 박스에서 하나도 안 열리면(`catalog.live_ids()`)
  `/auth/access` 표·`/auth/access/policy`(관리 화면 체크 목록) 행과 **권한 요청**에서 뺀다(요청은 404 '모르는 권한').
  **표시만 가린다** — 권한 계산(CAEG `*`)·`filter_tiles`·게이트웨이 정책(`/internal/access/policy`)은 바꾸지 않는다.
  숨긴 플랫폼도 게이트웨이 키가 있으면 도구는 계속 막혀야 하기 때문이다(테스트가 정책 응답이 같음을 본다).
- 관리 화면에서 사용자 허가를 저장하면 기존 허가 전체에서 시작하므로 숨긴 키가 이미 있어도 지워지지 않는다.
- 판정은 요청마다 카탈로그를 본다 — routes 줄을 넣고 `POST /systems/reload` 하면 타일·권한 행이 같이 나타난다.
