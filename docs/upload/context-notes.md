# 챗 파일 업로드 — 컨텍스트 노트

작업 중 내린 결정과 근거. 이어서 하는 세션이 재-derive 없이 잇게.

## 왜 새 저장소를 안 만드는가
업로드 대상이 전부 이미 있는 백엔드 MCP 도구다(register_material, import_record,
upload_file …). 포탈에 별도 DB·스토리지를 두면 진실이 두 곳이 된다. 포탈은
받아서→검사→확인→넘기는 오케스트레이터로 한정한다. 스테이징은 임시 파일일 뿐이다.

## 왜 물성 DB 부터인가
이번 세션 내내 물성이 초점이었고(심의 자유조회에 물성 도구 상시 바인딩, 전문가 공백
발굴이 배리어·계측으로 수렴), 수요가 가장 명확하다. register_tensile_test /
register_relaxation_test 로 시험 데이터 경로가 이미 있다. 대상을 늘리는 건 2차에 같은
틀에 백엔드만 갈아 끼우면 된다.

## dry_run 을 축으로 삼는 이유
import_record 가 dry_run=True 가 기본이고, register_* 도 검증 모드가 있다. "AI 가 채우고
사람이 확인" 이라는 요구가 dry_run 미리보기와 정확히 맞는다 — AI 초안을 dry_run 으로
돌려 검증 결과를 사람에게 보이고, 사람이 승인하면 dry_run=False 로 확정한다. 이 축을
UI 흐름의 중심에 둔다.

## 이 세션에서 배운 것을 미리 박아 둔다
- **파일 업로드엔 앱 하드 상한이 불필요하다.** 422 페이로드 폭발(커밋 48c2e7a)은 JSON
  본문 얘기지 multipart 파일에는 안 맞는다. 진짜 위험은 메모리 — 파일을 디스크로
  스트리밍하면 해소된다. 바깥 경계는 nginx 2GB(hwax.conf:25)가 이미 준다.
- **임시파일은 반드시 정리한다.** deploy-all 카운터 파일이 안 지워져 /tmp 에 쌓인 사고가
  있었다(커밋 4dd5126). 스테이징은 TTL + 확정 후 삭제.
- **무음 강등 금지.** 업로드는 쓰기라 사용자 자격증명이 필수다. PAT 가 거절되면 서비스
  계정으로 넘어가면 안 된다 — 그건 남의 이름으로 데이터를 쓰는 것이다. 강등 시 거부한다.
  (심의 무음 강등 가시화와 같은 원칙 — 커밋 b2e9044.)
- **성공 위장 금지.** 백엔드가 거절하면 그 사유를 사용자에게 그대로 보인다. "등록됐다 ≠
  들어갔다" 를 이 세션에서 여러 번 봤다.

## 미해결 — 착수 전 정할 것
- 스테이징 위치. /data/hwax/upload-staging 아래 사용자별? TTL 몇 시간?
- (해결) 크기 상한은 안 둔다 — 디스크 스트리밍 + nginx 2GB.
- 이미지·PDF 의 메타 추출 깊이. 1차는 파싱 도구가 주는 만큼만 — OCR 고도화는 2차.
- 여러 파일 동시 업로드 지원 여부. 1차는 한 번에 하나로 시작 권장.

## 진입점
- 백엔드 수신: backend/app/agent/routes.py (챗·심의·내보내기가 여기 있다 — 업로드도 여기)
- 프론트 첨부: frontend/src/components/chat/ (입력부 컴포넌트)
- 대상 도구: 게이트웨이 :9110 경유 register_material 등 (심의 자유조회가 이미 부르는 경로)
